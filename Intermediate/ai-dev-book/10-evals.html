Evals & Observability

Build the test suite for non-deterministic output, gate releases on it, and instrument every model call so you can explain any answer, its latency and its cost.

You will learn

  • How to turn vague goals into measurable success criteria.
  • How to build and version an eval set.
  • Three kinds of graders (code, LLM-as-judge, human) and when to use each.
  • How to handle variance, compare with a baseline and gate CI.
  • How to trace model calls with OpenTelemetry and track cost per feature.
  • How to close the loop with production feedback.

Evals are your test suite

You can't assert answer == "..." on a paragraph. You can assert properties of it, score it against a rubric, and track the pass rate over a fixed set of inputs. That's an eval.

🧠 Analogy: a driving test, not a spelling test. A spelling test has one right answer per word. A driving test has an examiner with a checklist: did they check the mirrors, signal, keep a safe distance? Two good drivers take different routes and both pass. Evals are driving tests for your feature: a fixed route (the eval set), a checklist (graders), and a pass rate over many drives.

☕ Java: the eval set is your fixtures, graders are your assertions, and a pass rate replaces pass/fail because the same input can give different outputs. The baseline is your last green build; the CI gate is the same idea as a coverage threshold.

Step 1: define success criteria

Good success criteria are specific, measurable, achievable and relevant, and most features need several dimensions. For DocsPilot:

Step 2: build the eval set

  • Start from reality: real questions from chat, tickets and search logs. Synthetic questions (a model can generate variations) fill gaps but shouldn't dominate.
  • Cover the distribution and the edges: easy, hard, ambiguous, misspelled, unanswerable, adversarial (injection attempts), multi-part.
  • Write references for answerable questions: the expected document and a short reference answer.
  • Version it in the repo as JSONL. When you fix a production bug, add the failing case.
  • Size: 50–100 cases is a useful start; grow to hundreds as the feature matures.

Code graders

Prefer code wherever the property is mechanical. Code graders are free, instant and never disagree with themselves:

LLM-as-judge

Rules for judges:

  • Give a rubric with concrete levels, and the inputs it needs (question, reference, retrieved context, answer).
  • Ask for reasoning before the verdict, and return it with structured output (Chapter 4).
  • Prefer binary or 3-point scales over 1–10; they are more consistent.
  • Calibrate: have humans label 50 cases, compare with the judge, and fix the rubric until they agree.
  • Use a capable model for judging, and don't let the system grade only itself with the same prompt.

Calibrating the judge against humans

Agreement rate alone flatters a judge when most answers are good (a judge that always says "correct" agrees 90% of the time on a set that is 90% correct). Cohen's kappa corrects for agreement by chance: 1 is perfect, 0 is no better than chance.

"Always yes" agrees 80% of the time and is useless; kappa shows it. Look at the cases where judge and humans disagree, fix the rubric, and repeat until kappa is high (above about 0.7 is a common bar).

Keep eval runs out of the unit-test phase. Real evals call a paid API and take minutes. Run them in a separate CI job (on prompt, model or retrieval changes, and nightly), not on every commit. Unit tests with FakeAnthropic stay in the normal test run.

How many cases do you need?

A pass rate from a small set is noisy. A Wilson interval shows how noisy, and tells you whether a change of a few points means anything:

With 20 cases, "85%" could be anything from about 64% to 95%: a 5-point "improvement" is noise. Grow the set before you trust small differences, and compare old and new versions on the same cases.

☕ Java: for code-gradable features, a JUnit test that computes accuracy over a JSONL file and asserts a threshold is a fine CI gate (in its own test group, so mvn test stays fast and free).

Observability: traces

Every answer should be explainable after the fact: which prompt version, which chunks, which tool calls, how long each took, what it cost. Use traces, which you already know from microservices. A DocsPilot request is a trace; retrieval, each model call and each tool call are spans; model, tokens, stop reason and prompt version are span attributes.

The anthropic SDK creates OpenTelemetry spans for its calls automatically once a tracer provider is registered, using the GenAI semantic conventions (gen_ai.request.model, gen_ai.usage.input_tokens and so on). Wrap them in your own spans for the steps around them:

The GenAI conventions are still evolving. Attribute names changed during 2025–2026 (gen_ai.provider.name replaced gen_ai.system) and aren't marked stable yet. Check the OpenTelemetry GenAI semantic conventions before building dashboards on them.

Logging prompts and outputs. Full prompts and answers are the most useful debugging data and the most sensitive. Decide deliberately: by default the SDK's spans leave content out. If you record it, send it to a restricted store with a retention period, redact secrets and personal data, and never put it in general application logs.

☕ Java: with the OpenTelemetry Java API, start a SpanKind.CLIENT span around each call and set the same gen_ai.* attributes from the response's usage; your existing Jaeger, Tempo or vendor backend shows LLM calls next to your database and HTTP spans.

Closing the loop

  • Collect explicit feedback (thumbs up/down with an optional reason) and implicit signals (the user re-asked, copied the command, opened the cited doc).
  • Review a sample of thumbs-down answers weekly. Every real failure becomes an eval case.
  • Watch online metrics per prompt version: abstention rate, citation-invalid rate, latency, cost.
  • Ship prompt and model changes behind a flag to a slice of traffic, and compare.

Recap

  • An eval is a fixed set of inputs, graders, and a pass rate compared with a baseline.
  • Define several specific, measurable criteria: correctness, groundedness, abstention, citations, latency, cost.
  • Build the set from real questions, including unanswerable and adversarial ones; version it; add every production failure.
  • Use code graders wherever possible, LLM judges with rubrics and structured verdicts for nuance, and humans to calibrate (kappa).
  • Repeat runs, look at intervals and per-tag results, and gate CI with a tolerance.
  • Trace every call (the SDK emits GenAI spans), track cost per feature, and feed production failures back into the set.

Exercise 2 🟢 easy improve

Show solution

"p95 end-to-end latency under 8 s over the nightly eval run; at least 85% of answerable eval questions judged correct by the calibrated judge; at least 90% of unanswerable questions declined." Each part names a metric, a threshold and how it's measured.

Exercise 3 🟢 easy explain

Why does the harness run each case three times?

Show solution

Outputs vary between runs. Repeats measure that variance and keep one lucky (or unlucky) run from deciding a release. A case that passes 1 time in 3 is a flaky case worth investigating.

Exercise 4 🟢 easy calculate

Use wilson to compare 45/50 with 90/100. Which result is more certain?

Show solution

Both are 90%, but 90/100 has the narrower interval: more cases, more certainty.

Show solution

Exercise 9 🔴 hard build it

Run the real harness end to end against the mock server: answer_fn is rag.answer with the real SDK, the judge is a FakeAnthropic that says correct. Which cases fail, and which grader fails them?

Show solution

The mock always quotes a document, so it never abstains: every unanswerable and adversarial case fails on the abstention grader, which is exactly what you want an eval to catch. (A real model with the "answer only from the documents" system prompt usually abstains; the eval measures how often.)

Exercise 10 🔴 hard design

Design the CI setup for DocsPilot's evals: when they run, what they block, how the baseline is updated, and what it costs.

Show solution
  • Unit tests with FakeAnthropic on every commit (free, seconds).
  • The eval job runs when files under prompts/, the retrieval code, the model config or the eval set change, plus nightly against main.
  • It blocks the merge if the pass rate drops more than the tolerance, or if any "must pass" case (security, privacy) fails.
  • The baseline is updated only by merging a change that passes; it's stored with the commit hash, prompt versions and model IDs.
  • Cost: cases × repeats × (answer + judge calls). 100 cases × 3 repeats × 2 calls ≈ 600 calls a run; with the price table, set a budget alarm on the CI key.
