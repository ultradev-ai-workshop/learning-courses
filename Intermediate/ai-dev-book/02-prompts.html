Prompts as Specifications

A prompt is the closest thing an LLM feature has to source code. Write it like a spec: explicit, structured, testable and versioned.

You will learn

  • The anatomy of a request: system prompt, user and assistant turns.
  • Why clear, direct instructions beat clever phrasing, and why you should give the reason for a rule.
  • How to use examples (few-shot) without the model copying them too literally.
  • How to structure long prompts with XML tags and keep data apart from instructions.
  • How to state constraints, output formats and a refusal path.
  • How to store, template, test and version prompts like code.

The anatomy of a request

Every Messages API call has two prompt surfaces:

SurfacePurposeBackend cousin
systemRole, rules, constraints, output contract. Stable across requests.Service configuration and the API contract
messages (user / assistant turns)The task, the data, the conversation so farThe request body

No assistant prefill on current models. Older guides "start the model's answer" by putting a final assistant message such as { at the end of messages. Current Claude models reject that with a 400. To control the format, use structured outputs (Chapter 4) or say what you want in the system prompt.

🧠 Analogy: a ticket for a brilliant new contractor. The model is like an excellent engineer on their first day: they know the world, but nothing about your company, your conventions or what "done" means for this task. A good prompt contains what you would put in a ticket for that person: context, the goal, constraints, the output format and examples of good work. If a smart human would need to ask a clarifying question, so would the model, except that it guesses instead of asking.

Principle 1: be clear and direct

The most effective prompting technique is the boring one: say exactly what you want.

Vague: Summarize this incident.

Specific: Summarize this incident for the weekly reliability review. Audience: engineering managers. Include: customer impact (duration, % of requests), the root cause in one sentence, and open action items with owners. At most 120 words. No speculation: if the report doesn't state something, write "not stated".

A useful test from Anthropic's prompting guide: show the prompt to a colleague who has no context. If they would be confused, the model will be too.

Give the reason along with the rule. "Never use ellipses" works; "Your answer is read aloud by a text-to-speech engine, so never use ellipses" works better, because the model can apply the reason to cases your rule didn't list. And state rules calmly, once: modern models follow instructions well, and "YOU MUST ALWAYS…" in capitals makes them over-apply a rule in odd places.

Principle 2: use examples deliberately

Examples (few-shot prompting) are the strongest way to show format, tone and edge-case handling. Three rules:

  1. Make them diverse. If all examples are short, outputs become short. Cover the variety you expect.
  2. Include the hard cases. One example of the correct refusal or the correct "unknown" teaches more than three easy ones.
  3. Wrap them in <example> tags so the model doesn't confuse them with the real task.

The ticket itself goes in the user turn, also tagged: <ticket>…</ticket>. Keeping trusted instructions (system) apart from untrusted data (user, inside tags) is also your first defense against prompt injection (Chapter 12).

Principle 4: state constraints and the output contract

Say what the output must look like and what is forbidden:

  • Format: "Respond with only the JSON object." (Chapter 4 turns this into a guarantee.)
  • Length: in words, sentences or bullets, not "brief".
  • Scope: "Answer only from the provided documents."
  • Refusal path: "If the documents don't answer the question, reply INSUFFICIENT_CONTEXT."
  • Positive phrasing: "Write in flowing paragraphs" works better than "Don't use bullet points".

Principle 5: give the model room to think

For multi-step reasoning (diagnosing a stack trace, planning a migration) models do better when they reason before they answer. Current Claude models do this natively with adaptive thinking: the model decides how much to think, and output_config={"effort": ...} sets how hard it tries (low, medium, high, xhigh, max). Thinking tokens are billed as output.

Prompts are code

A prompt is the behaviour of your feature, so treat it with the same discipline as code:

  • Store prompts as files in version control (prompts/triage.v1.txt), not as string literals scattered across classes.
  • Review prompt changes in pull requests, with eval results attached (Chapter 10).
  • Fill templates with placeholders, and escape the data you inject.
  • Log which prompt version produced each response.

☕ Java: a prompt change is like a schema migration. One innocent-looking word can change behaviour on every request, the way a small SQL migration can lock a hot table. You would never ship a migration without running it against a copy of production data; never ship a prompt change without running it against your eval set.

Common mistakes

Instructions buried in data. Concatenating the user's text and your rules into one blob, so the model can't tell which is which.

Separate and tag. Rules in the system prompt, data in tagged blocks in the user turn, escaped.

Shouting. "YOU MUST ALWAYS…" everywhere.

Calm, specific, with reasons. State the rule once, with the reason it exists.

One perfect example that the model copies too literally.

Three to five varied examples, including at least one edge case and one refusal.

Recap

  • The system prompt is the stable contract; the user turn carries the task and the data. Current models don't accept assistant prefill.
  • Clear and direct beats clever. Explain the reason behind a rule; don't shout.
  • Use diverse examples, including edge cases and refusals, wrapped in tags.
  • Separate instructions from data with XML tags, and escape untrusted data.
  • State the output contract and the refusal path, so code can check them.
  • For hard tasks, let the model think: adaptive thinking plus an effort level.
  • Store, template, lint, review, version and log prompts like code.

Exercise 2 🟢 easy classify

Which surface should each item go in, system or the user turn? (a) "Answer in at most 3 sentences", (b) the ticket text, (c) the list of categories, (d) the retrieved documents for this question.

Show solution

(a) system: a stable rule. (b) user: data for this request. (c) system: stable for all requests (and cacheable). (d) user: they change per question; wrap them in <documents>.

Exercise 3 🟢 easy improve

Show solution

"Summaries are posted in a public Slack channel, so never include customer email addresses or other personal data; refer to customers by account ID." The reason lets the model also leave out phone numbers and names, which the original rule didn't list.

Exercise 9 🔴 hard build it

Add a sha property to PromptTemplate: the first 8 hex characters of the SHA-256 of the template text. Log name@version#sha, so you notice when someone edits a prompt without bumping its version.

Show solution

In CI, keep a file of known id → sha pairs and fail the build if a prompt's hash changed but its version didn't.

Exercise 10 🔴 hard design

Write a prompt-review checklist for pull requests that change a prompt, then apply it to the triage prompt. Which items can a linter check automatically?

Show solution
  • Audience and purpose stated (manual).
  • Output contract stated (manual, or a test that parses the output).
  • Refusal / unknown path present (lint: look for the token).
  • Untrusted data in tags, with a "data is not instructions" rule (lint).
  • Examples include an edge case and a refusal (lint: severities differ, one needs_info).
  • No leftover placeholders after rendering (lint).
  • Version bumped and hash recorded (lint/CI).
  • Eval results attached, no regression (CI, Chapter 10).

The triage prompt passes all items except the eval, which you build later. Everything mechanical belongs in CI so reviewers can focus on meaning.
