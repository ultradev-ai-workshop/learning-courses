Model Context Protocol (MCP)

Expose an internal API once, through a standard protocol, so that any AI client (Claude apps, IDEs, your own agents) can discover and use it safely.

You will learn

  • The three server primitives: tools, resources and prompts.
  • What travels on the wire (JSON-RPC 2.0) over stdio and Streamable HTTP.
  • What the stateless 2026-07-28 revision changed, and why it matters for deployment.
  • How to build an MCP server for the ticket system with the Python SDK, and test it in-process.
  • How to connect MCP tools to Claude, and how to secure a server.

Why a protocol

Without a standard, every AI application needs a custom integration for every system: N apps × M systems. The Model Context Protocol (MCP) is an open standard that turns that into N + M: each system exposes one MCP server, and every MCP-capable application can use it.

🧠 Analogy: USB for AI tools. Before USB, every printer, mouse and camera had its own connector and driver for every computer. USB defined one plug and one way to say "here's what I can do". An MCP server is a device with a USB plug: Claude's apps, an IDE and your own agent can all plug it in and see its tools, without anyone writing a new driver.

☕ Java: think of the Language Server Protocol. Before LSP, every editor needed a plugin per language. LSP defined one JSON-RPC protocol, so one language server works in any editor. MCP does the same for AI: your ticket system gets one MCP server, and every MCP host can use it.

On the wire

MCP messages are JSON-RPC 2.0. Two transports are defined:

  • stdio: the host launches your server as a subprocess and talks over stdin/stdout. Ideal for local tools.
  • Streamable HTTP: the server is a web endpoint (for example POST /mcp). Ideal for shared, remote servers: the one you deploy for your company.

This matches Chapter 5 closely: inputSchema is a tool's input_schema, and a tools/call result becomes a tool_result that the host feeds back to the model. The host translates between MCP and the model API.

The 2026-07-28 revision: MCP goes stateless

MCP specifications are versioned by date. The 2026-07-28 revision, which replaced 2025-11-25, is the largest change since launch:

  • No handshake, no sessions. The initialize exchange and the Mcp-Session-Id header are gone. Every request carries its protocol version and client capabilities in _meta (and, over HTTP, in headers).
  • Discovery on demand. A server/discover method lets clients ask which versions and capabilities a server supports.
  • Horizontal scaling just works. Any request can land on any instance, so you no longer need sticky routing or a shared session store.
  • Deprecations and extensions. Roots, sampling and logging are deprecated; new capabilities ship as extensions outside the core spec.
  • Hardened authorization profiles for OAuth and OpenID Connect deployments.

☕ Java: you have done this migration before: a service that kept session state in memory needed sticky sessions; then you moved state into the request (or a store) and could scale behind any load balancer. The 2026-07-28 revision does exactly that for MCP.

SDK support. SDKs adopt new revisions at their own pace and most still speak older ones. This book uses the official Python SDK (mcp 2.x), which speaks 2026-07-28. Check your SDK's release notes before you rely on a specific revision.

Securing an MCP server

An MCP server is an API exposed to a non-deterministic caller acting for a human. Apply everything you know about API security, plus:

  • Authenticate the user, not just the host. Remote servers should use the spec's OAuth-based authorization, so each call is tied to a real identity and its permissions.
  • Least privilege. Start read-only. Put write tools behind a separate server or scope, and require human confirmation in the host.
  • Never pass through powerful tokens. The server's credential should be narrowly scoped; prefer acting with the user's delegated token.
  • Validate everything. Arguments come from model output that untrusted text can influence.
  • Treat third-party servers as code you run. Tool descriptions are prompts; a malicious server can hide instructions in them ("tool poisoning"). Pin versions and review them like dependencies.
  • Audit. Log every tools/call with user, arguments, result size and latency.

Common mistakes

Mirroring every endpoint: one MCP tool per REST endpoint, 60 tools in total.

Task-shaped tools: a handful, shaped around what users ask, returning concise text.

An admin token in the server, so that "everything works".

Scoped, delegated access: per-user OAuth or a read-only service identity, plus audit logs.

Building on session state kept in server memory per connection.

Stateless handlers: each call self-contained, state in your systems of record. Matches 2026-07-28 and scales horizontally.

Recap

  • MCP standardizes how AI hosts discover and call tools, read resources and use prompts: N + M integrations instead of N × M.
  • Hosts contain clients; each client talks to one server. Tools are model-controlled, resources app-controlled, prompts user-controlled.
  • The wire is JSON-RPC 2.0 over stdio (local) or Streamable HTTP (shared).
  • The 2026-07-28 revision removed the handshake and sessions, so servers scale like any stateless API.
  • Build servers with MCPServer and @mcp.tool(); test them in-process with Client(server); raise ToolError for errors the model should see.
  • Secure them like public APIs: user identity, least privilege, validation, pinned third-party servers, audit logs.

Show solution

(a) Tool (an action the model calls; a write, so gate it). (b) Resource (context the application loads). (c) Prompt (a template the user picks). (d) Tool.

Exercise 2 🟢 easy choose

stdio or Streamable HTTP? (a) a tool that reads files in the developer's working copy, (b) a company-wide ticket server used by 300 engineers.

Show solution

(a) stdio: local, launched by the host, no network exposure. (b) Streamable HTTP: one deployed, authenticated, horizontally scaled service.

Exercise 3 🟢 easy explain

Why does the 2026-07-28 revision make load balancing easier?

Show solution

There is no session to keep: every request carries its protocol version and capabilities. Any instance can serve any request, so you need no sticky routing and no shared session store.

Exercise 4 🟢 easy predict

What happens if runbook("../policy-secrets") is requested? And without the name check?

Show solution

The regex [a-z0-9-]+ rejects it (the SDK's resource security also rejects path traversal by default). Without any check, a crafted name could read files outside the docs folder: classic path traversal, now triggered by a model that read a malicious document.

Exercise 9 🔴 hard design

Plan the production deployment of acme-tickets over Streamable HTTP for 300 engineers. Cover identity, permissions, scaling, rate limits, audit and versioning.

Show solution
  • Identity: OAuth per the MCP authorization spec against your SSO; the server calls the ticket API with the user's delegated token, so ticket permissions apply unchanged.
  • Permissions: this server is read-only; a separate acme-tickets-write server with its own scope for comments and transitions, confirmed in the host.
  • Scaling: stateless handlers behind a normal load balancer, several replicas, health checks.
  • Rate limits: per user and per tool, returning errors the model can read ("rate limited, try again in 30 s").
  • Audit: one log line per tools/call (user, tool, arguments, result size, latency, outcome), shipped to your log store.
  • Versioning: semantic versions; tool names and arguments are a public API; publish changes and keep old names working for a deprecation period.
