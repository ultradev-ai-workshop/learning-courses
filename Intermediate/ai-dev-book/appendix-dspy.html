Appendix E · Popular Frameworks

DSPy

A framework that treats prompts as programs to be optimized rather than hand-written: you declare what goes in and out, write a metric, and let an optimizer choose instructions and examples against your data. It's evals-first development (Chapter 10) taken to its conclusion.

You will learn

  • Signatures: declaring inputs and outputs instead of writing prompt text.
  • Modules: Predict, ChainOfThought, ReAct, and composing your own.
  • Examples, metrics and Evaluate.
  • Optimizers ("teleprompters"): what LabeledFewShot, BootstrapFewShot and MIPROv2 change.
  • How to test DSPy programs with DummyLM, and how to inspect the prompts it generates.
  • When DSPy is worth it.

Versions. This appendix uses dspy 3.x, which calls providers through LiteLLM. Models are named "provider/model", for example dspy.LM("anthropic/claude-haiku-5-5"). Here ANTHROPIC_BASE_URL points LiteLLM at the book's mock server, which understands DSPy's field format, so programs run end to end (with placeholder answers).

Signatures and Predict

A signature says what a step takes and returns. DSPy turns it into a prompt and parses the reply into fields. The short form is a string; the class form adds instructions and field descriptions:

🧠 Analogy: SQL versus hand-written loops. In SQL you declare what you want and the query planner decides how to fetch it, using statistics about your data. In DSPy you declare the signature and the metric, and the optimizer decides how to phrase the prompt and which examples to include, using your labelled data. Hand-written prompts are the hand-written loop: sometimes best, often not worth it.

☕ Java: a signature is like an interface method declaration (Severity triage(String ticket)) whose implementation is generated and then tuned against a test suite. There's no mainstream Java DSPy; Java teams often run DSPy offline in Python to find a good prompt, then ship that prompt in their Java service.

Examples, metrics and Evaluate

An example is a labelled case; with_inputs says which fields are inputs. A metric is a function (example, prediction, trace=None) → bool or float. Evaluate runs a program over a dev set and reports the score:

This is Chapter 10's eval harness in DSPy form: a fixed set, a grader, a score. The metric can itself call a model (an LLM judge) for open-ended outputs.

Optimizers

An optimizer (DSPy also calls them teleprompters) takes a program, a training set and a metric, and returns an improved program:

OptimizerWhat it changesCost
LabeledFewShotadds k labelled examples as demonstrationsno model calls
BootstrapFewShotruns the program on training inputs, keeps the traces that pass the metric as demonstrationsone run per training example
MIPROv2 and newer optimizersproposes and searches instructions and demonstrations togethermany calls: budget it

Optimizing against your test set. An optimizer will happily overfit. Keep three splits: train (the optimizer sees it), dev (you compare runs) and a held-out test set you look at once, before shipping (Chapter 14).

Recap

  • Signatures declare inputs and outputs; DSPy writes and parses the prompt.
  • Modules (Predict, ChainOfThought, ReAct, your own) compose like functions.
  • Examples + metric + Evaluate = an eval harness.
  • Optimizers change demonstrations and instructions to raise the metric; guard against overfitting with splits.
  • DummyLM makes programs testable; inspect the generated prompts.

Exercises

Exercise 1 🟢 easy explain

What does a signature replace in a hand-written prompt?

Show solution

The instructions about what to produce and the output format ("reply with the severity…"), plus the parsing code. You still choose the field names, descriptions and the docstring, which become the prompt's content.

Exercise 2 🟢 easy predict

Which fields does dspy.ChainOfThought("ticket -> severity") return?

Show solution

reasoning and severity: ChainOfThought adds a reasoning field before the declared outputs.

Exercise 3 🟢 easy explain

Why must the metric be decided before optimizing?

Show solution

The optimizer maximizes whatever the metric rewards. A vague or wrong metric produces a program that is good at the wrong thing, as with any optimization.

Write a metric that gives partial credit: 1.0 for the exact severity, 0.5 if it's one level off (sev1 vs sev2), 0 otherwise. Evaluate a DummyLM that always says sev2.

Exercise 8 🟡 medium explain

BootstrapFewShot keeps only traces that pass the metric. Why does that tend to produce better demonstrations than hand-picked examples?

Show solution

The kept demonstrations are outputs the current model actually produced and that met your metric, in exactly the format the program uses, including intermediate fields like reasoning. Hand-picked examples may be in a style the model doesn't naturally produce, or miss the intermediate steps.

Exercise 9 🔴 hard build it

Run BootstrapFewShot with a scripted DummyLM that answers correctly for two training tickets and wrongly for the third. How many demonstrations survive?

Show solution

The failing trace ("slow page" answered sev3) is dropped; only passing traces become demonstrations.

Exercise 10 🔴 hard design

Plan a DSPy experiment to improve DocsPilot's triage prompt: data, splits, metric, optimizer, budget, and how the result reaches production.

Show solution
  • Data: 600 historical tickets with final severities; 300 train, 150 dev, 150 held-out test.
  • Metric: exact match, with a heavier penalty for under-rating a SEV1 (recall matters).
  • Baseline: the current hand-written prompt, evaluated on dev.
  • Optimizers: LabeledFewShot (free), then BootstrapFewShot, then MIPROv2 with a capped number of trials; record cost per run.
  • Decision: the best dev score, confirmed once on the test set; then export the optimized prompt (or ship the saved program), run the normal eval CI gate, and deploy behind a flag.
