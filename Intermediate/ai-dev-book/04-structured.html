Structured Output

Turn free-form text into typed, validated data your services can trust: a JSON Schema in, schema-conformant JSON out, then business validation, exactly like any other API boundary.

You will learn

  • Why "please answer in JSON" is not a contract.
  • The reliability ladder: prompting, strict tool inputs, and native structured outputs.
  • How to send a JSON Schema with output_config.format and get guaranteed-valid JSON.
  • How to define the schema as a Pydantic model and get typed objects back with messages.parse.
  • What a schema can't express, and the business validation you must still write.
  • How to handle truncation, refusals and wrong values: repair, retry once, or fall back.

Why structure matters

Most LLM features in a backend are not chat. They are functions: classify this ticket, extract the fields of this invoice, decide which runbook applies. Their callers are other services, and services need a contract. Free text breaks contracts in predictable ways: a friendly preamble ("Sure! Here's the JSON:"), a missing field, "Billing" instead of "billing", a trailing comment.

Only one reply of four is usable. Asking more nicely helps, but it never makes the failure rate zero.

🧠 Analogy: a letter versus a paper form. Asking for "JSON, please" is like asking a customer to write you a letter that contains their name, address and order number. Most letters will contain them, in creative places. Structured outputs hand the customer a form with labelled boxes and tick-boxes for the fixed choices: they can still write the wrong street name in the address box, but they can't skip the box or invent a new tick-box.

☕ Java: think of an OpenAPI response schema that the server enforces. Native structured outputs move that promise into the model's decoder: it may only produce tokens that keep the output valid against your schema (constrained decoding). You then deserialize into a record with Jackson, as you would any other payload.

Structured outputs work through constrained decoding: the API compiles your schema into a grammar and only lets the model emit tokens that keep the output valid. The parameter used to be a beta called output_format; today it is output_config.format, with no beta header.

Forcing a tool call is gone on the newest models. Older guides forced a "fake tool" with tool_choice={"type": "tool", ...} to get JSON. claude-opus-5-5 and claude-sonnet-5-5 reject a forced tool_choice with a 400. Use structured outputs for JSON, and strict: true on real tools.

Handling failure

Even with constrained decoding, three things go wrong:

  1. Truncation. If max_tokens is too small, the JSON stops mid-object. Check stop_reason == "end_turn" before parsing.
  2. Refusal. A refusal stop reason means there is no valid object. Route to a fallback.
  3. Valid but wrong. The right shape with the wrong values. Business rules catch some of these; evals (Chapter 10) measure the rest.

When validation fails, choose deliberately between repair (a deterministic fix in code), retry (one more call, sending the validation error back to the model) and fallback (a default value or a human queue). Never retry in an unbounded loop. Here is "retry once with feedback", tested with a scripted fake whose first answer breaks a rule:

Common mistakes

Trusting valid JSON. Writing a well-formed object straight to the database.

Recap

  • Machine-consumed output needs a contract; a prompt alone is not one.
  • output_config.format with a JSON Schema gives schema-valid JSON through constrained decoding; messages.parse(output_format=Model) does the schema and the parsing for you.
  • Define schemas as Pydantic models (records in Java) and generate the JSON Schema from them.
  • Use enums for closed sets and nullable fields for facts that may be missing.
  • Check stop_reason, then validate business rules; repair, retry once with feedback, or fall back.

Exercises

Exercise 1 🟢 easy predict

With structured outputs, can the model return "severity": "critical" for the Triage schema? Can it return a wrong but allowed severity?

Show solution

No: critical isn't in the enum, so constrained decoding can't produce it. Yes: it can choose sev3 for a real outage. The schema guarantees shape, not truth; evals measure the truth.

Exercise 2 🟢 easy order the steps

Put these in the right order: validate business rules, check stop_reason, parse JSON into the model, send the request.

Show solution

Send the request → check stop_reason → parse into the model → validate business rules. Parsing a truncated answer gives a confusing error far from the cause.

Exercise 3 🟢 easy build it

Write a Pydantic model Sentiment with a label (positive, neutral, negative) and a confidence between 0 and 1 (use Field(ge=0, le=1)). Validate {"label": "positive", "confidence": 1.3}.

Show solution

Range checks like this may not be enforced while decoding, so Pydantic's validation is your safety net.

Exercise 4 🟢 easy fix the bug

This code crashes now and then with ValidationError: EOF while parsing. What is missing?

Show solution

A stop_reason check. With max_tokens=60 the JSON is sometimes cut off (stop_reason == "max_tokens"). Check it first and raise a clear error, and give structured output enough room (1,000+ tokens is cheap: you only pay for what is generated).

Exercise 5 🟡 medium build it

Define DocsPilot's Answer: answerable (bool), answer (str), sources (a list of objects with doc_title and quote) and follow_ups (a list of strings). Add a check that every doc_title is one of the titles you actually sent.

Show solution

An invented source title is a cheap, reliable hallucination signal. Keep this check for the project.

Exercise 6 🟡 medium test it

Use mock_api() and the real SDK to show that max_tokens=5 on a structured request returns stop_reason == "max_tokens", and that your triage() from Step 2 raises before parsing.

Show solution

The text is the start of a JSON object, not a valid one. Parsing it would fail with a confusing error; the stop_reason check fails with a clear one.

Exercise 7 🟡 medium design

For each failure, choose repair, retry or fallback: (a) sev1 with needs_human=false; (b) a summary of 260 characters; (c) stop_reason == "refusal"; (d) an invoice whose lines don't add up.

Show solution

(a) Repair: the fix is deterministic. (b) Repair (truncate at a sentence boundary) or retry once with the error. (c) Fallback: retrying the same request won't change the answer. (d) Retry once with the error ("lines sum to X, total says Y"); if it still fails, send it to a human. Extracted money should never be "repaired" by guessing.

Exercise 8 🟡 medium build it

Write a schema for extracting action items from meeting notes: a list of items, each with task, owner (nullable) and due (nullable ISO date string). Validate an example with one item that has no owner.

Show solution

Pydantic turns the ISO string into a real date, so an invented "next Tuesday" fails validation instead of reaching your calendar.

Exercise 9 🔴 hard build it

Write a generic extract(client, model_cls, text, rules=()): structured request, stop_reason check, parse, run each rule function (each may raise ValueError), and one retry with feedback. Return (obj, attempts) or raise after the retry.

Show solution

Exercise 10 🔴 hard design

Your triage feature runs on 50,000 tickets a day. The retry path fires on 6% of them. List what you would look at, in order, to bring that down, and how you would know you succeeded.

Show solution
  1. Group the failures by rule: is it one rule (say, "sev2 must name a service")?
  2. If a rule fires often, move it into the schema if possible (an enum, a required field) or explain it in the field description and system prompt, with an example.
  3. Check whether the rule is right: maybe tickets genuinely don't name a service, and needs_info is the correct answer.
  4. Check truncation (stop_reason) and raise max_tokens if needed.
  5. Try a stronger model only after the prompt and schema are right.

Success: the retry rate falls on a fixed eval set (Chapter 10) and accuracy doesn't drop; then confirm in production metrics.
