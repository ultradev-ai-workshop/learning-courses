The one-paragraph model

A large language model (LLM) is a function that takes a sequence of tokens and returns a probability distribution over the next token. Generation is a loop: pick a token from that distribution, append it, run the function again. Everything else (chat, tool calls, JSON, reasoning) is built on that loop. The function's billions of parameters were fitted on a huge amount of text to predict the next token, and then trained further, with human and AI feedback, to follow instructions and be helpful.

You can see the loop with TinyLM, a model so small it only looks at the previous word. A real model looks at the whole context through a neural network, but the loop is the same:

Two seeds, two different continuations of the same prompt. Neither one is "the answer": each is a plausible path through the distribution.

🧠 Analogy: a very well-read improviser. Picture an actor who has read most of the internet and is brilliant at continuing any scene you start. Give them a script with a role ("you are a support engineer"), some facts and a question, and they will continue it convincingly. But they never stop to look anything up: if a fact isn't in the script or in their memory, they improvise something that sounds right. Your job as the engineer is to write good scripts and check the performance.

Two consequences matter most for you:

  1. The model has no state between requests. The API is stateless. If the model "remembers" an earlier turn, it is because your code sent that turn again.
  2. The model produces plausible text, not verified facts. Plausible and true overlap most of the time, which is exactly why the failures are hard to spot.

Tokens

Models do not read characters or words. A tokenizer splits text into tokens: common words become one token, rare words split into several, and code, JSON and non-English text usually need more tokens per character than English prose. llmkit.tokenize is a toy tokenizer, but it behaves the same way:

Tokens are the unit of three things you care about:

Measured in tokensWhy you care
PriceYou pay per million input tokens and per million output tokens, at different rates.
LimitsThe context window and max_tokens are token counts.
LatencyOutput is generated one token at a time, so output length drives response time.

A rule of thumb for English prose is 3–4 characters per token. Don't budget with rules of thumb in production: count. The API has a free endpoint that counts tokens for exactly the body you would send, including the system prompt and tool definitions:

Count in the same shape you send. The count endpoint accepts the same body as a real request. System prompts and tool definitions cost tokens on every call, and often cost more than the user's question.

The context window

The context window is the maximum number of tokens the model can consider in one request: the system prompt, all the messages, tool definitions, documents and the output it writes. Current Claude models have windows of up to 1M tokens.

A large window is a capability, not a strategy. Three reasons not to fill it:

  • Cost scales linearly with input. Sending 500k tokens on every request is expensive even when it works.
  • Latency grows with input. The model processes every input token before it writes the first output token.
  • Attention is finite. A fact buried in a huge context is recalled less reliably than the same fact in a short, focused one. Keeping only high-signal tokens in the window is called context engineering.

Sampling and non-determinism

At each step the model has a probability distribution over the next token, and sampling picks one. In the classic recipe, a temperature reshapes the distribution first: low temperature sharpens it (the favourite wins more often), high temperature flattens it (more variety).

Two facts every LLM developer must know:

  • Low temperature reduces variation, not errors. A confidently wrong answer at temperature 0 is still wrong, just consistently wrong.
  • Even "greedy" decoding isn't perfectly repeatable in a large serving system, because of batching and floating-point effects. Design for variation instead of assuming it away.

Current Claude models don't take temperature. Older tutorials set temperature, top_p or top_k. Current Claude models think adaptively, and the API rejects those sampling parameters with a 400; the current Python SDK doesn't even have arguments for them. The control you get instead is output_config={"effort": "low" | "medium" | "high" | ...}, which trades depth of thinking for speed and cost. Other providers still accept temperature, so check each model's docs.

Hallucinations

A hallucination is fluent output that is false or unsupported: an invented API method, a fake citation, a wrong config default stated with confidence. It happens because the model is optimized for plausible continuations; when it lacks the fact, a plausible-sounding fact is still the most likely continuation.

The engineering levers, from most to least effective:

  1. Ground it. Put the source material in the context and tell the model to answer only from it (RAG, Chapter 7).
  2. Let it say no. Explicitly allow "I don't know", or a structured "answerable": false field. Models invent less when abstaining is a legitimate answer.
  3. Verify downstream. Check claims mechanically wherever you can: compile the generated code, run the test, look up the ID in the database, resolve the citation.

Invented identifiers are the costliest kind. A made-up ticket ID, user ID, config key or library method looks exactly like a real one. Validate every identifier the model produces against a system of record before your code acts on it.

Cost and latency

You can estimate both before you write any feature code.

Cost per request = input tokens × input price + output tokens × output price. Output tokens cost several times more than input tokens, and thinking tokens are billed as output.

Model (October 2026)Typical roleUSD per million tokens, in / out
claude-haiku-5-5classification, routing, extraction at volume$0.10 / $0.50
claude-sonnet-5-5the default for most product features$2 / $10
claude-opus-5-5hard reasoning, agentic coding, long tasks$4 / $20

Prices change, and batch processing (50% off) and prompt caching (Chapter 11) change the math further, so always recompute from the live pricing page.

Latency has two parts: time to first token (TTFT), driven mostly by input size and model size, and generation time, driven by output length. Streaming (Chapter 3) does not make the total faster; it lets the user see progress sooner.

Common mistakes

Assuming the model remembers. Sending only the newest message and expecting the model to recall the previous turn.

Resend the history, trimmed to a budget. Your code owns conversation state.

"Temperature 0 means correct." Turning randomness down to fix wrong answers.

Ground and verify. Add sources to the context, allow abstention, check outputs mechanically.

Filling the window because it fits. Dumping the whole wiki into every request because the window is 1M tokens.

Send the smallest useful context. Retrieve the relevant chunks; pay for and wait on only what matters.

Recap

  • An LLM predicts the next token; generation is a loop over that prediction.
  • The API is stateless. Your code owns the conversation and resends it.
  • Tokens are the unit of price, limits and latency. Count them with the API, not with guesses.
  • A big context window is a ceiling, not a target.
  • Sampling makes output vary; current Claude models take effort, not temperature. Neither setting controls truth.
  • Reduce hallucinations by grounding, permission to abstain, and mechanical verification.
  • Estimate cost and latency from token counts before you build.

Exercises

Exercise 1 🟢 easy predict

A user has a 10-turn chat. On turn 11 your code sends only the new question. What does the model know about turns 1–10?

Show solution

Nothing. Each request stands alone; the model sees only what that request contains. To continue the conversation, send the earlier turns (or a summary of them) again.

Exercise 2 🟢 easy measure

Use llmkit.tokenize to compare the same data as pretty-printed JSON (json.dumps(d, indent=2)) and compact JSON (separators=(",", ":")). Which is cheaper?

Show solution

Compact JSON is cheaper: whitespace and newlines cost tokens too. At volume, compact formats (fewer keys, no indentation) save real money.

Exercise 3 🟢 easy calculate

A request has 10,000 input tokens and 1,000 output tokens on claude-opus-5-5 ($4 / $20 per million). What does it cost? Which part is bigger?

Show solution

Input: 10,000 × 4 / 1e6 = $0.04. Output: 1,000 × 20 / 1e6 = $0.02. Total $0.06. Input is bigger here even though output tokens cost 5× more, because there are 10× as many input tokens.

Exercise 4 🟢 easy choose

For each lever, say whether it reduces hallucinations: (a) lower temperature, (b) put the runbook in the prompt, (c) allow "I don't know", (d) look up every ticket ID the model mentions.

Show solution

(a) No: it reduces variety, not falsehood. (b) Yes: grounding. (c) Yes: permission to abstain. (d) Yes: mechanical verification, and the only one you can fully rely on before acting.

Exercise 5 🟡 medium build it

Estimate DocsPilot's monthly cost: 300 engineers × 6 questions a day × 22 working days, 6,000 input tokens (retrieved chunks) and 400 output tokens per answer, on claude-sonnet-5-5.

Show solution

Per request: 6,000 × 2 / 1e6 + 400 × 10 / 1e6 = $0.016. Prompt caching (Chapter 11) cuts the repeated part of the input substantially.

Exercise 6 🟡 medium experiment

Train TinyLM on the corpus from the first example and generate 5 continuations of "the" with seeds 0–4, first at temperature=1.0, then at temperature=0.1. What changes?

Show solution

At low temperature the favourites win almost every time, so there are fewer distinct outputs. Notice that "the queue is down" appears at 1.0 although the corpus never says it: the bigram model only knows "queue is", then "is down". That is a miniature hallucination: locally plausible, globally unsupported.

Exercise 7 🟡 medium fix the bug

This chat helper "forgets" everything. Fix it so that it keeps the conversation.

Show solution

The state lives in your object (in production: a database keyed by conversation ID), and every request carries it.

Exercise 8 🟡 medium build it

Write fits(input_tokens, max_tokens, window) that returns whether a request can fit in the context window, and test it with a 1,000,000-token window: 990,000 input tokens and max_tokens=16,000.

Show solution

Input and output share the window, so leave room for the answer. "It fits" still doesn't mean "it works well": see the context-engineering points above.

Exercise 9 🔴 hard design

Your team wants to add "explain this stack trace" to an IDE plugin with 2,000 users, each asking 15 times a day. Traces average 1,500 tokens, the prompt 400, answers 300. Estimate monthly cost (22 days) for Haiku and Sonnet, the latency for each answer (use the latency function above), and say which numbers you would measure before deciding.

Show solution

Measure: answer quality on 50 real traces for both models (an eval), real TTFT and tokens/second from your region, and the real output length (people may get 600-token answers, doubling the output cost). A 4-second wait suggests streaming the answer into the IDE.

Exercise 10 🔴 hard build it

Write summarize_old(messages, keep_last, summarize): if a history has more than keep_last + 1 messages, replace the old ones (except messages[0]) with a single user message that contains a summary produced by summarize(list_of_messages). Make sure roles still alternate correctly: user first, and no two assistant messages in a row.

Show solution

The summarizer would itself be a cheap model call (Haiku). The API accepts consecutive same-role messages by merging them, but keeping the alternation explicit makes the history easy to read and debug.
