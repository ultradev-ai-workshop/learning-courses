Embeddings & Vector Search

Represent the meaning of text as vectors, store them next to your data, and find related content by meaning instead of by keywords.

  • How approximate nearest-neighbour indexes trade accuracy for speed.
  • How to measure retrieval quality with recall@k before you build on it.

What an embedding is

An embedding model maps a piece of text to a fixed-length list of floats, for example 1,024 numbers. It is trained so that texts with similar meaning land close together. "How do I reset my password?" and "Steps to recover lost login credentials" share almost no words, yet their vectors point in nearly the same direction.

Closeness is usually measured with cosine similarity: the cosine of the angle between two vectors, from −1 (opposite) through 0 (unrelated) to 1 (same direction). Many embedding models return vectors normalized to length 1, so cosine similarity is just the dot product.

llmkit.embed is a tiny deterministic embedding model (256 numbers, built from words, synonyms and letter patterns). It's crude, but it behaves like the real thing on our sample docs:

The first line is the interesting one: no shared words, high similarity. A keyword search would miss it.

🧠 Analogy: a library arranged by topic. A keyword index is the alphabetical card catalogue: great when you know the exact title. Embeddings are a library where every book has been shelved by what it's about, so books on "credentials" and "passwords" sit on the same shelf even if their titles share no word. Search means walking to the shelf where your question would sit and taking the nearest books.

☕ Java: a B-tree index answers "rows where title = ?". A full-text index answers "rows containing these words". A vector index answers "rows whose meaning is nearest to this". It's still an index: you build it at write time, pay for it in storage and memory, and tune it for the queries you run.

Exact versus approximate search

Exact search compares the query with every row: perfect results, cost proportional to the number of rows. Approximate nearest-neighbour (ANN) indexes look at only part of the data. pgvector's HNSW builds a navigable graph; another classic, IVF, groups vectors into clusters and searches only the clusters closest to the query. IVF is easy to build in a few lines, which makes the trade-off visible:

Searching more clusters finds more of the true neighbours, at the cost of scanning more rows. HNSW has the same kind of dials:

  • Build time: m and ef_construction (graph quality versus build time and memory).
  • Query time: SET hnsw.ef_search = 100; (higher means better recall and slower queries).

Filters plus approximate indexes. With a selective WHERE (a rare acl_group), an approximate index can return fewer than k rows, because it finds neighbours first and filters afterwards. pgvector 0.8 added iterative index scans (SET hnsw.iterative_scan = relaxed_order;) to keep searching; check its README for your version.

Measuring retrieval quality

Before you build RAG on top, measure retrieval on its own. Write a small labelled set: realistic questions, each with the document (or chunk) that answers it. Then compute recall@k: the share of questions whose right document appears in the top k.

This number is your baseline. Chapter 7 tries to beat it with chunking, hybrid search and reranking, and you'll know whether each change helped because you measured first.

☕ Java: recall@k is the hit rate of your knowledge layer, like a cache hit rate. You would never tune a cache without measuring its hit rate. If the right chunk isn't in the top k, no prompt and no model can produce the right answer.

Why you must not mix models

Vectors from two different models live in different spaces; comparing them is meaningless, even when they have the same size. embed takes a model name to simulate a second model:

Same text, near-zero similarity across models, while a related text within one model scores high. Nothing raises an error: the search just returns nonsense. Store embed_model with every vector and re-embed everything when you switch.

Common mistakes

Mixing embedding models: querying vectors made by model A with a query embedded by model B.

One model per index, recorded per row; re-embed everything when you switch.

Filtering after retrieval: fetching the top 8 for everyone, then removing chunks the user may not see.

Filter in the query, so forbidden text never reaches the prompt.

Building RAG without a retrieval baseline, then blaming the prompt.

Measure recall@k first on labelled questions.

Recap

  • An embedding is a vector of meaning; similar texts have high cosine similarity.
  • Exact search is a matrix-vector product and a sort; fine up to tens of thousands of rows.
  • Anthropic doesn't ship an embedding model; use a provider such as Voyage AI and evaluate several. Use document/query input types when the model supports them.
  • pgvector gives you vectors, distance operators and HNSW indexes in the Postgres you already run.
  • Approximate indexes trade recall for speed; filters need care.
  • Measure recall@k on labelled questions before building RAG on top.

Exercises

Exercise 1 🟢 easy predict

Two texts share no words but mean the same thing. What do you expect from (a) a keyword search, (b) cosine similarity of good embeddings?

Show solution

(a) No match. (b) A high similarity: the vectors point in nearly the same direction. That's the reason to use embeddings.

Exercise 2 🟢 easy calculate

Compute by hand the cosine similarity of [1, 0] and [1, 1], then check it with NumPy.

Show solution

Dot product 1, lengths 1 and √2, so 1/√2 ≈ 0.707: a 45° angle.

Exercise 3 🟢 easy explain

Why does the pgvector query filter by acl_group in the WHERE clause instead of removing forbidden rows from the results in Python?

Show solution

Filtering afterwards means forbidden text has already left the database; one bug and it reaches the prompt (and the user). It also leaves you with fewer than k results. Filtering in the query is both safer and more correct.

Exercise 4 🟢 easy build it

Print the 4×4 similarity matrix for: "rotate the db password", "change postgres credentials", "create a kafka topic", "lunch menu".

Show solution

The vectors are normalized, so m @ m.T is the cosine matrix. Compare rankings, not raw scores: every model has its own scale.

Exercise 5 🟡 medium build it

Add a min_score parameter to VectorStore.search so weak matches are dropped. What should DocsPilot do when nothing passes?

Show solution

When nothing passes, don't call the model with irrelevant context: answer "I couldn't find this in the docs" directly. That's cheaper and stops ungrounded answers. Tune the threshold on your labelled set.

Exercise 6 🟡 medium build it

Add three more cases to CASES, including one vague and one misspelled question. Does recall@3 change?

Show solution

Realistic questions are messy. Misspellings hurt word-based models; real embedding models handle them better, and hybrid search (Chapter 7) helps too.

Exercise 7 🟡 medium explain

In the IVF example, what is the cost of nprobe=10 compared with exact search, and what did you get for it?

Show solution

It scanned about a fifth of the rows (plus the 50 centroids) instead of all of them, and still found all 10 true neighbours for these queries. With nprobe=1 it scanned 3% but missed almost a third of the neighbours. Approximate search is a dial between speed and recall; measure where your use case needs it.

Exercise 8 🟡 medium build it

Write ingest_batches(texts, embed_batch, size=64) that calls an embedding API in batches and keeps the results in input order, even if the API returns them shuffled (each result carries an index).

Show solution

Batching cuts HTTP overhead; sorting by index protects you from a silent, disastrous mix-up of texts and vectors.

Exercise 9 🔴 hard build it

Write a "related docs" function: for a given doc id, average the vectors of its sections (split on ## ) and return the two nearest other documents.

Show solution

Show the results to a teammate and collect "this is wrong" examples: they become labelled cases for your eval set.

Exercise 10 🔴 hard design

You must switch from embedding model A (1,024 dimensions) to model B (1,536) on a table with 2 million chunks, without downtime. Plan the migration.

Show solution
  1. Add a new column embedding_b vector(1536) (or a second table) and its index; keep embed_model per row.
  2. Backfill in batches with model B, idempotently; new writes embed with both models during the migration.
  3. Run your recall@k eval against both columns; switch only if B is better (or equal and cheaper).
  4. Flip the query path behind a flag, watch metrics, keep A for rollback.
  5. Drop column A and its index after a safe period.

The same playbook as any column migration, plus an eval gate. Queries must always use the model that made the vectors they search.
