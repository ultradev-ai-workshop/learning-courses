Calling LLM APIs

Call the Messages API with nothing but an HTTP client, then with the official SDK. Add streaming, timeouts, retries and the error handling you would expect from any production client.

You will learn

  • The exact shape of a Messages API request and response.
  • How to call it with Python's standard library only, so you know what an SDK hides.
  • How the official anthropic SDK maps to the same request, in sync and async code.
  • How to hold a multi-turn conversation.
  • How streaming works (Server-Sent Events) and when to use it.
  • Which errors to retry, which to surface, and how stop_reason tells you an answer is incomplete.

The request, on the wire

There is one core endpoint: POST https://api.anthropic.com/v1/messages.

Things to notice:

  • max_tokens is required. It caps the output, not the input.
  • content is an array of blocks, not a string. Today you get text; later you will see tool_use (Chapter 5) and thinking blocks.
  • stop_reason tells you why generation stopped. Always check it.
  • usage is your billing record. Log it on every call.

☕ Java: nothing here is special. An auth header, a version header (like an Accept-Version pin), a JSON body, a JSON response, standard HTTP status codes and a request-id response header for support tickets. Everything you know about calling a REST service applies.

Version 2: the official SDK

The SDK gives you typed requests and responses, automatic retries with backoff (2 by default), timeouts (10 minutes by default), streaming helpers and typed exceptions. Use it in production once you understand what it does.

The response is a typed object (a Pydantic model), so your editor completes message.usage.output_tokens, and message.to_dict() gives you the plain JSON when you need it.

Errors and what to do about them

Statuserror.typeMeaningAction
400invalid_request_errorbad body or parameter, too many tokensFix the request. Don't retry.
401authentication_errorbad or missing keyAlert. Don't retry.
403permission_errorkey lacks accessAlert. Don't retry.
404not_found_errorwrong model ID or endpointFix the config.
413request_too_largebody over the size limitShrink the request.
429rate_limit_errorover your rate limitsRetry after retry-after; shape traffic (Ch. 11).
500api_errorserver errorRetry with backoff.
529overloaded_errortemporarily overloadedRetry with backoff; consider a fallback model.

The SDK raises a typed exception for each. Catch the specific ones first, so retryable and non-retryable failures stay distinct:

Two failures that come back as HTTP 200

  • stop_reason: "max_tokens": the answer was cut off. The response is HTTP 200 but incomplete, and it is billed. Treat it as an error for structured output, or raise max_tokens.
  • stop_reason: "refusal": the model declined for safety reasons; stop_details says why. Show a graceful message; don't retry the identical request in a loop.

Retrying non-idempotent work. Retrying the API call itself is safe: creating a message has no side effects. Retrying a whole workflow that also sent an email or wrote a row is not. Keep side effects out of the retried section, or make them idempotent, exactly as with any other remote call.

Many providers and local model servers speak the OpenAI "chat completions" format. The ideas are identical; the field names differ. The system prompt is a message, the answer lives in choices[0].message.content, and finish_reason plays the role of stop_reason:

Frameworks such as LangChain (Appendix A) hide these differences behind one interface, which makes switching providers cheap.

Common mistakes

Reading content[0].text blindly. Assumes the first block is text and the answer is complete.

Iterate blocks, check stop_reason. Collect text blocks by type and branch on stop_reason before you use the result.

Retrying every error. Retrying 400s and 401s burns quota and hides config bugs.

Retry only transient failures: 408, 409, 429, 5xx, 529 and connection errors, with backoff and jitter, honouring retry-after.

No timeout. A hung request ties up a worker until the load balancer gives up.

Explicit timeouts on every call; stream long outputs.

Recap

  • One endpoint, JSON in and out, standard HTTP semantics, plus a request-id to log.
  • content is an array of typed blocks; stop_reason and usage come with every answer.
  • The SDK adds types, retries, timeouts, async and stream helpers on top of the same request.
  • Conversations are lists you store and resend.
  • Stream anything a human waits on; message_delta carries the final stop_reason and usage.
  • Retry transient errors with backoff; treat max_tokens truncation as a failure.

Exercises

Exercise 1 🟢 easy predict

A response comes back with HTTP 200 and stop_reason: "max_tokens". Is the answer complete? Is it billed?

Show solution

No, it was cut off at the cap you set. Yes, you pay for every token generated. Raise max_tokens, ask for a shorter answer, or treat it as a failure.

Exercise 2 🟢 easy classify

Which of these should a client retry? 400, 401, 404, 408, 429, 500, 529, a connection reset.

Show solution

Retry 408, 429, 500, 529 and the connection reset (with backoff, honouring retry-after). Don't retry 400, 401 or 404: they need a fix, not another attempt.

Exercise 3 🟢 easy fix the bug

Why does this crash with TypeError on the second call, and how do you fix it?

Show solution

The content of a message must be a string or a list of content blocks, not a whole Message (with its id, usage and so on). Append first.content (the list of blocks), or the extracted text.

Exercise 4 🟢 easy explain

Which streaming event carries the final stop_reason and output token count?

Show solution

message_delta. message_stop follows it and ends the stream. In the SDK, stream.get_final_message() gives you both on the assembled Message.

Exercise 5 🟡 medium test it

Write a test proving that ClaudeHttp does not retry a 401. Use mock_api(), which answers 401 for API keys that start with bad.

Show solution

One request, no retries. A retry here would just repeat the same mistake.

Exercise 6 🟡 medium build it

Add a total_retries counter to ClaudeHttp and check it against a mock server that fails 3 times with 429 (max_retries=3).

Show solution

Three waits, four requests. Export this counter as a metric: a rising retry rate is an early warning of rate-limit trouble.

Use the SDK's streaming helper to print the stream while also measuring the time to the first text piece (TTFT).

TTFT is what users feel; log it next to the total.

Exercise 9 🔴 hard build it

Write a Conversation class that stores history, trims it to a token budget using the count endpoint (client.messages.count_tokens), and drops the oldest user/assistant pair at a time so roles keep alternating.

Show solution

Exercise 10 🔴 hard design

Design a resilient CLI chat: history, streaming, a 20k-token budget, and a friendly message when the network is gone. Which of this chapter's pieces do you use for each requirement, and which failure would you still not handle?

Show solution
  • History and budget: the Conversation class from exercise 9.
  • Streaming: client.messages.stream(...) with text_stream, and get_final_message() to store the assistant turn.
  • Network loss: the SDK retries connection errors; catch anthropic.APIConnectionError after that and print "Can't reach the API, your message is kept; press Enter to retry".
  • Truncation: check stop_reason and offer "continue".
  • Still unhandled: a stream that breaks halfway. The partial text is shown but the final message never arrives; keep the partial text, mark the turn incomplete, and let the user retry.
