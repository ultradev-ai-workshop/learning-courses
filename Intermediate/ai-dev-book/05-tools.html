Tool Use

Let the model decide which of your functions to call and with what arguments, while your code stays in charge of actually calling them.

You will learn

  • The tool-use round trip: definitions, tool_use blocks, tool_result blocks.
  • How to build a tool registry from typed Python functions, and a bounded tool loop.
  • How parallel tool calls, tool_choice and strict: true work.
  • How to design tools that models use well, and how to report tool errors back.
  • How the SDK's Tool Runner automates the loop.
  • The difference between client tools (you run them) and server tools (Anthropic runs them).

The round trip

Tool use lets the model ask your code to run a function. The model never executes anything itself.

  1. You send a request with tools: each has a name, a description and an input_schema (JSON Schema).
  2. If a tool would help, the model replies with stop_reason: "tool_use" and one or more tool_use blocks, each with an id, a name and an input object.
  3. Your code validates the input, runs the function, and sends a new user message with one tool_result block per call, each pointing at its tool_use_id.
  4. The model continues, possibly calling more tools, until it answers with stop_reason: "end_turn".

🧠 Analogy: a manager with a phone and an assistant. The model is a manager who can't touch any system, but can say "please look up who's on call for payments" and read the answer. Your code is the assistant who decides whether the request is allowed, makes the call, and reports back. A good assistant also says "that number doesn't exist" instead of hanging up: that is an error result.

☕ Java: picture a client that reads your OpenAPI spec and decides which endpoint to call. The tool definitions are that spec, the tool_use block is a request the model proposes, and your code is the server: it authenticates, validates, authorizes, executes and responds, exactly as it would for any untrusted caller.

Defining tools well

The description is the most important field. The model chooses tools by reading it, the way a new teammate reads API docs.

  • Say what it does, when to use it, and when not to. Three or four sentences is normal.
  • Describe every parameter, with formats and examples ("Ticket key such as OPS-1234").
  • Prefer a few high-level tools over many thin CRUD wrappers. get_incident_context(incident_id) that returns what an engineer needs beats five tools the model must chain.
  • Return concise, meaningful results: names and readable fields, not raw rows with 40 columns and internal UUIDs. Every result token costs money and attention.
  • Namespace related tools (tickets_get, tickets_search) so they are easy to tell apart.

Parallel calls, tool_choice and strict

  • Parallel tool use is on by default: the model may return several tool_use blocks in one turn. Run independent calls concurrently, and return all results in a single user message. Splitting them over several messages teaches the model to stop making parallel calls. Set disable_parallel_tool_use: true in tool_choice if you need one call at a time.
  • Strict tool use: add "strict": true to a tool definition (next to name) to guarantee that input matches its schema, with the same constrained decoding as Chapter 4. The schema needs additionalProperties: false and required.
tool_choiceBehaviour
{"type": "auto"} (default)The model decides whether to call tools.
{"type": "none"}Tools are visible but can't be called.
{"type": "any"} / {"type": "tool", "name": ...}Force a call. Rejected with a 400 by claude-opus-5-5 and claude-sonnet-5-5; on those, use auto and name the tool in the prompt.

Reporting tool errors

Don't let a failing tool crash the request. Send the error text back with "is_error": true: the model can fix its input and try again, or tell the user honestly what went wrong. The registry above already does this; here is what the model sees:

Executing input unchecked. db.execute(tool_input["sql"]) because the model wrote it is a vulnerability, not a feature. Treat tool input like input from a public endpoint: typed parameters, allow-lists, and the user's permissions, never raw SQL or shell. Chapter 12 goes deeper.

The SDK's Tool Runner

The loop above is short, but you'll write it in every project. The SDK has a beta helper that does it for you: decorate typed functions with @beta_tool (the docstring's Args: section describes the parameters) and iterate over client.beta.messages.tool_runner(...). Each iteration yields the next assistant message; the runner runs the tools and feeds the results back until the model is done.

Write the manual loop when you need control the runner doesn't give you; otherwise prefer the runner. Approval gates don't need a manual loop: check inside the tool function and return "the user declined" as the result.

Client tools and server tools

Client tools are the ones you define and execute (everything above). Server tools, such as web search, web fetch and code execution, are defined by Anthropic and run on Anthropic's infrastructure: you list them in tools and their results arrive as content blocks in the same response, with no loop on your side.

Server tool names carry a version date and change over time; check the tool use overview for the current list and prices.

Common mistakes

Executing input unchecked: raw SQL, shell commands or URLs straight from tool_use.input.

Validate and authorize like a public endpoint: typed parameters, allow-lists, the user's permissions.

Throwing on tool failure, so one failed lookup aborts the whole request.

Return is_error results; the model can retry with fixed input or explain the failure.

No step limit: while res.stop_reason == "tool_use" with no cap.

A bounded loop with a maximum step count, plus a token or cost budget (Chapter 8).

Recap

  • Tools are JSON-Schema-described functions; the model proposes calls, your code executes them.
  • The loop: request → tool_use blocks → all tool_result blocks in one user turn → repeat until end_turn, with a step limit.
  • Descriptions drive tool selection: what, when, when not, and parameter formats.
  • Generate schemas from typed functions and validate input before running anything.
  • strict: true guarantees the input shape; forced tool_choice isn't available on the newest models.
  • Report failures as is_error results. The Tool Runner automates the loop; server tools run on Anthropic's side.

Exercises

Exercise 1 🟢 easy explain

Who executes a client tool's function: the model, the API, or your code? What follows from that?

Show solution

Your code. The model only proposes the call. So your code must validate the input, check the user's permissions and handle failures, exactly like an endpoint exposed to untrusted callers.

Exercise 2 🟢 easy fix the bug

The model returned three tool_use blocks. This code answers each in its own user message. What's wrong?

Show solution

All results for one assistant turn belong in one user message. Build the list first, then append a single {"role": "user", "content": results}. Split results break the expected structure and discourage parallel calls.

Exercise 3 🟢 easy improve

Rewrite this tool description so the model knows when to use it: "description": "Gets deploys".

Show solution

"Returns the deploys of one service in the last N hours (default 24), newest first, with version, author and time. Use when the user asks what changed, what shipped, or whether a deploy could explain an incident. Not for future or scheduled deploys." Plus a described service parameter with an enum, and hours with a range.

Exercise 4 🟢 easy predict

The registry receives {"team": "payments", "region": "eu"} for get_oncall. What happens, and why is that good?

Show solution

By default Pydantic ignores the unknown field, so the call runs with team="payments"; the schema sent to the model says additionalProperties: false, so with strict: true the model can't produce it at all. If you want unknown fields to be an error in code too, give the input model extra="forbid". Either way the function never receives a parameter it didn't declare.

Exercise 5 🟡 medium build it

Add a search_tickets(team, status) tool to the registry that returns the keys and titles of matching tickets. Test it with registry.run.

Show solution

Returning only key and title keeps results small; the model can call get_ticket for details.

Exercise 6 🟡 medium test it

Write a test that the loop raises after MAX_STEPS when a buggy "model" keeps calling tools forever.

Show solution

Exercise 7 🟡 medium build it

Make the registry produce strict tool definitions: add "strict": True to every definition, and check that every schema has additionalProperties: false and lists every property in required. Which tool fails the second check, and why?

Show solution

Strict schemas usually want every property listed in required. Express "optional" as a nullable type (int | None) and apply the default in code.

Exercise 8 🟡 medium design

A colleague proposes five tools: get_user, get_orders_for_user, get_order_items, get_shipment_for_order, get_carrier_status. The main question users ask is "where is my order?". What do you propose instead?

Show solution

One high-level tool such as get_order_status(order_id) that returns what an engineer or agent needs: status, items summary, carrier and the latest tracking event. Fewer steps means fewer chances to go wrong, lower latency and fewer tokens. Keep the thin tools only if real questions need them.

Exercise 9 🔴 hard build it

Add per-user permissions: Registry.run(name, input, user) must refuse tools the user's role may not use, returning an is_error result. Viewers may only use get_* tools.

Show solution

Even better: don't send tools the user can't use in tools at all. Then the model can't even propose them, and you save tokens.

Exercise 10 🔴 hard build it

Give the loop a cost budget: stop with a clear error when the total input + output tokens of all calls exceed max_tokens_total. Use res.usage.

Show solution

Each step resends the growing history, so tokens per step rise. A budget turns a runaway loop into a bounded cost.
