Applying AI at Work

Five production patterns for backend teams, each built from the parts you now know: the design, the critical code, how to evaluate it, and where it goes wrong.

You will learn

  • How to recognize which pattern from Chapters 3–12 a business problem needs.
  • Five concrete designs: incident triage, code migration, test generation, ticket classification and docs Q&A.
  • How to evaluate each with record-and-replay, builds, mutation testing and shadow mode.
  • How to scope a first version that ships in two weeks and earns trust.
  • How to measure value, not just quality.

Choosing the pattern

generate artifacts that can be checkedgenerate → verify mechanically → repair4, 8, 10

A good first project has a measurable baseline (how long humans take today), a cheap way to verify outputs, a low cost of errors, and users who want it.

🧠 Analogy: choosing a vehicle. You don't take a lorry to buy bread or a bicycle to move house. A single structured call is the bicycle: cheap, quick, good for one parcel. RAG is the delivery van with a fixed route. An agent is the lorry with a driver who decides the route: powerful, expensive, and you want a good reason to use it.

☕ Java: you don't pick Kafka, Postgres or Redis by fashion; you pick by access pattern and consistency needs. Same here: start from the problem shape and the cost of a wrong answer, then pick the simplest pattern that passes your evals.

Case 1: incident triage

Problem. On-call engineers spend the first 20 minutes of an incident collecting context: which deploy, which errors, which runbook.

Design. A read-only agent (Chapter 8) triggered by the alert webhook, with tools such as recent_deploys(service, since), error_summary(service, window) (pre-aggregated by your observability backend, not raw logs) and search_docs. It writes a structured note into the incident channel:

Key decisions. Pre-aggregate logs and give the model summaries (top error signatures with counts), not megabytes of lines. Read-only tools only: the note suggests, humans act. Evidence must reference tool output, and low confidence must be allowed and visible.

Evaluate with record and replay. Freeze the tool responses of 20 past incidents (like contract-test fixtures), replay the agent against them, and grade the notes. The fixtures make the run repeatable and free of side effects:

Confident wrong causes. A plausible but wrong cause can anchor a whole incident response. Show confidence prominently, always show the evidence, and measure how often "high confidence" was wrong.

Case 2: legacy code migration

Problem. 300 classes on JUnit 4, or javax.* to jakarta.*, or an internal framework you are retiring.

Design. A workflow, not an open-ended agent: list the files → for each file, one model call with the migration guide and two before/after examples → write the result → build and test → one repair attempt with the errors → otherwise revert and leave it for a human. The build is the grader. Here the "build" is Python's own compiler plus a test, and the "model" is scripted:

Key decisions. Deterministic tools first: if a codemod or OpenRewrite recipe exists for your migration, run it and send only the leftovers to the model. Commit per file or per module so review stays small. Evaluate with the share of files that build green, review time per PR, and defects found after merge.

Case 3: test generation

Problem. Low test coverage on legacy services; engineers avoid touching them.

Design. Generate → verify → keep only what passes. For each class: give the model the class, its collaborators' signatures and one existing test as a style example; run the generated tests; keep the passing ones.

  • A generated test that passes against current behaviour documents that behaviour; it doesn't prove it's right. Label these characterization tests.
  • Mutation score, not line coverage, is the quality bar: tests without real assertions inflate coverage.
  • Never let the generator modify production code to make a test pass.

Mutation testing in miniature: change the code slightly (a "mutant") and check whether the tests notice. A test that still passes against a mutant isn't really testing that behaviour:

All three tests pass and give the same line coverage, but only the boundary test catches the >= → > mutant. Tools such as PIT (Java) and mutmut (Python) do this at scale.

Case 4: ticket classification and routing

Problem. A shared support queue where tickets wait hours to reach the right team.

Design. The triage service from Chapter 4: Haiku with structured output (enums for team, category and severity, plus needs_info), interactive for new tickets and the Batches API for re-labelling history.

Key decisions. Historical tickets with their final team are a labelled set you already have. Measure per-class accuracy and a confusion matrix, not just overall accuracy. Start in shadow mode: the model labels every ticket, humans keep routing, and you compare, with zero risk.

Overall accuracy looks fine, yet the platform team's tickets are mostly misrouted to data. When two teams are confused, first check whether their boundary is clear to humans; often the fix is a clearer category definition in the prompt, not a bigger model.

Case 5: internal docs Q&A

Problem. Knowledge is spread across wikis, repos and runbooks. This is DocsPilot.

Design. Everything from Chapters 6–12: structural chunking and contextual retrieval; hybrid retrieval with ACL filters; reranking; cited answers; abstention; routing to tools for live data; an MCP server so other hosts can use it; evals in CI. Chapter 15 builds it end to end.

Key decisions. Freshness (re-ingest on doc change), ownership (each doc has an owner who receives "this answer was wrong" feedback) and trust (citations always visible, abstention preferred to guessing).

Developer productivity

Beyond the features you ship, AI changes how your team builds. Agentic coding tools such as Claude Code work best on the principles of this book: clear instructions (a project CLAUDE.md with conventions and commands), fast mechanical verification (tests, linters, type checks they can run), small reviewable changes, and permissions that match the risk. The same discipline that makes your LLM features reliable makes AI-assisted development reliable.

Common mistakes

Starting with the hardest problem: a fully autonomous incident remediator as the first AI project.

Start read-only and verifiable: triage notes, classification in shadow mode, cited Q&A.

No baseline: shipping without knowing how long the task takes today.

Measure before and after: record the human baseline, then the AI-assisted number.

Coverage as the goal for generated tests.

Mutation score, and tests labelled as characterization tests.

Recap

  • Pick the pattern from the problem shape and the cost of errors; start with the simplest.
  • Incident agents get pre-aggregated, read-only data and are evaluated with recorded fixtures.
  • Migrations use the build as the grader: migrate → build → repair once → revert.
  • Keep only generated tests that pass and kill mutants.
  • Run classifiers in shadow mode; read per-class recall and the confusion matrix.
  • Measure value against a baseline, not just quality.

Exercises

Exercise 1 🟢 easy choose

Name the pattern and the verifier: (a) generating OpenAPI specs from controllers, (b) summarizing weekly on-call handovers, (c) detecting personal data in support tickets.

Show solution

(a) Workflow per controller; verifier: an OpenAPI validator plus a contract test against the running service. (b) One structured call over the week's incidents; verifier: human rating of a sample, then a calibrated judge. (c) Classification/extraction with structured output (plus deterministic patterns); verifier: a labelled set with precision and recall.

Exercise 2 🟢 easy explain

Why should the incident agent get pre-aggregated error summaries instead of raw logs?

Show solution

Context is a budget: megabytes of logs are expensive, slow and dilute attention. Aggregating ("top 5 error signatures with counts") is ordinary data engineering that makes the agent better and cheaper, and it keeps sensitive log content out of prompts.

Exercise 3 🟢 easy explain

A generated test passes. What does that prove?

Show solution

Only that the code currently behaves as the test describes. If the code has a bug, the test may enshrine it. That's why they're labelled characterization tests, and why mutation testing checks whether they would catch a change.

Exercise 4 🟢 easy define

What is shadow mode, and what does it give you?

Show solution

The model makes its decision on real traffic, but humans keep doing the real work and nothing acts on the model's output. You get a real-world accuracy measurement, per class, with zero risk.

Exercise 8 🟡 medium design

Your manager asks for "an AI agent that fixes production incidents automatically". Propose a first version that ships in two weeks instead.

Show solution

A read-only triage note (Case 1) posted to the incident channel within 2 minutes of the alert: likely cause, evidence, runbook, next checks, confidence. Success: time to first meaningful action drops on the next 20 incidents, with no wrong "high confidence" notes. Remediation (rollback) comes later, as a suggested command with a human approval button, once the notes have earned trust.

Exercise 9 🔴 hard build it

Turn the shadow data into a routing policy: auto-route a class only if its recall is at least 95%; otherwise keep humans. Which classes are auto-routed?

Show solution

Per-class gating lets you ship value for the easy classes while you fix the confused boundary. Also check precision for the auto classes: a class that attracts misrouted tickets from others shouldn't be auto-routed blindly.

Exercise 10 🔴 hard write

Write the outline of a two-page proposal for one AI use case at your company.

Show solution
  1. Problem and baseline (with today's numbers).
  2. Chosen pattern and why the simpler ones aren't enough.
  3. Data and permissions: what the model sees, whose identity the tools use, what leaves the company.
  4. Eval plan: the set, the graders, success criteria.
  5. Rollout: shadow → suggest → limited → general, with exit criteria for each step.
  6. Risks and mitigations (security, wrong answers, cost).
  7. Cost estimate (tokens × prices × volume) and expected value.
