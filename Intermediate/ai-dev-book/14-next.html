Fine-tuning

Fine-tuning continues training a model on your own examples so it adopts a format, style or narrow skill more reliably. It's the most over-proposed technique in enterprise AI. Try these first, in order, measuring each with your evals:

  1. Better prompts with diverse examples (Chapter 2).
  2. Structured outputs for format problems (Chapter 4).
  3. Retrieval for knowledge problems (Chapter 7). Fine-tuning is a poor way to add facts: they go stale, can't be cited and can't be access-controlled.
  4. A larger model, or routing hard cases to one (Chapter 8).

Consider fine-tuning only with thousands of high-quality examples, a narrow and stable task, and a measured need (latency or cost at very high volume, or a style that prompting can't hold). Availability for Claude models depends on the model and platform; check the current docs and your cloud provider.

🧠 Analogy: a handbook versus retraining the employee. RAG hands a capable employee the current handbook for every question: when a policy changes, you edit one page. Fine-tuning sends them on a long course: they come back with habits, not a library, and when the policy changes next month the course is out of date.

☕ Java: prompting and RAG are configuration: cheap to change, easy to roll back, and you get upstream improvements for free. Fine-tuning is a fork of a dependency: you own it, it drifts from upstream, and every base-model update means redoing the work.

Local and open-weight models

Open-weight models can run on your own hardware with servers such as vLLM, llama.cpp or Ollama, many of which expose an OpenAI-compatible HTTP API.

data can't leave your networkGPU capacity, ops on-call, model updates
offline or edge deploymentusually lower quality than frontier models on complex tasks
very high volume of simple tasksengineering time to serve, scale and monitor
experimentation and researchyour evals must now cover a model you maintain

Quantization in one sentence. Quantization stores weights at lower precision (for example 8 or 4 bits instead of 16) so models fit on smaller GPUs, at some quality cost; always evaluate the quantized model you'll actually serve.

Machine-learning basics worth knowing

You don't need to train models to build excellent LLM systems, but these ideas make documentation and papers readable:

  • Training versus inference. Training fits the parameters to data (expensive, rare). Inference runs the fitted model (what you pay for per token).
  • Transformers and attention. The architecture behind LLMs. Attention lets each token weigh every other token in the context, which is why long contexts cost more.
  • Pretraining, instruction tuning, RLHF. Next-token prediction on a huge corpus, then training to follow instructions, then reinforcement learning from human (and AI) feedback towards helpful and harmless behaviour.
  • Embeddings (Chapter 6) as learned representations: the same idea behind recommendation systems.
  • Generalization and overfitting. A prompt tuned to your eval set may not hold on new data; keep a held-out set you never tune against.
  • Metrics. Precision, recall, F1, calibration and confusion matrices: the language of classification evals.

Model upgrades and deprecations

Model IDs retire. Keep them in configuration, one entry per role, and schedule upgrades like dependency upgrades: read the release notes and migration guide, run your evals on a branch, compare cost, roll out as a canary.

Watch for breaking changes, not just new names. Moving between model generations can change request rules, as you've seen in this book: sampling parameters and forced tool choice are rejected on the newest models, prefill is gone, and thinking is configured with effort. Read the migration guide for each upgrade and let your evals decide.

Staying current

The field changes monthly. A system beats a firehose:

  1. Primary sources, on a schedule: the Claude release notes and model deprecations, the MCP specification changelog, your SDKs' changelogs, the Anthropic Engineering blog. Thirty minutes a week.
  2. Your eval suite is your benchmark. When a new model ships, run your evals before reading anyone's opinion. Public benchmarks measure someone else's task.
  3. Track deprecations as tech debt, with owners and dates.
  4. Re-read the docs for the features you use when your SDK version changes.

☕ Java: treat a model upgrade like a major-version dependency upgrade: release notes and migration guide first, a branch, the full test suite (your evals), a canary, and a rollback plan. Nobody upgrades Spring Boot by reading a tweet.

Recap

  • Exhaust prompting, structured outputs, retrieval and routing before fine-tuning; never fine-tune to add facts.
  • Local models trade quality and ops effort for control; keep a provider-neutral seam and per-route evals.
  • Learn the ML vocabulary (attention, quantization, overfitting, precision/recall, calibration) to read primary sources.
  • Keep model IDs in config by role; treat upgrades like major dependency upgrades.
  • Stay current with a schedule, primary sources and your own evals.

Exercises

Exercise 1 🟢 easy choose

DocsPilot gives outdated answers about the deploy process. Fine-tune or fix retrieval?

Show solution

Fix retrieval: re-ingest the changed docs (and automate it). Knowledge problems are retrieval problems; fine-tuned facts go stale and can't be cited.

Exercise 2 🟢 easy choose

When does a local open-weight model most clearly make sense?

Show solution

When data truly can't leave your network, or for very high-volume simple tasks where an evaluated small model is good enough and you're ready to operate it. Decide per task with evals.

Exercise 3 🟢 easy explain

A new model is released. What do you do first?

Show solution

Read its release notes and migration guide for breaking changes, then run your own eval suite against it on a branch. Your evals measure your task; public benchmarks measure someone else's.

Exercise 4 🟢 easy explain

Why do long contexts cost more compute, according to the attention example?

Show solution

Every token is compared with every other token: the score matrix has n × n entries, so doubling the context roughly quadruples that part of the work. (Real systems use many optimizations, but the intuition holds.)

Exercise 5 🟡 medium build it

Write a third adapter for the seam, FakeModel, for unit tests: it returns canned answers per task and records the prompts.

Show solution

Because the seam is a Protocol, the fake needs no inheritance: anything with name and complete fits.

Exercise 6 🟡 medium experiment

Run the quantization example with 2 bits. What happens to the error, and what would that mean for a model?

Show solution

Most small weights round to zero, so the error explodes. Real low-bit methods use smarter scaling per group of weights, but the lesson holds: lower precision costs quality, and only an eval tells you how much.

Exercise 7 🟡 medium write

Write the checklist for your team's "model upgrade" runbook.

Show solution
  1. Read the release notes and migration guide; list breaking request changes.
  2. Update the model ID in config on a branch; fix code for breaking changes.
  3. Run the full eval suite (with repeats); compare pass rate, cost and latency per role.
  4. Re-tune effort and max_tokens if needed; re-check prompt caching hit rates.
  5. Canary to 5% of traffic with dashboards; watch fallback, abstention and error rates.
  6. Roll out, keep the old config for rollback, record the new baseline.

Exercise 8 🟡 medium calculate

From the shadow data in Chapter 13, the SEV1 classifier had precision 0.62 and recall 0.80. Which would you raise first, and how?

Show solution

Recall: a missed SEV1 is far worse than a false alarm. Lower the bar for "SEV1" (or route "maybe SEV1" to a human), add missed cases as examples, and re-measure; accept somewhat lower precision as the price.

Exercise 9 🔴 hard design

Your legal team says customer tickets may not leave the company network. Redesign ticket classification.

Show solution

Run an open-weight model on internal GPUs behind the same seam (OpenAI-compatible server), with the same structured-output contract (validate in code if the server can't constrain decoding). Build the eval from historical tickets, compare with the current numbers, and accept a lower bar only if the business agrees. Keep a redaction step so that, if policy later allows, only redacted text could ever go to an external provider.

Exercise 10 🔴 hard plan

Write your personal "radar" routine: sources, frequency, notes format, and what triggers an eval run.

Show solution
  • Weekly, 30 minutes: Claude release notes and deprecations, SDK changelogs (Python and Java), MCP spec changes, one engineering blog post.
  • Notes: one Markdown file, a dated line per change, tagged "affects us" or "watch".
  • Eval trigger: any new model in a tier you use, any SDK major version, any deprecation of a model you use.
  • Monthly: a 15-minute team share of the "affects us" lines.
