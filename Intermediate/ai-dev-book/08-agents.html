Agents & Orchestration

Know the difference between a workflow and an agent, build a bounded agent loop with budgets and memory, and recognize the many cases where you shouldn't build an agent at all.

You will learn

  • The difference between workflows and agents, and the five common workflow patterns.
  • How an agent loop differs from the tool loop of Chapter 5: goals, budgets, stopping rules.
  • Planning, working memory, compaction and long-term memory.
  • How to keep agents observable, interruptible and cheap.
  • A checklist for deciding when not to use an agent.

Workflows versus agents

Anthropic's engineering guidance draws a clear line:

  • A workflow orchestrates LLM calls and tools through predefined code paths. You own the control flow.
  • An agent lets the LLM direct its own process and tool use, choosing the next step at run time until the task is done.

Both are "agentic systems". The consistent advice: find the simplest solution that works, and add autonomy only when it measurably improves outcomes. Often a single well-prompted call with retrieval is enough.

🧠 Analogy: a recipe versus a chef. A workflow is a recipe: the steps are written down, and a kitchen assistant follows them, perhaps tasting (a model call) at step 3. An agent is a chef given a goal ("make dinner from what's in the fridge"): they look, decide, try, taste and adjust. Chefs handle the unexpected, but they cost more, take longer and occasionally make something strange. Don't hire a chef to boil an egg.

☕ Java: a workflow is a saga or a BPMN process: the steps are known, each may call an LLM, and you can draw the diagram before it runs. An agent is a job whose next step a planner chooses at run time from the current state, a bit like a query optimizer choosing a plan, except that the planner is non-deterministic.

The agent loop

An agent is the tool loop from Chapter 5 plus four things:

  1. A goal the model can tell it has reached, or can't reach.
  2. Tools to observe and act (search the docs, read a ticket, run a query).
  3. Budgets that your code enforces: steps, tokens, money, wall-clock time.
  4. Stopping rules beyond end_turn: budget exhausted, repeated identical calls, a tool that needs human approval.

Planning

For multi-step goals, agents do better when they plan explicitly and revise the plan as they learn. Two simple techniques:

  • Plan in the system prompt: "Before acting, list the steps you intend to take. After each tool result, update the list." Thinking models often do this internally.
  • A plan tool: give the agent update_plan(steps) and show its latest plan in your UI. That makes the agent observable to humans without parsing prose.

Long-term memory is an ordinary table with ordinary concerns: scope it per user, cap its size, and decide how facts expire. Never let one user's memory leak into another's context.

The user is bound when the tools are built, from your authenticated session, never from something the model says. The model can't ask for "sam's" memories because no tool takes a user parameter.

Platform features. The Claude API has features for long-running agents (a memory tool, context editing that clears old tool results, server-side compaction), and Anthropic also ships the Claude Agent SDK (a ready-made agent harness with file and shell tools) and hosted Managed Agents. They change quickly; read the agents and tools docs before you build your own version of something that exists. Frameworks such as LangGraph (Appendix B) give you the loop as a graph with checkpoints.

When not to use an agent

Work through this list before you build one:

  1. Can you draw the flowchart? Then build a workflow. It's cheaper, faster, testable and explainable.
  2. Is one call with good context enough? Measure that first (Chapter 10). It often is.
  3. Is latency critical? Each step is a full model round trip; 8 steps at 3 s each is a 24 s request.
  4. Are actions irreversible? Agents that can delete, pay, deploy or email need human approval gates (Chapter 12), or shouldn't be agents.
  5. Can you verify progress? Agents shine where results can be checked (tests pass, the query returns rows). Without a check, errors compound silently.

Good fits: incident investigation across several read-only systems, codebase exploration, research across many documents, open-ended support questions with read-only tools.

Common mistakes

An agent for a fixed process: an "onboarding agent" that always does the same six steps in the same order.

A workflow with LLM steps: six coded steps, two of which call a model.

Unbounded loops, "budgeted" by asking the model to stop after a few steps.

Budgets in code: steps, tokens, time and money checked by the loop, with an honest partial result.

Too many tools: forty fine-grained tools; the agent wanders and the context fills with definitions.

A few high-level tools that return what the task needs.

Recap

  • Workflows have code-defined paths; agents choose their path at run time.
  • Start with the simplest thing that passes your eval: one call → workflow → agent.
  • The patterns: chaining (with gates), routing, parallelization, orchestrator–workers, evaluator–optimizer.
  • An agent = goal + tools + budgets + stopping rules, all enforced by your code; inject the clock.
  • Make plans and memory explicit, scoped per user and observable.
  • Don't use agents for fixed processes, latency-critical paths or unverifiable irreversible actions.

Exercises

Exercise 1 🟢 easy classify

Workflow or agent? (a) a nightly summary of yesterday's incidents, (b) "why is checkout slow right now?", (c) translate release notes into four languages, (d) migrate 300 Java files from JUnit 4 to JUnit 5.

Show solution

(a) Workflow: fixed steps. (b) Agent: the path depends on what each read-only check reveals. (c) Workflow with parallelization. (d) Workflow (orchestrator–workers) with a compile-and-test step per file; at most a small agent per file for the hard ones.

Exercise 2 🟢 easy explain

Why does run_agent check the token budget in code instead of telling the model "stop after about 10 steps"?

Show solution

The model can't see its own token usage reliably and may ignore or misjudge the instruction; a budget is a promise about cost and latency, so it must be enforced by deterministic code. The prompt can still mention the budget so the model plans for it.

Exercise 3 🟢 easy predict

The agent calls search_docs({"query": "failover"}) twice in a row. What does the second call return in run_agent, and why is that better than running it again?

Show solution

An is_error result: "You already made this exact call. Use the earlier result." Running it again would return the same text, cost tokens, and do nothing to break the loop; the error nudges the model to try something else.

Exercise 4 🟢 easy calculate

An agent averages 6 steps per question at 2.5 s each, 9,000 input and 400 output tokens per step, on claude-sonnet-5-5. What are the latency and the cost per question?

Show solution

15 seconds and about 13 cents. A single RAG call might be 2 seconds and a cent. That gap is why you route only the questions that need an agent to the agent.

Exercise 6 🟡 medium test it

Exercise 7 🟡 medium build it

Add an approval stop rule: if the model calls a tool listed in NEEDS_APPROVAL, stop with needs_approval and return the pending call instead of running it.

Show solution

Persist the conversation and the pending call; when a human approves, run the tool and continue the loop from there. That's the "interruptible" property.

Exercise 8 🟡 medium build it

Implement compaction for run_agent's messages: when there are more than 8 messages, replace everything between the goal and the last 4 messages with a single summary (use a function argument summarize). Keep tool_use/tool_result pairs intact.

Show solution

Merging the summary into the first user message keeps the roles alternating. The API's server-side compaction does this for you on supported models.

Exercise 9 🔴 hard design

Design an incident-investigation agent for "why is checkout slow right now?". List its tools, budgets, stop rules and what it must return, and say which tools must not be included.

Show solution
  • Tools (read-only): get_metrics(service, window), recent_deploys(service, hours), search_logs(service, query, minutes), search_docs(query), get_oncall(team).
  • Budgets: 10 steps, 90 s, $0.50; results trimmed to the essentials.
  • Stop rules: end_turn, any budget, repeated calls, "no new information in 3 steps".
  • Output (structured): likely cause, evidence (quoted log lines, metric values, deploy IDs), confidence, next action, who to page.
  • Not included: rollback, restart, scale or any write tool. Suggest the command; a human runs it.

Exercise 10 🔴 hard build it

Measure the cost of autonomy: run the same question through the RAG path (1 call) and through the agent (scripted: 3 calls), with mock_api() and the real SDK, and compare total tokens.

Show solution

Against the mock the agent searches, gets an answer and stops; with a real model it may take more steps. Either way, the agent re-sends tool definitions and the growing history on every step, so its tokens add up quickly. Compare the totals with the RAG call's usage before choosing.
