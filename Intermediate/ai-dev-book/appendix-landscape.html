The Framework Landscape

A map of the other frameworks you'll hear about (Spring AI, LangChain4j, Semantic Kernel, CrewAI, AutoGen, Haystack, agent SDKs from the model providers) and a method for choosing between them, or choosing none.

You will learn

🧠 Analogy: web frameworks, again. You can serve HTTP with the standard library, a micro-framework or a full framework. None is "the best"; each fits a team and a problem. LLM frameworks are at the same stage web frameworks were around 2008: many options, fast change, and the underlying protocol (here, the Messages API) matters more than any of them.

Java: Spring AI

Spring AI brings LLMs into Spring Boot the Spring way: auto-configured clients from properties, a fluent ChatClient, structured output into records, @Tool methods, advisors (interceptors for memory, RAG and logging), a VectorStore abstraction (pgvector, and many more) and MCP client and server starters.

Everything from this book still applies: check how a framework maps structured output and tool choice onto the newest models (forced tool calls aren't accepted by claude-opus-5-5 and claude-sonnet-5-5), and run your evals against the Spring service exactly as against the Python one.

Java: LangChain4j

LangChain4j is framework-agnostic Java (it also has Spring Boot and Quarkus integrations). Its signature feature is AI Services: declare an interface, and LangChain4j implements it with a model, memory, tools and retrieval:

☕ Which one? Already on Spring Boot and want auto-configuration, actuator metrics and familiar idioms: Spring AI. Want a library that works the same in Quarkus, Micronaut or plain Java, or like the AI Services style: LangChain4j. Either way, keep the provider behind your own interface (Chapter 14) so the choice stays reversible.

Semantic Kernel

Microsoft's open-source SDK for C#, Python and Java. Functions are grouped into plugins that the model can call; it has connectors for many models (including Claude), memory and vector stores, and an agent framework. A natural choice in .NET shops and Azure-centred estates.

Multi-agent frameworks: CrewAI and AutoGen

These frameworks organize work as several agents that talk to each other: a "researcher", a "writer", a "reviewer". CrewAI models a crew of agents with roles, goals and tasks:

AutoGen (and its community fork AG2) models agents as participants in a conversation, with patterns like group chats and a user proxy that runs code.

More agents, more cost and more failure modes. Every agent turn is a model call, and agents can loop, agree with each other's mistakes, or lose the thread. Anthropic's guidance (Chapter 8) applies: start with a single call or a workflow; split into several agents only when the parts are genuinely independent (parallel research, per-file work) and your evals show it helps.

Haystack

deepset's framework for production search and RAG: typed components connected into pipelines (retrievers, rankers, generators), with strong document-store integrations. A good fit for teams whose product is search.

Provider agent SDKs

Model providers also ship their own harnesses. Anthropic's Claude Agent SDK packages the harness behind Claude Code (file, shell and web tools, subagents, hooks, permissions) as a library you run on your own infrastructure; Anthropic's hosted Managed Agents run the loop and a sandbox for you; and the anthropic SDK's Tool Runner (Chapter 5) automates a loop over your own tools. OpenAI and others have their own agent SDKs. These track their provider's features first; general frameworks give you portability.

Choosing

Write your requirements down, weight them, and score candidates; then confirm the top two with a spike measured on your eval set. A tiny scoring helper:

The numbers are only as good as your spike. The point is to make the trade-off explicit and reviewable, like an ADR.

Rules that survive every framework change. Keep prompts in files, model IDs in config, tools behind your own validation and permissions, and evals in CI. Then a framework is a replaceable implementation detail, and switching costs a sprint, not a rewrite.

Recap

  • Python: LangChain (building blocks), LangGraph (stateful graphs), LlamaIndex (data/RAG), Pydantic AI (typed agents), DSPy (optimized programs), Haystack (search pipelines).
  • Java: Spring AI for Spring Boot teams, LangChain4j for framework-agnostic Java; Semantic Kernel for .NET-centred estates.
  • Multi-agent frameworks (CrewAI, AutoGen) multiply calls; use them only when parts are independent and evals agree.
  • Provider SDKs track provider features first; general frameworks give portability.
  • Choose with weighted requirements and a spike measured on your eval set; keep the choice reversible.

Exercises

Exercise 1 🟢 easy match

Which framework fits best? (a) a Spring Boot team adding a chat endpoint, (b) an agent that waits a day for an approval, (c) a PDF-heavy knowledge base, (d) tuning a prompt against 500 labelled tickets.

Show solution

(a) Spring AI. (b) LangGraph (checkpoints + interrupts). (c) LlamaIndex (or Haystack). (d) DSPy.

Exercise 2 🟢 easy explain

What is a LangChain4j "AI Service"?

Show solution

A Java interface you declare (methods, system message annotations, return types) that LangChain4j implements at runtime by calling a model, optionally with memory, tools and retrieval. Callers just call the interface method.

Exercise 3 🟢 easy explain

What is a Spring AI advisor, in Spring terms?

Show solution

An interceptor around the ChatClient call, like a servlet filter or an AOP aspect: it can add memory to the request, inject retrieved documents (RAG), log, or post-process the response.

Exercise 6 🟡 medium review

A proposal says: "We'll use a 6-agent crew (planner, researcher, coder, tester, reviewer, manager) to answer DocsPilot questions." Review it.

Show solution

Most DocsPilot questions are answered by one RAG call; a crew multiplies calls, latency and failure modes for no gain. Ask for an eval comparison against the single-call and single-agent versions, with cost and latency. A crew might fit a different job (multi-file code changes), with per-file verification.

Exercise 7 🟡 medium design

What must you verify about any framework before using it with claude-opus-5-5 or claude-sonnet-5-5?

Show solution

That it doesn't send parameters these models reject: sampling parameters (temperature, top_p), forced tool_choice, assistant prefill, or old thinking budgets; that its structured-output mode uses native structured outputs; and that it passes effort and caching options through. Check the actual requests in a trace once.

Exercise 8 🟡 medium plan

Plan a one-week spike comparing two frameworks for DocsPilot's agent path.

Show solution
  1. Fix the eval set (live-data and mixed questions) and the tools (same functions behind both).
  2. Implement the agent in both frameworks with the same prompts and model.
  3. Measure pass rate, p95 latency, tokens and cost per question, lines of code, and test ergonomics.
  4. Try the hard requirement explicitly (an approval that pauses and resumes).
  5. Write an ADR with the numbers and the decision.

Exercise 9 🔴 hard design

Design a "provider-neutral" layer for a Java service so you could move from Spring AI to LangChain4j (or to the raw SDK) without touching business code.

Show solution
  • Your own interfaces: TextModel.complete(...), StructuredModel.extract(Class<T>, ...), Retriever.search(query, user), ToolRegistry.
  • One adapter module per framework implementing them; business code depends only on the interfaces.
  • Prompts as files, model IDs in configuration, tools as plain beans with your validation and permissions.
  • Contract tests run against every adapter with a fake model; the eval suite runs against the deployed service.

Exercise 10 🔴 hard write

Write the outline of an ADR "Framework for DocsPilot".

Show solution
  • Context: requirements (languages, approvals, RAG sources, team skills), constraints (dependencies, security review).
  • Options considered: plain SDK, LangGraph, Pydantic AI, Spring AI (if Java), with the spike numbers.
  • Decision and the requirement that decided it.
  • Consequences: what we own (evals, guardrails, permissions), upgrade policy, how to reverse the decision.
  • Review date (frameworks move fast: revisit in six months).
