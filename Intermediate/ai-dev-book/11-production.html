Production Concerns

Make LLM features behave like the rest of your production estate: bounded latency, graceful degradation, controlled spend, and outputs checked before they reach users.

The resilience stack

A model API is a remote dependency with variable latency and occasional overload. Treat it like any critical downstream:

LayerPurposeNotes for LLM calls
Timeoutsbound the waitlong generations need long timeouts; stream instead of raising them forever
Retries with backoff and jitterride out transient errors429, 5xx, 529, connection errors; honour retry-after (Chapter 3)
Circuit breakerstop hammering a failing dependencyopen on sustained 5xx/529 or timeouts; probe again after a cool-down
Fallbackdegrade instead of failinganother model, another platform, or a non-LLM path
Bulkheadprotect the rest of the servicecap in-flight model calls per feature

🧠 Analogy: a restaurant kitchen on a busy night. If the grill breaks, a good kitchen doesn't stop serving: it offers the pasta (a fallback model), stops sending orders to the grill for a while (the breaker), limits how many orders the grill station takes at once (the bulkhead), and, if everything fails, hands out bread and an apology (the non-LLM path: links to the top documents).

Silent quality drops. A fallback model may be measurably worse at your task. Record which model actually answered (msg.model) on every response, include the fallback models in your evals, and alert when the fallback rate rises.

Server-side fallbacks. For a different failure, a request the model declines (stop_reason == "refusal"), the Claude API can retry on a fallback model inside the same call: the fallbacks parameter on the beta Messages endpoint. It complements your own fallback chain, which handles outages. Check the refusals page for the current form of the parameter.

☕ Java: Resilience4j gives you CircuitBreaker, Bulkhead, Retry and TimeLimiter as decorators around the call. Keep retries inside the HTTP client and wrap each model in its own breaker, exactly as above.

Prompt caching

Many requests share a large, identical prefix: tool definitions, a long system prompt, a big document. Prompt caching lets the API reuse the processed prefix across requests. Cache reads are billed at a small fraction of the normal input price and are faster.

  • Mark the end of a reusable prefix with "cache_control": {"type": "ephemeral"} on a content block (the last tool, a system block, a document), or set cache_control at the top level to cache automatically up to the last block.
  • The cache key is the exact prefix, in order: tools → system → messages. Any byte change before the breakpoint is a miss.
  • The first request writes the cache (priced a little above normal input); later requests within the TTL read it (priced far below). The default TTL is 5 minutes, refreshed on each hit; a 1-hour TTL costs more to write.
  • There's a minimum cacheable prefix length, which varies by model; shorter prefixes silently don't cache.
  • usage reports cache_creation_input_tokens and cache_read_input_tokens. Track both.

What does it save? With reads at 0.1× and 5-minute writes at 1.25× the input price (check the prompt caching page for current multipliers):

One request costs slightly more (the write premium); from the second request on, the stable prefix costs a tenth. Caching pays off as soon as the same prefix is reused within the TTL.

Design prompts for caching. Stable content first, variable content last: tools, then the system prompt, then long shared documents, then the user's question. Keep tool lists in a fixed order and serialize JSON with sorted keys. Never interpolate timestamps, request IDs or user names into the system prompt: one changing character invalidates everything after it.

Three writes, zero reads. Put the date (to day precision) in the user turn instead.

Response caching

Caching complete answers is a separate, application-level decision:

  • Exact-match caching (a hash of model, prompt version, normalized input and retrieved chunk IDs) is safe and simple for classification-style features.
  • Semantic caching (return a stored answer when a new question is similar) saves money but can return the wrong answer to a different question. Use it only with a high threshold, narrow scope and evals.
  • Invalidate when source documents change: include document versions in the key.

A high similarity (a real embedding model scores pairs like this above 0.9) for questions with different answers: production rotation needs a change ticket. A semantic cache with a threshold loose enough to catch real paraphrases would serve the staging steps to someone working on production. That's why the safe default is exact match.

Rate limits

The API enforces limits per organization and model, in requests per minute and input and output tokens per minute, with tiers that rise with usage. Responses carry anthropic-ratelimit-* headers with your remaining capacity, and a 429 carries retry-after. Read the headers through with_raw_response:

Shape traffic on your side rather than discovering limits through 429s:

  • A client-side token bucket per model, sized below your limit (shared through Redis if you run many instances).
  • Priority: interactive requests first; background jobs (re-indexing, contextualization) get the leftover capacity.
  • Move offline work to batches.

The Message Batches API

For work nobody is waiting on (nightly ticket classification, re-contextualizing chunks, large eval runs), submit requests as a batch. Batches run asynchronously, usually well within 24 hours, at 50% of the normal price, with separate rate limits. Results arrive in any order: key them by custom_id, never by position.

Guardrails

Guardrails are checks around the model call, in code.

Input guardrailsOutput guardrails
size limits (characters and counted tokens) per field and per requestschema and business validation (Chapter 4)
detect and redact secrets and personal data before they reach the modelcitation and identifier validation: every cited doc was sent, every ticket key exists
scope check: a cheap classifier routes off-topic or abusive requests awayredaction of secrets and personal data with deterministic patterns
rate limits per userpolicy checks for high-risk features, with a safe fallback message

☕ Java: guardrails are input validation and output encoding for a component that can produce surprising output. You validate every request and encode every response even though most traffic is benign; this is the same discipline, and it's cheap compared with the incident it prevents.

Cost controls

  • Set max_tokens per feature to what the output really needs (and remember you pay only for what's generated).
  • Route by difficulty (Chapter 8); use the smallest model, and the lowest effort, that passes your evals.
  • Cache prefixes; batch offline work.
  • Enforce budgets per tenant and per agent run in code, and alert on spend rate.

Common mistakes

A timestamp in the system prompt: "Current time: 2026-10-31T09:14:07Z" at the top of a cached prompt.

Variable data last: the date, to day precision, in the user turn after the breakpoint.

A fallback nobody evaluated: switching to a smaller model that was never tested on this task.

Evaluated fallbacks: every model in the chain passes the eval suite at an agreed threshold.

Background jobs at interactive priority: re-indexing competes with users for rate limits.

Batches and priorities: the Batches API for offline work, priority and per-model buckets for the rest.

Recap

  • Wrap model calls in timeouts, retries, breakers, bulkheads and evaluated fallbacks; record which model answered.
  • Prompt caching rewards stable prefixes (tools → system → documents → question); check cache_read_input_tokens.
  • Response caching is safe for exact matches; semantic caching needs strict scoping and evals.
  • Read the rate-limit headers and shape traffic with token buckets and priorities.
  • Batches: half price, asynchronous, results keyed by custom_id.
  • Guardrails in code on the way in and out; budgets and alerts for cost.

Exercises

Exercise 1 🟢 easy order

Put these parts of a request in the best order for prompt caching: the user's question, tool definitions, retrieved documents, the system prompt.

Show solution

Tools → system prompt → retrieved documents → question. The API's prefix order is tools, system, messages; within the messages, stable shared content goes before the question.

Exercise 2 🟢 easy explain

Why is max_retries=0 set in the circuit-breaker demo? Would you do that in production?

Show solution

To make each failure visible to the breaker in the demo. In production keep a small number of SDK retries (they absorb blips) and let the breaker see the call's final outcome; just make sure the total time of retries fits your timeout budget.

Exercise 3 🟢 easy choose

Batch or interactive? (a) re-classify 200,000 old tickets, (b) the DocsPilot answer in Slack, (c) nightly eval run, (d) contextualizing chunks after a docs import.

Show solution

(a) Batch. (b) Interactive (someone is waiting). (c) Batch, unless it blocks a merge and must finish fast. (d) Batch.

Exercise 4 🟢 easy fix the bug

Cache reads stay at zero although every request has the same system prompt. The tools are built like this. What's wrong?

Show solution

Iterating a set doesn't guarantee a stable order, so the tool list (which comes first in the prefix) can change between requests and processes. Use sorted(enabled_tools), or a fixed list.

Exercise 5 🟡 medium test it

Test the breaker alone: after 3 failures it opens, after the cool-down it's half-open, and one more failure re-opens it.

Exercise 6 🟡 medium calculate

DocsPilot sends 6,000 tokens of tools and rules plus 1,500 tokens of documents and question per request, 40,000 requests a month on Sonnet ($2 per million input). Estimate the monthly input cost with and without caching the 6,000-token prefix, assuming one write per 100 requests.

Exercise 9 🔴 hard build it

Give the token bucket a wait_time(n) method (seconds until n tokens are available) and a priority rule: background jobs may only take tokens while more than half the capacity is left.

Show solution

Exercise 10 🔴 hard design

Write the runbook entry "LLM provider degraded" for DocsPilot: signals, automatic behaviour, manual steps, and how you know it's over.

Show solution
  • Signals: rising 529/5xx rate and latency on anthropic.messages.create spans; fallback rate above 5%; breaker-open events.
  • Automatic: SDK retries, per-model breakers, fallback to the evaluated smaller model, then the "links only" answer; batch jobs pause.
  • Manual: check the provider status page; if prolonged, switch the chain's primary by config flag; post in the incident channel; consider routing through another platform (for example a cloud provider's Claude endpoint) if pre-approved.
  • Over: breakers closed for 15 minutes, error rate back to baseline, fallback rate under 1%; resume batch jobs; note the incident in the eval log (answers given by the fallback may need review).
