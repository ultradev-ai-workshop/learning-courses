Chapter 15 · At Work & Beyond

Project: DocsPilot

Assemble everything into one service: routed questions, hybrid RAG with access control and citations, tools and a bounded agent for live data, guardrails, budgets, degraded mode, tracing, an MCP server, and acceptance tests that prove it.

You will learn

  • How the parts from Chapters 2–14 fit together in one request flow.
  • How to keep model IDs, prices and budgets in configuration.
  • How to make a feature degrade gracefully and refuse over-budget work before any model call.
  • How to expose the service to MCP hosts without bypassing its permissions.
  • How to turn acceptance criteria into automated tests that run offline.

The brief

Acme's engineers lose hours finding answers in runbooks, ADRs and guides, and in the ticket and on-call systems. You deliver DocsPilot: a service that answers engineering questions with citations, pulls live data through tools, refuses what it can't answer, and proves its quality with evals. Every part was built in an earlier chapter; this chapter assembles and hardens them. The finished module is also in the playground repository as docspilot_app.py, next to every module it imports.

Step 4: the MCP server

The MCP server calls the DocsPilot service, never the index or the database directly, so permissions, budgets, guardrails and tracing apply to MCP traffic too. Over HTTP, the user comes from the MCP authorization layer; here it's a parameter of the factory.

Step 5: acceptance tests

Each criterion becomes an automated check that runs offline: the real SDK against the mock server for the plumbing, FakeAnthropic where a test needs a specific model behaviour. With a real key, the same file (minus the scripted parts) becomes a smoke test against the real API.

Step 6: evals and the CI gate

The acceptance tests prove the plumbing. Quality comes from the eval harness of Chapter 10, pointed at DocsPilot.ask. The project's eval set should grow to at least 120 cases: 70 answerable documentation questions, 20 live-data or mixed questions, 15 unanswerable and 15 adversarial, with these targets:

#CriterionEvidence
AC1retrieval recall@5 ≥ 0.90 on the answerable questionsretrieval report
AC2answer correctness ≥ 85% (judge calibrated against 30 human labels)eval report + calibration
AC3groundedness ≥ 95%eval report
AC4100% of citations refer to sent documentscode grader
AC5≥ 90% of unanswerable questions declinedcode grader
AC60 restricted chunks for restricted users across all casesACL test
AC7≥ 90% of adversarial cases pass; 0 unrequested tool callseval report
AC8p95 latency ≤ 8 s; average cost ≤ $0.03 per answertraces and usage
AC9CI fails when the pass rate drops more than 2 points below baselinea CI run with a deliberately broken prompt

The mock routes everything to docs, so the adversarial "print your system prompt" is retrieved against, finds weak matches and is declined; whether a real model also declines is exactly what the adversarial cases in your real eval run measure.

Recap

  • The request flow: input guard and budget → router → docs (RAG + ACL + citations) or agent (tools + budgets) → output guard → trace and cost.
  • Configuration holds models, prices and limits; code holds behaviour.
  • Degraded mode and budget refusals are designed, tested behaviours, not accidents.
  • The MCP server goes through the service, so every rule applies to every host.
  • Acceptance criteria are automated checks; quality is an eval with a CI gate.

Exercises

Exercise 1 🟢 easy explain

Why does the unanswerable-question check expect exactly one model call (the router)?

Show solution

When retrieval finds nothing good enough, _docs answers "not in the docs" without calling the answer model: cheaper, faster, and it can't hallucinate. The test proves that the shortcut works.

Exercise 2 🟢 easy explain

Why does the MCP server call pilot.ask instead of querying the index itself?

Show solution

So that ACLs, budgets, redaction, tracing and cost tracking apply to MCP traffic too. A second path to the data would need all those rules again, and would eventually miss one.

Exercise 3 🟢 easy change config

Switch the answer model to claude-opus-5-5 by changing only configuration, and print the new cost of one answer.

Show solution

No code changed. Before doing this for real, run the eval suite: a stronger model isn't automatically better for your task, and it costs twice as much.

Exercise 4 🟢 easy predict

A question is 800 tokens long. What happens, and where would the web layer map it?

Show solution

ask raises ValueError("question too long") before any model call; the web layer maps it to HTTP 400 with a clear message.

Exercise 5 🟡 medium test it

Add an acceptance check: an out-of-scope question ("recommend a pizza place") returns answerable: false and makes exactly one model call.

Show solution

Exercise 6 🟡 medium build it

Add a rate(trace_id, thumbs_up, comment) feature: give each response a trace_id, store ratings, and report the thumbs-down rate per route.

Show solution

Every thumbs-down with a comment is a candidate eval case and a message for the document's owner.

Exercise 7 🟡 medium test it

Write an ACL test that runs every eval question as the restricted user and asserts that no restricted chunk is ever retrieved.

Show solution

Add a question aimed at the restricted document on purpose: a test that never tries to reach it proves nothing.

Exercise 8 🟡 medium design

The agent path ignores degraded if the model fails mid-loop. What happens today, and how would you improve it?

Show solution

A 529 during the agent loop propagates as APIStatusError and is caught by ask, which returns the degraded "links" answer; the tool results gathered so far are lost. Improvement: have the agent return a partial result (the tools it called and their outputs) and include them in the degraded answer ("I found: OPS-101 is an open SEV2; the payments on-call is priya").

Exercise 9 🔴 hard build it

Add prompt caching to the docs path: put the system prompt in a block with cache_control, then show that a second question reads the cache. (The mock caches prefixes of 1,024 toy tokens or more; make the system prompt long enough.)

Show solution

Router calls don't read the cache (their prefix is short and different); the second answer call does. In the real service, put cache_control in _docs directly.

Exercise 10 🔴 hard plan

Write the 10-minute demo script for DocsPilot's review, covering every requirement.

Show solution
  1. A docs question with citations (F1, F2); open the cited section.
  2. A live-data question and a mixed one; show the tool calls in the trace (F4).
  3. An unanswerable question: the polite decline and zero answer-model calls (F3).
  4. The same secrets question as two users with different groups (F5).
  5. An injection attempt from a poisoned test document; show the safe rendering (Chapter 12).
  6. Degraded mode with the mock returning 529 (N2), and a budget refusal (N3).
  7. The MCP Inspector calling all four tools (F6).
  8. The eval report, the CI gate failing on a deliberately broken prompt, and the cost per answer (N1, N4).
