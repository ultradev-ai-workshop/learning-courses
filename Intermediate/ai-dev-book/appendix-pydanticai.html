Appendix D · Popular Frameworks

Pydantic AI

An agent framework from the Pydantic team that feels like ordinary typed Python: an agent has a model, instructions, typed dependencies, typed tools and a typed output. It's the closest framework to the style of this book.

You will learn

  • Agents: model, instructions, run_sync / run, results and usage.
  • Typed output with Pydantic models, and how it maps to structured outputs.
  • Tools and dependency injection with RunContext.
  • Testing with TestModel, FunctionModel and agent.override.
  • Message history for multi-turn conversations, and usage limits.
  • When to choose Pydantic AI.

Versions. This appendix uses pydantic-ai-slim 2.x with the Anthropic extra. Model names use the "provider:model" form, for example "anthropic:claude-sonnet-5-5"; it reads ANTHROPIC_API_KEY (and here the mock server's base URL) from the environment.

Agents

🧠 Analogy: a typed function that happens to think. A Pydantic AI agent is used like a function with a signature: dependencies in, a validated object out. The model is an implementation detail behind that signature, which is exactly why it's easy to swap in a fake for tests.

☕ Java: the feel is close to LangChain4j's "AI Services" (an interface whose methods are implemented by a model, returning POJOs) or Spring AI's ChatClient...entity(Triage.class): typed in, typed out, with the plumbing hidden.

Tools and dependencies

Tools are decorated functions. @agent.tool tools receive a RunContext whose deps carries per-run dependencies (the current user, a database client, an HTTP client); @agent.tool_plain tools don't need it. Dependencies are how you keep tools acting on behalf of the user (Chapter 12) without globals:

The permission check lives in the tool, using the dependencies the application passed in, not anything the model said.

Testing without a model

Pydantic AI has two test models. TestModel calls every tool once with generated arguments and returns schema-valid output, which is great for smoke tests. Recap

  • Agent("provider:model", instructions=..., output_type=..., deps_type=...); run_sync returns output, messages and usage.
  • Typed outputs use native structured outputs on current Claude models.
  • Tools get per-run dependencies through RunContext: the place for user identity and permissions.
  • TestModel, FunctionModel and agent.override make agents unit-testable.
  • message_history continues conversations; UsageLimits enforces budgets.

Exercises

Exercise 1 🟢 easy explain

What's the difference between @agent.tool and @agent.tool_plain?

Show solution

@agent.tool functions take a RunContext as their first argument (with deps, usage and more); @agent.tool_plain functions don't. The model never sees the context: only the other parameters become the tool's schema.

Exercise 2 🟢 easy explain

Why pass the user through deps rather than as a tool parameter?

Show solution

Tool parameters are chosen by the model, so an injection could set user="admin". deps are set by your application from the authenticated session; the model can't change them.

Exercise 3 🟢 easy choose

Which test model would you use to check (a) that every tool can be called without crashing, (b) the exact behaviour when the model calls get_ticket with an unknown key?

Show solution

(a) TestModel: it calls each tool with generated arguments. (b) FunctionModel: you script exactly that call and assert on what follows.

Exercise 10 🔴 hard design

Compare Pydantic AI and LangGraph for DocsPilot's agent path. Which would you choose, and what would make you switch?

Show solution

Pydantic AI if the agent is a request-scoped loop with a few typed tools: less code, typed outputs, easy tests. LangGraph if runs must pause for approvals and resume later, survive restarts, or branch into many explicit steps. Switch when a requirement like "approve a write tool tomorrow morning" appears. Either way, the same eval set decides whether the rewrite kept quality.
