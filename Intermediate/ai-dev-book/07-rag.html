Chapter 7 · Building Blocks

Retrieval-Augmented Generation

Answer questions from your own documents: chunk them well, retrieve with both keywords and meaning, assemble a tight context, and return answers with verifiable citations.

You will learn

  • The RAG pipeline end to end, and where each kind of failure comes from.
  • Chunking that keeps meaning intact: heading paths and contextual retrieval.
  • Hybrid search: BM25 keywords plus vectors, merged with reciprocal rank fusion.
  • Reranking and context assembly within a token budget.
  • Native citations with the document content block.
  • How to evaluate retrieval and generation separately.

The pipeline

RAG has two phases:

  • Indexing (offline, whenever a document changes): load → clean → chunk → optionally add context → embed → store with metadata.
  • Answering (online, per question): optionally rewrite the query → retrieve candidates (keyword and vector) → fuse → rerank → assemble the context within a budget → generate with citations → validate.

🧠 Analogy: an open-book exam. Without RAG, the model takes a closed-book exam on your company: it guesses. With RAG, a librarian (retrieval) first fetches the few pages that matter, and the student (the model) answers with the book open, quoting page numbers. If the librarian brings the wrong pages, even a brilliant student fails, which is why most bad RAG answers are retrieval failures.

☕ Java: you've built this before. A search service returns candidate records, a service layer selects and orders the relevant ones, and a template renders a response from them. In RAG the "template" is a model that writes prose. Answer quality is capped by what the search layer found.

Chunking

A chunk is the unit you embed, retrieve and cite. Chunks that are too large dilute the embedding and waste context; chunks that are too small lose the meaning that makes them answerable.

StrategyHowGood for
Fixed size with overlapN tokens per chunk, M tokens of overlapunstructured text, a quick start
Structuralsplit on headings, paragraphs, code fencesMarkdown, wikis, runbooks (DocsPilot)
Semanticsplit where the topic shifts (embedding distance between sentences)long narrative documents

Practical defaults for internal docs: split on ## headings, cap chunks at a few hundred tokens, never split inside a code block or table, and keep the heading path ("Runbook: database failover › Steps") with every chunk.

Contextual retrieval

A chunk like "Run step 3 again with --force" is useless on its own: which runbook, which step? Anthropic's contextual retrieval asks a cheap model to write one or two sentences placing each chunk within its document, and prepends them to the chunk before embedding and keyword indexing. Hybrid search

Vectors are great at meaning and bad at exact tokens: error codes, ticket keys, command names, version numbers. Keyword search is the opposite. Use both. BM25 is the standard keyword ranking function (it's what Elasticsearch and OpenSearch use); the rank_bm25 package implements it in a few lines:

Reciprocal rank fusion (RRF) merges ranked lists without comparing their scores: an item scores 1/(60 + rank) in each list it appears in, and the sums decide. Reranking

Retrieval is tuned for recall (don't miss the right chunk); generation needs precision (send only what helps). A reranker scores each (question, chunk) pair directly. It's more accurate than vector distance, but too slow to run on the whole corpus, so you run it on the top 20–50 candidates. Options: a reranker model behind an API (Voyage has a rerank endpoint), a local cross-encoder, or a cheap Claude model asked for a relevance score with structured output.

Context assembly

Assembling the context is a small engineering problem with real impact:

  • Budget: cap the documents section (say 8k tokens) and stop adding chunks before you exceed it.
  • Deduplicate: never send the same chunk twice.
  • Order: most relevant first; keep chunks from one document together.
  • Metadata: give each chunk its title and heading path so the model, and the citations, can name it.

Generation with native citations

Instead of asking the model to write [Doc title] by convention (Chapter 2), send each chunk as a document content block with citations enabled. The API then returns text blocks whose citations point at exact passages. Because cited_text is extracted from your documents by the API, not written freely by the model, you can show it as a quote and link to the source with confidence.

Validate the citations as you validated structured output: every cited title must be one you sent, and the quote must appear in that chunk. Check the Citations page for the citation types (char_location for text, page_location for PDFs, content_block_location for custom content) and for feature compatibility: citations can't be combined with structured outputs in the same request.

☕ Java: the same request built with Jackson: one document node per chunk with "citations": {"enabled": true}, then a text node with the question. Read block.path("citations") on each text block of the response.

Evaluating RAG

Measure each stage separately, so you know what to fix:

StageMetricHow
Retrievalrecall@k, MRRlabelled question → expected chunk (above)
Groundednessare all claims supported by the retrieved text?an LLM grader given the context and the answer (Chapter 10)
Answer qualitycorrect and complete versus a reference answerhuman review of a sample, then a grader calibrated against it
Abstentiondoes it decline when the corpus doesn't contain the answer?include unanswerable questions in the set

MRR (mean reciprocal rank) rewards putting the right chunk first: each question scores 1/rank of the expected chunk (0 if missing), averaged.

Common mistakes

Blaming the model first: rewriting the prompt for weeks when the right chunk was never retrieved.

Check retrieval first. Log the retrieved chunk IDs with every answer; when an answer is wrong, look there first.

Vectors only, missing ERR_TLS_HANDSHAKE, ticket keys and command names.

Hybrid + RRF: keywords for exact tokens, vectors for meaning, fused.

Context stuffing: sending the top 50 chunks "just in case".

Rerank and budget. A few strong chunks beat many weak ones for quality, cost and latency.

Recap

  • RAG = an indexing pipeline + an answering pipeline; most failures are retrieval failures.
  • Chunk on structure, keep heading paths, consider contextual retrieval.
  • Hybrid search (BM25 + vectors) with RRF handles both exact tokens and paraphrases.
  • Rerank a wide candidate set down to a tight, budgeted, deduplicated context.
  • Use document blocks with citations for verifiable answers, and validate the citations.
  • Evaluate retrieval (recall@k, MRR), groundedness, answer quality and abstention separately.

Exercises

Exercise 1 🟢 easy explain

An answer is wrong. What do you check first, and why?

Show solution

The retrieved chunk IDs logged with the answer. If the right chunk wasn't retrieved, no prompt change can fix it; fix chunking, the index or the query. Only if the right chunk was there do you look at the prompt or the model.

Exercise 2 🟢 easy calculate

Compute RRF (k=60) by hand: list A = [x, y, z], list B = [z, x]. Which item wins?

Show solution

x: 1/61 + 1/62; z: 1/63 + 1/61; y: 1/62. Appearing high in both lists wins; appearing in only one list ranks below anything found by both.

Exercise 3 🟢 easy choose

Which retriever do you expect to do better on each question: "ERR_CONN_POOL_EXHAUSTED", "why are logins slow lately", "OPS-101"?

Show solution

Keyword for the error code and the ticket key (exact tokens that an embedding may blur); vector for the paraphrase. That's why hybrid search exists.

Exercise 4 🟢 easy build it

Call assemble on all chunks with a budget of 100 tokens. How many fit?

Show solution

The budget is a hard cap: assemble stops before exceeding it, even if a later, smaller chunk would fit. Whether to skip-and-continue instead is a design choice; skipping keeps more chunks but can drop a highly ranked one.

Exercise 5 🟡 medium build it

Print a table for the labelled set: question, keyword rank, vector rank and hybrid rank of the expected chunk (or "-"). What patterns do you see?

Show solution

Typical pattern: identifiers and command names favour keyword, paraphrases favour vector, and hybrid is rarely the worst of the two.

Exercise 6 🟡 medium build it

Write validate_citations(citations, sent_chunks) that rejects a citation whose quote doesn't appear in any sent chunk with that title.

Show solution

With native citations this should almost never fire, which is exactly why it's a good alarm when it does.

Exercise 7 🟡 medium experiment

Re-chunk with max_tokens=30 and measure hybrid recall@3 again. What happens, and why?

Show solution

The chunk IDs change, so compare at document level. Smaller chunks give more precise hits but lose context ("Promotion takes about 40 seconds" no longer sits next to the command it refers to). There is no universal best size: measure.

Exercise 8 🟡 medium design

Write three unanswerable questions for DocsPilot and say what a good system does with each.

Show solution

"What is the parental leave policy?" (not in the corpus), "What will the payments team ship next quarter?" (not knowable), "What's Priya's home address?" (must not answer). A good system abstains with a helpful pointer ("I couldn't find this in the engineering docs; HR policies live in the HR portal") and never invents. Put them in the eval set with the expected behaviour "abstain".

Exercise 9 🔴 hard build it

Implement contextual retrieval: for each chunk, ask a model for a one-sentence context (use FakeAnthropic with a function as the reply, which builds a sentence from the doc title and heading), prepend it, rebuild the index, and measure hybrid recall@3. Count the calls.

Show solution

One call per chunk, each repeating the whole document: put the document in a cached prefix so every chunk after the first reads it at a fraction of the price. Keep the change only if recall improves on your set.

Exercise 10 🔴 hard design

Docs change daily. Design re-indexing so that answers never mix old and new versions of a document and deleted docs disappear.

Show solution
  • Trigger on change (a Git webhook or a nightly diff of content hashes), per document.
  • Re-chunk and re-embed the whole document, then replace its chunks in one transaction (delete by doc_path, insert new), so a query sees either the old or the new version, never both.
  • Deletions: remove the rows; a nightly job compares paths in the index with the source to catch missed events.
  • Store content_hash to skip unchanged documents, and embed_model to detect stale vectors.
  • Re-run the retrieval eval after big doc changes; new docs may need new labelled cases.
