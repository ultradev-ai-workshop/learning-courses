Working with Objects

Objects are bags of properties, but each property carries hidden flags, keys have a defined order, and every way of listing or copying properties sees a slightly different subset. Knowing these rules explains many "where did my key go?" bugs.

  • Property access, in vs Object.hasOwn ES2022, and the property key order.
  • Object.keys/values/entries ES2017 and Object.fromEntries ES2019.
  • Property descriptors (writable, enumerable, configurable), plus freeze and seal.

Accessing properties

  • obj.name works for valid identifiers. obj["any key"] works for any string, symbol or variable.
  • Property keys are always strings or symbols: obj[1] and obj["1"] are the same property.
  • Reading a missing property gives undefined; reading through undefined throws, which is why ?. exists.
  • delete obj.key removes an own property.

📝 Older syntax you'll still see: obj.hasOwnProperty("key") and Object.prototype.hasOwnProperty.call(obj, "key"). Object.hasOwn replaces both, and it also works on null-prototype objects.

Property key order

Object keys are listed in a defined order, and it's not always insertion order:

  1. Integer-like keys ("0", "42") first, in ascending numeric order;
  2. then other string keys, in insertion order;
  3. then symbols, in insertion order (only for methods that include symbols).

("-1" and "01" aren't canonical array indexes, so they count as ordinary strings.) If you need guaranteed insertion order for number-like keys, use a Map.

Keys, values, entries

Property descriptors

Every property has a descriptor: either a data descriptor (value and writable) or an accessor descriptor (get and set), plus two flags:

  • enumerable: shows up in Object.keys, for…in, spread and JSON;
  • configurable: can be deleted or redefined.

Properties created by assignment or literals have all flags true. Properties created with Object.defineProperty default to false.

There's no built-in deep equality for objects: === compares identity. In Node, util.isDeepStrictEqual(a, b) works; in tests, use assert.deepStrictEqual (Appendix B). Don't compare JSON.stringify outputs, because key order makes equal objects look different.

Recap

  • Shorthand properties and methods, computed keys, and getters/setters make literals expressive.
  • Keys are strings or symbols; integer-like keys are listed first, in numeric order. in sees inherited keys and Object.hasOwn sees only own ones.
  • entries → map → fromEntries is the idiom for transforming objects.
  • Descriptors control writable/enumerable/configurable, and defineProperty defaults them to false. Freeze, seal and preventExtensions are shallow.
  • Spread copies own enumerable keys shallowly; structuredClone copies deeply but drops classes and throws on functions.

Exercise 8 🟡 medium explain why

Why is JSON.stringify(a) === JSON.stringify(b) a bad deep-equality check?

Show solution

Key order matters to stringify, so {a:1,b:2} and {b:2,a:1} look different. It also drops undefined and functions, turns NaN into null, and can't handle Maps, Sets, BigInt or cycles. Use util.isDeepStrictEqual or a tested library.

Exercise 10 🔴 hard mini-project · playground

Create playground/model.js exporting defineModel(fields). For example, defineModel({ title: "string", price: "number" }) returns a create(data) function that makes a sealed object with validating setters for each field, a non-enumerable _errors array, and a toJSON that outputs only the fields.

Show solution

Each field gets an accessor descriptor whose setter validates; Object.assign runs those setters. _errors and toJSON are non-enumerable, so they stay out of JSON, and toJSON's spread reads the getters.
