Appendix A

TypeScript in Node.js

TypeScript adds static types to JavaScript: you describe the shape of your data, and the compiler catches mistakes before the code runs. Node can now run .ts files directly by stripping the types. This appendix explains what that means, what syntax works, how type checking fits in, and the other ways to run and publish TypeScript.

You will learn

  • What TypeScript adds, and the difference between type checking and running.
  • Running .ts files natively with type stripping, and its rules (erasable syntax, .ts extensions, import type).
  • Type checking with tsc --noEmit and a tsconfig.json suited to Node.
  • The alternatives: transpiling with tsc, and runners like tsx.
  • Publishing a TypeScript package: compiled JavaScript plus .d.ts files.

What TypeScript adds

TypeScript is JavaScript plus type annotations: function total(items: Item[]): number. A separate tool, the TypeScript compiler (tsc), reads those annotations and reports errors like "you passed a string where a number is expected" — in your editor as you type, and in CI. The types themselves don't exist at run time: the JavaScript engine never sees them.

🧠 Analogy: a spell-checker with a grammar guide. Types are notes in the margin of your manuscript: "this word is a noun", "this sentence needs a verb". The proof-reader (tsc) checks the manuscript against those notes before it's printed. The printing press (Node) ignores the margin notes entirely — it prints the text. Node's type stripping is exactly that: it rubs out the margin notes and prints. It does not proof-read.

☕ Java: TypeScript's types feel familiar (interfaces, generics, union types), with two big differences: they're structural (any object with the right properties fits an interface, no implements needed), and they're erased — there's no runtime type information, no reflection on generics, and a wrong cast isn't checked at run time.

Running TypeScript natively

Since Node 23.6 (and in all current LTS versions), you can run a .ts file directly. Node removes the type annotations (replacing them with whitespace, so line and column numbers stay correct) and runs the JavaScript that remains:

Stripping does not check types

Node ran code that a careful type checker would flag (or that hides behind any and casts). Types describe your intent; only tsc verifies it, and only validation verifies data coming from outside (requests, files, env vars).

What syntax works: erasable only

Type stripping can only delete TypeScript syntax; it can't generate code. So TypeScript features that produce JavaScript at run time aren't supported:

Works (erasable)Doesn't work (needs code generation)
interface, type, annotations, generics, as, satisfies, !, import type, declare, abstract, access modifiers on fieldsenum, namespace with values, parameter properties (constructor(private x: number)), legacy decorators with metadata, import x = require()

Type checking with tsc

Install TypeScript as a dev dependency and let tsc check (but not emit) your code, in the editor and in CI:

A tsconfig.json that matches Node's native TypeScript rules:

  • erasableSyntaxOnly reports enums, parameter properties and other non-erasable syntax as errors.
  • verbatimModuleSyntax requires import type for type-only imports.
  • allowImportingTsExtensions lets you write ./user.ts; rewriteRelativeImportExtensions turns those into .js if you ever compile with tsc.
  • @types/node gives types for Node's APIs (fs, http, process…).

A typical package.json: "start": "node src/server.ts", "typecheck": "tsc", "test": "node --test" (the test runner finds *.test.ts files too).

Whatever runs the code, keep tsc --noEmit in CI: runners and type stripping are fast precisely because they skip type checking.

Publishing a TypeScript package

Packages on npm should ship JavaScript (so every consumer can run them, whatever their setup) plus declaration files (.d.ts) that carry the types for TypeScript users. Node doesn't strip types inside node_modules, which is another reason to compile.

The build config sets "declaration": true, "outDir": "dist" and turns noEmit off. prepublishOnly makes sure npm publish never ships stale files.

Recap

  • TypeScript = JavaScript + types checked by tsc; types are erased and don't exist at run time.
  • node file.ts strips types and runs; it does not type-check. Only erasable syntax works: no enums, parameter properties or value namespaces.
  • Import with full .ts extensions, and use import type for types; erasableSyntaxOnly + verbatimModuleSyntax make tsc enforce the rules.
  • Run tsc --noEmit in CI. Use tsx or compilation for full TypeScript syntax.
  • Publish compiled JavaScript + .d.ts files, with a "types" condition in exports.

Exercise 4 🟢 easy explain

Show solution
