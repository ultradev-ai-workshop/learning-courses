Chapter 9 · Files & Data

Working with Files & Folders

Reading configuration, saving uploads, writing logs, generating reports: almost every Node program touches the file system. This chapter covers building paths safely, the three styles of the fs API, file information, reading and writing (including safe "atomic" writes), file handles, folders, and the differences between operating systems that bite cross-platform code.

You will learn

  • The node:path module: join, resolve, basename, extname, relative, and why not to concatenate strings.
  • The sync, callback and promise flavours of node:fs, and when each is appropriate.
  • File stats, and checking existence without race conditions.
  • Reading and writing files, flags, appending, and atomic writes with rename.
  • File descriptors and FileHandle, folder operations, fs.glob, and common error codes.

File paths

A path like /home/ana/notes/todo.txt (macOS, Linux) or C:\Users\Ana\notes\todo.txt (Windows) tells the operating system where a file is. Building paths by gluing strings with "/" breaks on Windows and creates bugs with double or missing slashes. The node:path module does it right for the current platform:

path.resolve works like a series of cd commands, starting from the current working directory, and always returns an absolute path:

🧠 Analogy: giving directions. A relative path is "two doors down, then left": it only works if you know where the person is standing (the current working directory). An absolute path is a full postal address: it works from anywhere. path.join writes directions down neatly; path.resolve follows them from where you're standing and gives you the full address.

⚠️ Relative paths are relative to where Node was started, not to your script. readFile("config.json") works when you run node app.js inside the project folder and fails when a service manager starts it from /. For files that belong to your code, build paths from import.meta.dirname (Chapter 3).

Under the hood, asynchronous file operations run on libuv's thread pool (4 threads by default): the disk work happens off the main thread, and your callback or promise is resolved when it's done. That's why they don't block the event loop, and also why thousands of simultaneous file operations queue up (Chapter 13).

Reading files

readFile loads the whole file into memory. Pass an encoding ("utf8") to get a string; without one you get a Buffer of raw bytes (Chapter 10):

💡 Big files: readFile is perfect for configs and documents of a few megabytes. For log files of several gigabytes, reading everything at once wastes memory (and Node refuses files over about 2 GB as one string). Process them piece by piece with streams (Chapter 10) or fileHandle.readLines().

Writing files

writeFile creates the file or replaces its contents; appendFile adds to the end. The flag option chooses other behaviours:

FlagMeaning
"w" (default for writes)write; create or truncate
"a"append; create if missing
"wx" / "ax"like w/a but fail with EEXIST if the file exists
"r" (default for reads)read; fail if missing
"r+"read and write, without truncating

Atomic writes: never leave a half-written file

If the process crashes (or the power fails) in the middle of writeFile("db.json", …), the file can be left empty or truncated, and the old data is gone. The standard fix: write to a temporary file in the same folder, then rename it over the original. On the same disk, a rename is atomic: other readers see either the old file or the new one, never a mix.

🧠 Analogy: replacing a shop sign. You don't scrape the old sign off and paint the new one letter by letter while customers watch (if you're interrupted, the sign says "BAK"). You paint the new sign in the workshop, then swap it in one move. The temporary file is the workshop; rename is the swap.

File descriptors and FileHandle

When a program opens a file, the operating system gives it a small number called a file descriptor (fd) that identifies the open file. readFile and writeFile open, work and close for you. For more control — reading part of a file, writing many times, keeping a file open — open it yourself. With promises you get a FileHandle object:

⚠️ Leaking file descriptors. Every process has a limit on open files (often 256 or 1024). Forgetting close() in a server leaks one descriptor per request until EMFILE: too many open files. Always close in finally (or use await using fh = await open(…), which closes automatically). The last line of the example above, which opens a file just to check a method exists, is exactly such a leak — harmless in a script that ends, a bug in a server.

Working with folders

⚠️ rm(path, { recursive: true, force: true }) is rm -rf. Never pass it a path built from user input or from a variable that might be empty or "/". Validate the path, and keep it inside a known base folder.

Different file systems

Code that works on your Mac can fail on a Linux server or a Windows laptop. The usual suspects:

  • Case sensitivity. macOS and Windows usually treat Readme.md and README.md as the same file; Linux doesn't. An import of ./Utils.js for a file named utils.js works locally and breaks in production. Keep names lower-case and consistent.
  • Separators and drive letters. Use path.join, never "/" concatenation; convert to URLs with pathToFileURL for import().
  • Line endings. Windows text files may use \r\n. Split lines with /\r?\n/, and use os.EOL when writing files meant for the local platform.
  • Unicode file names. "café" can be stored as one character é or as e + an accent. Compare names with name.normalize().
  • Forbidden names and characters. Windows rejects :, ?, * and names like CON or NUL. Sanitise user-supplied file names.

Recap

  • Build paths with path.join/resolve; relative paths depend on the working directory, so anchor code-related files to import.meta.dirname.
  • fs comes in sync (startup/CLI), callback and fs/promises (default) flavours; async file I/O runs on libuv's thread pool.
  • Don't check-then-act: try the operation and handle ENOENT/EEXIST. stat gives size, times and type.
  • readFile/writeFile handle whole files; flags (a, wx) change behaviour; write to a temp file and rename for atomic saves.
  • Open files with open() for partial reads or many writes, and always close(). Folders: mkdir/readdir/rm/cp with recursive, and fs.glob.
  • Watch out for case sensitivity, line endings, Unicode normalisation and forbidden characters across platforms.
