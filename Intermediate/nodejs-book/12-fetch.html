Chapter 12 · Networking

fetch, HTTP Clients & WebSockets

Servers also talk to other servers: payment providers, weather APIs, your own microservices. Node has the browser's fetch built in, so you no longer need a package like axios. This chapter covers making requests, handling errors and timeouts correctly, streaming large downloads, retries, proxies in corporate networks, and the built-in WebSocket client for real-time connections.

You will learn

  • fetch in Node: GET and POST, headers, JSON, and reading responses.
  • The trap that fetch doesn't reject on 404 or 500, and how to handle errors properly.
  • Timeouts and cancellation with AbortSignal, and retrying safely.
  • Streaming large responses to disk, and limiting parallel requests.
  • Proxies (enterprise networks) and the WebSocket client.

To keep every example runnable offline, this chapter starts a small local test server first and talks to it. It answers a few routes: JSON data, an echo of what you send, slow responses, errors and a big download.

🧠 Analogy: ordering by mail. await fetch() is the moment the parcel arrives at your door: you can read the label (status, headers) right away. Opening the box (await res.json()) is a second step — and a body can only be opened once. Calling res.json() and then res.text() fails because the box is already empty.

Errors: fetch only rejects on network failures

This is the most common fetch bug. A 404 or 500 response is still a successful HTTP exchange, so the promise fulfils. It only rejects when there's no response at all: DNS failure, connection refused, aborted, invalid URL. Always check res.ok (true for 200–299):

Timeouts and cancellation

fetch waits a long time by default. A slow upstream API then makes your server slow, and requests pile up. Always set a timeout with a signal (Chapter 6):

🧠 Analogy: waiting on hold. Calling a support line without a time limit means you might sit on hold all afternoon while your own customers queue behind you. A timeout is deciding up front: "if they don't pick up within 5 seconds, I hang up and tell my customer to try again later." Failing fast is kinder than hanging forever.

Retrying safely

Some failures are temporary: 503 Service Unavailable, 429 Too Many Requests, connection resets. Retrying them with a growing delay often succeeds. But only retry requests that are safe to repeat (GET, PUT, DELETE — "idempotent"); retrying a POST /payments could charge a card twice, unless the API supports an idempotency key.

Streaming large responses

res.json() and res.text() load the whole body into memory. For a large download, stream res.body (a web ReadableStream) straight to disk, converting it with Readable.fromWeb (Chapter 10):

You can also iterate res.body with for await to show progress, or pipe it through createGunzip() or a parser. If you don't need the body, call await res.body?.cancel() so the connection can be reused.

Proxies and enterprise networks

In many companies, outgoing traffic must go through an HTTP proxy, and TLS traffic may be inspected with a company certificate authority. Typical symptoms: requests time out, or fail with UNABLE_TO_VERIFY_LEAF_SIGNATURE / SELF_SIGNED_CERT_IN_CHAIN. Node supports the standard environment variables:

⚠️ Never "fix" certificate errors with NODE_TLS_REJECT_UNAUTHORIZED=0. It turns off certificate checking for every connection, making man-in-the-middle attacks trivial. Add the company CA with NODE_EXTRA_CA_CERTS or --use-system-ca instead. Remember to configure npm too (npm config set proxy … and cafile).

WebSockets

HTTP is request → response. A WebSocket is a long-lived, two-way connection: after an HTTP "upgrade" handshake, either side can send messages at any time. Chat apps, live prices, multiplayer games and notifications use it. Node includes the browser's WebSocket client; for a server you'd normally install the ws package. 🧠 Analogy: letters vs a phone call. HTTP is exchanging letters: you write, they answer, the exchange is over; to hear news you must write again (polling). A WebSocket is a phone call: once connected, either side can speak whenever it has something to say, and the line stays open until someone hangs up.

🌐 Same API as the browser. new WebSocket(url), send, close and the open/message/close/error events work exactly as in browser code, so client logic can be shared and tested in Node.

Recap

  • fetch(url, { method, headers, body, signal }) is built in. Read the body once: .json(), .text(), or stream res.body.
  • fetch rejects only on network failures (see err.cause.code); check res.ok for HTTP errors.
  • Always set a timeout (AbortSignal.timeout); retry only transient errors and idempotent requests, with backoff and jitter.
  • Stream big downloads with Readable.fromWeb(res.body) + pipeline; limit concurrency for many requests.
  • Behind a proxy: HTTPS_PROXY + --use-env-proxy; trust company CAs with NODE_EXTRA_CA_CERTS — never disable TLS checks.
  • WebSocket (client) gives a two-way, long-lived connection with the browser's API.

Exercise 2 🟢 easy predict

A colleague writes try { const r = await fetch(url); data = await r.json(); } catch { data = null; } and says it "handles all errors". The API returns 500 with an HTML error page. What happens?

Show solution

fetch fulfils (a 500 is a valid response), then r.json() throws a SyntaxError on the HTML, so the catch sets data = null — by accident, and indistinguishable from "no data". If the error page happened to be JSON ({"error":"…"}), the code would treat the error body as real data. Check r.ok first.

Exercise 4 🟢 easy explain

Which of these are safe to retry automatically after a timeout, and why? GET /orders, POST /orders, PUT /orders/7, DELETE /orders/7, POST /payments with header Idempotency-Key: 4f1c….

Show solution

Safe: GET (reads only), PUT (sets the same state again), DELETE (deleting twice has the same end result), and the payment POST with an idempotency key (the server recognises the repeat and returns the first result). Not safe: plain POST /orders — a timeout doesn't tell you whether the first attempt was processed, so a retry may create a duplicate order.

Exercise 7 🟡 medium find the bug

This health check sometimes reports "up" for a server that's returning errors, and sometimes hangs. Find both bugs.

Show solution

1. A 500 or 503 response doesn't throw, so the function returns true; check res.ok. 2. There's no timeout, so a server that accepts the connection but never answers makes the check hang.
