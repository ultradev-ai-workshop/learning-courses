Testing with node:test

Node ships a complete test runner: test discovery, suites, hooks, assertions, mocking (including timers), coverage and watch mode, all without installing Jest or Mocha. This chapter shows how to write good tests with node:test and node:assert, how to test asynchronous code and HTTP servers, how to fake things you don't control, and how to measure coverage.

You will learn

  • Writing tests with test, describe/it and node:assert/strict, and running them with node --test.
  • Testing async code, errors and rejections; hooks; skip, only and todo.
  • Mocking functions, methods (like fetch) and timers with mock.
  • Testing an HTTP server end to end, and designing code to be testable.
  • Coverage, reporters, watch mode, and running tests in CI.

Why automated tests?

A test is a small program that runs a piece of your code and checks the result. Tests let you change code with confidence: if you break something, they tell you in seconds, not when a customer complains. They're also executable documentation of how your code is meant to behave.

🧠 Analogy: a smoke detector. You don't install a smoke detector because you plan to start fires; you install it so that when something goes wrong while you're busy, you find out immediately and cheaply. Tests are smoke detectors for your code: each one watches a specific room (a function, a route), and an alarm points you straight to the problem.

⚠️ Forgetting await in async tests. assert.rejects(...) returns a promise. Without await, the test function finishes before the assertion runs and the test passes even when it shouldn't. The same goes for any promise you're checking. Make the test async and await everything.

What makes a good test

  • Arrange, act, assert. Set up the inputs, call the code once, check the result. One behaviour per test, named after that behaviour.
  • Independent. Each test must pass alone and in any order: no shared state that one test leaves for the next (use beforeEach).
  • Deterministic. No real network, no real clocks, no randomness you don't control. Those make tests "flaky" (sometimes red for no reason). Inject them, or mock them.
  • Test behaviour, not implementation. Assert on outputs and visible effects, not on private details, so refactoring doesn't break the tests.
  • Include the edge cases: empty input, zero, negative numbers, huge values, invalid types, failures of dependencies.

Mocking

Real code depends on things you don't want in a unit test: a payment API, the clock, email sending. A mock (or test double) is a stand-in that you control and that records how it was used.

🧠 Analogy: a flight simulator. Pilots don't practise engine failures in a real plane over a real city. A simulator reproduces exactly the situation they want to rehearse, on demand, safely, as often as needed — and records everything they did. Mocks are simulators for your dependencies: "the payment API is down", "it's 23:59 on December 31st", rehearsed in milliseconds.

Coverage, reporters and watch mode

Coverage measures which lines, branches and functions your tests executed. It finds untested code; it doesn't prove the tests check the right things. Turn it on with a flag:

  • --test-coverage-lines=80 (and -branches, -functions) fail the run if coverage drops below a threshold.
  • --test-reporter=tap|dot|junit|lcov changes the output format; --test-reporter-destination writes it to a file (JUnit XML for CI dashboards, lcov for coverage services). Several reporters can run at once. The coverage table groups files by folder.
  • node --test --watch re-runs the affected tests whenever you save a file.

🧠 Analogy: a city map of where the patrol went. Coverage is a map showing which streets the police patrol drove through. Unvisited streets (uncovered lines) definitely weren't checked. But driving down a street isn't the same as noticing the open window: 100% coverage with weak assertions still misses bugs.

Tests in package.json and CI

A CI pipeline (GitHub Actions, GitLab CI…) then just runs npm ci and npm test on every push, ideally on each Node version you support. The non-zero exit code on failure is what turns the build red.

Recap

  • node:test + node:assert/strict need no dependencies; run with node --test (auto-discovers *.test.js and test/).
  • describe/it, hooks (before, beforeEach, after…), skip/todo/only. Make async tests async and await every assertion.
  • Good tests are independent, deterministic and test behaviour; inject dependencies so they can be replaced.
  • Mock with mock.fn, mock.method(globalThis, "fetch", …) and t.mock.timers; restore with mock.restoreAll() or use t.mock.
  • Test servers end to end: create without listening, listen(0) in before, close in after, send real requests.
  • Coverage with --experimental-test-coverage (+ thresholds), reporters for CI, --watch while coding.

Exercise 3 🟢 easy assertions

Which assertion would you use for each? (a) A function returns exactly 42. (b) A function returns { id: 1, tags: ["a"] }. (c) An ID looks like usr_ followed by 8 hex characters. (d) Calling with null throws a TypeError. (e) An async function rejects with a message containing "timeout".

Show solution

(a) assert.equal(f(), 42); (b) assert.deepEqual(f(), { id: 1, tags: ["a"] }); (c) assert.match(id, /^usr_[0-9a-f]{8}$/); (d) assert.throws(() => f(null), TypeError); (e) await assert.rejects(f(), /timeout/).

Exercise 4 🟢 easy hooks

Show solution

Open the connection once in before and close it in after (faster, and nothing leaks). Reset the data in beforeEach (truncate tables, or wrap each test in a transaction that afterEach rolls back) so every test starts from the same known state.
