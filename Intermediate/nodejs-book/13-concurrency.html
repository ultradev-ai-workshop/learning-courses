Don't Block the Event Loop: Workers & Processes

Node's single thread is its superpower for I/O and its weakness for CPU-heavy work. This chapter shows what "blocking" really means, the hidden ways code blocks (including regular expressions and huge JSON), how libuv's thread pool works, and the tools for real parallelism: splitting work into chunks, worker threads, child processes and the cluster module.

You will learn

  • Blocking vs non-blocking code, and why mixing sync and async APIs is dangerous.
  • The two thread types in Node: the event loop and libuv's worker pool (and which APIs use the pool).
  • Hidden blockers: expensive algorithms, catastrophic regexes (ReDoS), huge JSON.parse, sync crypto.
  • Partitioning work with setImmediate, and offloading it to worker_threads.
  • Child processes (spawn, execFile, fork) and the cluster module, compared.

Blocking vs non-blocking

Blocking means the JavaScript thread can't do anything else until an operation finishes. Every *Sync API blocks (readFileSync, execSync, pbkdf2Sync…), and so does any long-running JavaScript you write yourself. Non-blocking APIs start the operation and return immediately; the result arrives through a callback or promise.

We had to put the server in a separate process (with fork, explained later in this chapter) for a reason worth noticing: when the client and the server shared one process, the blocked server also blocked the client's timer, so the test couldn't even send /ping until the computation was over. A blocked event loop freezes everything in that process.

One expensive request delayed an unrelated, trivial one. With 1,000 users, every request computing something heavy makes the whole server crawl. The Node docs' golden rule: a server is fast when the work associated with each client at any given time is small.

⚠️ Mixing sync and async. Don't do fs.readFile(path, cb); fs.unlinkSync(path); — the delete runs before the read, because the read only started. When an operation depends on another, chain them (await the first, or put the second in the callback). And in request handlers, use only the async APIs.

Two kinds of threads

Node runs JavaScript on one thread, but it isn't a one-thread program. There are two kinds of threads:

  • The event loop (main thread): runs all your JavaScript callbacks, and does non-blocking network I/O through the operating system (epoll, kqueue, IOCP).
  • The worker pool (libuv's thread pool, 4 threads by default): runs work that the OS can't do asynchronously — file system operations, dns.lookup, the async crypto functions (pbkdf2, scrypt, randomBytes) and zlib compression.

🧠 Analogy: a restaurant kitchen. The event loop is the head chef: the only one who talks to waiters and decides what happens next, and who must never get stuck chopping onions for ten minutes. The worker pool is four kitchen porters who do the slow, boring tasks (washing, peeling) and ring a bell when done. Network calls are delivery drivers: they're out of the building entirely. If you hand the porters 100 sacks of potatoes at once, they work four at a time and the rest wait — the pool has a fixed size.

Hidden blockers

Blocking isn't only "a big for loop". These are classic causes found in real outages:

1. Regular expressions with catastrophic backtracking (ReDoS)

Some regexes take exponential time on inputs that almost match. Nested quantifiers like (a+)+, or alternatives that overlap like (a|a)*, are the warning signs. An attacker sends a crafted string to a form field, and your server freezes:

Defences: avoid nested quantifiers, limit input length before matching, and use well-tested validation libraries for things like emails and URLs.

2. Huge JSON

JSON.parse and JSON.stringify are synchronous: a 50 MB request body takes noticeable time on the main thread. Limit body sizes (Chapter 11), and stream large data instead of building giant strings.

3. Sync crypto, compression and file APIs

crypto.pbkdf2Sync, zlib.gzipSync and fs.readFileSync are handy in scripts, but in a server they do pool-sized work on the main thread. Use the async versions so the work happens on the worker pool.

Option 1: partition the work

If a computation can be split into small steps, run a batch of steps, then yield to the event loop with setImmediate so pending I/O and other requests get a turn, then continue (Chapter 7):

Partitioning keeps the server responsive, but the total work still happens on one thread (one CPU core). For truly heavy computation, use real parallelism.

Option 2: worker threads

node:worker_threads runs JavaScript in additional threads, each with its own event loop and its own memory. The main thread and workers communicate by sending messages; data is copied (with the structured clone algorithm), or transferred for ArrayBuffers.

🧠 Analogy: hiring a sous-chef with their own station. A worker thread is an extra cook with their own counter and their own ingredients (memory). You can't reach over and stir their pot; you pass a note through the hatch ("make the stock") and they pass a note back ("stock ready", plus a copy of the result). That isolation is what makes it safe — no two cooks fight over the same pot — but every note costs a little time, so give workers big tasks, not tiny ones.

  • Starting a worker takes a few milliseconds and memory. For many small jobs, keep a pool of long-lived workers (libraries like piscina do this) rather than one per task.
  • Use workers for CPU-bound work (image processing, compression, parsing, cryptography in JS). For I/O-bound work they don't help: async I/O is already parallel.
  • Sharing memory is possible with SharedArrayBuffer and Atomics, but message passing is simpler and safer.

☕ Java: worker threads are closer to separate actors or isolated processes than to Java threads: there's no shared heap, so no synchronized and no data races on objects — only on a SharedArrayBuffer, if you opt into one.

Option 3: child processes

node:child_process starts other programs (or other Node scripts) as separate processes: git, ffmpeg, python, a shell command. Each process has its own memory and can use another CPU core.

FunctionUse it for
execFile(file, args)run a program and collect its (small) output. No shell: safe with untrusted arguments.
spawn(file, args)run a program and stream its input/output (large or long-running output).
exec(command)run a shell command line (pipes, globs). Never with user input.
fork(script)run another Node script with a built-in message channel (send/on("message")).

The child's output arrives as stream chunks (Chapter 10): sometimes the three lines come in one chunk, sometimes in two or three, depending on timing. Never assume one data event per line; use readline on child.stdout when you need lines (Exercise 8).

⚠️ Command injection. exec(`convert ${userFileName} out.png`) runs a shell: a "file name" like x.png; rm -rf ~ executes the second command. Use execFile/spawn with an array of arguments, which never go through a shell.

🧠 Analogy: calling another restaurant. A child process is phoning a completely separate restaurant to cook part of the order. It has its own kitchen, staff and rules (memory, even a different language like Python), and you only exchange what goes through the phone line (stdin/stdout or messages). Very isolated, but more expensive to set up than a worker in your own kitchen.

Using all CPU cores for a server

One Node process uses one core for JavaScript. To use an 8-core machine, run several copies of your server. The node:cluster module forks worker processes that share one listening port; the primary distributes incoming connections:

In production, the same effect is often achieved outside Node: a process manager (PM2, systemd), or more commonly containers — several replicas behind a load balancer (Kubernetes, cloud platforms). Either way, processes don't share memory, so keep state (sessions, caches, rate-limit counters) in a database or Redis.

🧠 Analogy: opening several identical branches. Cluster is running several identical branches of the same restaurant, with one host at the shared entrance pointing each new guest to a branch with a free table. Each branch has its own kitchen and its own fridge, so if a guest's coat was left at branch 2, branch 3 doesn't know about it — shared things must live in a common warehouse (the database).

Recap

  • Blocking = the thread can't do anything else. Keep the work per request small; use async APIs in servers, and never mix sync/async on dependent steps.
  • Node has the event loop thread and libuv's worker pool (4 threads; UV_THREADPOOL_SIZE) for fs, dns.lookup, async crypto and zlib.
  • Hidden blockers: exponential regexes (ReDoS), huge JSON.parse, sync crypto/zlib/fs, expensive algorithms.
  • Partition with setImmediate to stay responsive; use worker_threads for parallel CPU work (messages, transfer, pools).
  • child_process runs other programs (execFile/spawn with argument arrays, never exec with user input); cluster or replicas use all cores, with shared state stored outside the processes.
