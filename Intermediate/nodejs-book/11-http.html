Building HTTP Servers

Node became famous for HTTP servers, and the built-in node:http module is what frameworks like Express and Fastify are built on. This chapter follows the life of one HTTP transaction — request in, response out — and builds up to a small JSON API with routing, request bodies, validation, errors, static files and graceful shutdown, using no dependencies.

You will learn

  • The anatomy of an HTTP transaction: method, URL, headers, body, status code.
  • The request (a Readable stream) and the response (a Writable stream).
  • Reading and limiting request bodies, parsing JSON and query strings.
  • Routing by method and path, and returning proper status codes and errors.
  • Serving files with streams, and shutting a server down gracefully.

The anatomy of an HTTP transaction

HTTP is a text-based conversation: the client sends a request, the server sends back a response. Here's what travels over the wire for a request to create a note:

🧠 Analogy: posting a letter at a counter. The request is a letter: the envelope has the method ("please deliver" / "please return"), the address (URL) and stickers with instructions (headers like "fragile", "contains JSON"); the contents are the body. The server is the clerk at the counter: it reads the envelope first, maybe opens the letter, then hands back a receipt with a status code — 2xx "done", 4xx "you made a mistake", 5xx "we made a mistake".

Creating a server

http.createServer(handler) creates a server; the handler runs once per request with two objects: req (an IncomingMessage) and res (a ServerResponse). listen(port) starts accepting connections.

Every example in this chapter follows this pattern so it can run on its own: listen on port 0 (any free port), send requests with fetch (Chapter 12), then close(). In a real app you'd listen(3000) and test with a browser or curl.

  • req.method, req.url (path + query string, no host) and req.headers (lower-case names).
  • res.statusCode + res.setHeader, or both at once with res.writeHead(status, headers).
  • res.write(chunk) any number of times, then res.end() exactly once. Forgetting end() leaves the client waiting until it times out.

Serving files

To send a file, stream it into the response (the response is a Writable). Set the right Content-Type, handle missing files, and — essential — make sure the requested path stays inside your public folder (path traversal, Chapter 9):

Clients like fetch normalise /../ segments before sending, but encoded slashes (%2f) pass through — and decodeURIComponent turns them back into real ../ on the server. That's why the check happens after decoding and joining. In production, static files are usually served by a CDN or a reverse proxy (nginx), but the technique — stream, set headers, guard the path — is the same.

Errors and robustness

  • Wrap each request's work in try/catch (an async handler's rejection is otherwise an unhandled rejection that crashes the server).
  • Return 4xx for client mistakes and 500 for your bugs; log the details on the server, send a generic message to the client.
  • Listen for error on the server (e.g. EADDRINUSE when the port is taken).
  • A client may disconnect mid-response: res.on("close") fires, and writes after that are ignored. Stop expensive work when req.signal-like cues say nobody is listening (Exercise 9).
  • Set timeouts: server.requestTimeout and server.headersTimeout protect against slow-loris attacks (Node sets sensible defaults).

Recap

  • An HTTP transaction is a request (method, URL, headers, body) and a response (status, headers, body).
  • http.createServer((req, res) => …): req is a Readable (read the body with for await, with a size limit), res is a Writable (writeHead, write, exactly one end).
  • Parse req.url with new URL(req.url, base); route on method + path (URLPattern for parameters); 404 vs 405.
  • Validate input, map errors to status codes (4xx client, 500 server), never leak internals, and catch errors in async handlers.
  • Stream files into responses with pipeline and guard against path traversal.
  • Shut down gracefully: server.close(), closeIdleConnections(), a hard timeout, and clean up resources.

Exercise 7 🟡 medium predict

A handler is async (req, res) => { const user = await db.find(id); res.end(user.name); } and db.find rejects for one request. What happens to that request, and to the server? How do you fix it?

Show solution

http doesn't look at the promise the handler returns, so the rejection is unhandled. That request never gets a response (the client hangs), and Node's default for unhandled rejections crashes the whole process — taking every other in-flight request down with it. Fix: try/catch inside the handler (or a wrapper like withErrors(handler)) that sends a 500 response, as in the notes API above.

Exercise 8 🟡 medium headers

Show solution

Without a Content-Length, Node uses chunked transfer encoding, so you can start sending before you know the total size.

Exercise 10 🔴 hard mini-project · playground

Create playground/rate-limit.js: middleware rateLimit({ limit, windowMs }) that allows each client IP at most limit requests per window, answering 429 with a Retry-After header (seconds) when exceeded, and adding X-RateLimit-Remaining to allowed responses. Old windows must not leak memory.

Show solution

This "fixed window" limiter lives in one process's memory; behind a load balancer with several instances you'd keep the counters in a shared store such as Redis. And behind a proxy, the real client IP comes from the X-Forwarded-For header — only trust it if your own proxy sets it.
