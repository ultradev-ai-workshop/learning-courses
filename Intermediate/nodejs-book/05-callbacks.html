Chapter 5 · Asynchronous Work

Callbacks & Asynchronous Flow Control

Before promises existed, all of Node's asynchronous APIs used callbacks, and many still offer them. Understanding callbacks explains how Node really schedules work, why error handling in async code is different, and how to run tasks one after another, all at once, or a few at a time.

You will learn

  • What makes a function asynchronous, and what a callback is.
  • The error-first callback convention used across Node's core APIs.
  • Why try/catch can't catch errors thrown later, and how to handle them instead.
  • The "always async" rule (don't release Zalgo) and process.nextTick.
  • Callback hell, and the three flow-control patterns: series, parallel and limited parallel.

Synchronous vs asynchronous

A synchronous function finishes its work before it returns; the caller waits. An asynchronous function starts work and returns immediately; the result arrives later. Since JavaScript runs on one thread (Chapter 1), the result can't just "appear" in the middle of other code. Instead, you pass a function to call when it's ready: a callback.

🧠 Analogy: the restaurant buzzer. At a busy café you order, get a buzzer and sit down. You don't stand at the counter (blocking); you chat or read until the buzzer goes off. The callback is "what I'll do when the buzzer rings": go and pick up the coffee. And the barista doesn't hand you the cup mid-sentence; you pick it up when you're free — just like the event loop only runs your callback when the current code has finished.

Error-first callbacks

Node's core APIs follow one convention: the callback is the last argument, and it's called with the error first: callback(err, result). If the operation succeeded, err is null; otherwise it's an Error object and the result is missing.

Errors in asynchronous code

A try/catch only catches errors thrown while its block is running. By the time a callback runs, the try has long finished, so an error thrown inside the callback isn't caught by it — it becomes an uncaught exception and crashes the process:

That's exactly why the error-first convention exists: async functions pass errors to the callback instead of throwing them, and you handle them inside the callback. As a last resort, process.on("uncaughtException") can log a crash before exiting, but it's not a way to continue as if nothing happened (Chapter 15).

🧠 Analogy: a safety net that's been packed away. try/catch is a safety net held under you only while you're on the trapeze. The callback is a jump you schedule for tomorrow; by then the net is folded up in the truck. If something can go wrong tomorrow, you have to bring tomorrow's net with you: handle the error inside the callback.

Always async: don't release Zalgo

A function that takes a callback should call it always asynchronously or always synchronously, never "sometimes one, sometimes the other". Asynchronous flow control

When you have many async tasks (download 100 files, process 1000 records), you need to decide how they run relative to each other. The Node.js Learn guide describes three patterns. We'll use one fake task throughout: it "processes" an item in a given number of milliseconds and logs when it starts and ends.

1. In series: one after another

Use series when order matters or each step depends on the previous one (database migrations, steps of a deployment). Total time = the sum of all tasks.

2. Fully parallel: all at once

Start everything immediately and wait for all of them. Total time ≈ the slowest task. Results arrive in completion order, so store them by index to keep the original order. Great for a handful of independent tasks.

3. Limited parallel: a few at a time

Fully parallel can overwhelm things: 10,000 simultaneous HTTP requests may exhaust sockets, memory, or the other server's patience (rate limits). Limited parallel keeps at most limit tasks running; whenever one finishes, the next starts.

🧠 Analogy: checkout lanes. Series is a shop with one till: customers are served one by one. Fully parallel opens a till for every customer at once — fast, but you'd need a hundred cashiers. Limited parallel is a normal supermarket: a few tills, one queue, and whenever a till frees up, the next customer steps forward. Choosing the number of tills is choosing the concurrency limit.

Recap

  • An async function starts work and returns; a callback receives the result later, when the thread is free.
  • Node convention: callback last, called once as callback(err, result); check err first and return.
  • try/catch can't catch errors thrown in later callbacks; pass errors to callbacks instead. Be always-async (process.nextTick), never sometimes-sync.
  • Nested callbacks become "callback hell": use named steps, or better, promises.
  • Flow control: series (one by one), parallel (all at once, store results by index), limited parallel (a fixed number of slots). util.promisify bridges to promises.
