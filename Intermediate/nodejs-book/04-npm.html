npm, Packages & Versions

npm is Node's package manager and the world's largest software registry. This chapter shows how a project is described by package.json, how dependencies are installed and versioned, why the lockfile matters, how scripts automate your workflow, and how to publish a package of your own — safely.

You will learn

  • The three parts of npm: the registry, the CLI and package.json.
  • Installing packages: dependencies vs devDependencies, global installs, npm ci.
  • Semantic versioning and ranges: ^, ~, exact versions and the 0.x rule.
  • package-lock.json: why it exists and why you commit it.
  • npm scripts, node --run, npx, publishing, and supply-chain safety.

What npm is

"npm" means three related things:

  • the registry at npmjs.com, holding millions of open-source packages;
  • the command-line tool npm, installed together with Node, which downloads packages and runs scripts;
  • the package.json file that describes your project: its name, version, dependencies and scripts.

Alternatives such as pnpm and Yarn use the same registry and the same package.json; they differ in how they lay out node_modules and in speed. Everything in this chapter maps directly to them.

🧠 Analogy: a recipe and a receipt. package.json is your shopping list: "flour, any brand from version 2", "eggs, ~ a dozen". package-lock.json is the receipt from the day you shopped: exactly which brand, which batch, which shop. The registry is the supermarket. With only the list, two people can come home with slightly different flour; with the receipt, they buy exactly the same things.

💡 dependencies or devDependencies? Ask: "does the code need this while running in production?" A web framework, a database driver: dependencies. Test runners, linters, TypeScript, build tools: devDependencies. Production installs (npm ci --omit=dev) skip devDependencies, making images smaller and safer.

Semantic versioning

npm packages follow semver: MAJOR.MINOR.PATCH, for example 4.17.21.

  • PATCH (4.17.21 → 4.17.22): bug fixes only.
  • MINOR (4.17 → 4.18.0): new features, backwards compatible.
  • MAJOR (4 → 5.0.0): breaking changes; your code may need updating.

In package.json you write ranges of acceptable versions:

RangeMeansAcceptsRejects
^1.4.2 (npm's default)same major, ≥ 1.4.21.4.2, 1.4.9, 1.9.02.0.0, 1.4.1
~1.4.2same minor, ≥ 1.4.21.4.2, 1.4.91.5.0
1.4.2exactly this version1.4.2everything else
>=1.4.0 <3explicit bounds1.4.0, 2.9.93.0.0
^0.3.1for 0.x, the minor is treated as major0.3.1, 0.3.80.4.0

🧠 Analogy: renting a flat. ^ says "any flat in this building, but not another building" (a new MAJOR is a different building, with different rules). ~ says "any flat on this floor". An exact version says "flat 4B, no substitutes". The 0.x rule exists because a package before 1.0 promises nothing: each minor release may be a whole new building.

The lockfile

Ranges leave room for change: ^1.4.2 installs 1.4.2 today and maybe 1.9.0 next month — on your colleague's machine, or on the production server. package-lock.json records the exact version (and download URL and checksum) of every package in the tree, including dependencies of dependencies.

  • Commit package-lock.json for applications and libraries alike.
  • Use npm ci in CI and production builds: it deletes node_modules and installs exactly what the lockfile says, failing if package.json and the lockfile disagree.
  • Use npm install while developing: it may update the lockfile when you add or change dependencies.

npm scripts

The "scripts" object gives names to commands, so every developer (and the CI server) runs tasks the same way:

  • npm start and npm test are shortcuts; every other script needs npm run name.
  • Arguments after -- are passed on to the script's command.
  • pre/post scripts run automatically around a script with the same name (pretest before test).
  • Scripts run with node_modules/.bin on the PATH, so "lint": "eslint ." finds the locally installed ESLint without npx.
  • node --run runs a script directly, without starting npm: noticeably faster, but it doesn't run pre/post scripts.

⚠️ Pitfall: typos run strangers' code. npx will happily download and run whatever package matches the name you typed. Double-check names (attackers publish look-alike packages, "typosquatting"), and prefer tools listed in your project's devDependencies.

Publishing a package

Publishing makes your package installable by anyone. The steps:

  1. Pick a unique name (or a scope you own: @yourname/slugger) and set "exports", "type", "license" and a README.
  2. Choose what goes into the package with the "files" field (an allow-list), so tests and secrets stay out.
  3. Check the contents with npm pack --dry-run.
  4. Bump the version with npm version patch|minor|major (which also creates a git tag), then npm login and npm publish (--access public for scoped packages).

Only the allow-listed file plus the always-included package.json and README are packed; secret-notes.txt stays home. (We don't run npm publish here, of course.)

☕ Java: npm is Maven/Gradle plus Maven Central. package.json ≈ pom.xml, dependencies ≈ compile scope, devDependencies ≈ test/provided scope, the lockfile ≈ a fully resolved dependency tree with checksums, and npm scripts ≈ Gradle tasks.

Supply-chain safety

Each dependency is code written by strangers that runs with your permissions, and it can pull in dozens of further dependencies. Good habits:

  • Add dependencies deliberately. Check downloads, maintenance and the size of the tree (npm ls --all). Often a few lines of your own code, or a built-in Node feature (Appendix B), are better.
  • Run npm audit to list known vulnerabilities, and keep dependencies updated (npm outdated, Dependabot/Renovate).
  • Install with npm ci from a committed lockfile so nothing changes unexpectedly.
  • Packages may run install scripts (preinstall, postinstall). Consider npm ci --ignore-scripts in CI, and be suspicious of new packages that need them.
  • Use two-factor authentication and trusted publishing (provenance) for packages you publish.

Recap

  • package.json describes the project; npm init -y creates it and npm pkg set edits it.
  • npm install pkg → dependencies; -D → devDependencies. Never commit node_modules.
  • Semver: MAJOR.MINOR.PATCH. ^ allows minor+patch, ~ only patch, and ^0.x only patch-level changes within that minor.
  • Commit package-lock.json and use npm ci for reproducible installs.
  • Scripts: npm start, npm test, npm run x -- args, pre/post hooks; node --run is faster. npx runs package binaries.
  • Publish with "files", npm pack --dry-run, npm version, npm publish; treat every dependency as a security decision.
