Buffers & Streams

Files, network connections and compressed data are sequences of bytes, and they're often far too big to hold in memory at once. Buffers are Node's way to hold bytes; streams are its way to process data piece by piece as it flows. Streams are behind HTTP requests and responses, file copies, compression and process.stdin. This chapter explains both, including the subtle but vital idea of backpressure.

You will learn

  • What a Buffer is: bytes, encodings (UTF-8, hex, base64), and byte length vs string length.
  • Why streams exist, and the four kinds: Readable, Writable, Duplex and Transform.
  • Consuming streams with for await, and connecting them with pipeline (not pipe).
  • Writing your own Transform streams, and object mode.
  • Backpressure: highWaterMark, write() returning false, and drain.

Buffers: raw bytes

Computers store everything as bytes — numbers from 0 to 255. Text is bytes interpreted with an encoding (usually UTF-8); images and zip files are bytes with their own formats. JavaScript strings are text only, so Node adds the Buffer class: a fixed-size sequence of bytes (it's a subclass of Uint8Array).

UTF-8 uses 1 byte for ASCII letters and 2–4 bytes for others: € is 3 bytes. That's why a file's size in bytes and its length in characters differ, and why HTTP's Content-Length must use Buffer.byteLength, not .length.

🧠 Analogy: an egg carton. A Buffer is an egg carton with a fixed number of slots, each holding one byte. The carton doesn't know whether the eggs spell a word or make up a photo; the encoding is the recipe that says how to read them. Read the same carton with a different recipe (hex, base64) and you get a different-looking result from the same eggs.

⚠️ Two buffer pitfalls. subarray (and the older slice) shares memory with the original: copy with Buffer.from(view) when you need independence. And never decode a chunk of UTF-8 on its own: a multi-byte character can be split across two chunks. Use setEncoding("utf8") on a stream, or a TextDecoder with { stream: true }, which keep partial characters until the rest arrives.

Why streams?

Suppose you want to send a 2 GB video file to a client. With readFile, Node reads all 2 GB into memory before sending the first byte. With ten clients at once, that's 20 GB. A stream reads a small chunk (64 KB), sends it, reads the next, and so on: memory stays tiny and the client starts receiving immediately.

🧠 Analogy: water through pipes. readFile is filling a bathtub with all the water first and then carrying the bathtub to its destination — you need a bathtub as big as the whole supply. A stream is a pipe: water flows from the source to the destination continuously, and at any moment only a little is in the pipe. You can also add filters along the pipe (decompress, convert, count) without ever storing all the water.

There are four kinds of streams:

KindData flowsExamples
Readableout of it (a source)fs.createReadStream, process.stdin, an HTTP request on the server
Writableinto it (a destination)fs.createWriteStream, process.stdout, an HTTP response
Duplexboth ways, independentlya TCP socket
Transformin, changed, outzlib.createGzip(), encryption, your own converters

All streams are EventEmitters (Chapter 8): they emit data, end, finish, error and close.

Reading a stream

The modern way to consume a Readable stream is for await: each iteration gives you the next chunk, and the loop ends when the stream ends.

Before async iteration existed, you listened to events: stream.on("data", chunk => …), stream.on("end", …) and stream.on("error", …). You'll see that in older code; it works, but error handling and early stopping are easier with for await (a break destroys the stream).

⚠️ Avoid .pipe() for anything important. The older source.pipe(dest) handles backpressure but not errors: if the source fails, the destination is never closed (leaking a file descriptor or socket), and errors on each stream need their own listener. pipeline was added to fix exactly this.

Backpressure

What happens when the source is faster than the destination? A disk can read at 2 GB/s, but a mobile client receives at 2 MB/s. If Node kept reading at full speed, the unsent data would pile up in memory until the process crashes. Backpressure is the mechanism that slows the producer down to the consumer's speed.

🧠 Analogy: a kitchen sink. The tap (Readable) pours water into a sink (the Writable's internal buffer) that drains through a narrow pipe (the slow destination). The sink has a "fill line" (highWaterMark, 16 KB for byte streams by default). When the water reaches the fill line, the sink shouts "stop!" (write() returns false) and the tap is turned off. When the sink has drained, it shouts "go on!" (the drain event) and the tap opens again. Ignore the shout and the kitchen floods: that's memory exhaustion.

pipeline (and for await + pipeline) handle all of this for you. You only deal with it by hand when you call write() yourself in a loop:

Ignoring the signal queued all 20 KB in memory; respecting it never let the queue go much past the 1 KB fill line. With a 10 GB source instead of 20 KB, that's the difference between a healthy server and a crash.

Web streams

Browsers have their own stream API (ReadableStream, WritableStream), which Node also supports; fetch responses use it (Chapter 12). Convert between the two with Readable.fromWeb() and Readable.toWeb(). Node streams remain the norm for files, sockets and most npm packages.

Recap

  • A Buffer holds bytes; encodings (utf8, hex, base64) turn them into text. Byte length ≠ character length. subarray shares memory.
  • Streams process data in chunks: low memory, fast first byte. Four kinds: Readable, Writable, Duplex, Transform; all are EventEmitters.
  • Read with for await (or readline for lines); write with write/end and wait for finish.
  • Connect stages with pipeline from node:stream/promises: it handles errors, cleanup and backpressure. Avoid bare .pipe().
  • Custom transforms: new Transform({ transform, flush }) or async generator functions; object mode carries JavaScript values.
  • Backpressure: when write() returns false, wait for drain. Ignoring it fills memory.
