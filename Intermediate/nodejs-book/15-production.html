Debugging, Security & Production

Code that works on your laptop still has to survive real users, real attackers and real load. This chapter covers finding bugs with the inspector, diagnosing slowness and memory leaks, the difference between development and production, crash handling and logging, and the security practices recommended by the Node.js team — including Node's permission model.

You will learn

  • Debugging with --inspect, Chrome DevTools or VS Code, and the debugger statement.
  • Diagnosing performance (CPU profiles, flame graphs, event-loop delay) and memory (heap snapshots, leaks).
  • Development vs production: NODE_ENV, structured logging, crash handling, health checks.
  • The main threats to Node apps and their defences: DoS, injection, prototype pollution, timing attacks, malicious packages.
  • The permission model: --permission and --allow-*.

Debugging

console.log debugging works, but a real debugger lets you pause the program, inspect every variable, and step line by line. Node includes the V8 inspector:

  • Chrome: open chrome://inspect and click "inspect" under your Node target. You get the DevTools you know from the browser: Sources, breakpoints, Console, Memory, Performance.
  • VS Code: open a "JavaScript Debug Terminal" and run node app.js — it attaches automatically. Click left of a line number to set a breakpoint.
  • A debugger; statement in your code acts as a breakpoint whenever a debugger is attached (and does nothing otherwise).
  • node inspect app.js is a minimal command-line debugger (c continue, n next, repl to inspect).

🧠 Analogy: a pause button and a magnifying glass. console.log is leaving notes around the house and reading them afterwards. A debugger is pausing time in the middle of the action, walking around the frozen scene with a magnifying glass (every variable, the call stack), then letting time run one step at a time.

⚠️ Never expose the inspector. Anyone who can connect to the inspector port can run arbitrary code in your process. Keep the default 127.0.0.1; for a remote server, use an SSH tunnel. (The Node security guide also warns about DNS rebinding attacks against a locally running inspector — don't leave --inspect on when you're not debugging.)

CPU profiles and flame graphs

A CPU profile samples the call stack thousands of times per second, so the functions where time is spent show up most often. --cpu-prof writes a .cpuprofile file when the process exits; open it in Chrome DevTools (Performance tab) or VS Code:

🧠 Analogy: a flame graph is a city skyline seen from the side. Each building is a function, stacked on the functions that called it; the width of a building is how much time was spent in it. You look for the widest buildings at the top of the skyline: that's where the CPU really burns. Narrow tall towers are deep call chains that don't matter much.

For quick measurements inside code, use performance.now() or console.time, and measure repeated runs: the first run includes V8's warm-up (Chapter 1).

Memory and leaks

JavaScript frees memory automatically with a garbage collector (GC): objects that nothing references anymore are reclaimed. A memory leak in JavaScript means something keeps referencing objects you no longer need, so they can never be collected:

Common leak sources: caches and maps without a size limit or expiry; event listeners added per request and never removed (Chapter 8); timers and intervals never cleared; closures capturing large objects; global variables. Fixes: bounded caches (LRU), WeakMap/WeakRef for metadata about objects owned elsewhere, and always removing listeners and timers.

🧠 Analogy: a cleaner who only throws away what nobody's holding. The garbage collector is a cleaner who may throw away anything that no one is holding onto. A leak isn't the cleaner failing; it's you holding on to things "just in case": a drawer (a global map) that keeps every receipt forever. The fix is to stop holding, not to call the cleaner more often.

To find a leak: take a heap snapshot, let the app run under load, take another, and compare them in Chrome DevTools (Memory tab, "Comparison" view): the object types whose counts keep growing are the suspects, and the "Retainers" panel shows what's holding them.

In production, start with node --heapsnapshot-signal=SIGUSR2 app.js and send kill -USR2 <pid> when you want a snapshot. Use --max-old-space-size=4096 to change the heap limit (in MB) when an app legitimately needs more.

Development vs production

The same code behaves differently in development and production mainly through configuration. By convention, NODE_ENV=production tells libraries to switch to production mode (Express caches templates and hides error details, React builds drop development checks). Node itself ignores it. Don't use it for your own feature switches; use explicit settings instead (LOG_LEVEL, CACHE_TTL…).

Structured logging

Production logs are read by machines first (log search, alerts). Write one JSON object per line, to stdout, with a level, a timestamp, a message and context fields. Libraries like pino do this very fast; the idea fits in a few lines:

A request id in every line lets you follow one request through all your logs. Never log secrets: passwords, tokens, full card numbers, or entire request bodies.

Crash handling

After an uncaught exception, your program is in an unknown state (half-finished operations, locks held, broken invariants). The safe reaction is: log it, finish what you can quickly, and exit, letting a supervisor (systemd, Docker, Kubernetes, PM2) restart a fresh process. Don't try to "keep going".

Health checks and readiness

Platforms decide whether to send traffic to an instance (and whether to restart it) by calling health endpoints: a liveness check ("the process responds") and a readiness check ("dependencies like the database are reachable; I can take traffic"). Return 503 during startup and shutdown so the load balancer drains traffic before you exit (graceful shutdown, Chapter 11).

Prototype pollution

Every ordinary object inherits from Object.prototype. If code copies keys from user input into an object without checking, a key named __proto__ can modify the prototype that all objects share:

🧠 Analogy: changing the master key template. Every new object is cut from the same master key template (the prototype). Prototype pollution is a visitor filling in a form field that quietly edits the template instead of their own key — from then on, every key cut in the building opens the admin office. Defence: never let form fields reach the template (skip those keys), or use containers with no template at all (Map, Object.create(null)).

Passwords and timing-safe comparison

Never store passwords: store a slow, salted hash (scrypt, argon2, bcrypt). And compare secrets in constant time: === stops at the first different character, and attackers can measure that difference to guess a token one character at a time.

The permission model

By default a Node program can do anything its user can: read your SSH keys, start processes, open sockets. The permission model (--permission) turns that around: everything is denied unless you allow it. It limits the damage a compromised dependency can do.

Other switches: --allow-fs-write=…, --allow-child-process, --allow-worker, --allow-addons, --allow-net. The permission model is a seat belt, not a sandbox for running untrusted code: combine it with containers and least-privilege OS users.

🧠 Analogy: a hotel key card. Without the permission model, your app is given the master key to the whole building. With it, the app gets a key card that opens only its own room and the gym (--allow-fs-read=./data). If a thief steals the card (a malicious package runs in your process), they can't get into the other rooms.

Recap

  • Debug with --inspect/--inspect-brk + Chrome DevTools or VS Code; keep the inspector on localhost. Use --enable-source-maps for compiled code.
  • Slow? CPU profile (--cpu-prof, flame graphs) and event-loop delay. Growing memory? Heap snapshots compared over time; look for unbounded caches, listeners and timers.
  • Production: NODE_ENV=production for libraries, structured JSON logs to stdout, crash = log + exit + restart, health/readiness endpoints, graceful shutdown.
  • Defend against DoS, injection, prototype pollution (__proto__ keys), timing attacks (timingSafeEqual), leaking secrets, and risky dependencies. Hash passwords with scrypt.
  • --permission with --allow-fs-read/--allow-fs-write/--allow-child-process… limits what code in the process can do.

Exercises

Exercise 1 🟢 easy debugger

You want to pause a script at its very first line to set breakpoints before anything runs. Which command do you use, and how do you then connect from Chrome?

Show solution

node --inspect-brk script.js. Then open chrome://inspect in Chrome and click "inspect" under the Remote Target (or use "Open dedicated DevTools for Node"). The script is paused on line 1; set breakpoints and press resume.

Exercise 2 🟢 easy classify

Which tool would you reach for first? (a) Memory grows by 50 MB per hour until the process is killed. (b) CPU is at 100% and responses are slow. (c) Responses are slow but CPU is low. (d) The process crashed at night with "FATAL ERROR: Reached heap limit".

Show solution

(a) Heap snapshots taken some time apart, compared. (b) A CPU profile / flame graph. (c) Event-loop delay plus timing of external calls (a slow database or API, or pool exhaustion). (d) --heapsnapshot-near-heap-limit or --report-on-fatalerror to capture data next time, then heap analysis as in (a).

Exercise 3 🟢 easy find the leak

Why does this server's memory grow with every request?

Show solution

seenUsers is a module-level array that only ever grows: each request adds an object (with all its headers) that stays referenced forever, so the GC can never free it. Keep only what you need (a counter, or a bounded structure such as the last 100 entries), or send the data to a log/metrics system instead of keeping it in memory.

Exercise 4 🟢 easy secrets

List three ways an API key can leak from a Node project, and the fix for each.

Show solution

1. Committed in code or in .env → load from environment variables, add .env to .gitignore, rotate any key that was committed. 2. Printed in logs (logging process.env or whole request headers) → log only chosen fields and redact authorisation headers. 3. Shipped in a published npm package → use a "files" allow-list and check npm pack --dry-run. (Also: sent to a browser bundle, or returned in error responses.)

Exercise 6 🟡 medium timing-safe

Write checkApiKey(provided, expected) that compares two strings in constant time. timingSafeEqual throws if the buffers have different lengths, so handle that without leaking the length through an early return... as well as you reasonably can.

Show solution

Hashing both values first gives equal-length buffers, so the comparison takes the same time whatever the input length.

Exercise 7 🟡 medium prototype pollution

A settings endpoint stores user preferences with Object.assign(prefs[userId] ??= {}, body), where prefs = {}. Show how a user id of "__proto__" causes trouble, and fix it with a Map.

Show solution

Map keys are just keys: no inheritance, no special names. Object.create(null) is the other option when you need a plain object.

Exercise 9 🔴 hard permissions

Run a script that writes a report into out/ and reads input from in/ under the permission model, allowing exactly those two folders. Show that writing into in/ is denied.

Show solution

The script can read the project (it needs to load itself and its input) but can write only into out/. A dependency trying to drop a file anywhere else would fail the same way.

Exercise 10 🔴 hard mini-project · playground

Create playground/health.js: an HTTP server with /healthz (always 200 while the process runs) and /readyz (200 only after a fake 30 ms "database connect" and before shutdown starts; 503 otherwise). On SIGTERM, readiness turns 503, the server closes gracefully and the process exits with 0. Simulate the sequence and print the statuses.

Show solution

Liveness says "don't restart me", readiness says "send me traffic". Separating them avoids restart loops while a slow dependency recovers, and lets deploys drain traffic before the old process exits.
