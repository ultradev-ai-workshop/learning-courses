Chapter 8 · Asynchronous Work

The Event Emitter

Servers emit request, streams emit data, processes emit exit. All of them are built on one small class: EventEmitter. Learning it well means understanding half of Node's APIs, and gives you a clean way to decouple parts of your own programs.

You will learn

  • The publish/subscribe idea, and the core API: on, once, emit, off.
  • That emit is synchronous, and what that means for ordering and errors.
  • The special error event, and why an emitter without an error listener can crash your app.
  • Extending EventEmitter in your own classes, and avoiding listener leaks.
  • Bridging to promises: events.once, events.on, and async listeners.

The idea: publish and subscribe

An event emitter is an object that announces things ("an order was paid", "a chunk of data arrived") by name. Other code subscribes to those names by registering listener functions. The emitter doesn't know or care who listens; listeners don't need to know how the event came about.

🧠 Analogy: a radio station. The station (emitter) broadcasts on named channels: "news", "traffic", "weather". Anyone with a radio (a listener) tunes in to the channels they care about. The station doesn't keep a list of who's listening on paper, doesn't wait for anyone, and keeps broadcasting even if nobody's tuned in. Adding a new listener — the traffic app, a delivery company — doesn't change the station at all.

The core API

MethodWhat it does
on(name, fn) (alias addListener)add a listener, called every time
once(name, fn)add a listener that removes itself after the first call
prependListener(name, fn)add to the front of the list
off(name, fn) (alias removeListener)remove that exact function
removeAllListeners(name?)remove all (for one event or all events)
emit(name, ...args)call the listeners synchronously, in order; returns true if there were any
listenerCount(name), eventNames(), listeners(name)inspect

Look at the last two lines: "(lights on)" appears before "1 true". JavaScript evaluates all the arguments of console.log before printing anything, and evaluating door.emit(…) runs the remaining listener right there, inside the call. That's the key fact of the next section: emit runs listeners immediately.

⚠️ off needs the same function. door.off("bell", (who) => …) with a fresh arrow function removes nothing, because it's a different function object. Keep a reference to listeners you'll want to remove.

emit is synchronous

Despite living in an "asynchronous" chapter, emit itself is plain synchronous code: it loops over the listeners and calls each one before returning. Events are a way to organise code, not to make it asynchronous. Any slowness in a listener slows down the emitter.

If a listener throws, the exception propagates out of emit to the code that called it, and later listeners don't run.

The error event

The event name "error" is special. When an emitter emits error and no listener is registered for it, emit throws the error — which, in an asynchronous callback, crashes the process. Streams, sockets and servers report failures this way, so always listen for error on them.

🧠 Analogy: a fire alarm. Normal events are announcements: if nobody's listening, nothing happens. The error event is a fire alarm: if no one is assigned to respond, the alarm escalates to the whole building (the process crashes). Registering an error listener is naming the fire warden.

To observe errors (for logging) without counting as a handler, listen to events.errorMonitor; the error still throws if there's no real error listener.

Listener leaks

Every listener is kept alive by the emitter. Code that adds a listener on every request (and never removes it) slowly fills memory and runs ever more listeners. To catch this, Node prints a warning when more than 10 listeners are added for one event:

The warning goes to stderr, printed on the next tick (after the main code). Fix the code (remove listeners when done, or use once) rather than silencing the warning. Raise the limit with emitter.setMaxListeners(n) only when many listeners are genuinely expected.

Waiting for an event that never comes, with only { signal: AbortSignal.timeout(20) } as a deadline, makes a script simply exit (code 13, "unsettled top-level await") instead of timing out — because nothing else is pending. Async listeners

emit ignores what listeners return. An async listener returns a promise, and if that promise rejects, nobody catches it: an unhandled rejection (Chapter 6). Either catch inside the listener, or create the emitter with { captureRejections: true }, which routes such rejections to the error event:

EventTarget: the web-standard cousin

Node also implements the browser's EventTarget (addEventListener, dispatchEvent), used by web APIs like AbortSignal and WebSocket. Its listeners receive an Event object and there's no special error behaviour. In Node-specific code, EventEmitter is the norm.

🌐 Browser: DOM events (button.addEventListener("click", …)) bubble through the page tree and have preventDefault; EventEmitter events don't bubble and are just function calls.

Recap

  • EventEmitter = publish/subscribe: on/once/prependListener to subscribe, emit to publish, off (same function!) to unsubscribe.
  • emit is synchronous: listeners run in order, inside the call. Exceptions propagate to the emitter.
  • An error event with no listener throws. Always handle error on streams, sockets and servers.
  • Extend EventEmitter to let classes announce their lifecycle without knowing who listens (Observer pattern).
  • More than 10 listeners per event triggers a leak warning; remove listeners you add per request.
  • events.once → promise, events.on → async iterator, captureRejections → async listener errors become error events.

Exercise 9 🔴 hard explain why

A route handler does priceFeed.on("update", (p) => res.write(p)) for every client using server-sent events, and never removes it. After a day, memory is high and there are warnings in the log. Explain what's happening and how to fix it properly.

Show solution

Each request adds a listener to a long-lived emitter. When the client disconnects, the listener (and the closure holding res, the socket and buffers) stays registered forever: a leak, and every update now tries to write to dead connections. Node warns after 10 listeners (MaxListenersExceededWarning). Fix: remove the listener when the response closes — const send = (p) => res.write(p); priceFeed.on("update", send); res.on("close", () => priceFeed.off("update", send)); — or use events.on with a signal that aborts on close. Raise setMaxListeners only after fixing, if hundreds of concurrent clients are expected.
