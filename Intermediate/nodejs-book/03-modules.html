Modules: CommonJS & ES Modules

Real programs are split into many files. Node has two module systems: the original CommonJS (require) and the standard ES modules (import). You'll meet both in every codebase, so this chapter explains how each works, how Node decides which one a file uses, how imports are found, and how the two systems work together.

You will learn

  • CommonJS: require, module.exports vs exports, the module wrapper and the cache.
  • ES modules in Node: named and default exports, file extensions, import.meta, top-level await.
  • How Node chooses: .mjs/.cjs, the "type" field, and syntax detection.
  • Built-in modules with the node: prefix, and how bare specifiers are resolved through node_modules.
  • package.json "exports" and "imports", JSON modules, and CommonJS ↔ ESM interop.

Why modules?

A module is a file with its own private scope. Variables declared in it are invisible to other files unless the module explicitly exports them, and other files explicitly import what they need. That gives you three things: no accidental name clashes, clear dependencies, and code you can reuse.

🧠 Analogy: rooms with a serving hatch. Each module is a room with a closed door. Whatever happens inside (helper functions, temporary variables) stays inside. The only things other rooms can get are what you put on the serving hatch: the exports. Another room asks for an item by name (an import) and gets exactly that, never the mess behind the hatch.

CommonJS: require and module.exports

CommonJS was Node's module system from day one, and much of npm still uses it. A file exports by assigning to module.exports, and imports by calling require(), which returns that value:

require is an ordinary function: it runs synchronously, reads and executes the file the first time, and returns its module.exports. Because it's a function, you can call it anywhere, even inside an if.

The module cache

A module's code runs once. The first require executes it and stores the result in require.cache; every later require of the same file returns the very same object. That makes modules natural singletons:

🧠 Analogy: one copy in the office. The first person who asks for the shared office calendar gets it printed and pinned on the wall. Everyone who asks later is pointed to the same sheet, so a meeting added by one person is seen by all. That's useful (shared config, a connection pool) and surprising if you expected a fresh copy.

ES modules in Node

ES modules (ESM) are the JavaScript standard (ES2015), shared with browsers. They use import/export statements, are always in strict mode, are loaded asynchronously, and support top-level await. New Node projects should use ESM. (The JavaScript Study Book, Chapter 14 covers the syntax in depth.)

⚠️ Pitfall: file extensions. In ESM, relative imports must include the full file name: "./lib/prices.js", not "./lib/prices", and directories don't automatically load index.js. CommonJS guessed extensions for you; ESM (like browsers) doesn't. Forgetting it gives ERR_MODULE_NOT_FOUND.

How Node decides: CommonJS or ESM?

For each file, Node picks a module system using these rules, in order:

  1. .mjs files are always ES modules; .cjs files are always CommonJS.
  2. For .js files, Node looks for the nearest package.json (walking up the folders). "type": "module" means ESM; "type": "commonjs" means CommonJS.
  3. With no "type" field, Node looks at the code: if it contains ESM-only syntax (import/export statements, top-level await, import.meta), it's run as ESM; otherwise as CommonJS. This syntax detection is convenient but slightly slower, so set "type" explicitly.

💡 Recommendation: put "type": "module" in every new project's package.json, use .js files with import/export, and use .cjs only for the occasional file that must be CommonJS (some config files).

Built-in modules and the node: prefix

Node's core modules can be imported with a node: prefix: node:fs, node:path, node:http. The prefix is optional for most of them, but always use it: it's obvious the module is built in, it can't be confused with an npm package of the same name, and some newer modules (node:test, node:sqlite) only work with it.

How imports are found

An import specifier (the string after from) comes in three kinds:

  • Relative: "./utils.js", "../lib/db.js" — resolved from the importing file's folder.
  • Built-in: "node:fs".
  • Bare: "express", "lodash/merge" — a package. Node looks for a node_modules/express folder next to the importing file, then in the parent folder, then the grandparent, all the way up to the root.

🧠 Analogy: looking for a book. To find a book you check the shelf in your room (./node_modules), then the living-room shelf (../node_modules), then the house next door… until you reach the town library at the root. The first copy you find is the one you read. That's why each project has its own node_modules, and why two projects can use different versions of the same package.

You normally never create node_modules by hand: npm install fills it (Chapter 4). We built a tiny package here to see the lookup at work.

Mixing CommonJS and ESM

You'll often have to use a CommonJS package from ESM code, or the other way round:

  • ESM importing CommonJS always works. The module.exports object becomes the default import, and Node also detects most named exports.
  • CommonJS requiring ESM works in current Node versions (require(esm), enabled by default since Node 22.12/20.19), as long as the ES module has no top-level await. Older code uses await import() instead.

⚠️ Pitfall: require of an ES module with top-level await throws ERR_REQUIRE_ASYNC_MODULE, because require must return synchronously. Our settings.js above has a top-level await, so CommonJS code would have to load it with await import("./settings.js").

☕ Java: a module is roughly a class file whose exports are its public members, and "exports" in package.json is like the exports clause of a Java module (module-info.java): unlisted packages stay internal. node_modules is like a per-project Maven repository folder, resolved by walking up the directory tree instead of a classpath.

Recap

  • CommonJS: require() is synchronous and returns module.exports; the wrapper provides require, module, exports, __filename, __dirname. Don't reassign exports.
  • Modules run once and are cached, so they behave like singletons.
  • ESM: import/export, full file extensions, import.meta.dirname/filename, top-level await, live bindings.
  • .mjs = ESM, .cjs = CommonJS, .js follows "type" in the nearest package.json (else syntax detection). Prefer "type": "module".
  • Bare specifiers are searched in node_modules folders up the tree; "exports" controls a package's public entry points, "imports" gives you # aliases.
  • ESM can import CommonJS (default = module.exports); CommonJS can require ESM without top-level await.

Exercise 4 🟢 easy explain

Why does exports = { a: 1 } export nothing, while module.exports = { a: 1 } works?

Show solution

exports is a parameter of the module wrapper function that initially points to the same object as module.exports. require returns module.exports. Reassigning exports only changes the local parameter to point somewhere else; module.exports still refers to the original empty object.

Exercise 5 🟡 medium predict the output

Three files, run with node main.js in a "type": "module" project. What's printed?

Show solution

Imports run depth-first before the importing module's own code: main needs b, which needs a, so a runs first, then b, then main. a runs only once even though two modules import it.
