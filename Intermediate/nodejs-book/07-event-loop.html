Timers & the Event Loop

The event loop is the heart of Node: it decides when each of your callbacks runs. Knowing its phases explains puzzles like "why did setImmediate run before setTimeout(…, 0)?" and "why did my server stop responding?". This chapter covers timers, the loop's phases, process.nextTick, promise microtasks and setImmediate.

You will learn

  • The timer functions: setTimeout, setInterval, setImmediate, clearing them, and unref().
  • The six phases of Node's event loop and what runs in each.
  • The two "jump the queue" lanes: the process.nextTick queue and the promise microtask queue.
  • setImmediate vs setTimeout(fn, 0), and when their order is guaranteed.
  • How the loop decides when the program exits, and how starvation happens.

Timers

Node provides the same timer functions as browsers, plus setImmediate:

  • Extra arguments after the delay are passed to the callback ("Ana" above).
  • The delay is a minimum, not a promise: the callback runs at the earliest after that time, when the loop gets to it. A delay of 0 becomes 1 ms.
  • In Node, timers return Timeout objects (not numbers as in browsers), with extra methods like unref() and refresh().

The event loop's phases

When you run node app.js, Node first executes your file from top to bottom (registering timers, starting I/O). Then it enters the event loop, which goes round and round through a fixed series of phases. Each phase has a queue of callbacks; the loop runs that phase's callbacks, then moves on:

  1. timers: callbacks of setTimeout/setInterval whose time has come.
  2. pending callbacks: a few system operations deferred from the previous round (e.g. some TCP errors).
  3. idle, prepare: internal housekeeping.
  4. poll: retrieve new I/O events and run their callbacks (file reads, incoming connections, data on sockets). If there's nothing else to do, the loop waits here for I/O, but not past the next timer's due time.
  5. check: setImmediate callbacks — they run right after the poll phase.
  6. close callbacks: close events, such as socket.on("close", …).

🧠 Analogy: a bus on a circular route. The event loop is a single bus driving round a loop with six stops. At each stop it picks up only the passengers (callbacks) waiting at that stop, then drives on. "Timers" is the stop for people whose alarm has rung; "poll" is the big station where people arriving from I/O wait, and where the bus parks if nobody is around; "check" is right after it, for people who said "take me on the very next round, after the station" (setImmediate). There's only one bus, so if one passenger takes ages to board (a slow callback), everyone at every stop waits.

nextTick and microtasks: jumping the queue

Two special queues aren't phases at all. They're drained after every single callback (and after the main script), before the loop continues:

  1. the process.nextTick queue, drained first;
  2. then the promise microtask queue: .then/.catch/.finally callbacks, code after await, and queueMicrotask.

⚠️ setTimeout(fn, 0) vs setImmediate in the main module: no guaranteed order. We used a 5 ms timer above. With 0 ms (really 1 ms), the timer may or may not be due when the loop reaches its first timers phase — it depends on how quickly the process started. Run it ten times and you'll see both orders. Inside an I/O callback, the order is guaranteed (see below).

A twist: ES modules run inside a promise

An ES module's top-level code is itself evaluated as part of a promise job (that's what makes top-level await possible). So when the module body finishes, Node is still inside the microtask queue: the promise callbacks queued by the module run first, and only then is the nextTick queue processed. Inside callbacks (timers, I/O, event handlers) both module systems behave the same: nextTick queue first, then promises. The lesson: never write code whose correctness depends on the relative order of nextTick and promise callbacks.

🧠 Analogy: finishing your sentence. Microtasks are like "finish what you're saying before you hand over the microphone". After any callback, Node first handles everything pushed with nextTick (the urgent whisper from the stage manager), then all the promise reactions (the end of your sentence), and only then lets the bus move on to the next stop.

Microtasks can starve the loop

Because these queues are drained completely — including entries added while draining — a nextTick or promise callback that keeps scheduling another one never lets the loop move on. Timers and I/O starve:

With an infinite chain, the timer would never run at all. setImmediate doesn't have this problem: immediates scheduled while running the check phase wait for the next round, so I/O gets its turn.

setImmediate vs setTimeout(0)

Inside an I/O callback you're in the poll phase. The next phase is check, so setImmediate always runs before a timer, which must wait for the next round's timers phase:

💡 The names are backwards. process.nextTick runs immediately (before the loop moves at all), while setImmediate runs on the next tick (iteration) of the loop. The Node docs admit it; it's too late to rename them. When in doubt, prefer setImmediate or queueMicrotask; use nextTick only when you specifically need "before anything else".

When does Node exit?

After each round, the loop checks whether anything could still produce a callback: active timers, open servers or sockets, pending file operations, child processes, ref'd handles. If nothing remains, the process exits (with process.exitCode). A promise that's pending forever does not keep Node alive by itself:

Recap

  • Timer delays are minimums. setInterval repeats regardless of how long callbacks take; chain setTimeout for gaps. unref() stops a timer from keeping the process alive.
  • The loop's phases: timers → pending → idle/prepare → poll (I/O, waits here) → check (setImmediate) → close.
  • After every callback: drain process.nextTick, then promise microtasks (at the top level of an ES module, promises come first). Recursive ones can starve the loop.
  • Inside I/O callbacks, setImmediate always beats setTimeout(0); in the main module, their order isn't guaranteed.
  • Node exits when no timers, handles or I/O remain; a pending promise alone doesn't keep it alive.

Exercise 9 🔴 hard explain why

Why is replacing every setImmediate in a library with process.nextTick a dangerous "optimisation" for a server? Show the problem with a tiny example.

Show solution

nextTick callbacks run before the loop moves on, so a recursive chain of them never lets the poll phase run: incoming requests, timers and I/O completions all starve. setImmediate callbacks added during the check phase wait for the next round, so I/O gets a turn in between.
