The Command Line: Run, REPL, Input & Output

Every Node program starts from a terminal. This chapter covers the ways to run code, the interactive REPL, writing output (and where it goes), reading input from arguments, the keyboard and pipes, environment variables, and the exit codes that tell other programs whether yours succeeded.

You will learn

  • Running files, one-liners (-e, -p), shebang scripts and --watch mode.
  • Using the REPL: special commands, _, multi-line input and the editor mode.
  • stdout vs stderr, console formatting, util.inspect, colours with util.styleText.
  • Reading input: process.argv, util.parseArgs, readline and piped stdin.
  • Environment variables, --env-file, and exit codes with process.exitCode.

Watch mode

While developing, node --watch app.js runs the file and restarts it whenever the file or anything it imports changes. It replaces the old nodemon tool for most uses. Use --watch-path=src to watch a specific folder.

The REPL

Run node with no arguments to start the REPL (Read–Eval–Print Loop): type an expression, Node evaluates it and prints the value. It's the fastest way to try an API.

Things worth knowing:

  • Declarations like const langs = … print undefined (omitted above). An error prints Uncaught … and the REPL keeps going.
  • _ holds the last result, _error the last error. Press Tab to autocomplete (try langs. + Tab), ↑ for history.
  • Unfinished input (an open { or () continues on a ... line.
  • Dot-commands: .help, .editor (paste or type several lines, finish with Ctrl+D), .save file.js, .load file.js, .exit (or Ctrl+D, or Ctrl+C twice).
  • Core modules are preloaded: type fs.existsSync(".") without importing anything. Top-level await works too.

Writing output

stdout and stderr

Every process has three standard streams: stdin (input), stdout (normal output) and stderr (errors and diagnostics). console.log and console.info write to stdout; console.error and console.warn write to stderr. In a terminal both appear on screen, but they can be redirected separately:

🧠 Analogy: two mail slots. A program has two outgoing mail slots: one for the letters you meant to send (stdout) and one for complaints (stderr). Whoever runs the program can collect them in different boxes — save the letters to a file, show the complaints on screen. That's why a well-behaved tool prints its result to stdout and everything else (progress, warnings, errors) to stderr: piping its output into another program then passes only the real data.

Formatting with console

The console.assert message went to stderr, so it isn't in this (stdout) output. Other useful methods: console.time("label")/console.timeEnd("label") to measure durations, and console.trace() to print a stack trace.

Writing without a newline, and colours

process.stdout.write writes exactly the string you give it, with no newline added. That's how progress indicators update a line in place. For colours, Node has util.styleText built in; it automatically drops the colour codes when the output isn't a terminal (for example when it's piped to a file) or when the NO_COLOR environment variable is set.

In a terminal the last two lines are green and bold red; captured into this book's checker (not a terminal) they're plain text. Libraries like chalk did this before styleText existed (Appendix B).

Environment variables

Environment variables are named string settings that a process inherits from whoever started it (your shell, Docker, a hosting platform). Node exposes them as process.env. They're the standard place for configuration that changes between machines: ports, database URLs, API keys, NODE_ENV.

🧠 Analogy: notes on the fridge. Environment variables are like notes stuck on the fridge before you leave the house: "dinner at 8", "the key is under the mat". Everyone who comes in (every child process) can read them, nobody has to ask, and the same family (program) behaves differently in different houses (machines) because the notes are different. You don't rewrite the family; you change the notes.

.env files

Typing variables on every command is tedious, so projects keep them in a .env file. Node can load it itself — no dotenv package needed:

Variables already set in the real environment win over the file. Use --env-file-if-exists when the file is optional, or call process.loadEnvFile(".env") from code.

⚠️ Pitfalls: every value is a string, so process.env.DEBUG = false stores "false", which is truthy. Add .env to .gitignore and commit a .env.example with dummy values instead. And never print the whole process.env in logs: it contains secrets.

Exit codes

When a process ends it reports a number to whoever started it: 0 means success, anything else means failure. Shells, CI pipelines and tools like npm test rely on it. Node exits with:

  • 0 when the program simply runs out of work;
  • 1 when an exception or promise rejection is never handled;
  • whatever you set with process.exitCode = n (exit normally, later) or process.exit(n) (exit immediately).

⚠️ Prefer process.exitCode over process.exit(). process.exit() stops the process right away, even if output is still being written or a file is half-saved. Setting exitCode lets Node finish its pending work and then exit with your code.

☕ Java: process.argv.slice(2) is String[] args, process.env is System.getenv(), process.exit(n) is System.exit(n), and console.error is System.err.println.

Recap

  • Run code with node file.js, node -e/-p, shebang scripts, and node --watch while developing. The REPL is for quick experiments (.editor, _, Tab).
  • Results go to stdout (console.log), diagnostics to stderr (console.error). util.inspect controls object formatting; util.styleText adds colours only on terminals.
  • Input: process.argv (strings!), util.parseArgs for options, readline/promises for questions, readline + for await for piped stdin.
  • Configuration comes from process.env (strings or undefined); load .env files with --env-file.
  • Exit code 0 means success. Set process.exitCode rather than calling process.exit().

Exercise 10 🔴 hard explain why

A deploy script runs node migrate.js && node server.js. migrate.js catches every error and logs it with console.log. Last night a migration failed, but the server started anyway on a broken database. Explain the two mistakes and fix them.

Show solution

&& runs the second command only if the first exits with 0. Because migrate.js caught the error and finished normally, it exited with 0, so the server started. Fix 1: after logging, set process.exitCode = 1 (or rethrow). Fix 2: log errors with console.error so they go to stderr, where deploy logs and monitoring look for problems.
