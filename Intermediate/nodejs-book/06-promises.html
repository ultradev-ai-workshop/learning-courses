Chapter 6 · Asynchronous Work

Promises & async/await in Node

Promises turned Node's callback pyramids into flat, readable code, and async/await made asynchronous code look almost synchronous. This chapter focuses on how to use them in Node: the promise-based core APIs, running work in sequence or in parallel, handling errors and unhandled rejections, cleaning up, and cancelling work with AbortSignal.

You will learn

  • What a promise is, and the promise versions of Node's core modules (fs/promises, timers/promises…).
  • async/await with try/catch/finally, and cleaning up resources.
  • Sequential vs parallel: Promise.all, allSettled, any, race, and a concurrency limit.
  • Unhandled rejections: why Node exits, and the "floating promise" bug.
  • Cancellation and timeouts with AbortController, AbortSignal.timeout and AbortSignal.any.

Promises in one page

A promise is an object that stands for a result that isn't ready yet. It starts pending and settles exactly once: fulfilled with a value, or rejected with an error. You react to it with .then()/.catch(), or wait for it with await inside an async function (or at the top level of an ES module).

🧠 Analogy: a parcel tracking number. When you order online you don't get the parcel, you get a tracking number. You can hand that number to someone else, ask "tell me when it arrives" (then), or wait at the door (await). The parcel either arrives (fulfilled) or the shop says it's lost (rejected), and once that's decided it never changes. A callback, by comparison, is you handing the shop your house key and hoping they use it only once.

The JavaScript Study Book, Chapter 12 covers promises from the language side (chaining, combinators, microtasks). Here we use them with Node's APIs.

async/await and errors

Inside an async function, await pauses that function until the promise settles: a fulfilled value is returned, and a rejection is thrown as an exception. So ordinary try/catch/finally works again — the big win over callbacks.

One try covered both the asynchronous failure (missing file) and the synchronous one (bad JSON). Note the pattern: handle the errors you expect and can recover from; wrap and rethrow the rest with a cause so the original error isn't lost.

Sequential vs parallel

🧠 Analogy: making breakfast. You can boil the kettle, wait for it, then toast the bread, wait, then fry the egg. Or you start all three and wait for the slowest. await in a row is the first way; Promise.all the second. Only cook sequentially when a step needs the previous one (you can't butter toast that isn't toasted).

⚠️ Promise.all doesn't cancel the others. When one promise rejects, all rejects immediately, but the other operations keep running in the background. If they must stop, give them an AbortSignal (below).

Unhandled rejections

If a promise rejects and nothing ever handles it (no catch, no await inside a try), Node treats it like an uncaught exception: it prints the error and exits with code 1. That's deliberate — silently ignored failures are worse than crashes.

⚠️ Floating promises. Calling an async function without await (or .catch) is the most common source of unhandled rejections — and of code that "finishes" before its work is done. Linters can flag it (@typescript-eslint/no-floating-promises). If you really want fire-and-forget, attach a handler: sendEmail(user).catch(logError).

You can observe unhandled rejections globally with process.on("unhandledRejection", (reason, promise) => …), typically to log them before exiting. Don't use it to keep running as if nothing happened.

Cancellation and timeouts with AbortSignal

A promise can't be cancelled from outside. Instead, Node's async APIs accept an AbortSignal: an object that says "please stop". You create one with an AbortController and call controller.abort(), or use AbortSignal.timeout(ms), which aborts by itself. The same signal works for fetch, fs.readFile, timers/promises, events.once, streams and child processes.

🧠 Analogy: the "cancel order" button. An AbortController is the remote control and its signal is the receiver you give to every worker. Pressing the button doesn't magically stop work; each worker that holds a receiver checks it and stops itself. That's why you must pass the signal to every operation you want to be cancellable.

Your own async functions should accept a signal too, and pass it down. AbortSignal.any([a, b]) combines signals: abort when the user cancels or a timeout expires.

Recap

  • A promise is a placeholder that settles once. Use the core /promises APIs (fs/promises, timers/promises, stream/promises) and events.once.
  • await turns rejections into exceptions: one try/catch covers sync and async failures; finally releases resources; wrap errors with cause.
  • Independent work → Promise.all/allSettled/any; many items → a worker pool with a limit. all doesn't cancel the rest.
  • Unhandled rejections crash Node (exit 1). Never leave floating promises: await or .catch them.
  • Cancel with AbortController, time out with AbortSignal.timeout, combine with AbortSignal.any, and pass { signal } down to every operation.
