1. Why Tailwind CSS instead of regular CSS?

Regular CSS asks you to name things and write rules in a separate file; Tailwind gives you a fixed vocabulary of small classes that you combine directly in the markup. That changes how a project feels after a few months more than on day one:

Problem with hand-written CSS in a growing projectHow Tailwind handles it
Naming: .card, .card-inner, .card__title--large… every element needs a name, and naming conventions drift.No names for styling. You name components (in React, templates), not every element.
The stylesheet only grows: nobody dares delete a rule because something somewhere might use it.CSS is generated from what's in your files. Delete the markup and its styles are gone in the next build (Chapter 1).
Changes have side effects: editing a shared class can break pages you didn't look at.Classes are on the element. Changing them changes that element only.
Inconsistent values: 17 different greys and paddings of 13, 14 and 15 px.Values come from a theme scale by default (Chapter 8); one-offs are possible but stand out as [13px].
Context switching: jumping between HTML and CSS files to style one button.You style while you write markup; states, breakpoints and dark mode are prefixes (Chapters 5–7).
Responsive and state styles need separate media queries and selectors.md:flex, hover:bg-sky-700, dark:text-white on the element.

2. When is regular CSS the better choice?

  • Content you can't add classes to: Markdown, CMS output, emails generated by other tools. (In a Tailwind project, the Typography plugin or a few element styles in @layer base cover this; Appendix B.)
  • A tiny site with one stylesheet and no build step, where a build tool is more work than the CSS.
  • Complex, one-of-a-kind visuals: an intricate animation, an art-directed landing page, a CSS drawing. Writing them in a CSS file (or a CSS module) is clearer than 40 utility classes.
  • A team that already has a strong design system in CSS and no problems with it.
  • Learning CSS itself: write plain CSS first, so you understand what the utilities do.

It's not either/or. Every Tailwind project can contain normal CSS; the docs show how to mix them (Chapter 11).

3. Isn't this just inline styles?

No. Inline styles (style="…") can't do hover, focus, media queries, dark mode or pseudo-elements; they don't use a design scale; and the same declarations are repeated on every element. Utilities are real CSS classes, defined once, with variants for every state and breakpoint, and values from your theme. Chapter 1 compares them in the browser. That said, inline styles are still right for runtime values, set as CSS variables (Chapter 3).

4. Doesn't it make the HTML ugly and hard to read?

Long class lists look noisy at first, and that's a fair criticism. In practice:

  • You stop reading them as noise after a week, the same way you stopped seeing <div> soup.
  • Prettier sorts them in a standard order and wraps long lines (Chapter 4).
  • Repeated groups move into components, so most files contain short lists (Chapter 10).
  • The alternative isn't "clean HTML": it's clean HTML plus a CSS file you must keep in sync. Total complexity is usually lower with Tailwind.

5. Do I need to know CSS before learning Tailwind?

Yes, at least the basics: the box model, display and position, flexbox and grid, selectors and the cascade. Tailwind doesn't hide CSS; it gives you shorter names for it. justify-between only makes sense if you know justify-content. This book explains the CSS behind each utility, but if flexbox is new to you, spend a day with MDN's CSS layout guides first or alongside Chapter 13.

6. How big is the CSS file? Is it slow?

Small. Tailwind generates only the classes you use (Chapter 1), so a typical site ships 10–30 KB of CSS before compression and a few KB after. The file grows with the number of different utilities, not the number of pages, so it levels off as the project grows. There's no runtime JavaScript (except the Play CDN, which is for experiments only). The capstone's two pages are fully static (Chapter 19).

7. What about separation of concerns?

The classic advice was "HTML for structure, CSS for presentation". In component-based apps, the more useful split is by component: a button's markup, behaviour and styles belong together, and changing it shouldn't require editing three files. Tailwind follows that split. If you need the old separation (a theme that restyles the same HTML completely), you can still use semantic CSS variables (Chapter 7) or component classes (Chapter 10).

9. Tailwind vs CSS Modules, Sass and CSS-in-JS?

  • CSS Modules solve naming collisions by scoping class names per file, but you still write and maintain the CSS. They combine well with Tailwind for the occasional complex component.
  • Sass adds variables, nesting and mixins to CSS. Modern CSS has variables and nesting built in, and Tailwind v4 isn't designed to be used with Sass preprocessors.
  • CSS-in-JS (styled-components, Emotion) writes CSS in JavaScript, often at runtime. It has fallen out of favour with React Server Components, which can't use runtime style injection. Tailwind generates static CSS at build time and works everywhere.

10. Do I need React or another framework?

No. Tailwind works with plain HTML (most of this book uses plain HTML and the CLI), server-side templates (Django, Rails, Laravel, Spring/Thymeleaf), and every front-end framework. A component system makes reuse easier, which is why Tailwind is especially popular with React, Vue and Svelte (Appendix C), but it isn't required.

11. Why does this book use v4 when my tutorial uses v2 or v3?

v4 is the current version (4.3 at the time of writing). It's much faster, configured in CSS, needs no content list, and uses modern CSS features. v2 is from 2020–2021 and no longer maintained; v3 gets security fixes only. Most class names are the same, but setup and some names changed. Appendix A translates old code, and the official upgrade tool migrates v3 projects automatically.

12. Are there ready-made components?

Tailwind itself ships no components. The Tailwind team sells Tailwind Plus (formerly Tailwind UI), a large set of professionally designed components and templates, and maintains Headless UI, free unstyled accessible components (menus, dialogs, tabs) for React and Vue that you style with utilities. Many free community libraries exist too (for example shadcn/ui for React, daisyUI as a plugin with Bootstrap-like class names). Building your own first, as this book does, teaches you what those libraries do.

13. Why doesn't my dynamic class name work?

Because Tailwind reads your files as text at build time and never runs your code. `bg-${color}-500` never appears as a complete class name, so nothing is generated. Write complete names and choose between them ({ red: "bg-red-500", green: "bg-green-500" }[color]), use a CSS variable for truly dynamic values, or safelist with @source inline() (Chapter 11).

14. Is Tailwind good for accessibility?

Tailwind is neutral: it styles whatever HTML you write. It does make good practice easy: sr-only for screen-reader text, focus-visible: for keyboard focus, motion-reduce: for reduced motion, forced-colors: for high-contrast mode, and aria-* variants that style state from accessibility attributes (Chapters 5, 12, 17). You still need semantic HTML, labels, and enough colour contrast.

15. How do teams keep Tailwind code consistent?

  • One theme file with the design tokens; avoid arbitrary values in reviews (Chapter 8, 9).
  • Prettier with prettier-plugin-tailwindcss and a CI check (Chapter 4).
  • Shared components for buttons, inputs, cards (Chapter 10, Appendix C).
  • The IntelliSense extension for completion and linting (Chapter 4).

16. How long does it take to learn?

If you know CSS, you'll be productive in a day or two: learn the naming pattern, the spacing scale and variants (Chapters 1–6), and look up the rest as you go. Becoming fluent, so you think in utilities and know when to extract components or customise the theme, takes a few weeks of real use. This book's 19 chapters, 220 exercises and the capstone are designed to get you there.
