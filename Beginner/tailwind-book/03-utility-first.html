Styling with Utility Classes

This chapter follows the docs' Styling with utility classes page. You'll learn how to read a utility's name, how the spacing scale and colour palette work, what Preflight changes, how to deal with conflicting classes and duplication, and when to reach for inline styles instead. These rules are the same for every utility in the rest of the book.

You will learn

  • How to build a component from utilities, step by step.
  • How utility names are made: property, value, and the spacing scale.
  • What variants (prefixes like hover: and md:) are, in a first look.
  • What Preflight resets, and why your h1 looks like plain text.
  • Conflicting classes, the ! important modifier and the prefix() option.
  • How to handle repetition and when to use inline styles.

🧠 Analogy: utilities are LEGO bricks. Hand-written CSS is like carving a new piece of wood for every toy: possible, but each toy needs its own piece and its own name. With bricks, you build anything from a fixed set of standard shapes, and when you change your mind you move bricks around instead of carving again.

How utility names work

Most names follow the pattern property-value, often with a side or axis in between:

PatternExamplesMeaning
{property}-{value}p-4, text-lg, opacity-50padding 4 steps, large text, 50% opacity
{property}{side}-{value}pt-2, mx-auto, border-b-2padding-top, horizontal margin, bottom border
{property}-{color}-{shade}bg-sky-500, text-red-700a palette colour, 50 (lightest) to 950 (darkest)
{color}/{opacity}bg-black/50the colour at 50% opacity
keywordflex, hidden, italic, underlineone fixed declaration
negative-mt-2, -rotate-6the negative value

Sides use the same letters everywhere: t top, r right, b bottom, l left, x left and right, y top and bottom, s start and e end (which follow the text direction).

The spacing scale

Spacing utilities (padding, margin, gap, width, height, inset…) are multiples of one variable, --spacing, which is 0.25rem (4 px) by default. Any number works, including halves:

So p-4 is 1 rem (16 px) and p-7 is 1.75 rem (28 px). In v3 there was a fixed list of steps; in v4 every number is allowed, because the value is computed from --spacing. Change that one variable (Chapter 8) and the whole layout gets tighter or looser.

The colour palette

The default theme has 26 colour names, each with 11 shades from 50 to 950: red, orange, amber, yellow, lime, green, emerald, teal, cyan, sky, blue, indigo, violet, purple, fuchsia, pink, rose, five greys (slate, gray, zinc, neutral, stone) and four muted tones added in v4.2 (mauve, olive, mist, taupe), plus black and white. Any colour utility takes any of them: bg-, text-, border-, outline-, fill-, stroke-, decoration-, shadow-…

Chapter 8 covers the palette in detail, including opacity (bg-sky-500/25) and adding your own colours.

A first look at variants

A variant is a prefix that makes a utility apply only in some condition. The syntax is variant:utility, and you can stack several:

Each variant becomes plain CSS: a pseudo-class (:hover), a media query (width >= 48rem), or both nested. Notice that hover: is wrapped in @media (hover: hover), so touch screens, which have no real hover, don't get "stuck" hover styles after a tap. Chapters 5 to 7 cover states, breakpoints and dark mode.

Preflight: why everything looks plain

The first time you use Tailwind, headings and lists look like body text. That's Preflight, the reset in the base layer. It's built on modern-normalize and makes every element start from zero, so the only styles are the ones you add:

  • Headings have no size or weight of their own: style them with text-2xl font-bold. The docs explain why: it stops you from picking a heading level for its looks instead of its meaning.
  • Lists have no bullets: add list-disc pl-5 when you want them.
  • Images are display: block and never wider than their container (max-width: 100%).
  • Every element uses box-sizing: border-box, so padding and borders are included in the width you set.
  • Borders are reset to 0 solid, so border alone gives a 1 px solid line in the current text colour.

Conflicting classes

What if one element has two classes that set the same property?

Both are grid. The order in the class attribute never matters in CSS; what matters is the order of the rules in the stylesheet, and Tailwind writes .grid after .flex. Don't rely on this: put only one of two conflicting classes on an element. If you need to switch between them, do it in your template logic ({isGrid ? "grid" : "flex"}) or with variants (flex md:grid).

The important modifier

When you really need a utility to win over other CSS, such as a third-party stylesheet, add ! at the end of the class:

The first p loses for two reasons: the <style> rule is not in a layer (unlayered styles beat layered ones), and #widget p is more specific anyway. !important beats both. Use it rarely; it's a sign that two systems are fighting. (In v3 the ! went at the start, !text-sky-700; v4 still accepts that but the docs now put it at the end.)

Managing duplication

The most common worry is repetition: "if I have ten buttons, do I repeat these eight classes ten times?" The docs' answer, in order of preference:

  1. Often it's fine. Repetition inside one file is easy to fix with multi-cursor editing or find-and-replace.
  2. Use a loop. A list of items rendered by a template loop or .map() has the classes written once.
  3. Use a component. In React, Vue, Svelte, Blade, Jinja… make a Button component; the classes live in one place (Appendix C).
  4. Use a custom class with @apply or plain CSS for small, truly global things that aren't components in your template language, like a .btn used in Markdown (Chapter 10).

When to use inline styles

Inline styles are still the right tool for values that come from data at runtime, such as a colour picked by a user or a progress percentage from an API. Tailwind can't generate a class for a value it never saw in your files. The cleanest pattern sets a CSS variable inline and uses it from a utility with the (--var) shorthand:

The classes stay fixed (so Tailwind can find them), and only the values change.

⚠️ Never build class names from pieces. class="bg-{{ color }}-500" or `text-${size}` produce names that don't appear in your files, so Tailwind never generates them. Write the full names and pick one: { red: "bg-red-500", green: "bg-green-500" }[color]. Chapter 11 explains how detection works.

Recap

  • Build components by adding utilities to plain markup; read classes as property-value pairs.
  • Spacing utilities are multiples of --spacing (0.25 rem); any number, including halves, works.
  • 26 colour names × 11 shades (50–950), usable with any colour utility; /50 sets opacity.
  • Variants (hover:, md:, dark:) apply a utility conditionally and can be stacked.
  • Preflight resets headings, lists, buttons and images; you style everything explicitly.
  • Avoid conflicting classes; use ! sparingly; prefix(tw) avoids name clashes.
  • Remove duplication with loops and components first; use CSS variables + inline styles for runtime values; never build class names from pieces.

Exercises

Exercise 1 🟢 easy compute

With the default --spacing, how many pixels are p-3, mt-10, gap-0.5 and w-72?

Show solution

Each step is 4 px: p-3 = 12 px, mt-10 = 40 px, gap-0.5 = 2 px, w-72 = 288 px.

Exercise 2 🟢 easy sides

Write classes for: padding on the left and right of 1.5 rem; margin-bottom 0.5 rem; a 2 px border on the top only.

Show solution

px-6 mb-2 border-t-2.

Exercise 3 🟢 easy Preflight

You write <h2>Settings</h2> and it looks like normal text. Is something broken? How do you make it look like a heading?

Show solution

Nothing is broken: Preflight removes default heading styles. Add classes, for example class="text-xl font-semibold mb-2".

Exercise 4 🟢 easy variants

Write a link that is blue-600, underlined on hover, and blue-400 in dark mode.

Show solution

<a class="text-blue-600 hover:underline dark:text-blue-400">

Exercise 5 🟡 medium build

Build an "alert" box: rounded corners, a light red background, dark red text, 1 rem padding, and a 1 px red border. Use only utilities.

Show solution

<div class="rounded-md border border-red-300 bg-red-50 p-4 text-red-800">Something went wrong.</div> Any shades that keep the text readable are fine.

Exercise 6 🟡 medium fix the bug

This React code doesn't colour the badges: <span className={`bg-${color}-100 text-${color}-800`}> with color being "green" or "red". Why? Rewrite it.

Show solution

Tailwind scans the source text and never sees bg-green-100, only the template pieces, so it generates nothing. Use full names: const styles = { green: "bg-green-100 text-green-800", red: "bg-red-100 text-red-800" }; then className={styles[color]}.

Exercise 7 🟡 medium runtime values

A user picks their profile colour from a colour picker, and it's stored as a hex string. Show how to use it as the background of their avatar while keeping Tailwind classes.

Show solution

Set a CSS variable inline and use it from a utility: <div class="size-10 rounded-full bg-(--avatar)" style="--avatar: #e11d48"> (in React: style={{ "--avatar": user.color }}).

Exercise 8 🟡 medium playground

In chapters/03/index.html of the playground, build the "Build finished" notification step by step, adding one group of classes at a time (layout, spacing, shape, colour, shadow). Then add a second notification with an amber border for a warning.

Show solution

Copy the chapter's markup; for the warning swap border-emerald-500 for border-amber-500 and change the text. If you find yourself copying it a third time, that's the moment to make it a component or a loop.

Exercise 9 🔴 hard cascade

Explain the result of the "important modifier" example: why does #widget p { color: red } beat text-sky-700, and why does text-sky-700! beat it? Would it still beat a color: red !important written in an unlayered stylesheet?

Show solution

Normal declarations: unlayered styles beat layered ones, and the id selector is more specific, so red wins. !important declarations are a higher level of the cascade than normal ones, so text-sky-700! wins. Between two !important declarations the layer order is reversed: important declarations in layers beat unlayered important ones. So text-sky-700! (in the utilities layer) would still win against an unlayered color: red !important.

Exercise 10 🔴 hard design

You have the same 12-class "primary button" in 40 places across a server-rendered site (Jinja templates). Describe two ways to remove the repetition and which one you'd choose.

Show solution

(1) A Jinja macro or include, {% macro button(label) %}<button class="…">{{ label }}</button>{% endmacro %}: classes in one place, still utilities, and the macro can take variants. (2) A .btn-primary class defined with @apply in @layer components (Chapter 10). Prefer the macro: it's a real component that also holds the markup (icon, attributes, accessibility). Use @apply only when markup can't be shared, such as in Markdown content.
