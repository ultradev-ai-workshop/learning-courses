Chapter 7 · Core Concepts

Dark Mode

Most operating systems let people choose a dark theme, and many sites follow it. In Tailwind, dark: is a variant like hover:: dark:bg-slate-900 applies only in dark mode. By default it follows the system setting. This chapter shows that default, how to switch to a manual toggle with a class or data attribute, how to remember the user's choice, and a cleaner way to theme large apps with CSS variables. The dark screenshots were taken with Chrome emulating a dark system theme.

You will learn

  • How dark: works with the system's prefers-color-scheme.
  • How to switch to a class-based or data-attribute toggle with @custom-variant.
  • A three-way toggle (light, dark, system) with localStorage and no flash.
  • The scheme-* utilities for scrollbars and form controls.
  • Theming with semantic colour variables instead of dark: on every element.

The default: follow the system

Out of the box, dark: is @media (prefers-color-scheme: dark). No JavaScript, and it switches the moment the user changes their system setting.

📝 The page background in the dark screenshot is still white: the example only styled the card. For a full dark page, style <body> or <html> too, for example <body class="bg-white dark:bg-slate-950">.

🧠 Analogy: the default dark: is a light sensor on a streetlamp: it switches by itself when the environment changes. A class-based toggle is a light switch on the wall: your page decides, usually because the user flipped it. Many sites wire the switch to "auto" by default, so it behaves like the sensor until someone touches it.

Light, dark, or system: a three-way toggle

A good toggle offers three choices and remembers them. The docs' approach: store "light" or "dark" in localStorage, or nothing for "system", and set the class in a script in <head>, before the page is painted:

⚠️ Avoid the flash. If you set the class from a script at the end of <body> or after your framework loads, the page first paints in light mode, then flips: a white flash for dark-mode users. The small inline script in <head> runs before the first paint. Frameworks have helpers for this (for example next-themes for Next.js).

Scrollbars and form controls: scheme-*

Browsers draw scrollbars, checkboxes and date pickers themselves. The CSS color-scheme property tells them which palette to use. Tailwind's utilities are scheme-light, scheme-dark, scheme-light-dark (follow the system), and scheme-normal:

Theming with variables instead of dark: everywhere

Writing bg-white dark:bg-slate-900 on hundreds of elements gets repetitive, and changing a dark colour means editing every one. Large apps usually define semantic colours (named for their role, not their look) as CSS variables that change in dark mode, then register them as theme colours with @theme inline (Chapter 8):

The markup says bg-surface text-ink once, and the CSS decides what those are in each mode. This is the pattern create-next-app uses for its bg-background and text-foreground colours, and the one the capstone uses.

Recap

  • dark: is a variant; by default it's @media (prefers-color-scheme: dark).
  • For a manual toggle, redefine it: @custom-variant dark (&:where(.dark, .dark *)); (or a [data-theme=dark] selector).
  • Set the class on <html> with an inline script in <head> that reads localStorage, to avoid a flash.
  • Offer light, dark and system; "system" removes the stored choice.
  • scheme-dark makes native controls and scrollbars dark too.
  • For big apps, define semantic colour variables that change in dark mode and register them with @theme inline.

Exercises

Exercise 1 🟢 easy write

Write classes for a card that is white with dark text in light mode, and zinc-900 with zinc-100 text in dark mode.

Show solution

bg-white text-zinc-900 dark:bg-zinc-900 dark:text-zinc-100

Exercise 2 🟢 easy default

Without any configuration, what decides whether dark: classes apply?

Show solution

The user's operating system or browser setting, through the media query prefers-color-scheme: dark.

Exercise 3 🟢 easy config

Write the CSS line that makes dark: depend on a dark class instead.

Show solution

@custom-variant dark (&:where(.dark, .dark *)); after @import "tailwindcss";.

Exercise 4 🟢 easy logos

Show logo-dark.svg only in dark mode and logo.svg otherwise, using two <img> tags and classes.

Show solution

<img src="logo.svg" class="dark:hidden"> and <img src="logo-dark.svg" class="hidden dark:block">.

Exercise 5 🟡 medium flash

A site sets the dark class in a React useEffect. Dark-mode users complain about a white flash on every page load. Explain why and fix it.

Show solution

useEffect runs after the first paint, so the page paints with light styles first. Move the decision into a small inline <script> in <head> (it runs before the body is painted), as shown in the three-way toggle.

Exercise 6 🟡 medium playground

In chapters/07/, the CSS file uses the class strategy. Add the three-way toggle, choose Dark, reload, and check DevTools → Application → Local Storage. Then choose System. What changes in storage?

Show solution

After Dark, theme = "dark" is stored and the page stays dark after reload. After System, the theme key is removed and the page follows the OS setting again.

Exercise 7 🟡 medium semantic colours

Add a semantic colour muted (slate-500 in light, slate-400 in dark) to the "Theming with variables" example, so text-muted works.

Show solution

Add --muted: oklch(55.4% 0.046 257.417) to :root, --muted: oklch(70.4% 0.04 256.788) in the dark block, and --color-muted: var(--muted); in @theme inline. (You can also write var(--color-slate-500) as the value, since the palette variables are available.)

Exercise 8 🟡 medium specificity

Why does the class strategy use &:where(.dark, .dark *) rather than .dark &?

Show solution

Two reasons: :where() adds zero specificity, so dark: utilities don't become stronger than other utilities; and the list includes the element itself (.dark), so you can put dark on the very element that has dark: classes, not only on an ancestor.

Exercise 9 🔴 hard both

You want dark: to apply when the user picked dark explicitly (data-theme="dark" on <html>), or when no choice was made (data-theme missing) and the system is dark. Write the @custom-variant using a block with @slot.

Show solution

@custom-variant dark { &:where([data-theme=dark], [data-theme=dark] *) { @slot; } @media (prefers-color-scheme: dark) { &:where(:root:not([data-theme]), :root:not([data-theme]) *) { @slot; } } }. @slot marks where the utility's declarations go; a block can contain several rules.

Exercise 10 🔴 hard design

A design system has 12 semantic colours, each with a light and dark value. Compare "use dark: on every element" with "semantic variables + @theme inline" for adding a third theme, "high contrast", later.

Show solution

With dark: everywhere, a third theme needs a new variant and a third class on every element (hc:bg-black…), touching all markup. With semantic variables, add one more CSS block ([data-theme=hc] { --surface: #000; … }) and no markup changes. Variables scale; per-element dark: is fine for small sites.
