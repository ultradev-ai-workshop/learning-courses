Appendix A

Coming from v2 or v3

A lot of Tailwind code online, in tutorials, Stack Overflow answers and older projects, was written for v2 (2020–2021) or v3 (2021–2024). Much of it still works, but the setup, the configuration and some class names changed in v4. This appendix maps old code to new, shows the automatic upgrade tool, and lists the renamed and removed utilities, each checked against Tailwind 4.3.5.

You will learn

  • How to recognise v2 and v3 code at a glance.
  • How setup and configuration moved from tailwind.config.js into CSS.
  • How to run the official upgrade tool, and how to keep a JavaScript config with @config.
  • Which utilities were renamed or removed, and which defaults changed.

The upgrade tool

For a v3 project, Tailwind provides an automatic migration. It updates dependencies, converts the config file into CSS, rewrites renamed classes in your templates, and updates the PostCSS or Vite setup. Run it in a clean Git branch so you can review the diff (it needs Node.js 20 or newer):

For v2 projects, upgrade to v3 first with the official v3 upgrade guide, or treat it as a rewrite of the setup: install v4 fresh (Chapter 2), move your theme into @theme, and fix renamed classes with the tables below.

Renamed utilities

v4 made the scales consistent: the "bare" name is no longer the default size, and every scale has an -xs step. Old names that still exist now mean something different, so a blind find-and-replace in the wrong order would shift everything by one size:

⚠️ The border colour change is the one people notice. In v3, class="border" drew a light grey line. In v4 it draws a line in the text colour, often black. The upgrade tool adds a compatibility base style; in new code, always name a border colour.

Extra notes for v2 code

  • v2 had separate @tailwindcss/jit and a mode: 'jit' switch; v3 made just-in-time the only mode, and v4 kept it.
  • v2's purge option became v3's content, and v4 removed it.
  • v2 used transform and filter classes to enable transforms and filters (transform rotate-45). Since v3 they're unnecessary; v4 still accepts them, but they do nothing useful.
  • v2's colour palette differs from v3's and v4's (v4 moved to OKLCH and slightly more vivid colours). Hex values copied from v2 designs won't match bg-blue-500 exactly.
  • Arbitrary values (top-[117px]) only arrived with JIT; v2 code without JIT uses the config for every custom value.

Recap

  • @tailwind directives, purge/content and tailwind.config.js mark old code.
  • v4 setup: @import "tailwindcss";; config: @theme, @custom-variant, @plugin, @source.
  • npx @tailwindcss/upgrade migrates v3 projects; @config keeps a JavaScript config working.
  • Scales shifted: v3 shadow/rounded/blur = v4 -sm; v3 -sm = v4 -xs.
  • *-opacity-* is gone (use /50); outline-none → outline-hidden; ring is 1 px.
  • Borders default to currentColor; buttons have a default cursor; hover: needs a hover-capable device.

Exercises

Exercise 1 🟢 easy identify

A tutorial's CSS file has three @tailwind lines and its config has purge. Which version is it?

Show solution

v2 (purge was renamed content in v3).

Exercise 2 🟢 easy rewrite

Rewrite for v4: bg-white bg-opacity-75 shadow rounded flex-shrink-0.

Show solution

bg-white/75 shadow-sm rounded-sm shrink-0

Exercise 3 🟢 easy dark mode

Convert darkMode: 'class' to v4.

Show solution

@custom-variant dark (&:where(.dark, .dark *)); in the CSS file.

Exercise 4 🟢 easy border

After upgrading, card borders look black instead of light grey. Why, and what's the cleanest fix in your templates?

Show solution

v4's default border colour is currentColor. Add an explicit colour wherever border is used: border border-gray-200.

Exercise 5 🟡 medium config

Convert to CSS: theme: { extend: { colors: { primary: { 500: '#3b82f6', 700: '#1d4ed8' } }, borderRadius: { card: '1.25rem' } } }.

Show solution

@theme { --color-primary-500: #3b82f6; --color-primary-700: #1d4ed8; --radius-card: 1.25rem; }

Exercise 6 🟡 medium order

You must replace v3's shadow-sm and shadow by hand. In which order do you do the two find-and-replace operations, and why?

Show solution

First shadow-sm → shadow-xs, then shadow → shadow-sm (as a whole word). The other order would turn the new shadow-sm classes into shadow-xs too.

Exercise 7 🟡 medium safelist

A v3 config has safelist: ['bg-red-500', 'bg-green-500']. What's the v4 equivalent?

Show solution

@source inline("bg-{red,green}-500"); (the safelist option isn't supported by @config).

Exercise 8 🟡 medium playground

The playground has chapters/appendix-a/old.html, a page written for v3. Fix every class so it looks as the comment at the top describes.

Show solution

Use the "Renamed utilities" and "Changed defaults" tables. Typical fixes: bg-opacity-* → slash opacity, shadow → shadow-sm, outline-none → outline-hidden, explicit border colours, cursor-pointer on buttons.

Exercise 9 🔴 hard plan

Plan the upgrade of a large v3 app that must also support Safari 15 users for another year.

Show solution

Don't upgrade yet: v4 targets Safari 16.4+. Stay on v3.4 (still maintained as v3-lts), clean up in the meantime (remove *-opacity-*, add explicit border colours, replace flex-shrink), and run npx @tailwindcss/upgrade in a branch when the browser requirement allows, reviewing the diff and visual changes page by page.

Exercise 10 🔴 hard explain

Explain why v4 changed outline-none, and what the old behaviour was useful for.

Show solution

v3's outline-none set a 2 px transparent outline, not outline: none, so Windows high-contrast mode (which makes transparent colours visible) still showed a focus indicator. The name was misleading, so v4 renamed that behaviour to outline-hidden and made outline-none really set outline-style: none.
