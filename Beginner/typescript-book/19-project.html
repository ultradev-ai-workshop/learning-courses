Capstone: Learn TypeScript the Official Way

The best way to learn TypeScript is the way the TypeScript team recommends adopting it: take working JavaScript and make it typed, one safe step at a time. This capstone follows the official guides Migrating from JavaScript and JS Projects Utilizing TypeScript. You start from a small library-loans app in plain JavaScript, with passing tests and three hidden bugs, and finish with a strict, tested TypeScript package that publishes its own types. Every command output on this page was produced by running it.

You will learn

  • The official migration path: checkJs → JSDoc → .ts files → strict → declarations.
  • How the compiler finds bugs that passing tests missed.
  • How every chapter of this book shows up in one real codebase.
  • How to structure, build, run and test a TypeScript project with tsc and node:test.

📝 Follow along in the playground. Clone coderhop-learning/typescript-playground (see Using the Playground). capstone-start/ is where you begin; reference/ is the finished version shown at the end of this chapter. Try each step yourself before reading the solution.

🧠 Analogy: renovating a house you live in. You don't knock it down and rebuild: you fix one room at a time while the family keeps living there. TypeScript is designed for this. JavaScript keeps running at every step, because emit never depends on type errors.

Step 0: it works… doesn't it?

The test passes, yet the scripted day goes wrong twice. Member m3 is a guest, allowed one loan, but the third line lent them a second book. Then returning L2 three days late crashes. The test only covered an on-time return. Keep these in mind and let the compiler find them.

Step 1: let TypeScript check the JavaScript

The first official step changes no code at all. Add a tsconfig.json that includes the JavaScript files (allowJs), checks them (checkJs) and writes nothing (noEmit). Start loose (strict: false) so the first report is short:

Even without a single annotation, TypeScript infers types from the code. The errors all have one cause: default parameter values become the parameter's type. onEvent = () => {} makes onEvent "a function with no parameters", and filter = () => true the same. The code that passes them arguments then looks wrong. The fix is a JSDoc comment that says what the parameter really is:

Now look at how much is still unknown. Running the same check with --strict counts the places where TypeScript had to fall back to any:

36 untyped parameters. In a big codebase you would now add JSDoc types file by file and turn on noImplicitAny. Plain JavaScript with JSDoc is a perfectly good final state for some projects (Chapter 17). Here we go on to TypeScript files.

Step 2: rename to .ts and write the shapes down

Rename each file (git mv src/fees.js src/fees.ts keeps the history), and put the shapes the code already uses into one types module. You don't invent anything: you write down what the JavaScript was doing. Here are the first converted files:

Only the type annotations were added; the bodies are the JavaScript ones (loans.ts shows just the two methods that matter here). Now compile:

Four errors, three bugs, and two of them are the ones you saw in step 0:

  1. options is possibly undefined: lateFee(lateDays) is called without options, and the body reads options.perDay. That's the crash. Fix: a destructured parameter with defaults, { perDay = 25, cap = 500 }: FeeOptions = {} (Chapter 5).
  2. memberID doesn't exist: a typo, so l.memberID === memberId was always false, every member always had zero open loans, and the limit never applied. That's the guest's second book. Fix: memberId.
  3. Object is possibly undefined: policyFor crashes for an unknown member id. Nobody had hit it yet. Fix: return undefined for unknown members and handle it in borrow (Chapter 4).

💡 This is the real payoff of TypeScript. The tests passed. The code "worked". The compiler found every bug just from the shapes, before any user did, and it will keep finding new ones like them on every change.

☕ Java / C#: this is the step a Java or C# developer expects to be first: declaring the types. In TypeScript it can come after the code works, because types are optional and erased. That's why a gradual migration is possible at all; you can't half-convert a Python program to Java.

Step 3: strict, and a better model

With the bugs fixed, turn on everything that keeps them from coming back: strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitOverride, and the tool-friendly verbatimModuleSyntax, isolatedModules and erasableSyntaxOnly (Chapter 18). Recap

  • The official path is gradual: checkJs on unchanged JavaScript, JSDoc where inference falls short, .ts files with written-down shapes, then strict and extras.
  • Types found three bugs that the tests missed: a crash, a broken business rule, and a crash nobody had hit yet.
  • After the migration, model the domain: brands, unions, as const tables, validated input, Result values.
  • Build with tsc, test the output with node:test, and publish .d.ts files with declaration.

Exercise 2 🟢 easy playground

Add a "vip" member type with 20 loans for 60 days. Which files did you have to change?

Only LOAN_POLICY in types.ts: add vip: { maxLoans: 20, days: 60 }. MemberType is derived from it, and parseMember checks against it, so everything else follows automatically.

Exercise 3 🟢 easy playground

Show solution

Add "audiobook" to the FORMATS tuple. "cassette" is rejected by parseBook with unknown format: cassette, because isFormat reads the same tuple.

Exercise 5 🟡 medium feature

Add renew(loanId, today): Result<Loan>: it extends the due date by the member's loan period, at most twice, and never for an overdue loan. Add a "renewed" event to LoanEvent. What does the compiler tell you to update?

Show solution

Add renewals: number to Loan (the compiler then points at borrow, where new loans must set renewals: 0) and { type: "renewed"; loanId: LoanId; due: Date } to LoanEvent. In renew, return { ok: false, … } when statusOf(loan, today) !== "active" or loan.renewals >= 2; otherwise update(loanId, { due: addDays(loan.due, policy.days), renewals: loan.renewals + 1 }) and emit the event. Any switch over event.type with a never check now fails until it handles "renewed".

Exercise 6 🟡 medium feature

Add a search command to the CLI: node dist/src/cli.js search austen prints matching titles. Use process.argv and keep the scripted day as the default.

Show solution

At the top of cli.ts: const [command, ...args] = process.argv.slice(2);. If command === "search", print catalog.search(args.join(" ")).map((b) => b.title) and process.exit(0). With noUncheckedIndexedAccess, command is string | undefined, which is exactly right.

Exercise 7 🟡 medium types

Write a switch over LoanEvent that turns each event into a sentence for an e-mail, with an exhaustiveness check. Then add the "renewed" event from exercise 5 and watch it fail.

Show solution

function sentence(e: LoanEvent): string { switch (e.type) { case "borrowed": …; case "returned": …; case "fined": …; default: { const x: never = e; return x; } } }. Adding a member to the union makes the never assignment an error that names the missing case (Chapter 4).

Exercise 8 🟡 medium tooling

Run the reference with Node's type stripping instead of tsc: what has to change in the imports, and which compiler options make tsc still produce correct .js files?

Show solution

Node loads .ts files directly, so imports must name them: "./fees.ts". Turn on allowImportingTsExtensions (so the checker accepts those paths) and rewriteRelativeImportExtensions (so tsc rewrites them to .js in its output). The code is already erasable, so no other change is needed. Run with node src/cli.ts on Node 22.18+ or 23.6+ (older 22.x versions need --experimental-strip-types).

Exercise 9 🔴 hard design

Add reservations: a member can reserve a book that has no copies left; when a copy is returned, the first reservation becomes a loan automatically. Model it with types first: which new types, events and Result reasons do you need?

Show solution

A ReservationId brand, interface Reservation { id; bookId; memberId; createdOn }, a second InMemoryRepository<Reservation>, events { type: "reserved"; … } and { type: "fulfilled"; reservationId; loanId }, and reasons such as "already reserved" and "book is available, borrow it instead". In giveBack, after the return, look up the oldest reservation for that book and call borrow for it; emit "fulfilled" if it succeeds. Writing the types first shows every place that must change before you write any logic.

Exercise 10 🔴 hard refactor

Replace the hand-written parseBook with a schema from a validation library (Zod, Valibot or ArkType), deriving the Book type from the schema. What do you gain, and what has to stay hand-written?

Show solution

For example with Zod: const BookSchema = z.object({ id: z.string().regex(/^b\d+$/).transform(BookId), title: z.string(), …, format: z.enum(FORMATS) }); type Book = z.infer<typeof BookSchema>;. You gain one source of truth for the runtime check and the type, and better error messages. Business rules (loan limits, fees) and the brand constructors stay hand-written. Note that this adds a runtime dependency, which the reference avoids on purpose.
