Declaration Files & JSDoc

Most of the code you call isn't yours: npm packages, Node itself, the browser. TypeScript knows their types from declaration files (.d.ts), which hold types but no code. This chapter follows the Handbook's Declaration Files and JavaScript sections: how to read, consume, generate and write .d.ts files, and how to type-check plain JavaScript with JSDoc comments.

You will learn

What is a declaration file?

A .d.ts file describes the shape of JavaScript that exists somewhere else. It has only type information: no function bodies, no values. The declare keyword says "this exists at runtime; trust me about its type":

You already use declaration files all the time: lib.es2024.d.ts describes Array, Map and Promise; @types/node describes process and node:fs; lib.dom.d.ts describes document.

🧠 Analogy: a menu without a kitchen. A declaration file lists every dish (function), what goes into it (parameters) and what comes out (return type). The cooking happens in the JavaScript file. TypeScript only ever reads the menu.

Where types come from

  1. Bundled with the package. Many packages ship .d.ts files and point to them with a "types" field (or exports conditions) in their package.json. Nothing to install.
  2. DefinitelyTyped. For packages written in plain JavaScript, the community maintains types in the DefinitelyTyped repository, published as @types/name. Install them as a dev dependency: npm install -D @types/node.
  3. The lib option. Built-in JavaScript and DOM APIs come from the lib.*.d.ts files inside the typescript package, chosen by target and lib.

A package with no types at all gives an error under strict ("Could not find a declaration file for module…"). Install its @types package if one exists, or write a small declaration yourself (below).

💡 The types compiler option limits which @types packages are loaded globally. Since TypeScript 6.0 it defaults to [] (none), so a Node project needs "types": ["node"], as tsc --init shows in a comment. Imported packages are always found, whatever types says.

Type-checking JavaScript with JSDoc

You can get most of TypeScript's checking without changing your files to .ts. Add // @ts-check at the top of a .js file (or turn on checkJs for the whole project), and write types in JSDoc comments. Your editor and tsc then check it, and the file still runs unchanged in Node:

The JSDoc tags you'll use most:

TagMeans
@type {T}the type of a variable
@param {T} name, @param {T} [name]a parameter, an optional parameter
@returns {T}the return type
@typedef {object} Name + @propertya named object type (like an interface)
@template Ta type parameter
@import { Book } from "./types.js"import a type into a JS file (TS 5.5+)
@satisfies {T}, @ts-expect-errorsatisfies, and "the next line must have an error"

Recap

  • .d.ts files contain only types; declare describes values that exist at runtime.
  • Types come from the package itself, from @types/* (DefinitelyTyped), or from lib. Set "types": ["node"] for Node globals.
  • declaration (+ emitDeclarationOnly) generates .d.ts from TS, or from JS with JSDoc.
  • A .d.ts next to a .js file, or a declare module "pkg", types untyped code.
  • Follow the Do's and Don'ts: lowercase primitives, void callbacks, unions over overloads.
  • // @ts-check / checkJs + JSDoc gives type checking in plain .js files.

Exercise 9 🔴 hard explain

Why do the types you install from @types/express have their own version number, and what can go wrong when it doesn't match the express version you use?

Show solution

DefinitelyTyped types are written separately from the library, by different people, so they're versioned and published separately (usually matching the library's major and minor version). If they drift, the types may describe functions that don't exist in your version, or miss new ones: the code type-checks but fails at runtime, or works but doesn't type-check. Pin both together and upgrade them together.
