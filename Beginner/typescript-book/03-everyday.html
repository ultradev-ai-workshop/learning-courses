Everyday Types

These are the types you'll write every day. Following the Handbook's Everyday Types page, this chapter goes from primitives and arrays to object types, unions, type aliases, interfaces, literal types and type assertions. Most of TypeScript is these pieces combined.

You will learn

  • The primitives string, number, boolean (and why not String).
  • Arrays, any, and annotations on functions, including async functions.
  • Object types with optional properties.
  • Union types, type aliases and interfaces, and how to choose between the last two.
  • Literal types, as const, type assertions and the non-null ! operator.

The primitives

⚠️ Lowercase only. String, Number and Boolean (capital letter) are the wrapper objects you get from new String("x"). You almost never want them as types. Always write string, number, boolean.

☕ Java / C#: there is no int, long, float or double. JavaScript has one number type (a 64-bit floating-point value, like double) plus bigint for arbitrarily large integers (123n). char doesn't exist either: a character is a string of length 1.

Arrays

An array of numbers is number[]. The generic spelling Array<number> means exactly the same thing (Chapter 8 explains generics).

[number] is something else: a tuple with exactly one element. Tuples are in Chapter 6.

any means "don't check this". You can call anything on it, assign it anywhere, and TypeScript stays quiet:

Type aliases

Writing the same object type or union twice is tedious. A type alias gives any type a name. It's only a name: it doesn't create a new, different type.

Interfaces

An interface is another way to name an object type. For objects, it works almost the same as a type alias:

The main differences:

interfacetype
Describesobject shapes (and classes)any type: unions, primitives, tuples, functions, objects
Extend withextends& (intersection)
Re-open later to add fields✅ yes (declaration merging)❌ no: a duplicate name is an error

💡 Which one? The Handbook's advice: use interface for object shapes until you need something only type can do (a union, a mapped type…). Many teams simply pick one style. Both are fine; be consistent.

☕ Java / C#: a TypeScript interface is closer to a C# record shape or a Java interface with only getters than to a "contract with behaviour". It describes data and methods, but there's no implements required (structural typing), and it disappears completely at runtime: you can't write x instanceof Book when Book is an interface.

Type assertions

Sometimes you know more than the checker. A type assertion value as Type tells it to treat the value as that type. It's not a cast: nothing is checked or converted at runtime.

TypeScript refuses assertions between types that can't possibly overlap, like string to number. (You could force it with as unknown as number, but that's lying to the compiler.)

⚠️ An assertion on JSON.parse output is a promise you make, not a check. If the JSON is missing pages, your code still believes it's there. Chapter 4 shows how to check data properly.

Literal inference: let vs const

A const can't change, so its type is the literal. A let can, so it gets the wider type. Object properties are like let: they can be reassigned.

Recap

  • Use lowercase string, number, boolean; arrays are T[] or Array<T>.
  • any switches checking off and spreads; prefer unknown when you don't know a type.
  • Annotate parameters and returns; async functions return Promise<T>; callbacks get contextual types.
  • Object types list properties; ? marks optional ones.
  • Unions mean "one of these". Narrow them with runtime checks before using member-specific features.
  • type names any type; interface names object shapes, can extends, and can be merged.
  • Literal types and as const pin exact values. as and ! are unchecked promises to the compiler.

Exercise 10 🔴 hard design

Write a type Price that is either { kind: "free" } or { kind: "paid"; cents: number }, and a function show(p: Price) that prints "free" or "12.99". Why does checking p.kind let you read p.cents?

Show solution

Each member has a different literal in kind, so checking it tells TypeScript which member you have. This is a discriminated union, one of the most useful patterns in TypeScript. Chapter 4 covers it in depth.
