Appendix B

Tooling & TypeScript 7

TypeScript is a language, a compiler and a language service that powers your editor. This appendix covers the tools around it as of TypeScript 7.0: installing and running the compiler, running .ts files directly, editors, linting, testing and formatting, plus what changed with the native compiler and where TypeScript 6 still matters. It follows the Handbook's TypeScript Tooling in 5 minutes, Integrating with Build Tools and Nightly Builds pages.

💡 Facts on this page change often. Version numbers and tool support were checked in November 2026. Before you rely on one, check the TypeScript blog and each tool's release notes.

You will learn

  • What TypeScript 7 changed, and the @typescript/typescript6 package.
  • Three ways to run TypeScript: tsc + Node, Node's type stripping, and tsx.
  • Editor support, tsc --watch and the language service.
  • Linting with typescript-eslint, testing with node:test or Vitest, formatting with Prettier.
  • Picking versions: typescript@latest, @next, and @types/node.

TypeScript 7: the native compiler

TypeScript 7.0 is the same type checker, ported from TypeScript (running on Node) to Go (a native binary). The project was known as "Project Corsa", and its previews shipped as the @typescript/native-preview package with a tsgo command. Since 7.0, it is the typescript package and its command is tsc.

Where TypeScript 6 still matters

Linters (typescript-eslint), some framework template checkers (Vue, Svelte, Angular) and other tools use TypeScript's API in-process. Until 7.x ships a stable API, they keep using TypeScript 6. The TypeScript team publishes 6.0 under a separate name so both can be installed side by side:

At the time of writing, typescript-eslint declares support for typescript versions below 6.1. Check your tools' docs for how they pick up TypeScript 6.

Running TypeScript

WayType-checks?SupportsGood for
tsc, then node dist/app.js✅everythinglibraries, servers, this book

npx tsx app.ts❌almost everything (uses esbuild)development, scripts
bundler (Vite, esbuild, webpack)❌everything the bundler supportsweb apps

Node's type stripping is on by default from Node 22.18 and 23.6 (earlier 22.x versions need --experimental-strip-types). Node only deletes the types; it doesn't check them and doesn't read tsconfig.json. That's why the "erasable syntax only" rule exists: no enums, namespaces or parameter properties (Chapters 13 and 18), and imports must name the .ts file. Whichever runner you use, keep tsc --noEmit in your editor, pre-commit hook and CI.

🧠 Analogy: the spell checker and the printer. Type stripping, tsx and bundlers are fast printers: they print whatever you give them. tsc --noEmit is the spell checker. You want both, and you don't want the printer waiting for the spell checker on every keystroke.

Editors and watch mode

  • VS Code has TypeScript support built in, powered by the same compiler. Use the workspace's TypeScript version ("TypeScript: Select TypeScript Version" → "Use Workspace Version") so the editor matches tsc.
  • Other editors (JetBrains IDEs, Neovim, Zed, Helix) talk to TypeScript through the Language Server Protocol.
  • tsc --watch (-w) re-checks on every save; with --noEmit it's a fast error panel in your terminal. tsc -b -w watches project references.
  • The online Playground lets you pick a version, see emitted JavaScript and .d.ts output, and share a link to an example.

Linting, testing, formatting

Linting

The compiler checks types; a linter checks patterns (unused variables, floating promises, any creeping in). The standard is typescript-eslint, with type-aware rules such as no-floating-promises and no-unsafe-assignment:

Faster alternatives written in Rust (Biome, Oxlint) cover many rules without the TypeScript API, and are adding type-aware rules.

Testing

  • node:test (built in): compile with tsc and run node --test "dist/test/**/*.test.js" (the capstone does this), or run .ts test files directly with type stripping.
  • Vitest and Jest (with a TypeScript transform) run .ts tests directly. Vitest also has expectTypeOf for type tests (Chapter 10).

Formatting

Prettier (or Biome) formats TypeScript, including types. Let the formatter own style and the linter own correctness, so they never argue.

Choosing versions

  • npm install -D typescript installs the latest stable release; pin it in package.json (this book uses 7.0.2). TypeScript doesn't follow semantic versioning strictly: a minor release (7.0 → 7.1) can add new errors. Upgrade on purpose and read the release notes.
  • npm install -D typescript@next gives the nightly build, useful to try upcoming features (Handbook: Nightly Builds).
  • @types/node: match the major version of the Node.js you run (for example @types/node@22 for Node 22), not the newest.

☕ Java / C#: the split mirrors javac vs your IDE's incremental compiler, Checkstyle/SpotBugs (or Roslyn analyzers) for linting, and JUnit/xUnit for tests. The big difference is that running the code doesn't require the type checker at all; in Java you can't run what doesn't compile.

A removed option, and what to use instead

Removed options are errors that name the replacement. Upgrading to 6.0 first shows the same list as deprecation warnings, which is the gentler path.

Finding a slow type

--extendedDiagnostics prints counts and timings. The one-line Pin type added about 11,000 types to the program (most of them come from the built-in libraries, which are the same in both runs). A jump in "Types" after a change usually points to a type that grew too large. --generateTrace writes a detailed trace for deeper digging.

Recap

  • TypeScript 7 is the native (Go) compiler: same language, about 10× faster, stricter defaults, some old options removed.
  • Tools that use the compiler API (linters, some framework plugins) still use TypeScript 6 (@typescript/typescript6, tsc6) until 7.1.
  • Run TypeScript with tsc + Node, Node's type stripping (22.18+/23.6+, erasable syntax), tsx or a bundler; always also run tsc --noEmit.
  • typescript-eslint for linting, node:test/Vitest for tests, Prettier for formatting.
  • Pin TypeScript, upgrade deliberately, and match @types/node to your Node major version.

Exercises

Exercise 1 🟢 easy commands

Which command prints the compiler version, and which only type-checks a project?

Show solution

tsc --version (or -v) and tsc --noEmit.

Exercise 2 🟢 easy true or false

"node app.ts reports type errors." True or false?

Show solution

False. Node only strips types; a file with type errors runs as long as its JavaScript is valid.

Exercise 3 🟢 easy pick a tool

You want to run a one-off TypeScript script that uses an enum, without a build step. Which tool?

Show solution

npx tsx script.ts: tsx transforms enums. Node's type stripping rejects them (unless you add --experimental-transform-types).

Exercise 4 🟢 easy versions

Your server runs Node 22. Which @types/node version should you install?

Show solution

@types/node@22. Newer majors describe APIs your Node doesn't have.

Exercise 5 🟡 medium upgrade

A project on TypeScript 5.9 has "target": "es5", "moduleResolution": "node" and no strict. List what to change before upgrading to 7.0.

Show solution

Raise target to at least es2015 (ideally what your runtime supports); replace moduleResolution: "node" (node10) with nodenext or bundler; set "strict": false explicitly if you're not ready for strict mode (it's now the default); add "types": ["node"] if you use Node globals. Upgrading to 6.0 first shows these as deprecation warnings.

Exercise 6 🟡 medium explain

Why can't typescript-eslint simply run on the TypeScript 7 compiler yet?

Show solution

Its type-aware rules call TypeScript's JavaScript API in the same process (to get types of nodes). TypeScript 7 is a Go binary, and its JavaScript API isn't stable yet, so the linter keeps using TypeScript 6's API. Your build and editor can use 7 at the same time.

Exercise 7 🟡 medium setup

Write the scripts section for a project that checks types, runs tests from compiled output, and has a fast dev mode with tsx.

Show solution

"check": "tsc --noEmit", "build": "tsc", "test": "tsc && node --test \"dist/test/**/*.test.js\"", "dev": "tsx watch src/main.ts", and run npm run check in CI.

Exercise 8 🟡 medium playground

In the playground, run npx tsc --extendedDiagnostics --noEmit and note the "Check time". Then add the Pin type from this appendix to an exercise file and run it again.

Show solution

The type count and check time go up noticeably. Template literal types with unions multiply; keep them small, or use a pattern like `${number}` plus a runtime check instead.

Exercise 9 🔴 hard design

Design the checks for a pull request in a TypeScript monorepo so that type errors, lint errors and test failures are all caught, but developers' local edit-run loop stays fast.

Show solution

Locally: an editor with the workspace TypeScript, tsx watch or type stripping for running, and tsc -b -w --noEmit (or just the editor) for errors; an optional pre-commit hook running the formatter and a fast linter on changed files. In CI: npm ci, tsc -b (project references keep it incremental), typescript-eslint with type-aware rules (on TypeScript 6 for now), tests, and a check that formatting is clean. Fail the PR on any of them.

Exercise 10 🔴 hard explain

The TypeScript team rewrote the compiler in Go rather than in Rust or keeping it in TypeScript. From what this appendix says, what problem were they solving, and what did they choose not to change?

Show solution

They solved speed and memory: large codebases took minutes to check and editors became slow. They chose a port rather than a rewrite, keeping the same type system, rules and output, so existing code keeps compiling the same way. (The team explained that Go's structure is close to the existing TypeScript code, which made a faithful port practical.) The cost is the temporary API gap for tools.
