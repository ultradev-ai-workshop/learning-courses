Conditional Types & infer

A conditional type is an if for types: A extends B ? X : Y. With it, and with infer to pull types out of other types, you can describe functions whose return type depends on their input, and build most of the utility types in Chapter 12 yourself. This chapter follows the Handbook's Conditional Types page.

You will learn

  • The syntax T extends U ? X : Y and when it's useful.
  • Conditional types in generic functions, instead of overloads.
  • infer: extracting element types, return types and promise results.
  • Distributive conditional types over unions, and how to switch it off.
  • How to "unit test" types with a tiny Expect/Equal helper.

The basic form

SomeType extends OtherType ? TrueType : FalseType. When the type on the left is assignable to the one on the right, you get the first branch, otherwise the second. It's the same extends as in constraints: "fits into".

On their own, conditional types with concrete types aren't very useful: you already know the answer. Their power comes with generics.

You don't need to write these: ReturnType, Parameters and Awaited are built in (Chapter 12). But now you know they're just conditional types with infer.

🧠 Analogy: a stencil. Promise<infer V> is a stencil with a hole labelled V. Hold it over a type: if the shape matches, whatever shows through the hole becomes V. If it doesn't match, you take the "false" branch.

Distributive conditional types

When the checked type is a bare type parameter and you pass a union, the conditional type is applied to each member separately, and the results are joined again. This is called distribution:

Wrapping both sides in [ ] (a one-element tuple) turns distribution off. Distribution is what makes the built-in Exclude and Extract work:

(never disappears in a union: "a" | never is just "a". That's how a member gets dropped.)

☕ Java / C#: Java and C# generics can't compute a type from another type. There's no "if T is a string, the result is X". The nearest Java idea is overloading, and the nearest C# idea is a set of generic overloads with different constraints, both resolved per call. TypeScript's conditional types are closer to C++ template metaprogramming or Scala's match types. Use them for library-level typing; most application code needs very few.

Recap

  • T extends U ? X : Y picks a type based on assignability; it's most useful with generics.
  • A conditional return type can replace a set of overloads (with an as inside the body).
  • infer X captures part of a matched type; infer X extends C adds a constraint.
  • Over a bare type parameter, conditional types distribute across unions; wrap in [T] to stop it.
  • never vanishes from unions, which is how Exclude/Extract filter members.
  • Test type-level code with Expect<Equal<A, B>>.

What is IsNumber<42> and IsNumber<"42"> if type IsNumber<T> = T extends number ? true : false?

Show solution

true (the literal 42 is a number) and false.

Exercise 3 🟢 easy infer

Write PromiseValue<T> that gives string for Promise<string> and T itself otherwise.

Show solution

type PromiseValue<T> = T extends Promise<infer V> ? V : T; (the built-in Awaited also unwraps nested promises and "thenables").

Exercise 4 🟢 easy distribution

Is ToArray<"a" | "b"> equal to ("a" | "b")[] or to "a"[] | "b"[], with type ToArray<T> = T extends any ? T[] : never?

Show solution

"a"[] | "b"[]: T is a bare type parameter, so the conditional distributes over the union.

Exercise 9 🔴 hard explain

Why is IsString<never> equal to never instead of "no", with type IsString<T> = T extends string ? "yes" : "no"? How do you get "no"?

Show solution

never is the empty union. A distributive conditional type maps over each member, and there are none, so the result is the empty union, never. Write [T] extends [string] ? "yes" : "no" to avoid distribution; then [never] is assignable to [string] and you get "yes" (never fits everything). To answer "no" for never, check [T] extends [never] first.

Exercise 10 🔴 hard design

Write DeepReadonly<T> using a conditional type: functions stay as they are, arrays become readonly arrays of deep-readonly items, objects get readonly deep-readonly properties. Show that nested assignment fails.

Show solution

Both mutations are compile errors. At runtime, though, nothing is frozen: the emitted JavaScript happily changes student and pushes to tags, because types never change behaviour. Pair DeepReadonly with Object.freeze (recursively) if you need a runtime guarantee as well.
