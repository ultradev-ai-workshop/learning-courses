Appendix A

TypeScript for Java & C# Developers

If you know Java or C#, TypeScript's syntax looks familiar from day one: classes, interfaces, generics, public, private. The traps are in the semantics. This appendix follows the official TypeScript for Java/C# Programmers page and collects every ☕ box from the book into one mapping, plus the habits worth unlearning.

You will learn

  • A side-by-side mapping of Java/C# concepts to TypeScript.
  • The four big mental shifts: structural typing, erased types, functions as values, and unions.
  • Which OOP patterns translate directly, and which have simpler TypeScript equivalents.
  • Common mistakes Java and C# developers make in their first TypeScript project.

The four mental shifts

1. Types are sets of values, compared by shape

In Java and C#, a type is a declared name in a hierarchy. In TypeScript, a type is a set of values, and a value belongs to every type whose shape it fits. That's why unions (A | B, set union), intersections (A & B) and literal types ("overdue", a set with one value) feel natural in TypeScript and have no Java equivalent.

🧠 Analogy: a guest list versus a dress code. Java checks the guest list (is your class's name on it?). TypeScript checks the dress code (are you wearing the right things?). Anyone who meets the dress code gets in, whatever their name.

2. Types are erased

Nothing about types survives compilation: no reflection on generics, no runtime casts, no instanceof on interfaces. Validate data at runtime yourself, at the edges (Chapter 4).

3. Functions are first-class; classes are optional

You don't need a class to hold a function. Modules export functions directly. Many Java patterns become plain functions: Strategy → a function parameter, Factory → a function, Singleton → a module-level const, Builder → an options object with defaults.

4. Unions replace many hierarchies

Where Java would create an abstract class and subclasses, TypeScript often uses a discriminated union of plain objects plus functions that switch on the tag. It's less code, the data is JSON-friendly, and the compiler checks exhaustiveness.

Recap

  • Most Java/C# syntax carries over; the semantics differ: structural typing, erased types, one number type, nullability in the type.
  • Types are sets of values: unions, intersections and literal types follow naturally.
  • Prefer functions, modules, plain data and discriminated unions; use classes for behaviour plus private state.
  • Validate at runtime at the edges; don't "cast" JSON.
  • The official TS for Java/C# Programmers page is a short, worthwhile read after this appendix.

Exercise 3 🟢 easy predict

Is x instanceof Book allowed when Book is an interface? When it's a class?

Show solution

Interface: no. It's an error, because interfaces don't exist at runtime ("'Book' only refers to a type, but is being used as a value here"). Class: yes, but it only tells you the object was created with new Book, not whether it has a Book's shape.

Show solution

number is a binary double, like Java's double. Store integer cents and format only for display.

Exercise 7 🟡 medium explain

A C# developer writes class BookService { private readonly repo: BookRepo; constructor(repo: BookRepo) { this.repo = repo; } } and asks how to do dependency injection "properly". What would you suggest?

Show solution

Constructor injection works the same way: pass dependencies in, typed by an interface, and wire them up in one place (the "composition root", like the capstone's cli.ts). No container is required; because typing is structural, tests can pass a plain object literal that fits the interface, with no mocking library. Frameworks like NestJS or Angular add containers with decorators if you want one.

Show solution

Exercise 9 🔴 hard explain

Why can TypeScript accept Dog[] where Animal[] is expected, when Java rejects List<Dog> for List<Animal>? Which bug does that allow?

Show solution

TypeScript compares arrays structurally and treats method parameters (like push) bivariantly, so arrays are covariant (Chapter 14). Java's generics are invariant to prevent exactly this bug: code holding the Animal[] reference can push a Cat into what is really a Dog[]. Use readonly Animal[] parameters to make the covariance safe.

Exercise 10 🔴 hard design

Translate a Java Optional<Member> findById(String id) API into idiomatic TypeScript. Show the caller side, and compare it with using a branded MemberId parameter.

Show solution

Member | undefined plus ?. and ?? replaces Optional with less ceremony, and strictNullChecks forces the caller to handle the missing case, like Optional does by convention only. The brand makes it impossible to pass a book id by mistake, something a Java String parameter can't prevent.
