Decorators & Mixins

Two ways to add behaviour to classes without changing their source. Decorators (@logged) are functions that wrap or replace a class or its members when the class is defined. Mixins build classes from small reusable pieces. Java and C# developers will recognise the @ syntax; this chapter shows where the similarity ends. It covers the reference pages Decorators and Mixins.

You will learn

  • Standard (ECMAScript) decorators, supported since TS 5.0: class, method, field, getter and accessor decorators.
  • The context object, addInitializer, and decorator factories (@retry(3)).
  • Typing decorators so they only apply where they make sense.
  • Legacy experimentalDecorators, still used by Angular and NestJS.
  • The mixin pattern: functions that take a class and return an extended class.

What a decorator is

A decorator is a function. You put @name before a class or class member, and when the class is defined (not when it's instantiated), JavaScript calls the function with the thing being decorated and a context object. A method decorator can return a new function to replace the method:

The generic parameters make the replacement function keep the exact signature of the method: This is the class, Args the parameter tuple, R the return type.

🧠 Analogy: gift wrapping. The method is the gift. A decorator wraps it: callers still receive "the method", but opening it first runs the wrapper (logging, timing, checking). You can wrap the same gift several times.

☕ Java / C#: they look like Java annotations or C# attributes, but they work differently. An annotation is passive metadata: nothing happens until a framework reads it with reflection. A decorator is active code that runs once, at class definition, and can replace the member. The closest Java idea is a Spring AOP aspect or a dynamic proxy, applied explicitly per member.

Legacy decorators: experimentalDecorators

Long before the JavaScript standard, TypeScript had its own decorator design, turned on with "experimentalDecorators": true. It has a different signature ((target, propertyKey, descriptor)), supports parameter decorators, and, with emitDecoratorMetadata, emits runtime type information. Angular, NestJS and TypeORM are built on it.

📝 Which one should I use? If your framework requires experimentalDecorators (Angular, NestJS), use it as its docs say. For everything else, use standard decorators (no flag needed). The two can't be mixed in one project, and their decorator functions aren't interchangeable.

Recap

  • Standard decorators (TS 5.0+, no flag) are functions called at class definition with (value, context).
  • Method/getter decorators return replacements; field decorators return initializers; accessor decorators return { get, set, init }.
  • Factories (@retry(3)) return decorators; context.addInitializer runs setup code.
  • Type decorators with the Class…DecoratorContext types so misuse is a compile error.
  • experimentalDecorators is the older, different design used by Angular/NestJS.
  • Mixins are class factories; constrain TBase to require base members.

Exercises

Exercise 1 🟢 easy true or false

"A method decorator runs every time the method is called." True or false?

Show solution

False. The decorator runs once, when the class is defined. The replacement function it returns runs on every call.

Exercise 2 🟢 easy predict

In @a @b method() {}, which decorator is applied first?

Show solution

b, the one closest to the method. Decorators are applied bottom-up (inside-out), so a wraps the result of b.

Exercise 7 🟡 medium explain

A NestJS project has "experimentalDecorators": true. A colleague copies a standard (value, context) decorator from this chapter into it. What happens, and why?

Show solution

It fails to type-check (and would misbehave at runtime): with experimentalDecorators, TypeScript calls method decorators as (target, propertyKey, descriptor), so the second argument is a string, not a context object. The two decorator systems have different calling conventions; a project uses one or the other.

Exercise 9 🔴 hard explain

Why does the logged decorator in this chapter use three type parameters instead of (target: Function, context: ClassMethodDecoratorContext)?

Show solution

With Function, the replacement method's type would be unknown, so callers of fee would lose its parameter and return types, and the decorator couldn't call target with typed arguments. The type parameters capture this, the argument tuple and the return type from the decorated method, so the replacement has exactly the same signature and the decorated class stays fully typed.

Exercise 10 🔴 hard design

Write a mixin Observable that adds on(listener) and a protected-style emit(event), constrained to bases that have an id: string. Apply it to a Loan class whose close() emits "closed".

Show solution

A class can extend a mixin's result directly (extends Observable(LoanBase)), and it gets both the base's and the mixin's members, fully typed.
