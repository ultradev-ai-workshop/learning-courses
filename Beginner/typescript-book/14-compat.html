Type Compatibility & Inference

When is a value of type A allowed where type B is expected? And how does TypeScript work out a type you didn't write? This chapter covers the reference pages Type Compatibility and Type Inference, plus two tools that build on them: the satisfies operator and branded types, which give you nominal typing when you need it.

You will learn

  • The rules of structural compatibility for objects, functions, classes and generics.
  • Why function parameters are checked "in reverse" (strictFunctionTypes).
  • The special roles of any, unknown and never in assignability.
  • Inference: best common type, contextual typing and widening.
  • satisfies: check a value against a type without losing its precise type.
  • Branded types: making BookId and MemberId incompatible.

Objects: at least these properties

The basic rule: x is assignable to type T if x has at least the properties T requires, with compatible types. Extra properties are fine (apart from the fresh-literal excess check of Chapter 6). The check is recursive, member by member.

Think of it as sets: every Dog value is also a Pet value, so Dog is a subtype of Pet. More properties means a smaller set of values, so a narrower type.

Functions: parameters in reverse

For functions, the return type works like objects: the source may return something more specific. Parameters are the other way round. A function that accepts more (or fewer parameters) can stand in for one that accepts less, never the opposite:

Whoever calls a Handler will pass a dog without a chip. needsChip would read a missing property. This "reverse" rule is called contravariance, and strictFunctionTypes (part of strict) enforces it for function types.

🧠 Analogy: hiring a vet. The job says "treats dogs". A vet who treats all animals can take the job. A vet who treats only microchipped dogs can't, because some dogs that walk in won't have a chip. Returning results is the opposite: if the job says "writes a report", writing a detailed report is fine.

⚠️ For compatibility with old code, parameters of methods (written m(x: T): void in an interface) are still checked both ways ("bivariantly"). Declare callbacks as properties, m: (x: T) => void, to get the strict check.

Fewer parameters is always fine (that's why arr.forEach((x) => …) works although forEach passes three arguments). Optional and rest parameters are treated loosely in both directions.

Classes, generics and enums

  • Classes: only the instance members are compared. Static members and constructors don't matter. private, protected and # members must come from the same declaration (Chapter 7).
  • Generics: compared after substitution, by the members that actually use the type parameter. An empty interface Box<T> {} makes Box<string> and Box<number> compatible, because nothing uses T.
  • Enums: values of different enums are never compatible with each other; numeric enums are compatible with number.

any, unknown and never

Three types sit at the edges of the "type sets" picture:

☕ Java / C#: unknown is TypeScript's Object/object: everything is one, but you must cast (here: narrow) to use it. never is like Kotlin's Nothing; Java has no direct equivalent (a method that always throws). any is like C#'s dynamic: the compiler steps aside completely.

Contextual typing

Inference also goes "from the outside in": the expected type of a position types the expression put there (Chapter 3). That works for callbacks, return statements, and object literals assigned to annotated variables.

Widening

A literal is widened to its general type when it's stored somewhere mutable: let x = "a" is string, const x = "a" is "a", and properties of a const object are widened, unless you use as const.

Branded types: nominal typing on demand

Structural typing means type BookId = string and type MemberId = string are interchangeable, so you can pass a member id where a book id is expected. A brand is a fake property that exists only in the type, making the two incompatible:

☕ Java / C#: in Java you'd write record BookId(String value); in C#, readonly record struct BookId(string Value). Those wrappers exist at runtime. A TypeScript brand has zero runtime cost: the value is still a plain string, and the brand is erased. The minting functions (bookId(...)) are where you'd validate the format.

Recap

  • Objects: the source needs at least the target's properties. More properties = subtype.
  • Functions: returns may be more specific; parameters must accept at least as much (contravariance, strictFunctionTypes). Method-style declarations are checked loosely.
  • Classes compare instance members; generics compare the members that use T.
  • unknown is the top type, never the bottom type, any turns checking off.
  • Inference: best common type, contextual typing, literal widening.
  • satisfies checks without widening. Brands make structurally identical types incompatible, at zero runtime cost.

Exercises

Exercise 1 🟢 easy predict

Is { id: string; title: string } assignable to { id: string }? And the other way round?

Show solution

Yes; no (the second has no title).

Exercise 2 🟢 easy predict

Can (a: string) => void be assigned to (a: string, b: number) => void? And the reverse?

Show solution

Yes: ignoring extra arguments is fine. No: the second function needs b, which callers of the first type won't pass.

Exercise 3 🟢 easy satisfies

Rewrite const limits: Record<string, number> = { student: 3, staff: 10 }; so that limits.staf is an error.

Show solution

With the annotation, any string key is allowed (and limits.staf is number). With satisfies, the type keeps its exact keys.

Exercise 4 🟢 easy true or false

"never can be assigned to any type, and no type (except never) can be assigned to never." True or false?

Show solution

True. It's the empty set: it's a subset of every set, and nothing else is a subset of it. (any also can't be assigned to never.)

Exercise 6 🟡 medium inference

What is the inferred type of [new Date(), "today"]? How do you make it a tuple [Date, string] without writing the type?

Show solution

(string | Date)[]. Use as const (giving readonly [Date, "today"]) or annotate. A function with a tuple-typed rest or a const type parameter also infers tuples.

Exercise 7 🟡 medium contravariance

Explain why this is an error, using the vet analogy: const sort: (cmp: (a: string | number, b: string | number) => number) => void = …; sort((a: string, b: string) => a.localeCompare(b));

Show solution

sort will call the comparator with numbers too. A comparator that only "treats strings" can't take a job that says "treats strings and numbers": it would call localeCompare on a number. Parameters must accept at least what callers pass.

Exercise 8 🟡 medium playground

In exercises/ch14/ids.ts, create branded BookId, MemberId and LoanId types with validating constructors (b…, m…, L… followed by digits) that throw on bad input. The capstone uses them everywhere.

Show solution

Exercise 9 🔴 hard explain

Why are method parameters still checked bivariantly, even under strict? Give a built-in example where strict checking would break.

Show solution

Many built-in types are written with methods, and are used covariantly. The classic example is Array<T>: push(...items: T[]) is a method, and people expect Dog[] to be assignable to Animal[]. With strict parameter checks, Dog[] wouldn't be an Animal[] (because push on an Animal[] accepts any animal). TypeScript chose to keep that convenient (but technically unsound) behaviour for methods.

Exercise 10 🔴 hard design

Write a config object of fee rules that satisfies Record<string, { perDay: number; cap?: number }>, then a function fee(kind: keyof typeof config, days: number). Show that config.dvd.cap is known to exist when you wrote it, and that a misspelled key fails.

Show solution

The checker rejects "magazine"; the emitted JavaScript runs anyway and crashes on that call, as predicted.
