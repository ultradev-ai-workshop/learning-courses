Modules, Namespaces & Merging

Real programs are split into files. TypeScript uses JavaScript's own module system (ES modules) and adds a few things on top: type-only imports, rules for how import paths are resolved, and declaration merging, which lets several declarations with one name combine into one. This chapter follows the Handbook's Modules page, the Modules Reference, and the reference pages on namespaces and declaration merging.

You will learn

  • Which files are modules, and the import/export forms in TypeScript.
  • Type-only imports and exports, and verbatimModuleSyntax.
  • Why you write ./catalog.js when importing catalog.ts (module: "nodenext").
  • ES modules vs CommonJS from TypeScript's point of view.
  • Namespaces: what they are and why you rarely need them now.
  • Declaration merging and module augmentation.

What is a module?

In JavaScript, a file with a top-level import or export is a module: its variables are private unless exported. A file without them is a script, and its top-level declarations are global. TypeScript follows the same rule, and the option moduleDetection: "force" (set by tsc --init and used in this book) treats every non-declaration file as a module, so there's no accidental global code.

Type-only imports and exports

Book is only a type; it doesn't exist at runtime. Marking it with type (either import { type Book } or import type { Book }) tells every tool that this import can be deleted when compiling. With the option verbatimModuleSyntax (recommended, and set by tsc --init), the rule is simple: imports without type are kept in the output, imports with type are removed, and importing a type without type is an error:

This is exactly the bug the error warns about. The import has no type marker, so it was kept in the JavaScript output, and at runtime catalog.js has no export called Book: interfaces don't exist there. Writing import { type Book } fixes both the error and the crash. Why does this matter so much? A file-by-file transpiler (esbuild, Babel, Node's type stripping) can't look into catalog.ts to see whether Book is a type or a value. The type keyword tells it, so it never emits an import of something that doesn't exist.

💡 Exports work the same way: export type { Book } from "./catalog.js"; re-exports only the type.

Import paths and module resolution

Look at the import again: from "./catalog.js", although the file is catalog.ts. With module: "nodenext" (the right setting for Node), TypeScript checks imports the way Node will run them. Node runs the emitted catalog.js, and Node's ES module loader requires full file names with extensions. TypeScript doesn't rewrite import paths, so you write the path that will be correct at runtime, and TypeScript maps it back to the .ts file for checking:

Your code runs in…SetImport paths
Node (with tsc output)"module": "nodenext""./catalog.js"
A bundler (Vite, webpack, esbuild)"module": "preserve", "moduleResolution": "bundler""./catalog" is fine
Node with type stripping (node file.ts)nodenext + allowImportingTsExtensions, rewriteRelativeImportExtensions"./catalog.ts"

The Modules Reference's guide Choosing Compiler Options has the full decision table. The key idea: tell TypeScript where the code will run, and its import checks will match reality.

🧠 Analogy: addressing a letter for the destination country. You write the address in the format the receiving post office understands (the .js file Node will load), not the format of the country you're writing from (your .ts source).

ES modules and CommonJS

Node has two module systems: ES modules (import/export) and the older CommonJS (require/module.exports). With nodenext, TypeScript decides per file, exactly like Node: .mts → ESM, .cts → CommonJS, and .ts follows the nearest package.json's "type" field. This book's work folder has "type": "module", so every .ts file is ESM.

Importing a CommonJS package from ESM gives you its module.exports as the default import. TypeScript models this with the esModuleInterop behaviour, which is always on in TypeScript 7 (turning it off was removed):

Namespaces

Before ES modules existed, TypeScript had namespaces (originally "internal modules") to group code under one global name:

A namespace compiles to an object built by a function (an IIFE). In new code, use modules instead: every file is already its own namespace, and tools understand modules better. Namespaces aren't erasable (they generate code), so erasableSyntaxOnly rejects them. You'll still meet them in older code and in declaration files (Chapter 17), where declare namespace describes global libraries.

☕ Java / C#: a TypeScript namespace looks like a C# namespace or a Java package, but it's really an object at runtime. The Java "package = folder" idea maps better onto modules: one file, one module, and imports by path. There's no package-private visibility; anything not exported from a module is private to that file.

Recap

  • Files with import/export are modules; moduleDetection: "force" makes every file one.
  • Mark type-only imports with type; verbatimModuleSyntax makes this a rule and keeps tools honest.
  • With module: "nodenext", write runtime paths (./x.js); for bundlers use preserve + bundler.
  • TypeScript follows Node's ESM/CommonJS rules per file (.mts, .cts, "type").
  • Namespaces are legacy grouping objects; use modules in new code.
  • Interfaces and namespaces merge; declare module and declare global augment other people's types.

"A non-exported const in a module is visible to other modules as a global." True or false?

False. Module scope is private. Only exports are visible, and only to files that import them.

Exercise 9 🔴 hard explain

Why doesn't TypeScript simply rewrite "./catalog" to "./catalog.js" in its output, so you could write paths without extensions?

Show solution

One of TypeScript's design rules is that it doesn't change the meaning of JavaScript expressions it emits; it only removes types. An import specifier is a runtime string: rewriting it would be easy for ./catalog but ambiguous for package paths, dynamic imports with variables, or folders. Instead, TypeScript checks that the path you wrote will work where the code runs. (Since TS 5.7, rewriteRelativeImportExtensions rewrites .ts → .js for relative paths only, for code that also runs directly as .ts.)
