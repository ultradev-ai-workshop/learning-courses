Project Configuration

A tsconfig.json decides which files are compiled, how strict the checker is, what JavaScript comes out, and how imports are resolved. TypeScript has well over a hundred options; you need about twenty. This chapter follows the Handbook's Project Configuration section and the TSConfig reference: the options tsc --init picks for you, the ones you'll change, and how to split a big codebase with project references.

You will learn

  • The structure of tsconfig.json: compilerOptions, include/exclude/files, extends.
  • What tsc --init sets in TypeScript 7, and why.
  • The option groups: environment, modules, emit, strictness, and "tool-friendliness".
  • Debugging a config with --showConfig and --explainFiles.
  • Project references and build mode (tsc -b).
  • Recommended configs for a Node app, a library and a bundled web app.

The structure of tsconfig.json

tsconfig.json allows comments and trailing commas (it's "JSON with comments"). Two things surprise people:

  • exclude only filters what include found. A file you import is always compiled, even if it matches exclude.
  • A tsconfig.json marks a project. Editors use the nearest one for each file, so a file outside every include gets default settings in the editor.

Not part of strict, but recommended: noUncheckedIndexedAccess and exactOptionalPropertyTypes (Chapter 6), noImplicitOverride (Chapter 7), noFallthroughCasesInSwitch, noImplicitReturns.

Tool-friendliness

These make sure other tools (esbuild, Babel, Node's type stripping) can compile each file on its own:

OptionRequires
isolatedModulesevery file can be transpiled without looking at others
verbatimModuleSyntaximport type for type-only imports (Chapter 15)
erasableSyntaxOnlyno enums, namespaces or parameter properties (Chapter 13)
skipLibChecknot a requirement: it skips checking .d.ts files, for speed

🧠 Analogy: a car's settings menu. Environment is the country you're driving in (which side of the road), modules are the road rules, emit is what the dashboard records, strictness is how sensitive the warning beeps are, and tool-friendliness makes sure any mechanic can service the car.

Debugging a configuration

  • tsc --showConfig: the effective options (above).
  • tsc --listFiles / --explainFiles: every file in the program, and why it's there ("Matched by include pattern", "Imported via …"). Use it when an "excluded" file still gets compiled.
  • tsc --traceResolution: step-by-step import resolution, for "Cannot find module" mysteries.
  • tsc --extendedDiagnostics: timings and memory, for slow builds.

Project references and build mode

A large codebase (a monorepo, or an app plus a shared library) can be split into several TypeScript projects that reference each other. Each is checked and built separately, and only rebuilt when it changes. The referenced project must set composite: true, which also turns on declaration, because dependants use its .d.ts output instead of its source:

tsc -b (build mode) builds the referenced projects first, in dependency order, and skips the ones that are up to date. (The sed just removes the timestamps from --verbose output.)

The second build does nothing. The .tsbuildinfo files record what was built; incremental: true gives single projects the same speed-up. In a real monorepo, cli would import core by package name (with npm/pnpm workspaces) rather than by a relative dist path.

☕ Java / C#: project references are TypeScript's version of Maven/Gradle multi-module builds or a .NET solution with project references: modules with declared dependencies, built in order, each publishing its "API" (here: .d.ts files, there: compiled classes or assemblies) to the modules that depend on it. tsconfig.json itself plays the role of the .csproj or the compiler section of pom.xml; the "extends" field is like a parent POM.

Recap

  • tsconfig.json = compilerOptions + which files (include/exclude/files) + extends + references.
  • tsc --init (TS 7) is strict and modern; add rootDir/outDir, types and a concrete target.
  • Think in groups: environment (target, lib, types), modules, emit, strictness, tool-friendliness.
  • --showConfig, --explainFiles and --traceResolution debug configs.
  • Project references + composite + tsc -b split big codebases into incremental builds.

Exercises

Exercise 1 🟢 easy match

Which option do you need to (a) put output in dist/, (b) only type-check, (c) see Node's process global, (d) emit .d.ts files?

Show solution

(a) outDir (with rootDir), (b) noEmit, (c) "types": ["node"] with @types/node installed, (d) declaration.

Exercise 2 🟢 easy predict

"exclude": ["src/legacy"] is set, but src/app.ts imports ./legacy/old.js. Is old.ts compiled?

Show solution

Yes. exclude only removes files from the include globs; imported files are always part of the program. tsc --explainFiles would say "Imported via './legacy/old.js' from file 'src/app.ts'".

Exercise 3 🟢 easy strict family

Name three checks that strict turns on.

Show solution

Any three of: noImplicitAny, strictNullChecks, strictFunctionTypes, strictBindCallApply, strictPropertyInitialization, noImplicitThis, useUnknownInCatchVariables, alwaysStrict, strictBuiltinIteratorReturn.

Exercise 4 🟢 easy bundler

Your React app is built by Vite. Which values do you use for module, moduleResolution and emit?

Show solution

"module": "preserve", "moduleResolution": "bundler", and "noEmit": true: Vite strips types and bundles; tsc --noEmit runs only to check.

Exercise 5 🟡 medium extends

Write a tsconfig.base.json with your strict options, and two configs that extend it: one for src (emitting to dist) and one for test (no emit, with "types": ["node"]).

Show solution

Paths in an extended config (like include) are resolved relative to the file that declares them.

Exercise 6 🟡 medium sourceMap

What does sourceMap change for you when a compiled program throws an error, and how do you enable it in Node?

Show solution

With .js.map files, a debugger (and, with node --enable-source-maps, Node's stack traces) shows src/app.ts:12 instead of dist/app.js:9. Turn on "sourceMap": true and run Node with --enable-source-maps.

Exercise 7 🟡 medium migration

You're adding TypeScript to a large JavaScript project with allowJs. Which strict checks would you turn off first to keep the error count manageable, and in which order would you turn them back on?

Show solution

Start with "strict": false (or strict: true plus noImplicitAny: false and strictNullChecks: false). Turn on noImplicitAny first (it finds untyped edges), then strictNullChecks (the biggest change, often done folder by folder), then the rest of strict, and finally extras like noUncheckedIndexedAccess. Chapter 19 walks through this order.

Exercise 8 🟡 medium playground

Open the playground's tsconfig.json and run npx tsc --showConfig. Which of the options in the "tool-friendliness" table are on? Then run npx tsc -p reference --showConfig and compare.

Show solution

The playground has isolatedModules, verbatimModuleSyntax and skipLibCheck on. The reference adds erasableSyntaxOnly: it was written without enums, namespaces or parameter properties, so type-stripping tools can run it. (The exercises leave it off, because Chapters 7 and 13 practise parameter properties and enums.)

Exercise 9 🔴 hard explain

Why does a referenced project need composite: true, and why do dependants read its .d.ts files rather than its .ts sources?

Show solution

composite guarantees the project can be built on its own and that its outputs are predictable: declaration is on, all files are listed by include/files, and rootDir is fixed. Dependants read the .d.ts output because it's much smaller and cheaper to check than the full sources, and it changes only when the public API changes. That's what makes builds incremental and lets a big codebase be checked in parts.

Exercise 10 🔴 hard design

Design the tsconfig layout for a monorepo with packages/models (shared types and validation), packages/api (a Node server) and packages/web (a Vite app), all depending on models. List the files and the key options of each.

Show solution
  • tsconfig.base.json: strict options, verbatimModuleSyntax, isolatedModules, skipLibCheck.
  • packages/models/tsconfig.json: extends base; composite: true, rootDir src, outDir dist, module: nodenext, erasableSyntaxOnly, types: [].
  • packages/api/tsconfig.json: extends base; module: nodenext, types: ["node"], outDir dist, references: [{ path: "../models" }].
  • packages/web/tsconfig.json: extends base; module: preserve, moduleResolution: bundler, lib with dom, noEmit, jsx, references to models.
  • Root tsconfig.json: "files": [] and references to all three, so tsc -b at the root builds everything in order.
