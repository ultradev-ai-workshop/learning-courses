The Basics: tsc & Strictness

This chapter follows the Handbook's The Basics page. You install the compiler, compile a first file, see what tsc writes out, and meet the switches that decide how strict the checker is. By the end you can set up a small TypeScript project from nothing.

You will learn

  • How to install TypeScript in a project and run tsc.
  • What tsc emits, and how target changes it ("downleveling").
  • Why tsc still writes files when there are errors, and noEmitOnError.
  • Explicit type annotations: where to write them and where to leave them out.
  • The two most important strict checks: noImplicitAny and strictNullChecks.
  • A first tsconfig.json, --noEmit and --watch.

Installing the compiler

Install TypeScript per project, as a development dependency. Then every teammate and the CI server use the same version, written in package.json.

npx tsc runs the compiler from node_modules/.bin. Inside package.json scripts you can just write tsc. In this book, a $ tsc line means the project's compiler.

📝 A global install (npm install -g typescript) also works, but then different projects can't pin different versions. Prefer the local install.

Why emit at all? While you move a JavaScript project to TypeScript, you'll have hundreds of errors for a while, and the code still worked yesterday. TypeScript doesn't block you. When you want it to, set noEmitOnError:

🧠 Analogy: a building inspector who doesn't hold the keys. The inspector (the checker) writes a report of every problem. The builder (the emitter) hands over the keys either way, unless you made a rule (noEmitOnError) that no keys are handed over while the report has problems.

Explicit types

An annotation is : Type after a name. You'll write them in three places:

  1. Function parameters: always, because TypeScript can't guess what callers will pass.
  2. Return types: optional, but useful on exported functions. They document intent and catch a wrong return early.
  3. Variables: only when there's no initial value, or when the inferred type is too narrow or too wide.

💡 Rule of thumb: annotate the edges (parameters, exported functions, public APIs), let inference do the inside. If you hover a variable in your editor and the inferred type is right, don't repeat it.

Downleveling with target

target tells tsc which JavaScript version the output must run on. Newer syntax is rewritten for older targets. That rewriting is called downleveling. Template literals arrived in ES2015, so watch what happens with --target es5:

TypeScript 6.0 deprecated es5, and TypeScript 7 removed it: every browser and Node version still in use runs ES2015+. The lowest target is now es2015, and the default is the newest (esnext). Pick the oldest runtime you support; for Node 22+ that is es2024.

📝 target only rewrites syntax. It doesn't add missing built-in functions (like Array.prototype.findLast) to old runtimes. That's what polyfills are for, and it's why you also set lib, the list of built-ins the checker assumes exist (Chapter 18).

Strictness

TypeScript can be loose (good for a first migration) or strict (good for everything else). The strict flag turns on a family of checks at once. Since TS 7.0, strict is on by default, which is why you saw "use strict" above. The two checks you'll feel the most:

noImplicitAny

When TypeScript can't work out a type, it falls back to any, which switches checking off for that value. noImplicitAny turns that silent fallback into an error:

A first tsconfig.json

Passing flags on the command line gets old fast. A tsconfig.json file marks the root of a project and holds its settings. The example project below lives in a folder called first-project/. tsc --init writes a commented starter file; run tsc with no file names to compile the project it describes.

  • rootDir/outDir keep sources in src/ and output in dist/.
  • tsc --noEmit only type-checks. That's what you run in CI when another tool builds the code.
  • New in TypeScript 7: naming files while a tsconfig.json exists is an error (TS5112), because people were surprised that their settings were ignored.
  • tsc --watch (-w) keeps running and recompiles when a file changes.

Recap

  • Install TypeScript per project (npm i -D typescript) and run npx tsc or tsc in npm scripts.
  • tsc file.ts checks and emits file.js. Errors still emit unless noEmitOnError is set; the exit code is non-zero.
  • Annotate parameters and public return types; let inference handle locals.
  • target picks the output syntax (ES2015 or newer in TS 7); lib picks which built-ins exist.
  • strict (on by default in TS 7) includes noImplicitAny and strictNullChecks.
  • tsconfig.json marks a project; run tsc, tsc --noEmit or tsc -w with no file names.

Exercise 9 🔴 hard explain

Why does TypeScript emit JavaScript even when there are type errors, and in which situation would you turn on noEmitOnError?

Show solution

Because type errors don't mean the JavaScript is broken: the types are only a model of it. During a gradual migration the old code still runs, so blocking output would stop the team. Turn on noEmitOnError when tsc produces the shipped build (a library or a server), so a type error can never reach production as a "successful" build.
