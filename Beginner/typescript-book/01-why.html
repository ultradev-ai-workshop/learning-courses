Chapter 1 · Getting Started

Why TypeScript?

TypeScript is JavaScript with a type checker in front of it. You write the same JavaScript you already know, add notes about what kind of value goes where, and a compiler tells you about mistakes before the code runs. This chapter follows the official TypeScript for JavaScript Programmers page: what TypeScript adds, what it doesn't change, and how the compiler fits into your work.

You will learn

  • What a static type checker is, and which bugs it catches before you run anything.
  • The golden rule: types are erased. The JavaScript that runs is the same JavaScript you wrote.
  • Type inference: TypeScript works out most types for you.
  • The three ideas the whole book builds on: defining types, composing types, and structural typing.
  • What changed in TS 7.0: the new native compiler.

JavaScript plus types

JavaScript checks types only while the program runs. If you call a method that doesn't exist, you find out when that line runs, maybe in production. A static type checker reads your code without running it and reports the mistakes it can prove. "Static" just means "before running".

🧠 Analogy: a spell checker for your program's shape. A spell checker doesn't understand your essay, and it doesn't stop you from printing it. It only underlines words that can't be right. TypeScript is the same: it underlines code that can't be right, and leaves the meaning to you.

The golden rule: types are erased

Browsers and Node run JavaScript, not TypeScript. The compiler, tsc, does two separate jobs:

  1. Type-check the code and report errors.
  2. Emit JavaScript by removing the type annotations.

These jobs are independent. Even when there are type errors, tsc still writes the JavaScript by default. The types are gone from the output, so they can't change what the program does:

☕ Java / C#: in Java and C#, types exist at runtime too. The JVM and the .NET runtime check casts, and instanceof or is can look at a generic's metadata (C#) or a class. TypeScript is different: once the code is compiled, the types are gone, much like Java's type erasure for generics, but applied to every type. A failed "cast" in TypeScript (as) never throws.

JavaScript's own types are all available: string, number, boolean, bigint, symbol, null and undefined. Structural typing

TypeScript compares types by their shape, not by their name. If an object has the properties a type needs, it fits, even if it was never declared as that type. This is called structural typing (or "duck typing, checked at compile time").

☕ Java / C#: Java and C# use nominal typing: a class fits an interface only if it says implements HasTitle (or : IHasTitle). In TypeScript the implements keyword exists (Chapter 7), but it's only a check you ask for. Any value with the right shape is accepted. This one difference explains many surprises for Java and C# developers.

🧠 Analogy: a plug and a socket. Nominal typing asks "is this plug from the approved brand?". Structural typing asks "do the pins fit the socket?". TypeScript only looks at the pins.

The compiler today: TypeScript 7 TS 7.0

For its first ten years, the TypeScript compiler was written in TypeScript and ran on Node. TypeScript 7.0 (2026) is a port of the same compiler to Go. It checks code about 10× faster and uses much less memory. The language and its rules are the same as in TypeScript 6.0. Only the engine changed.

  • You still install it with npm install -D typescript and run tsc.
  • strict mode is on by default now. Every example in this book uses it.
  • Tools that load TypeScript as a library (some linters and framework plugins) still use TypeScript 6 until the new programmatic API is stable. Appendix B explains this.

Where TypeScript runs

Since TypeScript is erased, "running TypeScript" always means "remove the types, then run JavaScript". You have three common choices:

HowChecks types?Used for
tsc → .js files → node✅ yeslibraries, builds, this book
node file.ts (Node 22.18+ and 23.6+ strip types themselves)❌ noquick scripts, tests
a bundler or tool (Vite, esbuild, tsx)❌ no, run tsc --noEmit alongsideweb apps

The tools that only strip types are fast because they skip checking. You still run tsc --noEmit (check only, write nothing) in your editor, in a pre-commit hook or in CI.

💡 The official Playground at typescriptlang.org/play runs the compiler in your browser. Paste any example from this book, see the errors, and look at the emitted JavaScript in the .JS tab. No install needed.

TypeScript is a superset of JavaScript: any JavaScript program is also a TypeScript program. It may have type errors, but it parses. That's why you can rename a .js file to .ts and fix errors one by one (the capstone in Chapter 19 does exactly that).

Recap

  • TypeScript is JavaScript plus a static type checker: it finds mistakes without running the code.
  • Types are erased. tsc checks, then emits plain JavaScript, even when there are errors. Types never check runtime data.
  • Most types are inferred. You write them for function parameters and for shapes you want to name.
  • Build types with interface/type, unions ("a" | "b") and generics (Array<T>).
  • TypeScript is structural: shape matters, names don't. Java and C# are nominal.
  • TS 7.0 is the native (Go) compiler: same language, about 10× faster, strict by default.

Exercise 3 🟢 easy true or false

"If my TypeScript code compiles, a function declared as (n: number) can never receive a string at runtime." True or false?

Show solution

False. Types are erased. A caller written in plain JavaScript, data from JSON.parse, or an as any can still pass a string. TypeScript only proves things about the code it checked.

Exercise 9 🔴 hard explain

Your team says: "We'll add TypeScript, so we can delete our input-validation code." Explain in two or three sentences why that's wrong, and what TypeScript does let you delete.

Show solution

Input arrives at runtime, and types are erased, so TypeScript can't check it; validation code is still needed at the edges (HTTP requests, files, user input). What TypeScript lets you delete is defensive checks inside your own code ("is this really a string?") between functions that are already type-checked, plus many unit tests that only checked shapes and argument counts.

Exercise 10 🔴 hard playground

Write exercises/ch01/erased.ts that proves types are erased: declare function double(n: number), call it once correctly and once through as any with "21", and print both results. Predict the output before you run it.

Show solution

Both calls give 42 because * converts the string. Nothing at runtime knows that n was meant to be a number.
