Project: CLI Expense Tracker

Build a complete, tested command-line program from scratch, using nearly every chapter of this book: expenses add 12.50 food, expenses list, expenses summary.

You will learn

  • How to split a program into a package of focused modules.
  • How to model data with a dataclass, a StrEnum, and integer cents.
  • How to store data safely as JSON, with clear custom errors.
  • How to build a real CLI with argparse subcommands, exit codes and stderr.
  • How to test the whole thing with unittest, and install it as a command.

The plan

We'll build tracker, a small package in playground/. (The finished version is in playground/reference/ if you get stuck; clone the playground from coder-hop/python-book-playground if you don't have it.) It replaces the little tracker package from Chapter 8's exercise.

Step 1: the data model (models.py)

This module knows nothing about files or the command line. It only describes the data. Keeping it free of input/output makes it easy to test and reuse.

{{file:tracker/models.py}}
  • Category.parse is a classmethod that converts user text into an enum member. It replaces the enum's terse error with a helpful one, and from None hides the internal cause (Chapter 10). ", ".join(cls) works because StrEnum members are strings.
  • parse_amount validates the text by hand with partition and isdigit, and accepts both 12.5 and 12,50. Its docstring contains a doctest.
  • format_money uses divmod on the absolute value, then :, and :02d format specs (Chapter 9).
  • to_dict and from_dict convert to and from JSON-friendly types: dates become ISO strings and enums become their values.

Step 2: storage (storage.py)

{{file:tracker/storage.py}}
  • EAFP: just try to read the file. FileNotFoundError means "first run", so return an empty list.
  • Any parsing problem (bad JSON, a missing key, an unknown category) becomes one StorageError, chained with from exc so the original cause stays visible to anyone debugging.
  • save writes to expenses.json.tmp first, then replace()s the real file in one step. A crash halfway through writing can never corrupt your data.
  • max(..., default=0) handles the empty list when picking the next id.

Step 3: reports (report.py)

{{file:tracker/report.py}}
  • select is a generator with keyword-only filters (*, Chapter 5). totals_by_category(select(...)) never builds an intermediate list.
  • defaultdict(int) starts each total at 0, and sorted(..., key=lambda kv: kv[1], reverse=True) puts the biggest first. Since dicts keep insertion order, the result stays sorted.
  • bar draws a tiny text chart with string repetition (Chapter 2).

Step 4: the command-line interface (cli.py)

{{file:tracker/cli.py}}
  • Subcommands: add_subparsers gives each command its own arguments, so expenses add -h shows only the options for add.
  • A closure: _arg(convert) returns a wrapper function that remembers convert (Chapter 5). argparse calls it for each argument, and an ArgumentTypeError makes argparse print our message instead of a generic one.
  • Functions as values: COMMANDS maps names to functions, a "dispatch table". Each command returns True if the data changed, so main only saves when it needs to. (A match args.command: block would work just as well.)
  • Exit codes and stderr: expected problems print error: … to stderr, and main returns 1. Bugs are not caught, so they still show a full traceback, which is exactly what you want while developing.
  • main(argv=None): argparse reads sys.argv when argv is None, so tests can pass their own list instead.

Recap

  • Split by responsibility: model (pure data) → storage (files) → report (calculations) → CLI (input and output).
  • Integer cents, an enum and a dataclass make invalid data hard to create. Validate at the edges, where user input comes in.
  • Catch expected errors, show them on stderr with exit code 1, and let bugs raise.
  • Write main(argv=None) and return codes, so tests can call it directly.
  • python3 -m tracker for development; pyproject.toml with pip install -e . for a real command.

Exercise 3 🟢 easy explain why

Why does cmd_delete raise LookupError instead of printing the error itself?

Show solution

It keeps the command focused on its job and leaves the decision about how to report to main, which turns every expected error into the same error: … line on stderr with exit code 1. Tests can also check the behaviour without parsing printed text.

Exercise 4 🟢 easy predict the output

What does parse_amount("3.5") return? And parse_amount("3.")?

Show solution

350 ("5".ljust(2, "0") is "50"), and 300 (an empty fraction becomes "00"). Both are reasonable. If you'd rather reject "3.", add a check and a test.
