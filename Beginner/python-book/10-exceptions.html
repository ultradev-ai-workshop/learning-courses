Syntax errors

A syntax error means Python couldn't even parse your code, so nothing runs. The parser points with ^ at the place where it got confused. The real mistake is often just before that point.

Exceptions

Code that is syntactically fine can still fail while running. Those run-time errors are exceptions. If nothing handles one, the program stops and prints a traceback. The last line gives the exception type and a message.

Python's error messages keep getting friendlier. Python 3.15 even suggests fixes for common mix-ups from other languages:

Handling exceptions: try / except

Put the risky code in try. If an exception happens, Python skips the rest of the try block and looks for an except clause that matches the exception's type.

The rules:

  1. The try block runs.
  2. If no exception happens, all the except clauses are skipped.
  3. If an exception happens, the rest of try is skipped, and the first matching except runs.
  4. If no except matches, the exception travels up to the caller. If nobody handles it, the program stops with a traceback.

Several exception types

The else clause

Code in else runs only if the try block raised nothing. It keeps the try block small, so you don't accidentally catch errors from code you didn't mean to protect.

EAFP: "it's easier to ask forgiveness than permission"

Python code often tries an operation and handles the failure, rather than checking every condition first. Checking first is called "look before you leap", or LBYL; the try-first style is called EAFP. EAFP avoids race conditions (the file could vanish between the check and the open), and it is often shorter.

Raising exceptions

raise throws an exception: either an instance like ValueError("message"), or a class, which Python instantiates for you.

A bare raise inside an except block re-raises the current exception. Use it when you want to do something (such as logging) and still let the error continue upwards.

☕ Java: Python has no checked exceptions and no throws clause. Any function may raise anything; document the important ones in the docstring. The keywords map as throw → raise and catch → except.

Exception chaining

If a new exception is raised while another one is being handled, Python links them and shows both: "During handling of the above exception, another exception occurred". To say on purpose "this error was caused by that one", use raise NewError(...) from original.

raise ... from None hides the original exception, for when it is an internal detail the user shouldn't see.

User-defined exceptions

Create your own exception types by subclassing Exception (classes are covered in Chapter 11). End the name in Error. A small hierarchy lets callers catch everything from your app with one clause, or catch just the specific cases.

Clean-up actions: finally

A finally block always runs as the try statement is left: after success, after a handled exception, after an unhandled one (which is then re-raised after finally), and even after return, break or continue.

⚠️ Pitfall: a return, break or continue inside finally silently swallows any exception and overrides the try block's return value. Since 3.14, Python warns about it (SyntaxWarning: 'return' in a 'finally' block, PEP 765). Don't do it.

Predefined clean-up actions: with

Some objects know how to clean up after themselves. Files close themselves, and locks release themselves. The with statement guarantees that clean-up happens, so it replaces most try/finally blocks.

Objects that work with with are called context managers. You can write your own with contextlib.contextmanager, which you'll see in Chapter 12's generators.

Raising and handling several unrelated exceptions

Sometimes several independent things fail at once: validating a whole form, or running several tasks in parallel. ExceptionGroup bundles several exceptions together, and except* handles the ones of each type in the group.

Unlike plain except, several except* clauses can run for one group, one per matching type. Any exceptions left unhandled are re-raised in a smaller group.

Enriching exceptions with notes

err.add_note(text) attaches extra context to an exception after it was created. The notes are printed in the traceback, below the message.

Recap

  • Syntax errors stop parsing. Exceptions happen at run time. Read the last line of the traceback first.
  • try/except Type as e catches the first matching type, including its subclasses, so order the clauses specific → general. Never use a bare except:.
  • else runs if nothing was raised. finally always runs; don't return inside it.
  • raise X(...) throws, a bare raise re-raises, and raise X from e chains. Custom exceptions subclass Exception.
  • with handles clean-up. ExceptionGroup with except* handles several errors at once, and add_note() adds context.

Exercise 8 🟡 medium explain why

Why should you write except FileNotFoundError instead of first checking os.path.exists(path) and then opening the file?

Show solution

Between the check and the open, another program could delete or create the file. That is called a race condition. Opening and handling the error does both in one step (EAFP). It also covers other failures, like permissions, if you catch OSError.
