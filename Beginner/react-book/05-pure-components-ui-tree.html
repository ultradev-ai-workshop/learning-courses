Pure Components & the UI Tree

One rule keeps React apps predictable: components must be "pure". Then you'll see how React views your app as a tree.

You will learn
  • What "pure" means, and why React needs it
  • How to spot and fix impure components
  • Where side effects belong instead
  • The render tree and the module dependency tree

What is a pure function?

In maths, a formula like y = 2x always gives the same answer for the same input: if x = 3, then y is always 6. A pure function works the same way. It has two properties:

  1. Same inputs → same output. Given the same props, a component always returns the same JSX.
  2. It minds its own business. It doesn't change anything that existed before it was called: no outside variables, no objects passed in.

Think of a component as a recipe: if you follow it and don't add new ingredients halfway, you get the same dish every time.

An impure component (and the bug it causes)

You might expect guests #1, #2 and #3. But React can call components any number of times and in any order. In development, StrictMode calls each one twice, so you'd see #2, #4, #6. Calling Cup gives a different result every time, so it's unpredictable.

The fix: pass the data in as a prop.

How StrictMode helps In development, React calls each component function twice. A pure component gives the same result both times, so you won't notice anything. An impure one misbehaves, which reveals the bug early. That's why your console.logs sometimes print twice.

The problem is only changing things that existed before the render: outside variables, props, state, or other components' data.

Where side effects go

Changing the screen, starting an animation, fetching data, writing to localStorage: these are side effects, things that happen "on the side" rather than during rendering. Apps need them, of course. They just don't belong in the component body.

  • First choice: event handlers. Code that runs when the user clicks, types or submits (Chapter 6). Event handlers don't run during rendering, so they don't need to be pure.
  • Last resort: Effects. useEffect runs code after rendering (Chapter 13).
Rules of thumb for the component body
  • Don't change props, state or outside variables.
  • Don't call fetch, setTimeout or document.title = ... directly in the body.
  • Just calculate and return JSX.

Why purity matters

  • Components can run anywhere, including on a server, and give the same output.
  • React can skip re-rendering components whose inputs didn't change. That's safe only because they're pure.
  • React can pause and restart rendering when something more urgent happens.
  • The React Compiler relies on purity to optimise your code automatically.

Your UI as a tree

React, like the browser, models UI as a tree: things that contain other things. Seeing this tree helps you understand how data flows, where state lives, and what re-renders.

The render tree

Given this app:

React builds this render tree, which shows which component rendered which:

  • Root: the first component (App).
  • Top-level components sit near the root. They affect everything below them and usually hold shared state.
  • Leaf components have no children. They re-render often and are usually simple.
  • With conditional rendering, the tree can differ from one render to the next.

The tree contains only components. HTML tags like <div> are left out because they're just the output.

Recap

  • A pure component returns the same JSX for the same props and doesn't change anything that existed before it ran.
  • Creating and changing local variables during render is fine.
  • Side effects go in event handlers first, and in useEffect only as a last resort.
  • StrictMode double-calls components in development to catch impurity.
  • The render tree shows who renders whom. The dependency tree shows who imports whom.
