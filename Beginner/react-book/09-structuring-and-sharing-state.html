Reacting to input with state

With plain JavaScript you write instructions: "disable the button, show the spinner, hide the form…". In React you describe the different visual states your UI can be in, and switch between them by changing state.

Think of a quiz form. Work through it in five steps:

Step 1: list the visual states

  • empty: the form has a disabled Submit button
  • typing: the form has an enabled Submit button
  • submitting: everything is disabled and a spinner shows
  • success: a "Thank you!" message replaces the form
  • error: like typing, plus an error message

Step 2: what triggers the changes?

Human inputs (typing, clicking Submit) and computer inputs (the network response arrives, success or failure).

Step 3: represent it with as little state as possible

Instead of several booleans (isTyping, isSubmitting, isSuccess…) that could contradict each other, one status can only ever be one value at a time.

Don't copy props into state The only reason to copy a prop is to deliberately ignore later changes. Name it to make that clear: initialColor.

4. Avoid duplication: store IDs, not copies

5. Avoid deep nesting

Deeply nested state is painful to update (remember all the copying in Chapter 8). Consider a flat structure, where items reference each other by ID, like database tables.

The goal Make state as simple as possible, but no simpler. Store the minimum, and calculate everything else.

Sharing state between components: lifting state up

Sometimes two components need the same data. Example: an accordion where only one panel can be open at a time.

Before: each panel has its own state

The panels can't coordinate, so both can be open at once.

After: move the state up to the common parent

There are three steps:

  1. Remove the state from the children.
  2. Pass the data down from the parent as props.
  3. Add the state to the parent, and pass down event handlers so the children can ask for changes.

Data flows down as props, and requests to change it flow up through event handler props. This is the pattern you'll use most in React.

Controlled vs uncontrolled

  • An uncontrolled component keeps its own local state. It's easy to use, but the parent can't influence it.
  • A controlled component gets its important data from props. It's more flexible, because the parent is in charge.

After lifting the state up, Panel is controlled by Accordion.

A single source of truth Every piece of state should live in exactly one component. To decide which one, find the closest common parent of all the components that need it.

Recap

  • Think in visual states, and prefer one status over many booleans.
  • Group related state, avoid contradictions, don't store what you can calculate, store IDs instead of copies, and keep it flat.
  • To share state, lift it up to the closest common parent and pass it down with props and handlers.
