Chapter 10 · Managing State

Preserving State & Reducers

When does React keep state, and when does it throw it away? And how do you tidy up complicated update logic?

You will learn
  • Why state is tied to a component's position in the tree
  • When React keeps or resets state
  • How to force a reset with key
  • How to move update logic into a reducer with useReducer

Part A · Preserving and resetting state

State lives at a position in the tree

You might think state lives "inside" a component. Actually React holds it, and attaches it to the component's position in the UI tree.

Each <Counter /> is at a different position, so each has separate state. If you stop rendering a component, React destroys its state. Render it again later, and it starts fresh.

Same component at the same position → state is kept

Toggling isFancy does not reset the count. Either way it's a Counter in the same spot, so React treats it as the same component with new props.

What matters React cares about the position in the returned JSX tree, not where the code sits in your function.

Different component at the same position → state is reset

Switching from Counter to <p> removes the Counter and its state. The same happens if the parent element changes type (for example <div> → <section>): the whole subtree is reset.

❌ This is why you never define components inside components Every render creates a different MyTextField function. React sees a different component at that position and resets its state, so the input loses its text every time the parent re-renders.

Resetting state on purpose with key

Sometimes you want a reset. Example: a chat app where the draft message should clear when you switch contacts.

A key tells React "this is a different chat when the key changes". When contact.id changes, React throws away the old Chat (including its draft) and makes a fresh one.

When a component has many event handlers that all update the same state in different ways, the logic gets scattered. A reducer gathers it all into one function, outside the component.

Why is it called a "reducer"? It's named after the array method reduce(), which takes "the result so far + the next item" and returns the new result. A React reducer takes "the state so far + the next action" and returns the new state.

useState vs useReducer

useStateuseReducer
Code sizeLess code for simple stateMore code up front
ReadabilityGreat for simple updatesBetter when there are many kinds of update
DebuggingHarder to see why state changedLog each action in one place
TestingTied to the componentThe reducer is a plain function, easy to test
Rules for reducers
  • They must be pure: no fetches, timers or mutations. Just calculate the next state.
  • Each action should describe one user interaction ('reset_form'), even if it changes several fields.

Recap

  • React keeps state as long as the same component is rendered at the same position.
  • A different component type at that position, or a removed component, means the state is reset.
  • Change the key to force a reset. Never define components inside other components.
  • useReducer(reducer, initial) moves update logic into one pure function. Handlers dispatch actions that describe what happened.
