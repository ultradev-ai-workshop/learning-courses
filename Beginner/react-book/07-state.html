State & Rendering

State is a component's memory. This chapter explains how it works and how React updates the screen when it changes.

You will learn
  • Why normal variables can't update the screen
  • How to use useState
  • The three steps of an update: trigger → render → commit
  • Why state behaves like a snapshot
  • How to queue several updates with updater functions

Why a normal variable isn't enough

Here's a gallery that tries to show the next sculpture when you click:

It doesn't work, for two reasons:

  1. Local variables don't survive between renders. On the next render, Gallery() runs from scratch and let index = 0 starts over.
  2. Changing a local variable doesn't trigger a render. React doesn't know anything changed.

To update the screen you need two things: keep the data between renders, and tell React to render again. useState gives you both.

State is private to each copy

If you render <Gallery /> twice, each copy gets its own index. Clicking one doesn't affect the other. State belongs to a specific component on screen, not to the function.

The Rules of Hooks Functions starting with use are Hooks. Call them only at the top level of a component, never inside if, loops or nested functions. React tells your state variables apart by the order of the calls, so that order must never change between renders.

Render and commit: how the screen updates

Picture React as a kitchen: components are cooks and React is the waiter.

  1. Trigger: an order comes in. Either the app starts (the initial render via createRoot().render()) or some state was updated with a setter.
  2. Render: the cooks prepare the dish. React calls your component functions to find out what the screen should look like. On updates it calls the component whose state changed, and its children.
  3. Commit: the dish is served. React applies the minimal changes to the real DOM. If the output is the same as last time, React doesn't touch the DOM at all.

After the commit, the browser repaints the screen.

"Rendering" ≠ "changing the page" In React, rendering means "calling your component". Only the commit step touches the page, and only where something actually changed. That's why text you've typed into an <input> survives a re-render of its parent.

Queueing updates with updater functions

To update the same state several times in one event, pass a function that computes the next value from the previous one:

React puts the updates in a queue and processes them in order after your handler finishes:

Queued updatenreturns
n => n + 101
n => n + 112
n => n + 123

This is called batching. React waits until all the code in the event handler has run, then does one re-render with the final result. That's efficient, and you never see a half-updated screen.

When to use which
  • setX(5) or setX(value) when the new value doesn't depend on the old one.
  • setX(x => x + 1), setOn(on => !on) when it depends on the previous value. It's always safe.
  • Name the parameter after the state's first letter (n, c) or prev... (prevCount).

Recap

  • Use state for data that changes and should update the screen: const [x, setX] = useState(initial).
  • Calling a setter stores the new value and triggers a re-render.
  • Updates go trigger → render (call components) → commit (minimal DOM changes).
  • State is a snapshot: the variable keeps its value until the next render.
  • Use setX(prev => ...) to queue updates that build on each other.
  • Call Hooks only at the top level.
