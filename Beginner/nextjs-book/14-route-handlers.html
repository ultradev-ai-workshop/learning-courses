Route Handlers

Pages return HTML for people. Sometimes you need an endpoint that returns data for programs: a mobile app, a partner's system, a webhook from a payment provider, a fetch from a browser extension. Route Handlers are those endpoints. They use the web-standard Request and Response APIs, and this chapter, following the docs' Route Handlers page, builds a small JSON API for the Reading List and tests it with curl.

You will learn

  • The route.ts convention and the supported HTTP methods.
  • Reading params (RouteContext), the query string, the body, headers and cookies.
  • Returning JSON, status codes and headers with Response and NextResponse.
  • How GET handlers are prerendered or run per request with Cache Components.
  • Why a route.ts and a page.tsx can't share a folder.
  • When to use a Route Handler and when a Server Function is better.

The convention

A route.ts file in app/ defines an endpoint for its folder's URL. Export a function named after each HTTP method you support: GET, POST, PUT, PATCH, DELETE, HEAD or OPTIONS. A request with any other method gets 405 Method Not Allowed.

Headers, cookies and NextRequest

The handler's request is a standard Request, so request.headers.get(…) works. Next.js also offers:

  • headers() and cookies() from next/headers, the same functions as in Server Components and Server Actions.
  • NextRequest and NextResponse (from next/server), which extend the standard classes with conveniences: request.nextUrl (a parsed URL), request.cookies.get(), response.cookies.set(), and NextResponse.redirect().

-c/-b make curl store and send cookies like a browser, so the second call sees visits=1.

Caching GET handlers

With Cache Components, GET handlers follow the same model as pages:

  • A handler that uses no uncached or runtime data is prerendered at build time.
  • One that reads the request (request.url, headers, cookies), uncached I/O (database, fetch, async file reads) or random values runs at request time.
  • Data from a "use cache" helper can be part of a prerendered response. You can't put "use cache" directly in the handler body: extract a helper function.

Other methods (POST, DELETE…) are never cached.

Here's the third symbol: ƒ (Dynamic) for handlers that run on every request. /api/books reads the request URL and the data file, /api/whoami reads cookies, so they're dynamic. /api/info and the cached /api/genres are prerendered (○), the latter revalidated daily. A route and a page can't share a folder

A route.ts takes over all HTTP methods of its URL, and a page.tsx answers GET with HTML, so they can't be in the same folder. That's why APIs usually live under app/api/:

Route Handlers also don't take part in layouts or client-side navigation: they're the lowest-level routing primitive. Special files like sitemap.ts, robots.ts and opengraph-image.tsx (Chapter 13) are Route Handlers too, cached like any GET.

Route Handler or Server Function?

Use a…When
Server Function (Chapter 7)Your own UI changes data: forms, buttons. You get type-safe calls, progressive enhancement and UI updates in one round trip, with no URL to design.
Route HandlerSomething other than your UI calls you: webhooks, mobile apps, third parties, cron jobs; or you need a specific URL, method, status code, header or content type (CSV, RSS, files).
Server Component (Chapter 6)Your own pages read data. Don't call your own Route Handlers from Server Components: call the data function directly.

🧠 Analogy: Server Functions are the internal phone line between departments of one company: quick, and nobody outside needs the number. A Route Handler is the public reception desk with a published address: anyone can walk in, so it has fixed procedures and checks ID.

Recap

  • route.ts exports functions named after HTTP methods; unexported methods get 405.
  • Handlers use web-standard Request/Response; Response.json(data, { status, headers }) is the usual reply.
  • Params come from the context, typed with RouteContext<"/path/[id]">; the query string from new URL(request.url) or request.nextUrl.
  • NextRequest/NextResponse add parsed URLs, cookie helpers and redirects; headers()/cookies() work too.
  • With Cache Components, GET handlers are prerendered (○) unless they use request or uncached data (ƒ); cache data in a "use cache" helper.
  • A route.ts can't share a folder with a page.tsx. Use Server Functions for your own UI and Route Handlers for external callers.

Exercise 9 🔴 hard anti-pattern

A Server Component does await fetch("http://localhost:3000/api/books"). List three problems with this, and the fix.

Show solution
  1. An extra HTTP round trip from the server to itself, with serialization both ways: slower for nothing.
  2. The URL is environment-specific (port, host, HTTPS), and during next build no server is running, so prerendering fails.
  3. It loses type safety and makes caching and error handling harder (now there's a network error to handle).

Fix: import and call the data function (getBooks()) directly. Keep the Route Handler for external clients.

Exercise 10 🔴 hard design

Design a small versioned REST API for the Reading List's future mobile app: list, read, create, update and delete books, plus "mark as read" per user. Give the folder layout, methods and status codes, and say where authentication goes.

Show solution

Every handler starts by reading the session or a bearer token (Chapter 16) and returns 401/403 before touching data; share that check in a helper (e.g. requireUser(request)). Validate bodies with Zod. Keep business logic in lib/ so the web UI's Server Functions and this API share it. The v1 folder lets you change the API later without breaking old app versions.
