Chapter 1 · Foundations

What Next.js Is (and Isn't)

The official docs open with one sentence: "Next.js is a React framework for building full-stack web applications." This chapter unpacks it. You'll see what React gives you, what Next.js adds on top, which problems that solves, and when you don't need Next.js at all. Every example is a real Next.js 16.4 app that was built and opened in a browser to get the output shown.

You will learn

  • The difference between a library (React) and a framework (Next.js).
  • What "full-stack" means here: pages, data and an API in one project.
  • Why HTML made on the server helps first load, search engines and slow phones.
  • The rendering words you'll meet: prerendering, static, dynamic, streaming, Cache Components.
  • When Next.js is a good fit, and when plain React (or something else) is better.

React is a library for building UI

React does one job: it turns components (functions that return JSX) into UI, and updates that UI when state changes. It doesn't decide how URLs map to screens, where data comes from, how code is bundled, or how the app reaches users. You pick those pieces yourself: a router, a bundler like Vite, a data library, a server for your API.

A typical React app built with Vite is a single-page application (SPA). The server sends an almost empty HTML file, and JavaScript builds the whole page in the browser:

Until that JavaScript downloads and runs, the user sees a blank page. So does any tool that reads only the HTML.

Next.js is a framework built on React

A framework makes those other decisions for you and wires the pieces together. You still write React components. Next.js adds:

You give up some choice (the seats are Next.js seats), and in return you drive away today, and the parts are made to work together.

Interactivity: Client Components

Server-rendered HTML can't respond to clicks by itself. For that you write a Client Component: a file that starts with "use client". It still renders to HTML on the server first, then its JavaScript is sent to the browser to make it interactive. That step is called hydration.

The output was read after clicking the button three times. This is plain React (useState, onClick); Next.js only decided where it runs. Chapter 5 explains when to use each kind of component.

"Full-stack": an API in the same project

Next.js also runs server code that isn't a page. A file named route.ts is a Route Handler: it answers HTTP requests using the web-standard Request and Response objects.

So one project, one deployment and one language (TypeScript) cover the pages, the data access and the API. That is what "full-stack" means in the docs' sentence.

What problems does Next.js solve?

Each feature exists because plain single-page apps run into the same problems again and again:

  1. Slow first load and a blank screen. An SPA must download, parse and run its JavaScript before anything appears. Next.js sends HTML first, and much of it can be prerendered at build time.
  2. Search engines and link previews. Crawlers and social apps read the HTML. With Next.js, the content and the <title>/<meta> tags are in it.
  3. Too much JavaScript. In an SPA every component ships to the browser. Server Components send no JavaScript, and each route only loads the code it needs (automatic code splitting).
  4. Request waterfalls. Fetching in useEffect means: load JS → render → fetch → render → fetch again. Server Components fetch on the server, close to the database, before HTML is sent.
  5. Secrets in the browser. Code that talks to a database needs credentials. In Server Components it stays on the server; only the result is sent.
  6. Glue code. Routing, bundling, TypeScript, CSS, image resizing, font loading and an API server are all configured and work together.

The rendering words you'll meet

Older articles talk about SSR, SSG and ISR as separate "modes". Next.js 16 with Cache Components (on by default in new projects) uses a simpler model, but you'll still see the old words, so here they are side by side:

TermMeaningIn Next.js 16
CSR (client-side rendering)The browser builds the page with JavaScript.What Client Components do after hydration.
SSR (server-side rendering)The server builds HTML for each request."Dynamic" rendering: content that depends on the request (cookies, search params) or must be fresh.
SSG (static site generation)HTML is built once, at build time."Prerendering": the default for anything that doesn't depend on the request.
ISR (incremental static regeneration)Static HTML is rebuilt in the background after a time or an event.Cached content with cacheLife, refreshed with revalidateTag/updateTag (Chapters 8–9).
PPR (partial prerendering)One page mixes a static shell with dynamic parts.What Cache Components does: a prerendered static shell, with dynamic parts streamed in through <Suspense>.

You can see the build's decisions in the output of next build. The ○ marks routes that were prerendered:

All four routes are static: none of them reads anything from the request. In later chapters you'll see ◐ (a static shell with streamed dynamic parts) and ƒ (rendered on demand) appear.

🧠 Analogy: a bakery. Static pages are bread baked before opening: ready the moment you ask. Dynamic pages are sandwiches made to order: fresh, but you wait. Partial prerendering is a sandwich on bread baked this morning, filled while you watch: most of the work was done in advance, and only the personal part happens now. Revalidation is the baker making a fresh batch when the old one gets stale.

So what is the main difference between Next.js and React?

In one line: React is how you describe UI; Next.js is how you build, serve and run a whole web app with that UI. Next.js isn't a replacement for React. Every Next.js app is a React app, and everything you know about components, props, state and hooks still applies. The FAQ goes into more detail.

ReactNext.js
What it isA UI libraryA framework that uses React
RunsIn the browser (and on a server if you set it up)On the server, at build time, and in the browser
RoutingNot includedFile-system routing
Data loadingYour choiceServer Components, Server Functions, caching
DeploymentStatic files on any hostA Node.js server, a platform like Vercel, or static export
Learning costSmallerReact + server concepts (this book)

When is Next.js the better choice?

✅ Good fit:

  • Public sites that must load fast and rank in search: shops, blogs, marketing pages, documentation.
  • Apps that mix public pages and logged-in screens.
  • Teams who want front end and back end in one TypeScript codebase.
  • Content that changes sometimes (product lists, articles) and benefits from caching.
  • Projects that want sensible defaults instead of assembling a toolchain.

❌ Probably not needed:

  • A purely client-side tool behind a login, where SEO doesn't matter and you already have an API (an admin panel, an in-browser editor). Vite + React is simpler.
  • A widget embedded in someone else's page.
  • A site of a few static pages, where plain HTML or a static site generator is enough.
  • Hosting that can only serve static files and a team that needs server features (Next.js can export static files, but loses its server features: Chapter 18).
  • A large back end with jobs, queues and many services: keep that in a dedicated back end (Node, Java, Python…) and let Next.js be the web front end that calls it.

⚠️ Common misunderstanding: "Next.js needs Vercel." It doesn't. Vercel makes Next.js and hosts it well, but next build + next start runs on any server with Node.js, and there are Docker and adapter options too (Chapter 18).

App Router and Pages Router

Next.js has two routers. The App Router (the app folder) is the current one; it supports Server Components, streaming and Server Functions. The Pages Router (the pages folder) is the original one, still supported. This book teaches the App Router, as the docs recommend for new projects. Appendix B explains the Pages Router so you can read older code.

Recap

  • React builds UI from components; Next.js is a framework that adds routing, server rendering, data loading, an API layer and build tooling.
  • Components in app/ are Server Components by default: their HTML is made on the server and they ship no JavaScript.
  • "use client" marks a Client Component for interactivity; it's prerendered to HTML, then hydrated.
  • route.ts files are API endpoints in the same project: that's the "full-stack" part.
  • next build prerenders what it can (○); Cache Components mixes a static shell with streamed dynamic parts.
  • Next.js suits public, fast, SEO-relevant apps; a client-only tool behind a login may not need it.

Exercises

Exercise 1 🟢 easy definitions

In your own words: what is the difference between a library and a framework? Which one is React, and which is Next.js?

Show solution

You call a library when you need it; you choose the rest of the architecture. A framework provides the architecture and calls your code at the right places (for example, Next.js calls your page.tsx component when a URL is requested). React is a library for UI; Next.js is a framework built on React.

Exercise 2 🟢 easy predict

A page component contains console.log("rendering"). It's a Server Component with no dynamic data. Where does the message appear: in the browser's console, in the terminal, or both? When?

Show solution

In the terminal, never in the browser. A Server Component's code runs on the server. Because the page is static, in production it runs once, during next build, when the page is prerendered. In development (next dev) it runs on every request, so you see it each time you reload.

Exercise 3 🟢 easy match

Match each need to the Next.js feature: (a) an endpoint that returns JSON, (b) a button that counts clicks, (c) the URL /about, (d) reading from a database before HTML is sent.

Show solution

(a) A Route Handler, app/api/…/route.ts. (b) A Client Component with "use client" and useState. (c) A file app/about/page.tsx. (d) An async Server Component that awaits the query.

Exercise 4 🟢 easy true or false

True or false? (1) You must deploy Next.js to Vercel. (2) Every Next.js app is a React app. (3) Client Components are never rendered on the server. (4) A Server Component's code is included in the browser's JavaScript.

Show solution

(1) False: any Node.js server works. (2) True. (3) False: Client Components are prerendered to HTML on the server too, then hydrated in the browser. (4) False: only its rendered output is sent.

Exercise 5 🟡 medium choose

For each project, say whether you'd pick Next.js or plain React + Vite, and why: (a) an online bookshop, (b) an image editor that runs entirely in the browser, (c) a company blog with 300 articles, (d) an internal dashboard that calls an existing Java API and is only used by logged-in staff.

Show solution
  • (a) Next.js: product pages must be fast and indexed; carts and checkout need server code.
  • (b) Vite + React: everything is client-side and interactive; server rendering adds little.
  • (c) Next.js (or a static site generator): articles can be prerendered and cached; SEO matters.
  • (d) Either. Vite + React is enough if the API exists and SEO is irrelevant. Next.js still helps if you want server-side calls to the API (secrets stay on the server) or one TypeScript codebase.

Exercise 6 🟡 medium explain

Explain the "request waterfall" in a client-rendered React page that fetches a user, then that user's orders, in useEffect. How does a Server Component improve it?

Show solution

In the browser: download HTML → download JS → render → effect fetches the user → render → effect fetches orders → render. Each step waits for the one before, over the user's (maybe slow) network. A Server Component runs on the server, near the database: it awaits the user and the orders there (in parallel if they're independent, see Chapter 6), and sends finished HTML in one response.

Exercise 7 🟡 medium rendering words

A product page shows the product's name and description (they change once a week) and the price for the logged-in user's country (read from a cookie). Using this chapter's table, which parts are "static" and which are "dynamic"? What does Next.js 16 do with such a page?

Show solution

Name and description are cacheable: they can be part of the prerendered static shell (refreshed when they change). The price depends on a cookie, so it's dynamic: it must be rendered per request. With Cache Components, Next.js sends the static shell immediately and streams the price in when it's ready, inside a <Suspense> boundary. That's partial prerendering.

Exercise 9 🔴 hard investigate

Build the counter example with npm run build and start it with npm start. Open the page with JavaScript disabled in your browser's DevTools. What do you see? Can you click the button? What does this tell you about Client Components?

Show solution

You see "Counter" and the button text "Clicked 0 times": the Client Component was prerendered to HTML on the server. Clicking does nothing, because the onClick handler only exists after the JavaScript loads and hydrates the button. Client Components are "server-rendered first, interactive after hydration", not "browser-only".

Exercise 10 🔴 hard argue

Your team lead says: "We'll use Next.js so we don't need a back end." Give two cases where that's right and two where you'd still want a separate back end.

Show solution

Right: (1) a site whose server needs are reading and writing one database (Server Components and Server Functions do this well); (2) small JSON endpoints for a mobile app, written as Route Handlers. Still want a back end: (1) long-running work such as video processing, scheduled jobs or queues, which don't fit request/response handlers; (2) an existing system or many clients (mobile, partners, other services) that need a stable API owned by its own team. There, Next.js is the web front end and calls that API from the server, a pattern the docs call "Backend for Frontend".
