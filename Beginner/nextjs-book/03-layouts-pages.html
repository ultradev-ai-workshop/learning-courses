Layouts and Pages

Next.js uses file-system routing: folders and files define your routes. This chapter follows the docs' Layouts and Pages page. You'll create pages, wrap them in shared layouts, nest layouts, and organise folders without changing URLs. You'll also see the key property of layouts, proved in a real browser: they keep their state when you navigate.

You will learn

  • How folders become URL segments, and why a page file makes a route public.
  • Layouts: shared UI that wraps pages, nests, and doesn't re-render on navigation.
  • The root layout's rules, and the LayoutProps and PageProps helper types.
  • Templates: layouts that re-mount on every navigation.
  • Route groups (name) and private folders _name for organising code.
  • Why layouts can't read the pathname or search params, and the client hooks that can.

Creating a page

A page is the UI for one route. Create a file called page.tsx and export default a React component. The folder it's in decides the URL:

FileURL
app/page.tsx/
app/about/page.tsx/about
app/blog/page.tsx/blog
app/blog/authors/page.tsx/blog/authors

Each folder is a route segment. The URL /blog/authors has three: the root segment (/), blog, and the leaf segment authors. A folder without a page file isn't a route: visiting it gives a 404.

Creating a layout

A layout is UI shared by several pages: a header, a navigation bar, a footer. Export a component from a layout.tsx file. It receives the page (or a nested layout) as its children prop:

The same header and footer appear on /about. <Link> (from next/link) is Next.js's version of <a>: it navigates on the client, without a full page reload. Chapter 4 covers it in detail.

The root layout's rules

  • app/layout.tsx is the root layout. It's required, and it must render <html> and <body>.
  • Don't add <head>, <title> or <meta> tags by hand. Use the Metadata API (Chapter 13), which handles streaming and de-duplication.
  • An app can have several root layouts (one per route group, below). Navigating between them causes a full page load.

LayoutProps and PageProps

Next.js generates two global types from your folders, so you don't need to write prop types by hand:

  • LayoutProps<"/dashboard">: children, any parallel-route slots, and params.
  • PageProps<"/blog/[slug]">: params (a promise of { slug: string }) and searchParams.

The string must be a real route in your app; a typo is a type error. They're generated by next dev, next build or next typegen. Writing { children }: { children: React.ReactNode } by hand, as the docs' first examples do, also works.

Layouts keep their state on navigation

This is the most important thing about layouts. When you navigate between two pages that share a layout, the layout isn't re-rendered or re-mounted. Only the part below it changes. The docs say layouts "preserve state, remain interactive, and do not rerender".

To prove it, put a Client Component with state in a layout:

Open /shop/shoes, click the counter three times, then click the Hats link:

The page changed to Hats, but the counter still says 3. The layout, and the state of everything in it, survived the navigation. That makes layouts the right place for things that should persist: a search box with typed text, a playing audio player, an open sidebar. It's also faster: the server only sends the part of the page that changed.

🧠 Analogy: a layout is a picture frame, and the page is the picture. When you navigate, Next.js swaps the picture and leaves the frame on the wall. Anything you've done to the frame (a note stuck on it, a light turned on) is still there.

Templates: when you want a fresh copy

Sometimes you want the shared UI to reset on every navigation: an enter animation, a feedback form that should start empty, an effect that should run for every page. Use a template.tsx instead of (or as well as) a layout. It wraps children the same way, but it gets a new key for each route, so React re-mounts it:

Same clicks, same navigation, and the counter is back to 0. Use layouts by default and templates only when you need the reset.

Layouts can't see the URL; Client Components can

Because a layout doesn't re-render on navigation, it can't receive the current pathname or search params: they would go stale. If shared UI needs them (an "active" link, a breadcrumb), put that piece in a Client Component and use a hook from next/navigation:

  • usePathname() returns the current path, e.g. "/shop/hats".
  • useSearchParams() returns the query string as a read-only URLSearchParams.

Route groups: organise without changing URLs

A folder in parentheses, like (marketing), is a route group. It's left out of the URL. Use groups to:

  • organise routes by section or team;
  • give a set of routes their own layout, without adding a URL segment;
  • create several root layouts.

The URLs are /pricing and /cart: no (marketing) or (shop) in them. Each group has its own layout.

Colocation and private folders

A route is only public when it has a page (or route) file, and only what that file returns is sent. So you can safely keep other files next to your routes: components, helpers, styles, tests.

A folder whose name starts with an underscore, like _components, is a private folder. Next.js ignores it and all its subfolders for routing, even if it contains a page.tsx:

Private folders are optional; plain colocation works without them. They're useful to make "this isn't a route" obvious and to avoid clashes with future Next.js file names. The docs' Project Structure page shows three common strategies: keep code outside app/ (in components/, lib/), keep it in top-level folders inside app/, or split it by feature next to the routes that use it. Pick one and be consistent.

Recap

  • Folders are URL segments; a page.tsx file makes a segment a public route.
  • layout.tsx wraps a segment and all its children; layouts nest. The root layout is required and renders <html> and <body>.
  • Layouts persist on navigation: they don't re-render and their state is kept. template.tsx re-mounts instead.
  • Layouts can't read the pathname or search params; use usePathname/useSearchParams in a Client Component.
  • (group) folders organise routes and add layouts without changing URLs; _private folders are never routed.
  • LayoutProps<"/route"> and PageProps<"/route"> are generated, global prop types.

Exercise 3 🟢 easy true or false

Show solution

(1) False. (2) True. (3) Don't: use the Metadata API. (4) False: it's a global type, generated from your routes.

Exercise 5 🟡 medium predict

A layout contains a text <input> in a Client Component. You type "dune", then click a <Link> to a sibling page under the same layout. What does the input contain? What if the input lived in the page instead?

Show solution

In the layout, it still contains "dune": the layout isn't re-mounted. In the page, it's empty: the old page is unmounted and the new one mounted, so its state is gone. (The same is true for an input in a template.tsx.)

Exercise 8 🟡 medium layout or template?

For each, choose a layout or a template: (a) a sidebar whose sections can be collapsed, (b) a fade-in animation for every page, (c) a "Was this page helpful?" widget that should reset for each page, (d) a music player in the header.

Show solution

(a) Layout: keep the collapsed state. (b) Template: the animation must re-run on each navigation. (c) Template: it must start fresh. (d) Layout: the music must keep playing.

Exercise 9 🔴 hard debug

A developer writes this layout to highlight the active tab and finds it "sometimes shows the wrong tab after clicking a link". Explain the bug and fix it.

Show solution

Layouts don't re-render on client-side navigation. The header is read once, when the layout first renders, so after navigating to a sibling page active is stale. (Reading headers() also makes the layout dynamic, so under Cache Components it would need a <Suspense> boundary.) The fix: make Tabs a Client Component that calls usePathname(), and drop the header logic.
