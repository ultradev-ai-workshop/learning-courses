Chapter 9 · Rendering & Data

Revalidating

A cache is only useful if it's refreshed when the data changes. Revalidation updates cached data while you keep serving fast responses. This chapter follows the docs' Revalidating page. It covers the two strategies (time-based and on-demand), tags, and the difference between updateTag and revalidateTag. You'll watch stale-while-revalidate happen in real requests, and connect the "Add a book" form from Chapter 7 to the cache from Chapter 8.

You will learn

  • Time-based revalidation with cacheLife, and what "stale-while-revalidate" means.
  • Tagging cached data with cacheTag.
  • updateTag for read-your-own-writes, revalidateTag for background refreshes.
  • revalidatePath, and why tags are usually better.
  • Revalidating from outside the app: a webhook Route Handler.
  • What happens when you forget to revalidate.

Two strategies

  • Time-based: the cache refreshes itself after a set time, configured with cacheLife. Good for data that changes on its own schedule: news, prices, "trending" lists.
  • On-demand: your code invalidates the cache when it knows the data changed (after a mutation, or when a CMS sends a webhook), with updateTag, revalidateTag or revalidatePath.

They're often combined: a long lifetime (max) plus a tag you invalidate on every edit.

🧠 Analogy: a supermarket shelf. Time-based revalidation is the "best before" date: after it passes, the next customer still gets the old carton while staff restock in the back. On-demand revalidation is a recall: the supplier phones and says "these are wrong", and the shelf is cleared. updateTag is clearing it while you, the customer who reported it, wait at the shelf, so you get the new carton. revalidateTag just marks it for restocking: the next shopper might get one last old carton.

Time-based revalidation

Chapter 8 introduced cacheLife. Its revalidate time is what drives time-based revalidation, using stale-while-revalidate (SWR) semantics: once an entry is older than revalidate, the next request is still served the old (stale) value immediately, and that request triggers a refresh in the background. The request after that gets the fresh value. Nobody waits.

Tagging cached data: cacheTag

For on-demand revalidation, give cache entries a tag: a string you choose, like "books" or "book-42". Call cacheTag inside the "use cache" scope. One entry can have several tags, and one tag can be shared by many functions, so invalidating it refreshes them all.

The "database" in this chapter is a JSON file, so that every part of the app (pages, Server Actions, Route Handlers) reads and writes the same data. Module-level variables, as in Chapter 7, aren't safe for that: each route can be bundled with its own copy of a module.

updateTag: the user sees their own change

When a user submits a form, they expect to see the result straight away. updateTag(tag) expires the tagged entries immediately, and the page the action re-renders already uses fresh data. This is called read-your-own-writes. updateTag can only be called in Server Actions.

revalidateTag: refresh in the background

revalidateTag(tag, profile) marks tagged entries as stale instead of expiring them. The next request gets the stale data immediately and triggers a background refresh, the same SWR behaviour as time-based revalidation. Use it when a short delay is acceptable (a product catalogue, a blog). It works in Server Actions and Route Handlers. The second argument says how long stale content may be served; the docs recommend "max".

⚠️ Protect webhook endpoints. Anyone can POST to a public URL. A real webhook route checks a shared secret (for example a header compared with an environment variable, Chapter 16) before revalidating. When a webhook needs the data gone immediately, and updateTag isn't available because it's not a Server Action, pass { expire: 0 } as the second argument.

revalidatePath

revalidatePath("/books") invalidates the cached data and output of a route. Use it when you don't know (or haven't set up) the tags a page depends on. Chapter 7 used it with uncached data, where it simply re-rendered the page. With a type argument it can cover a whole dynamic route or a layout and everything below: revalidatePath("/books/[id]", "page"), revalidatePath("/", "layout").

💡 The docs recommend tags over paths when possible. A tag follows the data: change a book and updateTag(`book-${id}`) refreshes the detail page, the list, the home page widget and the search results, wherever that data is used. A path refreshes one route, so you must remember every page that shows the book.

What if you forget to revalidate?

The mutation succeeds, but the cache keeps serving the old data until its lifetime runs out. With cacheLife("max"), that's 30 days:

"second note" was saved on the server, but even after a reload the page shows only the first. If "my change doesn't show up" happens to you, look for a missing updateTag, revalidateTag or revalidatePath.

What should I cache?

  • Cache data that doesn't depend on the request (cookies, headers, search params) and that may be served from a cache for a while.
  • For content that changes only when someone edits it (CMS content, product data): cacheLife("max") + cacheTag, and revalidate from the edit action or a webhook. This avoids pointless timed refreshes.
  • For content that changes on its own (rankings, prices from another system): a time-based profile like minutes or hours.
  • For per-user or per-request data: don't share it in a cache; stream it in <Suspense>.

refresh() is not revalidation. refresh() re-renders the current page, but cached functions keep returning cached values. It's for uncached data (as in Chapter 7) or client-side state that depends on the server. After changing cached data, use a tag or path.

Recap

  • Time-based: cacheLife's revalidate refreshes entries in the background with stale-while-revalidate.
  • cacheTag("tag") labels cached entries; one tag can cover many functions, one entry can have many tags.
  • updateTag (Server Actions only) expires entries now, so users see their own writes. revalidateTag(tag, "max") marks them stale for a background refresh, and works in Route Handlers too.
  • revalidatePath refreshes a route; prefer tags, which follow the data.
  • Protect revalidation webhooks with a secret. A missing revalidation means stale data until the lifetime ends.

Exercises

Exercise 1 🟢 easy definitions

Explain "stale-while-revalidate" in two sentences.

Show solution

When cached data is past its revalidate time (or has been marked stale), the next request is still answered immediately with the old data. That request triggers a refresh in the background, so later requests get the new data.

Exercise 2 🟢 easy choose

updateTag or revalidateTag? (a) A user edits their profile name and is sent back to their profile page. (b) A nightly job imports new books and calls an API route. (c) An admin publishes a blog post; readers may see it a few seconds later.

Show solution

(a) updateTag: they must see their change. (b) revalidateTag(…, "max") in the Route Handler (updateTag isn't allowed there). (c) revalidateTag(…, "max"); updateTag in the publish action is fine too if the admin should see it at once.

Exercise 3 🟢 easy true or false

True or false? (1) updateTag can be called from a Route Handler. (2) One cacheTag call can add several tags. (3) refresh() invalidates cached functions. (4) Revalidation happens when a page is next requested.

Show solution

(1) False: Server Actions only. (2) True: cacheTag("books", "book-1"). (3) False. (4) True.

Exercise 4 🟢 easy predict

A function uses cacheLife("hours") and no tag. Data changes at 10:00; the entry was created at 9:30. When will users first see the change, at the earliest?

Show solution

The entry becomes stale at 10:30 (revalidate = 1 hour). The first request after 10:30 still gets the old data and triggers a refresh; the request after that sees the change. So shortly after 10:30, not at 10:00. Add a tag and revalidate on change if that's too slow.

Exercise 6 🟡 medium tags design

A book appears on: its detail page, the full list, "Books by this author", and the home page's "Recently added" widget. Design tags so that (a) editing a book refreshes all four, (b) adding a book refreshes the list, the author page and the widget, but no other book's detail page.

Exercise 8 🟡 medium debug

An admin renames a book with a Server Action that calls refresh(). The admin page shows the new name (it reads uncached data), but the public book page still shows the old one. Why, and what's the fix?

Show solution

refresh() only re-renders the current page; it doesn't touch the cache. The public page reads the book through a cached function, which keeps returning the old value. Fix: call updateTag(`book-${id}`) (and updateTag("books") if the list shows the name) in the action.

Exercise 9 🔴 hard explain

Why does revalidateTag take a second argument (a profile), and what does { expire: 0 } change? When would you use it?

Show solution

The second argument sets how long stale content may still be served while the refresh runs. With "max" (a year), requests always get an instant, possibly stale answer. With { expire: 0 }, stale content is never served: the next request waits for fresh data (a cache miss). Use it from a Route Handler (where updateTag isn't available) when correctness matters more than speed, for example after a price correction or a legal takedown.

Exercise 10 🔴 hard design

Your bookshop gets prices from a supplier system that updates them at random times, roughly hourly, with no webhook. Customers must never be charged a stale price at checkout, but the catalogue can be up to an hour old. Design the caching and revalidation.

Show solution
  • Catalogue pages: cache the price lookup with cacheLife("hours") (time-based). They're fast and at most about an hour stale.
  • Checkout: don't use the cached price. Read the price fresh from the supplier inside the order Server Action, compare it with the price the customer saw, and ask them to confirm if it changed.
  • Optionally: when checkout detects a changed price, call updateTag(`price-${id}`) so the catalogue catches up early.

Caching is for reading; decisions that involve money or permissions should use fresh data.
