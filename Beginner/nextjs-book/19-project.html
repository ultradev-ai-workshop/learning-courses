Capstone: Reading List App

Time to put everything together, the way the docs recommend building a Next.js app in 2026: Server Components that read cached data, Server Actions that change it and revalidate tags, streaming where data depends on the request, a signed-cookie login with a data access layer, a small JSON API, metadata and OG images, and tests. The result is the Reading List: the app the playground exercises have been building since Chapter 1. Every file below is the finished reference in playground/reference/ of the nextjs-playground repo, and the whole app was built, browsed and tested to produce the outputs on this page.

You will build

  • A home page with reading statistics and recent books, fully prerendered from cached data.
  • A searchable book list (next/form + searchParams + Suspense) and prerendered detail pages with metadata, OG images and a 404.
  • A login with a signed, httpOnly session cookie, a data access layer and an optimistic Proxy check.
  • An admin page whose Server Actions add, delete and mark books with updateTag, so changes appear immediately.
  • A JSON API, robots.txt and a sitemap.
  • Unit tests with Vitest and end-to-end tests with Playwright.

The plan

Work through the steps in your playground, or read them alongside the reference. The playground how-to explains how to run the reference.

Step 1: Data and types

Books live in a JSON file, so pages, actions and Route Handlers all see the same data (the lesson of Chapter 9). Reads go through "use cache" functions tagged books and book-<id> with cacheLife("max"): they're prerendered and only refreshed when an action calls updateTag. Writes go straight to the file.

import "server-only" guarantees the file system code never ends up in a Client Component. searchBooks isn't cached itself: it filters the cached list, which is cheap.

Step 2: Pure logic you can test

Statistics and validation are plain functions with no Next.js in them, so Vitest can test them directly (Step 9).

Step 3: Layout, navigation and styles

The root layout sets the metadata template and metadataBase (Chapter 13), loads Geist with next/font (Chapter 12), and imports Tailwind (Chapter 11). The navigation is the only Client Component in the layout, because it needs usePathname (Chapter 3).

Step 4: Public pages

The home page awaits cached data directly, so it's fully static. The list reads searchParams, so its results stream inside <Suspense> while the heading and the search form are in the static shell. The search form uses <Form> from next/form: a regular HTML GET form (works without JavaScript) that, with JavaScript, navigates client-side and prefetches like a <Link>.

The detail page prerenders every book with generateStaticParams, builds its title from the data with generateMetadata (one cached read serves both), and calls notFound() for unknown IDs. Each book also gets a generated Open Graph image.

Step 5: Sessions and login

This is Chapter 16's auth, unchanged in structure: a signed JWT in an httpOnly cookie, demo users with scrypt password hashes, and a data access layer that every protected read and action goes through. The Proxy does a fast, optimistic check for /admin; the real check is in the DAL.

Step 6: The admin area

Every admin action starts with requireAdmin() (Chapter 7's rule: Server Functions are public endpoints), validates with the Zod schema from Step 2, writes, and calls updateTag so the admin, and every other visitor, sees the change immediately (Chapter 9). The ID for delete and toggle is bound with .bind; the action re-checks permissions anyway.

The admin layout's metadata adds robots: { index: false }, so search engines don't index it even if they find the URL.

Step 7: API and SEO files

Step 8: Configuration

The next.config.ts is create-next-app's, plus poweredByHeader: false (Chapter 18), with one deliberate change explained in the note below. The session secret comes from .env.local, which is never committed; the repo has a .env.example.

⚠️ A note on Partial Prefetching. While testing this capstone with Next.js 16.4.5, the end-to-end test found a problem with partialPrefetching: true (the create-next-app default). After an admin added a book (updateTag("books")), if the next request for a book page was a client-side navigation, the regenerated page lost its <title> ("Reading List" instead of "Dune · Reading List"), and that version was cached for later visitors too. A full page load first, or partialPrefetching: false, avoided it. The reference therefore sets it to false. This is exactly the kind of behaviour that changes between releases: on a newer version, set it back to true, run npm run test:e2e after adding a book in the admin page, and keep the default if the test passes.

Step 9: Build and try it

The build's route table shows the rendering decisions you made:

  • /, the book pages and the sitemap are static, with cacheLife("max")'s 30-day revalidation (refreshed earlier by updateTag).
  • /books and /admin are ◐: static shells with streamed results (search params, session).
  • The API handlers read the request, so they're ƒ; the OG images are generated per book at build time (●). ƒ Proxy confirms proxy.ts was picked up.

Recap

  • Cached, tagged reads ("use cache" + cacheTag) make most pages static; updateTag in actions keeps them fresh.
  • Request-dependent parts (search, session) stream inside <Suspense>, behind a static shell.
  • Every action and handler checks its own permissions and input; Proxy is only a fast first filter.
  • Pure logic lives in lib/ and is unit-tested; real user flows are tested end to end against next start.
  • next build's route table is your map of what's static, partial and dynamic.

Exercises

These extend the capstone. Solutions describe one good approach; compare with your own.

Exercise 1 🟢 easy playground

Add a pages number to every book (data, type, schema, form, detail page). Show "n pages" on the detail page.

Show solution

Add pages: number to Book in lib/types.ts (it flows into NewBook), add "pages" to each book in data/books.json, add pages: z.coerce.number().int().min(1).max(20000) to NewBookSchema and "pages" to FieldErrors, add an input to AddBookForm, and render {book.pages} pages on the detail page. TypeScript points you to every place that must change, and npm run build confirms it.

Exercise 2 🟢 easy playground

Add a genre filter to /books: links "All · Fantasy · Sci-fi · Literary" that set ?genre=, combined with the existing search.

Show solution

In Results, read genre from searchParams as well and filter after searchBooks(query). Build each link with href={{ pathname: "/books", query: { q: query || undefined, genre } }} so the search term is kept. The links can live in the page (static) or in Results if you want to highlight the current genre.

Exercise 3 🟢 easy playground

Add a loading.tsx-style skeleton for the admin panel instead of the text "Checking your session…".

Show solution

Create app/admin/admin-skeleton.tsx returning a few grey boxes (animate-pulse rounded bg-zinc-200 h-6) and use it as the <Suspense> fallback. Don't use loading.tsx here: the heading is outside the boundary and should stay in the static shell.

Exercise 4 🟢 easy tests

Add a unit test that parseNewBook rejects a title of 201 characters.

Show solution

Exercise 5 🟡 medium feature

Let admins edit a book: /admin/books/[id]/edit with a pre-filled form, an updateBook(id, …) action that validates, saves, calls updateTag("books") and updateTag(`book-${id}`), then redirects to the book page.

Show solution

Add updateBookData(id, input) to lib/books.ts. The page awaits getCurrentUser() and getBook(id) inside <Suspense> (or notFound()), and renders a client form with defaultValues and useActionState(updateBook.bind(null, id), {}). The action calls requireAdmin(), parseNewBook, saves, revalidates both tags, then redirect(`/books/${id}`) last.

Exercise 6 🟡 medium feature

Make the API accept POST /api/books for admins, authenticated with the session cookie, returning 401/403/400/201 as appropriate. Reuse the schema and insertBook.

Show solution

In app/api/books/route.ts, add POST: const session = await decrypt((await cookies()).get("session")?.value); return 401 if null, 403 if not admin. Parse the JSON body with NewBookSchema.safeParse (not parseNewBook, which expects FormData), return 400 with z.flattenError. Then insertBook, revalidateTag("books", "max") (updateTag is for Server Actions only), and 201 with a Location header.

Exercise 7 🟡 medium per-user data

Today "read" is global. Make it per user: store readBy: string[] on each book, show "✅ read" based on the logged-in user, and keep the book pages static. Where does the user-specific part go?

Show solution

The book data (title, author…) stays cached and static. The read status depends on the session, so render it in a small component inside <Suspense> on the detail page: it reads the session (runtime data) and the book's readBy. If you cache the lookup, pass the user ID in as an argument (Chapter 8). Toggling calls an action that checks the session and updates readBy for that user only, then updateTag(`book-${id}`).

Exercise 8 🟡 medium E2E

Write a Playwright test that logs in as Ben (reader) and checks that the add form isn't shown, and that a direct call to the delete action still fails. (Hint: the second part is easier as a test of requireAdmin with a mocked session.)

Show solution

E2E: log in as Ben, go to /admin, await expect(page.getByPlaceholder("Title")).toHaveCount(0). Unit: in Vitest, vi.mock("@/lib/dal", () => ({ verifySession: async () => ({ userId: "u2", role: "reader" }) })) and vi.mock("next/cache"), then await expect(deleteBook("1")).rejects.toThrow("Only admins").

Exercise 9 🔴 hard database

Replace data/books.json with SQLite using Node's built-in node:sqlite module. Which files change, and what do you need to watch out for with Cache Components (Chapter 8's "predictable values")?

Show solution

Only lib/books.ts changes: open the database once at module scope, and implement the same functions with SQL. Nothing else in the app knows where data comes from: that's the payoff of a data layer. Watch out: node:sqlite is synchronous, and synchronous I/O counts as a predictable value, so an uncached query runs during prerendering and gets baked into the page. Keep the reads inside "use cache" with tags (as now), or call await connection() before queries that must be fresh per request.

Exercise 10 🔴 hard deploy

Deploy the reference app. Write the steps for a VM with Docker: the Dockerfile outline, environment variables, where data/books.json lives so it survives restarts, and how you'd check the deployment.

Show solution
  1. Set output: "standalone". Dockerfile: a deps stage (npm ci), a build stage (npm run build), and a small runner stage that copies .next/standalone, .next/static and public and runs node server.js as a non-root user.
  2. Environment: SESSION_SECRET (from the platform's secret store), NODE_ENV=production, PORT.
  3. Data: mount a volume at /app/data so the JSON file survives container restarts. (One instance only, because instances don't share the file or the in-memory caches; for more, move to a real database and a shared cache handler, Chapter 18.)
  4. Put nginx in front with TLS and buffering disabled.
  5. Check: curl the home page and /api/books, open a book page and check its title and OG image, log in, add a book, and run the Playwright suite against the deployed URL with PORT/baseURL changed.
