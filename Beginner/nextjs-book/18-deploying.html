Deploying, Self-hosting & Upgrading

An app on your laptop helps nobody. This chapter follows the docs' Deploying and Upgrading pages and the Self-Hosting guide. It covers the four ways to run Next.js in production and what each supports, the settings that matter when you host it yourself, and how to keep up with new versions. You'll build a standalone server and a static export, and see what a static export can't do.

You will learn

  • The deployment options: Node.js server, Docker, static export, platform adapters.
  • output: "standalone" for small server images, and output: "export" for static hosting.
  • Self-hosting essentials: reverse proxy, streaming, images, caches, multiple instances.
  • Running code at server start with instrumentation.ts.
  • Upgrading with next upgrade and codemods.
  • A short production checklist.

Deployment options

OptionFeature supportWhat it is
Node.js serverAllnpm run build then npm run start on any machine with Node.js.
Docker containerAllThe same server in a container, for Kubernetes or a cloud container service.
Static exportLimitedPlain HTML/CSS/JS files for any web server or bucket (S3, nginx, GitHub Pages). No server features.
AdaptersVariesPlatform integrations via the Deployment Adapter API. Verified adapters (Vercel, Bun) run the full Next.js test suite; Cloudflare, Netlify and others have their own integrations.

This book's examples all ran on the first option: next build + next start. It supports every feature and is what you'd use on a VPS, a PaaS like Railway or Render, or behind your company's load balancer.

🧠 Analogy: a food business. A Node.js server is your own restaurant: full menu, cooking to order. Docker is the same restaurant in a shipping container you can drop anywhere. A static export is selling pre-packed sandwiches through vending machines: cheap and everywhere, but nothing made to order. An adapter is a franchise agreement with a food court that has its own kitchens and rules.

Standalone output for small images

A normal deployment needs your whole node_modules. With output: "standalone", the build traces which files are actually used and copies only those, plus a minimal server.js, into .next/standalone. That folder runs on its own with node server.js, which is what the official Docker example uses.

The standalone server doesn't copy public/ and .next/static/, because ideally a CDN serves them. Copy them next to server.js (into standalone/public and standalone/.next/static) if the server should serve them itself. A typical multi-stage Dockerfile installs dependencies, runs npm run build, and copies only .next/standalone, .next/static and public into a small final image that runs node server.js. Use the docs' with-docker example as your starting point.

Static export

With output: "export", next build writes every page as HTML into an out/ folder. Any static host can serve it, and you can add a server later.

Each page has an .html file for the first visit and a .txt file with its RSC payload, which <Link> loads for client-side navigation. Files from public/ are copied too, and _next/ holds the JavaScript and CSS. The whole out/ folder can be uploaded anywhere. Features that need a server at request time don't work in a static export: cookies() and headers(), Route Handlers that read the request, Server Actions, Proxy, ISR and revalidation, dynamic params without generateStaticParams, and default image optimization (you need a custom loader or unoptimized). Self-hosting essentials

When you run next start yourself, the docs' Self-Hosting guide lists what to set up:

  • Reverse proxy. Put nginx (or a load balancer) in front of Next.js instead of exposing it directly. It handles TLS, malformed requests, slow-connection attacks, payload limits and rate limiting.
  • Streaming end to end. Streaming and Partial Prerendering need every layer to pass chunks through. In nginx, disable buffering (Next.js sends X-Accel-Buffering: no for this); make sure load balancers support chunked responses. Otherwise the static shell and the streamed parts arrive together at the end, and PPR's fast first byte is lost.
  • Images. next/image optimization works with next start with no configuration (it uses the sharp library). On some Linux systems, follow sharp's memory-allocator advice; or use a separate image service with a custom loader.
  • Caching. Prerendered pages and cache entries are stored on disk and in memory per instance. Several instances need a shared cache handler (cacheHandlers in the config) so they don't serve different versions, and so revalidation reaches all of them.
  • Several instances. Set the same NEXT_SERVER_ACTIONS_ENCRYPTION_KEY on all of them (Server Function closures are encrypted with it; a per-build random key would break actions across instances), and a deploymentId for version-skew protection during rolling deploys.
  • Build cache. Keep .next/cache between CI builds to make them faster: that's the "No build cache found" warning you've seen in every build output.
  • Graceful shutdown and after(). Work scheduled with after() runs after the response is sent; give the server time to finish it on shutdown.

💡 Every response says X-Powered-By: Next.js. Set poweredByHeader: false in next.config.ts to remove it, a small thing reviewers often ask for.

Upgrading

Next.js has a release roughly every month and a major version about once a year. Since Next.js 16.1 the CLI can upgrade itself:

For major versions, read the version guide (Upgrading to Version 16 lists every breaking change) and run the codemods it mentions: scripts that rewrite your code automatically. Examples from this book:

  • middleware-to-proxy: renames middleware.ts to proxy.ts (Chapter 15).
  • next-lint-to-eslint-cli: replaces the removed next lint with the ESLint CLI (Chapter 2).
  • The Next.js 15 codemods that made params, searchParams, cookies() and headers() asynchronous.

The docs also describe upgrading with a coding agent, which uses the docs bundled in node_modules/next/dist/docs/ and the AGENTS.md file that create-next-app writes.

⚠️ Upgrade on a branch, then run the whole pipeline: npm run lint, type-checking, unit tests, npm run build, and the E2E tests against next start. Many behaviour changes (caching, prerendering rules) only show up in a production build, as you've seen throughout this book.

A production checklist

Condensed from the docs' Production Checklist:

  • ✅ npm run build passes with no type errors; the route table shows the rendering you expect (○, ◐, ƒ).
  • ✅ Every Server Function and Route Handler checks authentication, authorization and input.
  • ✅ Secrets are server-only environment variables; nothing secret starts with NEXT_PUBLIC_.
  • ✅ Every "use cache" has a cacheLife, and mutations revalidate the right tags.
  • ✅ Slow data sits inside <Suspense> with meaningful fallbacks; error.tsx and not-found.tsx exist for important segments.
  • ✅ Images use <Image> with alt, fonts use next/font, and metadata, metadataBase, robots and sitemap are set.
  • ✅ Logging and monitoring are set up (instrumentation.ts), and you can find an error by its digest.
  • ✅ The hosting supports streaming; caches are shared if you run several instances.

Recap

  • Node.js server and Docker support every feature; static export is limited; adapters vary by platform.
  • output: "standalone" copies only the needed files plus server.js; copy public and .next/static or serve them from a CDN.
  • output: "export" writes HTML into out/; server features (cookies, actions, Proxy, revalidation, request-reading handlers) aren't available.
  • Self-hosting: a reverse proxy, streaming without buffering, a shared cache and the same encryption key across instances, a deploymentId, a persisted build cache.
  • instrumentation.ts's register() runs at server start.
  • Upgrade with npx next upgrade, read the version guide, run codemods, and test a production build.

Exercise 1 🟢 easy choose

Pick a deployment option: (a) a documentation site with no logins, hosted on GitHub Pages; (b) the Reading List with logins and Server Actions on a company VM; (c) the same app on Kubernetes.

Show solution

(a) Static export. (b) Node.js server (next build + next start, behind nginx). (c) Docker, ideally with output: "standalone".

Exercise 2 🟢 easy true or false

True or false? (1) A static export supports Server Actions. (2) next/image optimization works with next start without configuration. (3) The standalone folder includes public/ by default. (4) npx next upgrade exists since Next.js 16.1.

Show solution

(1) False. (2) True. (3) False. (4) True.

Exercise 3 🟢 easy explain

Why does the docs' guide recommend a reverse proxy in front of next start? Name three things it handles.

Show solution

Next.js isn't designed to face the internet directly. A reverse proxy handles TLS termination, malformed requests, slow-connection attacks, payload size limits and rate limiting, so the Node.js process can focus on rendering.

Exercise 4 🟢 easy recall

What does a codemod do? Name one you'd run when upgrading an app from Next.js 15 to 16.

Show solution

A codemod is a script that rewrites your source code automatically for an API change. From 15 to 16: npx @next/codemod@canary middleware-to-proxy . (or next-lint-to-eslint-cli).

Exercise 5 🟡 medium playground

Build the playground with output: "standalone", copy public and .next/static into .next/standalone, and start it with PORT=4000 node .next/standalone/server.js. Check that pages, images and styles load.

Show solution

Without the two cp commands, HTML loads but CSS, JavaScript chunks and public images return 404. The data file (data/books.json) must also be present in the standalone folder; check that file tracing copied it, or copy it in your Dockerfile.

Exercise 6 🟡 medium static export

Could the Reading List capstone be a static export? Go through its features (book pages, add-book form, login, admin, API, revalidation) and say which would have to go or change.

Show solution

Book pages: yes, with generateStaticParams, but new books need a rebuild. The add-book form (Server Action), login (cookies, sessions), the admin area (Proxy, DAL), the JSON API (request-reading handlers) and revalidation all need a server: they'd have to go, or move to a separate backend called from the browser. So no: it's a full-stack app, and the Node.js server is the right target.

Exercise 8 🟡 medium debug

After moving behind nginx, users say pages "feel slower": the loading skeletons never appear; the whole page shows up at once after a second. What's the likely cause and the fix?

Show solution

nginx is buffering the response, so streamed chunks (the static shell first, then Suspense content) are held back and delivered together at the end. Disable proxy buffering for the app (proxy_buffering off;, or respect the X-Accel-Buffering: no header Next.js sends), and check any load balancer in front for the same problem.

Exercise 9 🔴 hard multi-instance

You scale the Reading List from one to three instances behind a load balancer. Users report two problems: "Failed to find Server Action" errors, and sometimes seeing a book they just deleted. Explain both and fix them.

Show solution

(1) Each instance's build generated its own encryption key for Server Function closures, so an action rendered by instance A can't be decrypted by B. Build once and deploy the same artifact everywhere, and set the same NEXT_SERVER_ACTIONS_ENCRYPTION_KEY on all instances. (2) Each instance has its own in-memory and on-disk cache; updateTag on instance A doesn't clear B's and C's caches. Configure a shared cache handler (cacheHandlers, for example backed by Redis) and the docs' multi-instance cache coordination. Add a deploymentId for rolling deploys.

Exercise 10 🔴 hard plan

Write an upgrade plan for moving a team's app from Next.js 16.4 to a future 17.0. Include where you read, what you run, and how you verify.

Show solution
  1. Read the release blog post and the "Upgrading to Version 17" guide (in the docs and in the new package's node_modules/next/dist/docs/); list breaking changes that affect you.
  2. On a branch: npx next upgrade, then the codemods the guide lists.
  3. Fix what's left by hand: search for deprecated APIs from the guide.
  4. Verify: lint, type-check, unit tests, npm run build (compare the route table with the old one), E2E tests against next start, a manual smoke test of key flows.
  5. Deploy to staging, watch logs and error digests, then roll out.
