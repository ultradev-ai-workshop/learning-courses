Linking, Navigating & Dynamic Routes

Real apps have routes made from data: /books/1, /books/2, and so on. This chapter covers dynamic segments, then follows the docs' Linking and Navigating page: how <Link> makes server-rendered pages feel instant through prefetching, streaming and client-side transitions. You'll also meet the first rule of Cache Components: data from the request must sit inside <Suspense>, unless it's known at build time.

You will learn

  • Dynamic segments [id], catch-all [...slug] and optional catch-all [[...slug]].
  • Two ways to render a dynamic page with Cache Components: generateStaticParams or <Suspense>.
  • notFound() for IDs that don't exist.
  • <Link>, prefetching, streaming with loading.tsx, and client-side transitions.
  • Search params on the server (searchParams) and in the browser (useSearchParams).
  • Navigating from code with useRouter, and showing progress with useLinkStatus.

Dynamic segments

Wrap a folder name in square brackets to make a dynamic segment: app/books/[id]/page.tsx matches /books/1, /books/42, /books/dune… The value arrives in the page's params prop. params is a promise, so you await it.

A first try, and a build error

The obvious version awaits params at the top of the page:

This is Cache Components at work. At build time, Next.js tries to prerender a static shell for every route: the parts of the page that are the same for everyone. It doesn't know which id a visitor will ask for, so params is runtime data. Reading it at the top of the page would leave nothing to prerender, and every visitor would wait for the server. Next.js refuses to build that by accident, and the error lists three fixes. The first two are the normal ones:

  1. Tell Next.js the IDs in advance with generateStaticParams, so they're no longer unknown.
  2. Stream: put the code that reads params inside <Suspense>, so the rest of the page can be prerendered.

The third, export const instant = false, accepts a page that blocks. Use it only when you've decided that's acceptable.

  • An ID that isn't in the list still works: it's rendered on its first request and then saved. Here, /books/99 finds no book:

The first request for /books/99 gets status 200. That isn't a bug. For an unlisted ID, Next.js starts streaming the static shell right away, and once streaming starts the status line has been sent and can't change. When notFound() runs, the 404 UI is streamed in, together with <meta name="robots" content="noindex"> so search engines don't index it. The result is saved, and later requests get a real 404. Fix 2: Suspense around the param

When the set of IDs is too large or unknown (user names, search results), don't list them. Instead, keep the page's frame static and move the param-dependent part into a component inside <Suspense>. This is the docs' pattern: pass the params promise down, and await it inside the boundary:

At build time, Next.js prerenders the shell, here the <h1> and the fallback "Loading books…". On a request, the server sends that shell at once and streams the AuthorBooks HTML into the same response when it's ready. The build marks such routes with ◐:

🧠 Analogy: a hotel restaurant. generateStaticParams is the buffet: the dishes are known, so they're cooked before guests arrive. <Suspense> is ordering à la carte: you get the table, bread and water at once (the static shell), and your dish arrives when the kitchen finishes it (streaming). The build error is the head waiter refusing to seat guests at an empty table with no bread while the kitchen waits for orders.

💡 Which fix to use? If the list of values is known and not huge (product IDs, blog slugs, a few hundred categories), use generateStaticParams: visitors get finished HTML. If values are unbounded or personal, use <Suspense>. You can also combine them: list the most popular IDs and let the rest render on demand.

Catch-all and optional catch-all segments

FolderMatchesparams
[slug]/docs/a{ slug: "a" }
[...slug]/docs/a, /docs/a/b/c (not /docs){ slug: ["a", "b", "c"] }
[[...slug]]/docs as well{ slug: undefined } for /docs

The types follow the folder: string for [slug], string[] for [...slug], and string[] | undefined for [[...slug]]. Values are always strings: a user can type anything into the address bar, so validate params before trusting them.

How navigation works

Pages are rendered on the server, so in principle every click waits for a server response. Next.js hides that wait with four techniques:

  1. Server rendering. The server produces the next page, either ahead of time (prerendering, cached) or on request (dynamic rendering).
  2. Prefetching. When a <Link> scrolls into view, Next.js loads its route in the background. Static routes are prefetched completely. For dynamic routes, the static shell is prefetched (with partialPrefetching, on in new apps) or the loading.tsx skeleton is.
  3. Streaming. The server sends parts of a dynamic page as they're ready, so the user sees the shell at once.
  4. Client-side transitions. Instead of a full reload, <Link> swaps the changed part of the page and keeps shared layouts and their state (Chapter 3).

📝 Prefetching only happens in production (next build + next start), not in next dev. Judge navigation speed on a production build.

loading.tsx: instant feedback for dynamic routes

A loading.tsx file next to a page wraps it in a <Suspense> boundary, with your component as the fallback. Navigation then happens immediately: the skeleton shows, and the page replaces it when ready. Chapter 6 covers loading.tsx and streaming in depth.

Search params

The query string (?genre=sci-fi) can be read in two places:

  • On the server, with the page's searchParams prop. Use this to load data (filtering, pagination). Like params, it's a promise and it's runtime data, so read it inside <Suspense>.
  • In the browser, with useSearchParams() in a Client Component, for UI that only reacts on the client.

A query value can be a string, an array (?genre=a&genre=b) or missing, hence the typeof genre === "string" check.

Navigating from code: useRouter

Sometimes you navigate after an event rather than from a link: after a form is validated, when a select changes. In a Client Component, useRouter() from next/navigation gives you:

  • router.push(href): navigate, adding a history entry. router.replace(href) replaces it instead.
  • router.back() and router.forward().
  • router.refresh(): re-render the current route on the server, keeping client state.
  • router.prefetch(href): prefetch by hand.

Choosing "Sci-fi" pushed /pick?genre=sci-fi, and both components re-rendered with the new value. Note the <Suspense>: during prerendering the search params are unknown, so a component that calls useSearchParams() must be inside a boundary too. Without one, the build fails with a "missing Suspense boundary" error.

⚠️ Import useRouter from next/navigation, not next/router. The latter belongs to the Pages Router (Appendix B) and doesn't work in app/. In Server Components and Server Functions, use redirect() instead (Chapters 7 and 10).

Parallel and intercepting routes (overview)

Two advanced conventions build on what you know. They're useful for specific UI patterns, and you can skip them on a first read:

  • Parallel routes: a folder named @slot becomes an extra prop of the parent layout, so a layout can render two pages side by side (a dashboard with @analytics and @team). A default.tsx file gives a slot its fallback.
  • Intercepting routes: folders like (.)photo or (..)photo show another route inside the current layout, for example a photo opening as a modal over a feed while the URL changes to /photo/1. Reloading shows the full photo page.

See the docs' Parallel Routes and Intercepting Routes references for complete examples.

Recap

  • [id], [...slug] and [[...slug]] create dynamic segments; params is a promise of strings.
  • With Cache Components, unknown params are runtime data. Either list values with generateStaticParams (prerendered, ○), or read them inside <Suspense> (◐, static shell + streamed content).
  • notFound() shows the 404 page; once a response is streaming, the status stays 200 and a noindex tag is added. dynamicParams isn't compatible with Cache Components; validate and call notFound() instead.
  • <Link> prefetches routes in view and navigates client-side; loading.tsx gives instant feedback.
  • searchParams (server, in Suspense) loads data; useSearchParams (client, in Suspense) drives UI.
  • useRouter() from next/navigation navigates from event handlers.

Exercise 1 🟢 easy params

What is params for each URL? (a) app/u/[user]/page.tsx at /u/ada; (b) app/files/[...path]/page.tsx at /files/a/b.txt; (c) app/shop/[[...cat]]/page.tsx at /shop.

Show solution

(a) { user: "ada" }. (b) { path: ["a", "b.txt"] }. (c) { cat: undefined }. In each case you get it with await params.

Exercise 2 🟢 easy symbols

What do ○ and ◐ mean in the route table of next build? In this chapter's table, why does /books/[id] appear with both?

Show solution

○ Static: prerendered as static content. ◐ Partial Prerender: a static HTML shell with dynamic content streamed from the server. The IDs returned by generateStaticParams are fully prerendered (○ /books/1…); the ◐ /books/[id] entry is the shell used for any other ID, which is rendered on its first request.

Exercise 3 🟢 easy Link or a?

Which should use <Link> and which <a>? (a) /books/2, (b) https://github.com, (c) /about, (d) mailto:hi@example.com.

Show solution

<Link> for (a) and (c), routes inside your app. <a> for (b) and (d), which leave the app.

Exercise 8 🟡 medium predict

A page has generateStaticParams returning IDs 1–3, and calls notFound() for unknown IDs. What happens for /books/2, and for the first and second requests of /books/abc? What happens if a teammate adds export const dynamicParams = false?

Show solution

/books/2 serves the prerendered HTML. The first request for /books/abc streams the shell with status 200, then the not-found UI with a noindex meta tag. The result is saved, so the second request gets a 404 status. With dynamicParams = false, the build fails: that option isn't compatible with Cache Components.

Exercise 9 🔴 hard explain

Explain why Next.js reports a build error, rather than silently rendering on every request, when a page reads params outside <Suspense> and has no generateStaticParams. What would the user experience be without the error?

Show solution

Without a boundary, nothing on the page can render before the param is known, so there'd be no static shell: every navigation would wait for a full server render, with no instant feedback, and prefetching couldn't help. Older Next.js versions did this silently, and it was easy to make a whole site slow by accident. Cache Components makes the trade-off explicit: prerender (list the params), stream (Suspense), or opt in to blocking (instant = false).

Exercise 10 🔴 hard design

Build a <SearchBox> Client Component for /books: an input whose value is kept in ?q=. Typing updates the URL with router.replace (no new history entry per key), and the server list filters by title. Where does each piece run, and why does it need <Suspense>?

Show solution

SearchBox runs in the browser (it reacts to typing); Results runs on the server (it filters data). Both depend on the query string, which is unknown at build time, so each needs a <Suspense> boundary. The heading and layout stay in the static shell. Chapter 6 adds debouncing so you don't send a request per key.
