Chapter 6 · Rendering & Data

Fetching Data & Streaming

Server Components can simply await data. That simplicity hides two questions this chapter answers, following the docs' Fetching Data page and the Streaming guide. What does the user see while slow data loads? And how do you avoid waiting for one request after another? You'll stream with loading.tsx and <Suspense>, fetch in parallel, de-duplicate with React.cache, and pass promises to Client Components with use.

You will learn

  • Fetching with fetch or a database in an async Server Component.
  • Why uncached data must be streamed (or cached) with Cache Components.
  • Streaming a whole page with loading.tsx, or parts of it with <Suspense>.
  • Sequential vs parallel fetching, measured.
  • React.cache to share one result between components in a request.
  • Streaming a promise to a Client Component with React's use.

Fetching in Server Components

Make the component async and await any asynchronous I/O: the fetch API, a database client, an ORM, the file system. Because the code runs on the server, credentials and query logic never reach the browser.

The rule: uncached data is streamed, or cached

Try to await it at the top of a page, as you would in a tutorial for an older version:

It's the same error as for params in Chapter 4. With Cache Components, fetch calls and database queries are not cached by default. When Next.js prerenders the page and hits I/O that doesn't finish right away, it treats it as uncached data. That data has two valid homes:

  • Stream it: render it inside <Suspense> (or below a loading.tsx), so it's fetched fresh on every request while the rest of the page is prerendered. This chapter.
  • Cache it: mark the function with "use cache", so the result is computed once and reused, and can be part of the prerendered page. Chapter 8.

📝 The earlier chapters' data modules returned their arrays immediately, without real I/O, so prerendering could finish them. A real database call always counts as uncached data.

The first bytes arrive in a few milliseconds; the response completes after about 0.8 seconds, the time of the "query". The HTML contains the fallback, followed later in the same response by the real list and a tiny script that swaps them. This is streaming: one HTTP response, sent in chunks.

🧠 Analogy: a restaurant that brings bread and water the moment you sit down, then each dish as it's ready, instead of making you wait at an empty table until the whole meal is cooked. loading.tsx is the bread for the whole table. <Suspense> lets each dish have its own placeholder.

Streaming parts of a page with Suspense

loading.tsx replaces the whole page while it loads. With <Suspense> you choose which parts wait. Content outside the boundaries is shown at once, and each boundary streams in on its own:

The heading and description are part of the prerendered static shell; the reviews are fetched on each request and streamed in. Put boundaries close to the slow data, so as much as possible appears immediately.

💡 Meaningful loading states. A fallback should look like what's coming: a skeleton with the shape of the list, a cover image placeholder, a title. That tells the user the app is responding. You can preview fallbacks in React DevTools, or with the Navigation Inspector in the Next.js DevTools.

📝 Bots and crawlers aren't streamed to. Next.js waits for all data and sends the complete page, so search engines see the full content.

Sequential vs parallel fetching

Each await waits for the one before it. If two requests don't depend on each other, start both first and await them together with Promise.all. The page below measures how long each approach takes, rounded to 100 ms:

Sequential fetching is right when one request needs the result of another (you need an artist's ID before you can load their playlists). Then the docs suggest showing what you have and streaming the dependent part:

⚠️ If one promise in Promise.all rejects, the whole thing rejects. Use Promise.allSettled when partial results are acceptable. Also note that layouts and pages of one route already render in parallel: a slow layout doesn't delay the page's fetches from starting.

Sharing one result: React.cache

Often several components need the same data: a header shows the user's name, the page shows their books. Passing it down as props is tedious. Instead, call the data function wherever it's needed, and wrap it in React.cache so that, within one request, the same arguments return the same result without a second query. Recap

  • Server Components await data directly from fetch, databases or files; credentials stay on the server.
  • With Cache Components, uncached I/O must be inside <Suspense> (streamed per request) or cached with "use cache".
  • loading.tsx streams the whole page; <Suspense> streams parts. The first byte arrives at once; content follows in the same response.
  • Start independent requests together with Promise.all; stream what depends on earlier results.
  • React.cache de-duplicates calls within one request; identical fetch calls are memoized automatically.
  • Pass a promise to a Client Component and read it with use; use SWR or TanStack Query for browser-driven fetching.

Exercises

Exercise 1 🟢 easy recall

Name the two ways the build error "encountered uncached or runtime data during prerendering" suggests for a slow database query, and say what each does for the user.

Show solution

Stream it with <Suspense> (or loading.tsx): the user gets the static shell immediately and fresh data shortly after, on every request. Cache it with "use cache": the result is computed once and reused, so the data can be part of the prerendered page and appears instantly, at the cost of possibly being stale until revalidated (Chapters 8–9).

Exercise 2 🟢 easy predict

Three independent queries take 300, 500 and 200 ms. How long does a component take if it awaits them one after another? With Promise.all?

Show solution

Sequentially about 1000 ms (300 + 500 + 200). In parallel about 500 ms, the slowest one.

Exercise 3 🟢 easy loading.tsx or Suspense?

Choose loading.tsx or <Suspense>: (a) a search results page where everything depends on the query; (b) a product page whose price and stock are slow but whose description is static; (c) a dashboard with four independent widgets.

Show solution

(a) loading.tsx is fine: there's nothing useful to show without the data. (b) <Suspense> around price and stock, so the description shows at once. (c) One <Suspense> per widget, so each appears when ready.

Exercise 4 🟢 easy true or false

True or false? (1) React.cache shares results between different users' requests. (2) A loading.tsx covers slow data in the layout of the same folder. (3) Search engine bots receive the fallback HTML. (4) Identical fetch calls in one render are memoized.

Show solution

(1) False: it's per request. (2) False: loading.tsx sits inside the layout, so it can't cover the layout's own data; wrap that in its own <Suspense>. (3) False: bots get the complete page. (4) True.

Exercise 9 🔴 hard explain

A teammate wraps the entire root layout's {children} in one <Suspense fallback={<Spinner />}> "to fix all the build errors at once". The build passes. What's wrong with this for users?

Show solution

The static shell becomes almost empty: just a spinner. Every page shows a full-screen spinner until all its slow data has loaded, even parts that could have been prerendered (headings, descriptions, navigation inside pages). Users lose the instant, meaningful first paint that Cache Components is designed to give. Boundaries should sit close to the slow data, with fallbacks shaped like the content.

Exercise 10 🔴 hard preload

A page awaits checkIsAvailable(id) (300 ms), then renders <Item id={id} />, which awaits getItem(id) (500 ms). Total: 800 ms. Using the docs' preloading pattern, get it to about 500 ms. What must be true of getItem?

Show solution

The item query runs during the availability check, so the total is about max(300, 500) = 500 ms. getItem must de-duplicate calls (here with React.cache; fetch does it automatically; with Cache Components, "use cache" also works), so Item reuses the request preload started instead of starting a second one.
