1. What is the main difference between Next.js and React?

React is a library for building user interfaces; Next.js is a framework for building whole web applications with React. React gives you components, props, state and hooks: it turns data into UI and keeps the UI in sync when data changes. It doesn't decide how URLs map to screens, where code runs, how data is loaded, how the app is bundled or how it's served. Next.js makes those decisions and builds them in:

React (e.g. with Vite)Next.js
Kind of toolUI libraryFull-stack framework built on React
Where code runsIn the browserOn the server, at build time and in the browser (Server and Client Components)
First HTMLMostly empty; JavaScript builds the pageReal content, prerendered or streamed from the server
RoutingA library you add (React Router…)File-system routing in app/
DataFetched in the browser (effects, SWR…) from an API you buildasync Server Components, Server Actions, caching
Back endA separate serverRoute Handlers and Server Functions in the same project
OptimisationsYour jobImages, fonts, code splitting, prefetching, metadata built in
HostingStatic files anywhereA Node.js server (or Docker, adapters, or static export)

The two aren't competitors: every Next.js app is a React app. Chapter 1 shows the difference with real HTML: a Vite app sends <div id="root"></div>, a Next.js page sends the content.

2. What problems does Next.js solve, and when is it the better choice?

It solves the problems you hit when a React single-page app grows up:

  • Slow first load and blank screens: HTML is prerendered or streamed, so content appears before JavaScript runs (Chapters 1, 6).
  • Search engines and link previews see real content and metadata (Chapter 13).
  • Too much JavaScript: Server Components ship none, and each route loads only its own code (Chapter 5).
  • Request waterfalls from fetching in effects: data is loaded on the server, close to the database (Chapter 6).
  • Secrets stay on the server (Chapters 5, 16).
  • Glue work: routing, bundling, TypeScript, CSS, images, fonts and an API layer come configured and working together (Chapter 2).
  • Performance at scale: caching and partial prerendering serve most of a page from a CDN while personal parts stream (Chapters 8–9).

Next.js is the better choice for public sites that must load fast and rank well (shops, content sites, marketing pages, docs), for apps that mix public pages with logged-in areas, and for teams who want front end and back end in one TypeScript codebase. It's probably not needed for a purely client-side tool behind a login that already has an API (Vite + React is simpler), an embeddable widget, or a handful of static pages. And a large back end with queues, jobs and many clients still deserves its own service; Next.js then becomes its web front end. Chapter 1, When is Next.js the better choice?, has a checklist.

3. Do I need to learn React before Next.js?

You need the basics: components, JSX, props, useState, event handlers, lists with keys. The docs list React as prerequisite knowledge. You don't need to master effects, data-fetching libraries or React Router first: Next.js replaces most of those with Server Components and file-system routing. If you know some React, Appendix A is a refresher; if you don't, do the React Beginner Book first.

4. Do I need Vercel to use Next.js?

No. Vercel created and maintains Next.js and hosts it very well, but Next.js is open source (MIT licence) and next build + next start runs on any machine with Node.js, in Docker, or on platforms with adapters (Bun, Cloudflare, Netlify, AWS Amplify, and others). Every example in this book ran on a plain Node.js server. Chapter 18 covers self-hosting, and what you need to configure when you do (a reverse proxy, streaming, shared caches).

5. Is Next.js a back end? Can it replace Express or Spring?

Partly. Next.js runs server code (Server Components, Server Functions, Route Handlers, Proxy), so for many apps it is the back end: reading and writing a database, authentication, JSON endpoints for a mobile app. It's built around request/response and rendering, though. Long-running jobs, queues, WebSocket servers, heavy computation, or a large API shared by many teams usually belong in a dedicated service (Node, Java, Python…), with Next.js as the web front end that calls it from the server, the "Backend for Frontend" pattern in the docs. Chapter 14 compares the options.

6. SSR, SSG, ISR, CSR, PPR: which is which in Next.js 16?

Those acronyms come from older versions, where you picked a mode per page. With Cache Components (the default for new apps), you mark parts of a page instead, and Next.js combines them:

  • Static (formerly SSG): anything that doesn't depend on the request is prerendered at build time.
  • Cached (formerly ISR): "use cache" + cacheLife results join the static shell and are refreshed in the background, or on demand with tags.
  • Dynamic / streamed (formerly SSR): request data and uncached data render per request inside <Suspense>.
  • Partial Prerendering (PPR) is the combination: a static shell sent instantly, with dynamic parts streamed into it.
  • Client rendering (CSR) is what Client Components do after hydration.

The build's route table shows the result: ○ static, ◐ partial prerender, ƒ dynamic, ● SSG. Chapters 1, 4, 6 and 8 cover this.

7. App Router or Pages Router?

For new projects, the App Router (app/), as the docs recommend: it supports Server Components, streaming, Server Functions, layouts and Cache Components. The Pages Router (pages/) is still supported, and you'll see it in older projects and tutorials. Both can live in one app while you migrate. Appendix B maps one to the other.

8. When do I need "use client"?

When a component needs state, event handlers, effects, browser APIs (window, localStorage) or hooks that use them. Put the directive in the smallest file that needs it (a button, a form, a menu), not in pages or layouts, because everything that file imports becomes browser JavaScript too. Server Components can render Client Components, and pass them serializable props or other Server Components as children. Chapter 5 shows the rules and the build errors you get when you break them.

9. Server Actions or Route Handlers?

Use a Server Action when your own UI changes data (forms, buttons): it's type-safe, works without JavaScript and returns updated UI in one round trip. Use a Route Handler when something else calls you (webhooks, mobile apps, third parties) or you need a specific URL, method, status code or content type. Read data in Server Components, not through your own API. Either way, both are public endpoints: always check authentication, authorization and input (Chapters 7, 14, 16).

10. Why doesn't my page update (or why isn't it cached)?

With Cache Components, nothing is cached unless you add "use cache". If a page doesn't update after you change data, a cached function is still serving the old result: call updateTag (in Server Actions), revalidateTag (in Route Handlers or webhooks) or revalidatePath, or give the cache a shorter cacheLife. If a page isn't cached when you expected it, check whether it reads request data or uncached I/O outside a cached function. And always judge caching on next build + next start: next dev renders on every request. Chapters 8 and 9 explain it, with real stale-while-revalidate timings.

11. Is Next.js good for SEO?

Yes, which is a main reason people choose it. Pages arrive as HTML with their content, the Metadata API generates titles, descriptions, canonical URLs and Open Graph tags, file conventions produce robots.txt, sitemaps and preview images, and bots get the complete page instead of a stream. Good SEO still depends on your content, fast pages (<Image>, next/font, caching) and correct status codes (see Chapter 10 on 404s and streaming). Chapter 13 covers it.

12. How does Next.js compare with Vite, React Router, Astro and others?

  • Vite + React: a fast build tool for client-side React apps. Simpler, no server; you add routing and data fetching yourself.
  • React Router (in framework mode, the successor of Remix): another full-stack React framework with server rendering, loaders and actions.
  • Astro: content-focused, ships little JavaScript by default, and can use React for interactive "islands".
  • TanStack Start: a newer full-stack React framework built around TanStack Router.

All are good tools. Next.js has the largest ecosystem, the deepest integration of React Server Components, and the most hosting options with first-class support. Pick by your app's needs, and remember that the React you learn transfers between them.

13. What is AGENTS.md, and do AI assistants know Next.js 16?

create-next-app writes an AGENTS.md file that tells AI coding agents: "This is NOT the Next.js you know… read the relevant guide in node_modules/next/dist/docs/." The point is that models trained on older code often suggest outdated patterns: getServerSideProps, middleware.ts, export const dynamic, fetch caching options, priority on images. This book hit several of these during testing; the build rejected dynamicParams with Cache Components, for example. Use AI help, but check its code against the docs for your version and run npm run build.

14. How long does it take to learn Next.js?

If you know React and TypeScript, the core (Chapters 1–10) takes a couple of weeks of evenings, and you can build real apps after it. The full book, including the capstone, takes roughly the hours shown on the course card in the launcher. Mastery comes from building: finish the capstone, then extend it (the Chapter 19 exercises are a good list), and read the docs' guides for the features you use.

Recap

  • React builds UI; Next.js is the framework that makes it a fast, full-stack web app.
  • Choose Next.js for public, SEO-relevant or mixed public/private apps; plain React for client-only tools.
  • You don't need Vercel; you do need to understand Server vs Client Components and caching.
