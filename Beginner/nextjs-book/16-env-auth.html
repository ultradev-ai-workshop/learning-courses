Environment Variables & Auth Basics

Two topics every real app needs, and that go together: configuration and secrets (database URLs, API keys, the key that signs session cookies) and authentication (who is this user?) with authorization (what may they do?). This chapter follows the docs' Environment Variables and Authentication guides. You'll build a small but complete login flow: a form, a signed session cookie, a data access layer, protected pages and logout.

You will learn

  • How .env* files are loaded, and in which order.
  • Why only NEXT_PUBLIC_ variables reach the browser, and that they're fixed at build time.
  • The three parts of auth in the docs: authentication, session management, authorization.
  • A stateless session in an encrypted, signed, httpOnly cookie.
  • A data access layer with verifySession(), and data transfer objects.
  • Where to check auth: pages, Server Actions, Route Handlers, and (optimistically) Proxy.

Environment variables

Next.js loads variables from .env* files in the project root into process.env. Values set in the real environment (your shell, your hosting platform) always win. Then the files are read in this order, and the first one that defines a variable wins:

  1. process.env (the real environment)
  2. .env.$(NODE_ENV).local, e.g. .env.production.local
  3. .env.local (not loaded when NODE_ENV is test)
  4. .env.$(NODE_ENV), e.g. .env.development
  5. .env

next dev uses NODE_ENV=development; next build and next start use production. The create-next-app template adds .env* to .gitignore: you almost never commit these files. (Teams often commit a .env.example listing the names without real values.)

Three things to notice. .env.production won over .env for SITE_NAME, because this is a production build. The Client Component sees the NEXT_PUBLIC_ variable. And it sees DATABASE_URL as undefined, so the secret never reached the browser. The build output confirms it:

⚠️ NEXT_PUBLIC_ values are inlined at build time. next build replaces process.env.NEXT_PUBLIC_… with the literal value in the JavaScript bundle. Changing the variable later, without rebuilding, has no effect in the browser. That also means: never put a secret in a NEXT_PUBLIC_ variable, because it's published to everyone. Dynamic lookups such as process.env[name] aren't inlined.

Server code reads non-public variables at the time it runs. In a page that's prerendered, that's build time; in code that runs per request (after connection(), in Route Handlers that read the request, in Server Actions), it's request time. So one build (for example a Docker image) can run in several environments with different server-side values. Outside Next.js (a test runner, an ORM config), load the same files with loadEnvConfig from @next/env.

🧠 Analogy: server-side variables are the combination of the safe in the back office: staff can read it whenever they need it. NEXT_PUBLIC_ variables are printed on the leaflets you hand out. Once the leaflets are printed (the build), changing the number on the office wall doesn't change the leaflets already in people's hands.

Auth in three parts

The docs split auth into three concepts:

  • Authentication: verifying who the user is (email and password, a passkey, "Log in with GitHub").
  • Session management: remembering that across requests, usually with a cookie.
  • Authorization: deciding what that user may see and do.

The docs recommend an auth library for production (Auth.js, Better Auth, Clerk and others listed in the guide); they handle OAuth providers, password resets, rate limiting and many security details. Building a minimal version yourself once, as below, makes it clear what those libraries do and where Next.js expects the checks to happen.

Stateless sessions in a cookie

A stateless session stores the session data (here, the user's ID and role) in the cookie itself, encrypted or signed so the user can't change it. The docs' guide uses the jose library to sign a JWT with a secret key from the environment:

The cookie options are the docs' recommendations. httpOnly keeps the token away from browser scripts (so an XSS bug can't steal it), secure keeps it off plain HTTP, and sameSite: "lax" limits cross-site requests. The signature means a user who edits the cookie (say, to change role to admin) just gets null from decrypt.

Logging in: a Server Action

The login form posts to a Server Action. It validates the fields, checks the password against a stored hash, creates the session and redirects. Passwords are never stored in plain text: here we use Node's built-in scrypt, a slow hashing function designed for passwords.

Recap

  • .env* files load into process.env; the real environment wins, then .env.$(NODE_ENV).local, .env.local, .env.$(NODE_ENV), .env. Don't commit them.
  • Only NEXT_PUBLIC_ variables reach the browser, inlined at build time; never put secrets in them.
  • Auth = authentication + session management + authorization. Prefer an auth library in production.
  • A stateless session is a signed (or encrypted) token in an httpOnly, secure, sameSite cookie; the secret comes from the environment.
  • A server-only data access layer with a cached verifySession() and DTOs keeps checks in one place and data minimal.
  • Check auth in pages, Server Actions and Route Handlers, not in layouts; Proxy is an optional optimistic filter.

Exercises

Exercise 1 🟢 easy load order

API_URL is defined in .env (a), .env.local (b) and .env.production (c). What does the server see in next dev? In next start? If the platform also sets API_URL=d?

Show solution

next dev: b (.env.local beats .env; .env.production isn't loaded in development). next start: b too (.env.local beats .env.production). With a real environment variable: d always wins.

Exercise 2 🟢 easy public or not?

Which of these may be NEXT_PUBLIC_? (a) the Stripe publishable key, (b) the Stripe secret key, (c) the analytics site ID, (d) the session signing secret.

Show solution

(a) and (c): they're designed to be public. Never (b) or (d).

Exercise 3 🟢 easy definitions

Match the term to its meaning: authentication, session management, authorization. (1) "May Ada delete this book?" (2) "Is this really Ada?" (3) "Remember that Ada logged in."

Show solution

Authentication is (2), session management is (3), and authorization is (1).

Exercise 4 🟢 easy cookie options

What does each session cookie option protect against? httpOnly, secure, sameSite: "lax", expires.

Show solution

httpOnly: scripts (including injected ones) can't read the cookie. secure: it's never sent over unencrypted HTTP. sameSite: "lax": it isn't sent with most cross-site requests, which limits CSRF. expires: the session ends after a while instead of living forever.

Exercise 7 🟡 medium build-time trap

A Docker image is built once with NEXT_PUBLIC_API_URL=https://staging.example.com and then deployed to production with NEXT_PUBLIC_API_URL=https://api.example.com. The browser keeps calling staging. Why? Give two fixes.

Show solution

NEXT_PUBLIC_ values were inlined into the JavaScript during the build. Fixes: (1) build a separate image per environment; or (2) don't read the URL in client code: have the client call your own Route Handler or Server Function, which reads a non-public variable at request time; or pass the value from a dynamically rendered Server Component as a prop.

Exercise 8 🟡 medium review

Review this login action and list the problems:

Show solution
  1. No validation of the form data.
  2. user may be undefined (crash for unknown emails).
  3. Plain-text password comparison: passwords must be hashed (scrypt, bcrypt, argon2) and compared in constant time.
  4. The error reveals whether the email exists and is thrown (it reaches an error boundary, and its message is hidden in production): return a generic "Wrong email or password" instead.
  5. The cookie is an unsigned user ID: anyone can set userId=1. Use a signed or encrypted session, with httpOnly, secure and sameSite.
  6. No redirect, and no rate limiting against password guessing (libraries help).

Exercise 9 🔴 hard explain

Why does the docs' guide warn against doing the auth check in a layout? Describe a concrete scenario where it fails.

Show solution

Layouts don't re-render on client-side navigation, and pages render in parallel with them, so a page's data can be fetched regardless of the layout's check. Scenario: app/admin/layout.tsx checks the session; the admin opens /admin, then their session expires (or is revoked); they click links to /admin/users and /admin/settings: the layout isn't re-run, and if those pages don't check themselves, they keep loading private data. Also, a Server Action defined in an admin page is reachable directly by POST without the layout ever running. Check in the page or data layer, and in every action.

Exercise 10 🔴 hard design

Stateless (cookie) or database sessions? List two advantages of each, and choose one for the Reading List and for a bank.

Show solution

Stateless: no database lookup per request (fast, simple); scales without shared storage. Database sessions: can be revoked instantly (log out everywhere, ban a user); the cookie holds only an opaque ID, so no user data travels in it. The Reading List can use stateless sessions with a short expiry. A bank should use database sessions (plus a library, multi-factor authentication and short idle timeouts), because instant revocation matters more than one database read per request.
