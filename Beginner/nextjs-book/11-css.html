Chapter 11 · Styling & Assets

CSS & Tailwind

Next.js supports several ways to style an app. The docs' CSS page lists Tailwind CSS, CSS Modules, global CSS, external stylesheets, Sass and CSS-in-JS. This chapter covers the first four, which are what you'll use most, and the rules for how Next.js orders and bundles CSS. The examples check styles by reading the browser's computed values, so you can see exactly what each rule does.

You will learn

  • How create-next-app sets up Tailwind CSS v4, and how to use utility classes.
  • CSS Modules: locally scoped class names in *.module.css files.
  • Global CSS and stylesheets from npm packages.
  • How CSS is ordered and merged, and the docs' recommendations.
  • Differences between development and production.

Tailwind CSS

Tailwind CSS is a utility-first framework: instead of writing a .card rule in a CSS file, you compose small classes in your markup, like p-4 rounded-lg bg-white shadow. Each class sets one thing. Tailwind scans your files and generates CSS only for the classes you use.

Apps created with the recommended defaults already have Tailwind v4. It takes three pieces:

  1. The packages tailwindcss and @tailwindcss/turbopack (dev dependencies).
  2. A Turbopack loader rule in next.config.ts that runs CSS files through Tailwind (Chapter 2 showed it).
  3. @import "tailwindcss"; at the top of app/globals.css, which the root layout imports.

text-3xl is 30 px, font-bold is weight 700, p-4 is 1 rem (16 px) of padding, rounded-lg is 8 px. Modifiers add conditions: hover:underline, sm:flex (from 640 px wide), dark:bg-black.

📝 The docs' manual setup uses the PostCSS plugin instead: install tailwindcss @tailwindcss/postcss and add a postcss.config.mjs with plugins: { "@tailwindcss/postcss": {} }. Both work; create-next-app now uses the Turbopack loader. For very old browsers, the docs have a Tailwind v3 guide.

CSS Modules

A file ending in .module.css is a CSS Module. Importing it gives you an object of class names, and Next.js rewrites each name to be unique, so the same class name in two files never collides:

The real class name is a short hash followed by the original name (in this build _5pvCyG_blog; the hash changes when the file changes), so you never type it yourself: always use styles.blog. Use CSS Modules for component-specific styles that Tailwind utilities can't express well, such as complex selectors, animations, or styles you want to keep out of the markup.

Global CSS

A plain .css file imported somewhere in app/ is global: its rules apply to the whole page. Import global styles once, in the root layout, as create-next-app does with globals.css.

⚠️ You can import a global stylesheet in any layout, page or component, but stylesheets aren't removed when you navigate away. Next.js integrates CSS with React's Suspense support, so a global rule imported by one page stays active on the next. Keep page-specific styles in CSS Modules or Tailwind classes, and global CSS in the root layout.

Ordering and merging

In production, Next.js merges stylesheets into a few minified, code-split CSS files per route. The order of the CSS follows the order of your imports. If a component imports base-button.module.css and a page imports that component before its own page.module.css, the button's styles come first, so the page's styles win when specificity is equal.

The docs' recommendations for predictable ordering:

  • Import global styles and Tailwind in the root layout only.
  • Use Tailwind for most styling, and CSS Modules where utilities aren't enough.
  • Name modules consistently, e.g. button.module.css next to button.tsx.
  • Put shared styles in shared components instead of importing the same CSS in many places.
  • Turn off linters or formatters that sort imports automatically (such as ESLint's sort-imports): re-ordering imports re-orders CSS.
  • The cssChunking option in next.config.ts controls how CSS is split.

Development vs production

  • next dev applies CSS changes instantly with Fast Refresh, and needs JavaScript for that.
  • next build concatenates, minifies and code-splits CSS. In production, CSS loads even with JavaScript disabled.
  • CSS order can differ in development: always check the final order in a build.

CSS Modules are wallpaper bought for one room, with that room's number printed on the back. Tailwind utilities are a box of labelled stickers you put on each item directly.

Recap

  • New apps use Tailwind CSS v4: @import "tailwindcss" in globals.css, imported by the root layout; utilities go in className.
  • Tailwind v4 is configured in CSS with @theme; write class names in full so they're detected.
  • *.module.css files are CSS Modules: class names are made unique per file.
  • Global CSS belongs in the root layout; stylesheets aren't removed on navigation.
  • CSS order follows import order; production merges and minifies CSS, which works without JavaScript.

Exercise 8 🟡 medium debug

A teammate writes <div className={`bg-${status === "ok" ? "green" : "red"}-500`}>. In production the background is missing. Why, and how do you fix it?

Show solution

Tailwind scans source files for complete class names and never sees bg-green-500 or bg-red-500, so it doesn't generate them. Write the full names: status === "ok" ? "bg-green-500" : "bg-red-500".

Exercise 9 🔴 hard ordering

In development, a page's button is blue (from page.module.css); in production it's grey (from button.module.css). Both rules have the same specificity. Explain what's happening and two ways to fix it.

Show solution

CSS order follows import order, and development can order CSS differently from the production build. In production, button.module.css ends up after page.module.css (for example because an import was reordered, or the button is imported later), so it wins. Fixes: make the page's override more specific or move it into the component as a variant prop (<Button variant="primary">); or import the component before the page's own CSS module and stop tools from sorting imports. Always check styling in next build.

Exercise 10 🔴 hard design

Your team must choose between Tailwind everywhere, CSS Modules everywhere, or a mix for the Reading List app. Write a short recommendation with reasons, based on the docs' recommendations.

Show solution

A mix, as the docs recommend: Tailwind for layout, spacing, colours and most components (fast to write, no naming, unused styles removed); CSS Modules for the few component-specific needs utilities handle poorly (complex animations, intricate selectors, third-party markup you can't add classes to); one globals.css in the root layout for the theme variables and base styles. Agree on conventions (name.module.css next to name.tsx) and disable import sorting.
