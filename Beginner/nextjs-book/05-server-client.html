Chapter 5 · Rendering & Data

Server and Client Components

This is the central idea of the App Router. Some components run only on the server and send no JavaScript; others are also sent to the browser to handle clicks and state. This chapter follows the docs' Server and Client Components page. You'll learn when to use each, how "use client" draws the boundary, what can cross it, and the patterns for combining the two. Several examples show the real build errors you'll hit when you get it wrong.

You will learn

  • What each kind of component can do, and how to choose.
  • How rendering works: the RSC Payload, prerendered HTML, and hydration.
  • The "use client" directive as a boundary in the module graph.
  • Passing data from server to client as serializable props.
  • Interleaving: Server Components as children of Client Components.
  • Context providers, third-party components, and keeping server code out of the browser with server-only.

When to use each

You need…ServerClient
Fetch data close to the source (database, internal API)✅via an API
Use secrets: API keys, tokens✅❌ never
Send less JavaScript to the browser✅ (none)❌
State and event handlers (useState, onClick)❌✅
Effects and lifecycle (useEffect)❌✅
Browser APIs (localStorage, window, geolocation)❌✅
Custom hooks that use any of the above❌✅

Every component in app/ is a Server Component unless it's marked otherwise. A good default: keep pages and layouts as Server Components that load data, and make small, leaf-level Client Components for the interactive bits. How rendering works

On the server, for each route segment (layout and page):

  1. Server Components render into the RSC Payload (React Server Component Payload), a compact description of the rendered tree. It contains the output of Server Components, placeholders for Client Components with references to their JavaScript files, and the props passed to them.
  2. Client Components and the RSC Payload are used to prerender HTML.

In the browser, on first load:

  1. The HTML shows a fast, non-interactive preview.
  2. The RSC Payload lets React rebuild the component tree.
  3. The JavaScript for Client Components hydrates them: React attaches event handlers to the existing HTML, and they become interactive.

On later navigations, the RSC Payload is prefetched and cached, and Client Components render entirely in the browser. No HTML is needed.

You can ask for a route's RSC Payload yourself by sending the RSC: 1 header, as <Link> does when it navigates (-L follows the redirect to /posts/1?_rsc that Next.js adds). It's a text format with one piece of the tree per line. Here is the line for the page's <main>:

🧠 Analogy: furniture delivery. A Server Component is furniture that arrives assembled (finished HTML, nothing to do). A Client Component arrives flat-packed with instructions (JavaScript): there's a photo of the finished piece in the box (the prerendered HTML) so you can see it at once, but it only works after you assemble it (hydration). The RSC Payload is the delivery note listing what goes where, including which boxes still need assembly.

"use client" is a boundary

Put "use client" at the very top of a file, above the imports. It marks the file as an entry point to the client bundle. Everything that file imports, and every component it renders directly, becomes client code too. So you don't add the directive to every component: only to the files where server code hands over to client code.

You can see the boundary in the build. Below, a page (server) imports a helper and renders a Client Component that imports a different helper. Only the client side's text shows up in the JavaScript sent to browsers, under .next/static:

SERVER-ONLY-NOTE is in the page's HTML, but not in any JavaScript file. CLIENT-SIDE-NOTE had to ship, because the widget may show it after a click.

💡 Keep boundaries low. Marking a whole layout "use client" to make one search box interactive sends the whole layout, and everything it imports, to the browser. Put the directive on search.tsx instead, and keep the layout on the server.

Passing data across the boundary

A Server Component passes data to a Client Component through props. Those props travel over the network inside the RSC Payload, so they must be serializable by React: strings, numbers, booleans, null, undefined, arrays and plain objects of these, Date, Map, Set, typed arrays, promises, JSX, and Server Functions (Chapter 7). Ordinary functions and class instances can't cross.

The Date and the Set arrived as a real Date and Set. Passing the optional format function from the page, though, fails:

The fix is to do the formatting on one side: format the date on the server and pass a string, or define format inside the Client Component. The message mentions "use server": Server Functions can be passed, as Chapter 7 shows.

⚠️ Everything you pass as a prop is visible in the browser. If a Server Component loads a whole user record and passes it to a Client Component, the password hash goes along with it. Pass only the fields the client needs. The docs' Data Security guide recommends a data access layer that returns minimal objects (Chapter 16).

Interleaving: Server Components inside Client Components

A Client Component can't import a Server Component: anything it imports becomes client code. But it can receive one as a prop, usually children. The Server Component is rendered on the server first, and the client gets the finished result in its slot. The docs' example is a Cart that loads data on the server, shown in a Modal that toggles on the client:

The page (a Server Component) composes both: Cart is rendered on the server and passed into Modal's children slot. Modal decides whether to show it, without knowing what it is. cart.tsx stays out of the browser bundle.

🧠 Analogy: a Client Component with children is a gift box with a lid that opens and closes. The box (client) handles the lid. What's inside was packed in the shop (server). The box doesn't need to know how to make the gift, only where to hold it.

Keeping server code on the server: server-only

A module can be imported from both sides. If a data module that reads a secret is imported by a Client Component by mistake, its code ships to the browser. (Secret environment variables are replaced with empty strings there, so it would just fail. Chapter 16 covers environment variables.) Make that mistake a build error by importing server-only at the top of the module:

The import trace shows the chain that pulled the module into the client: app/page.tsx (a Client Component) imports lib/secret-data.ts.

Installing the server-only package is optional: Next.js recognises the import itself. The opposite package, client-only, marks modules that must never run on the server (for example, code that touches window).

Recap

  • Components in app/ are Server Components by default: they fetch data, use secrets and ship no JavaScript.
  • "use client" marks the entry to the client bundle; its imports and the components it renders become client code. Keep boundaries small and low in the tree.
  • First load: HTML preview → RSC Payload → hydration. Later navigations use the prefetched RSC Payload.
  • Props from server to client must be serializable, and everything in them is visible in the browser.
  • Pass Server Components to Client Components as children (interleaving); wrap context providers and hook-based third-party components in Client Components.
  • import "server-only" turns accidental client imports into build errors.

Exercises

Exercise 1 🟢 easy classify

Server or Client Component? (a) A list of books loaded from a database. (b) A "dark mode" toggle. (c) A footer with links. (d) A chart that animates on hover. (e) A component that reads localStorage.

Show solution

(a) Server. (b) Client (state, event). (c) Server. (d) Client (events, maybe effects). (e) Client, and it reads localStorage in an effect.

Exercise 2 🟢 easy true or false

True or false? (1) Every component in a Client Component's file must have "use client". (2) Client Components are rendered to HTML on the server too. (3) A Client Component can import a Server Component. (4) A Server Component can render a Client Component.

Show solution

(1) False: the directive goes once, at the top of the entry file. (2) True. (3) False: an imported component becomes client code; pass Server Components as props/children instead. (4) True.

Exercise 3 🟢 easy serializable?

Which props can a Server Component pass to a Client Component? "Dune", { id: 1, tags: ["a"] }, new Date(), () => alert("hi"), new Map([["a", 1]]), <p>Hello</p>.

Show solution

All except the arrow function. Strings, plain objects and arrays, Date, Map and JSX are serializable. Ordinary functions aren't (Server Functions are, Chapter 7).

Exercise 4 🟢 easy read the error

A build fails with "You're importing a module that depends on useEffect into a React Server Component module". Give two different fixes.

Show solution

(1) Add "use client" at the top of that file, if the whole component needs to be interactive. (2) Better, usually: move the part that uses useEffect into its own small Client Component file, and keep the rest on the server.

Exercise 5 🟡 medium playground

Add a "♡ Want to read" toggle button to the playground's book detail page. The page stays a Server Component; create app/_components/want-button.tsx as a Client Component that receives the book title as a prop.

Show solution

Chapter 7 makes this persist with a Server Function.

Exercise 6 🟡 medium refactor

This layout is all client code because of one search box. Refactor it so only the search box is a Client Component.

Show solution

Logo, NavLinks (unless it uses usePathname), Footer and the layout itself now stay on the server.

Exercise 7 🟡 medium interleave

Write a Client Component <Tabs> that takes two props, first and second (both React.ReactNode), and shows one at a time with two buttons. Use it from a Server Component page, passing two server-rendered lists.

Show solution

Any prop of type ReactNode works as a slot, not just children.

Exercise 8 🟡 medium security

A page loads user = { id, name, email, passwordHash, isAdmin } and renders <ProfileMenu user={user} />, a Client Component that only shows the name. What leaks, and how do you fix it?

Show solution

The whole object is serialized into the RSC Payload and the HTML, so the email, password hash and admin flag can be read in the browser (view source, or the network tab). Pass only what's needed: <ProfileMenu name={user.name} />. Even better, have your data layer return a minimal object, so a full record never reaches a component (Chapter 16).

Exercise 9 🔴 hard predict

chart.tsx has "use client" and imports heavy-chart-lib (300 KB). It's rendered by a page only when showChart is true. The page passes showChart={false}. Is the 300 KB downloaded? What could you do about it?

Show solution

Probably yes: the import is static, so the chart module is part of the client bundle for that route, whether or not it renders. To load it only when needed, use a dynamic import inside the Client Component: const Chart = dynamic(() => import("./chart")) with next/dynamic (or React.lazy), so the code downloads when the chart first renders. The docs' Lazy Loading guide covers this.

Exercise 10 🔴 hard design

Design the component split for a book detail page with: title, author and description (from a database), a "Want to read" button, a reviews list (from the database), and a "Write a review" form with a character counter. Mark each component server or client, and say what props cross the boundary.

Show solution
  • BookPage (server): loads the book and its reviews.
  • BookHeader (server): title, author, description. No JS.
  • WantButton (client): gets bookId and initialWanted: boolean.
  • ReviewList (server): renders reviews. No JS.
  • ReviewForm (client): character counter state; gets bookId, and later a Server Function to submit (Chapter 7).

Only IDs, booleans and a Server Function cross the boundary; the description and reviews stay as server-rendered HTML.
