Appendix B · Reference

Pages Router & Migrating

Next.js has two routers. This book teaches the App Router, which the docs recommend for new apps. But many existing projects, tutorials and Stack Overflow answers use the original Pages Router, which is still supported and still being improved. This appendix explains enough of it to read and maintain such code, maps each concept to its App Router equivalent, and summarises the docs' migration guides from the Pages Router, Create React App and Vite. The Pages Router examples were built and run in a separate app.

You will learn

  • How routing works in pages/, and what _app.tsx and _document.tsx are.
  • The Pages Router's data functions: getStaticProps, getStaticPaths, getServerSideProps.
  • API Routes, next/router and next/head.
  • A side-by-side map from Pages Router to App Router.
  • How to migrate incrementally, and how to move a Create React App or Vite project to Next.js.

Routing in pages/

In the Pages Router, every file in pages/ is a route (not only files named page): pages/index.tsx is /, pages/about.tsx is /about, pages/posts/[id].tsx is /posts/1. All components are what the App Router calls Client Components: they're prerendered on the server and hydrated, but there are no Server Components.

Data fetching functions

Pages Router components can't be async. Instead, a page file exports a special function that Next.js runs on the server, and its result is passed to the component as props:

FunctionRunsApp Router equivalent
getStaticPropsAt build time (and on revalidation with revalidate)An async Server Component with cached data ("use cache")
getStaticPathsAt build time: which dynamic paths to prerendergenerateStaticParams
getServerSidePropsOn every requestAn async Server Component reading uncached or request data (inside <Suspense>)

next/head sets <title> and meta tags in the Pages Router; the App Router uses the Metadata API instead (Chapter 13).

🧠 Analogy: the Pages Router is a house where every room has its own front door (every file is a route) and a single entrance hall (_app). The App Router is a building of corridors (folders) with wallpaper per corridor (layouts), doors only where you put them (page files), and kitchens inside the walls (Server Components) instead of a delivery hatch at each door (getServerSideProps).

Migrating incrementally

Both routers can live in one project, so the docs' App Router migration guide moves one route at a time:

  1. Upgrade Next.js and React; keep everything in pages/ working.
  2. Create app/layout.tsx from your _app.tsx and _document.tsx (global CSS imports, providers, <html> and <body>).
  3. Move a page: create app/<route>/page.tsx, turn its getStaticProps/getServerSideProps into an async Server Component, move interactive parts into Client Components, then delete the old file. (A route can't exist in both folders.)
  4. Replace next/router with next/navigation and next/head with metadata in moved pages.
  5. Move API Routes to Route Handlers (or Server Actions) when convenient.

Navigation between a Pages Router page and an App Router page is a full page load, so migrate related routes together.

Migrating from Create React App or Vite

The docs have step-by-step guides for both. The shape is the same:

  1. Install next and add the dev/build/start scripts; add next.config.ts.
  2. Create app/layout.tsx from your index.html (title and meta tags become metadata).
  3. Start as a single-page app: one catch-all route, app/[[...slug]]/page.tsx, that renders your existing app as a Client Component (loaded with next/dynamic and ssr: false if it uses browser APIs at the top level). Your app runs unchanged, now built by Next.js.
  4. Replace import.meta.env.VITE_* or process.env.REACT_APP_* with NEXT_PUBLIC_*.
  5. Then adopt Next.js features step by step: move routes out of React Router into the file system, fetch data in Server Components, use <Image> and next/font.

Recap

  • In pages/, every file is a route; _app.tsx wraps all pages; all components are client components.
  • Data comes from getStaticProps (build time, ISR with revalidate), getStaticPaths and getServerSideProps (per request).
  • API Routes in pages/api use req/res; next/router and next/head are Pages Router APIs.
  • Both routers can coexist; migrate route by route, and start CRA/Vite migrations as a single-page app.

Exercise 1 🟢 easy recognise

You open a project and see pages/, getServerSideProps and import { useRouter } from "next/router". Which router is it? What about app/, "use client" and next/navigation?

Show solution

The first is the Pages Router; the second is the App Router.

Exercise 2 🟢 easy map

Give the App Router file for: pages/index.tsx, pages/blog/[slug].tsx, pages/api/books.ts, pages/_app.tsx.

Show solution

app/page.tsx, app/blog/[slug]/page.tsx, app/api/books/route.ts, app/layout.tsx.

Exercise 3 🟢 easy match

Match each Pages Router function to its App Router equivalent: getStaticPaths, getServerSideProps, getStaticProps with revalidate.

Show solution

getStaticPaths → generateStaticParams. getServerSideProps → an async Server Component that reads request or uncached data inside <Suspense>. getStaticProps + revalidate → an async Server Component whose data is cached with "use cache" and cacheLife.

Exercise 4 🟢 easy true or false

True or false? (1) Pages Router components can be async. (2) app/ and pages/ can coexist. (3) The same URL can be defined in both. (4) proxy.ts works with both routers.

Show solution

(1) False. (2) True. (3) False. (4) True.

Exercise 9 🔴 hard plan

Plan the migration of a 40-page Pages Router e-commerce app to the App Router. In what order would you move things, and why?

Show solution
  1. Upgrade Next.js; create app/layout.tsx from _app/_document; ensure shared providers work in both trees.
  2. Move simple, mostly static pages first (about, help, legal): low risk, quick wins.
  3. Move product listing and product pages together (they link to each other a lot; cross-router navigation is a full reload), converting getStaticProps to cached Server Components with tags.
  4. Move account and cart pages, converting getServerSideProps and API calls to Server Components and Server Actions with proper auth checks.
  5. Move API Routes last, keeping the ones external clients use stable.

After each step: build, run E2E tests, deploy.

Exercise 10 🔴 hard Vite

A Vite + React Router SPA reads import.meta.env.VITE_API_URL and uses window.localStorage at module level. Describe the first, minimal step to run it on Next.js.

Show solution

Create app/layout.tsx and a catch-all app/[[...slug]]/page.tsx. In a Client Component, load the old app entry with dynamic(() => import("../../src/App"), { ssr: false }), so module-level localStorage access never runs on the server. Rename the variable to NEXT_PUBLIC_API_URL and update its uses. Run next dev; React Router keeps handling routes inside the SPA until you move them to the file system.
