Mutating Data: Server Actions & Forms

Reading data is half of an app; the other half is changing it. In a classic React app you'd write an API endpoint and call it with fetch. In Next.js you write a Server Function: an async function marked "use server" that the browser can call. This chapter follows the docs' Mutating Data page and the Forms guide: creating Server Functions, calling them from forms and event handlers, validation, pending states, refreshing and redirecting, cookies, and the security rule you must never forget.

You will learn

  • What Server Functions and Server Actions are, and how they're called (a POST request).
  • Defining them inline in a Server Component, or in a "use server" file for Client Components.
  • Forms with action, progressive enhancement, and FormData.
  • Validation errors and pending UI with useActionState and useFormStatus.
  • Calling a Server Function from an event handler.
  • Updating the UI after a change: revalidatePath, refresh, redirect; and setting cookies.
  • Why every Server Function must check its input and the user's permissions.

What are Server Functions?

A Server Function is an asynchronous function that runs on the server and can be called from the client through a network request. When it's used to handle a form submission or another mutation, it's also called a Server Action. Server Function is the broader term; you'll see both in the docs.

  • You mark one with the "use server" directive: at the top of the function body, or at the top of a file to mark all its exports.
  • Calling it from the browser sends a POST request to the current page. Next.js routes it to your function, and can send back the updated UI and data in the same response.
  • When passed to a form's action (or a button's formAction), it runs inside a React transition automatically.

🧠 Analogy: a Server Function is a letterbox in the server's door. The browser doesn't need to know the address of an API or the shape of a request: it drops a form in the slot (calls the function), and the server reads it inside. But anyone walking past can post a letter into that slot too, which is why the function must check every letter it receives.

The examples in this chapter use an in-memory "database": a module that keeps a list in a variable. It lives as long as the server process, which is enough for learning here. It isn't a real database, though: every server instance has its own copy, and a module isn't guaranteed to be shared between different routes (Chapter 9 runs into this with a Route Handler and switches to a JSON file). Real apps use a database.

  2. Next.js runs createBook on the server.
  3. revalidatePath("/") tells Next.js that the page's data changed, so the response includes the re-rendered page (Chapter 9 explains revalidation in full).

Progressive enhancement

📝 Why "Loading…"? Streamed <Suspense> content arrives in the HTML, but a small inline script swaps it in. The form keeps working without JavaScript, but content inside boundaries needs it. Content that must be visible without JavaScript belongs in the static shell, for example cached with "use cache" (Chapter 8).

In Client Components, submissions made before hydration are queued and sent once React is ready.

Server Functions in their own file

Client Components can't define Server Functions, but they can import them from a file that starts with "use server". Every export of that file becomes a Server Function. This is the usual structure in real apps: one actions.ts per feature.

After a mutation: refresh, revalidate, redirect

A Server Action usually ends by making the UI show the new data. There are three tools, all called inside the action:

CallFromEffect
refresh()next/cacheRe-renders the current page on the server and updates the client. Doesn't touch cached data.
revalidatePath("/books")next/cacheMarks a path's cached data and pages as stale, so they're rebuilt, and refreshes the UI.
updateTag("books"), revalidateTag(…)next/cacheExpire cached data by tag: precise invalidation (Chapter 9).
redirect("/books")next/navigationSends the user to another page. It throws, so code after it never runs: revalidate before redirecting.

Security: Server Functions are public endpoints

⚠️ The most important rule in this chapter. A Server Function can be called by anyone who sends the right POST request, not only through your form. Hiding the button doesn't protect the action. Inside every Server Function:

  1. Authenticate: is there a logged-in user?
  2. Authorize: is this user allowed to change this record?
  3. Validate all input: FormData values are untrusted strings (or files).

Recap

  • A Server Function is an async function marked "use server"; called from the client, it runs on the server via a POST request. Used for mutations, it's a Server Action.
  • Define actions inline in Server Components, or in a "use server" file to import them into Client Components; they can also be passed as props.
  • <form action={action}> passes FormData and works without JavaScript (progressive enhancement).
  • useActionState gives returned state (errors, messages) and a pending flag; useFormStatus and useOptimistic help with feedback.
  • After a change, call revalidatePath/updateTag or refresh(); redirect() throws, so call it last.
  • Always authenticate, authorize and validate inside every Server Function: they're public endpoints.

Exercises

Exercise 1 🟢 easy definitions

What's the difference between a Server Function and a Server Action? Which HTTP method calls them?

Show solution

A Server Function is any async function marked "use server" that the client can call. A Server Action is a Server Function used for a mutation, typically passed to a form's action or a button's formAction (it then runs in a transition). Both are invoked with POST, and only POST.

Exercise 2 🟢 easy where does "use server" go?

Where do you put "use server" (a) for an action defined inside a Server Component, (b) for actions a Client Component imports? Can you define a Server Function inside a Client Component?

Show solution

(a) As the first statement of the function body. (b) As the first line of a separate file; every export becomes a Server Function. You can't define one inside a Client Component, only import it or receive it as a prop.

Exercise 3 🟢 easy predict

What does this log, and why? revalidatePath("/"); redirect("/"); console.log("done");

Show solution

Nothing: redirect() throws a special exception that Next.js catches to perform the redirect, so console.log never runs. That's why you revalidate before redirecting. (Don't wrap redirect in a try/catch that swallows errors, or the redirect won't happen.)

Exercise 4 🟢 easy true or false

True or false? (1) A form with a Server Action needs JavaScript to submit. (2) Hiding a "Delete" button for non-admins secures the delete action. (3) useActionState's action receives the previous state as its first argument. (4) Server Functions are a good way to load data for a page.

Show solution

(1) False: it works without JS. (2) False: the action can be called directly; check permissions inside it. (3) True. (4) False: they're dispatched one at a time and meant for mutations; read data in Server Components.

Exercise 5 🟡 medium playground

Add an "Add a book" form to the playground's /books page: fields title, author and year. Put the action in app/books/actions.ts. It should validate (title and author required, year a whole number between 1450 and 2100), add the book to the in-memory list, and call revalidatePath("/books"). Show errors with useActionState.

Show solution

z.coerce.number() turns the form's string into a number before checking it. Chapter 9 replaces revalidatePath with tags once the book list is cached.

Exercise 6 🟡 medium bind

Write a Server Component that lists books with a "Mark as read" button per book. Pass the book's ID to the action with .bind, not a hidden input. What must the action still check?

Show solution

The bound ID is serialized into the page, so a user can change it. The action must still check that the ID exists and belongs to the current user.

Exercise 7 🟡 medium pending

Write a reusable <SubmitButton label="Save" /> that disables itself and says "Saving…" while its form is submitting, without receiving any props about the pending state.

Show solution

Use useFormStatus() from react-dom, as in the tip in this chapter. It reads the status of the closest parent <form>, so it must be rendered inside the form, and the file needs "use client".

Exercise 8 🟡 medium choose

Which would you call after each action: refresh(), revalidatePath, or redirect? (a) "Save and close" on an edit page. (b) Toggling a "favourite" star on the current page, where the data isn't cached. (c) Adding a comment to a page whose comments list is cached.

Show solution

(a) revalidatePath for the pages that show the book, then redirect to the detail page. (b) refresh(): nothing cached needs invalidating, just re-render. (c) revalidatePath for that page (or, better, updateTag on the comments' cache tag, Chapter 9).

Exercise 9 🔴 hard security review

Review this action and list every problem:

Show solution
  1. No authentication: anyone can call it.
  2. No authorization: even a logged-in normal user could make themselves admin. Check that the caller is an admin.
  3. No validation: as is a type assertion, not a check. role could be any string, and userId could be missing (null) or a File. Validate with Zod (z.enum(["admin", "user"])).
  4. No revalidation, so the admin UI won't show the change.
  5. Nothing is returned or logged; consider returning a result for the UI and logging role changes for auditing.

Exercise 10 🔴 hard design

Design a "rate this book" widget for the playground with five star buttons. It should show the new average immediately (optimistic), save it with a Server Action, and work without JavaScript. Sketch the components and the action signature.

Show solution
  • Server: the book page loads the average and renders <RateForm bookId={id} average={avg} />.
  • Action (app/books/[id]/actions.ts): rate(bookId: string, formData: FormData), bound with rate.bind(null, id). It validates stars as an integer 1–5, checks the user, saves, and calls updateTag(`book-${bookId}`) or revalidatePath.
  • Client RateForm: a <form action={…}> with five <button name="stars" value="1…5">. Without JS, a click is a normal form post with stars in the body, so it still works. With JS, useOptimistic shows the expected new average while the action runs.
