Caching with Cache Components

Chapter 6 streamed slow data on every request. Often that's wasteful: a book's description doesn't change between two visitors. Caching stores a result so later requests reuse it. In Next.js 16, caching is explicit: nothing is cached unless you write "use cache". This chapter follows the docs' Caching page: the directive, cache lifetimes, cache keys, how cached, static and streamed content share one page, and the rules for random values, time and request data.

You will learn

  • "use cache" on data functions and on components (data-level and UI-level caching).
  • Cache lifetimes with cacheLife: stale, revalidate, expire, and the built-in profiles.
  • Cache keys: how arguments create separate entries.
  • How a page combines static, cached and streamed parts (Partial Prerendering).
  • Random values, Date.now() and connection().
  • Why cached code can't read cookies(), and what to do instead.
  • Where cached results live, and how this differs from older Next.js versions.

Why explicit caching?

Older Next.js versions cached many things automatically (fetch results, whole pages), and developers often couldn't tell why a page showed stale data. With Cache Components (cacheComponents: true, the default for new apps), the rule is simple:

  • Everything is dynamic by default. Data is fetched fresh, and slow I/O must be streamed inside <Suspense> (Chapter 6).
  • You opt in to caching with "use cache", where you know staleness is acceptable, and say for how long with cacheLife.

Cached results can be part of the prerendered static shell, so they appear instantly and are served from disk or a CDN.

🧠 Analogy: a café. Freshly squeezed juice is made per order (dynamic, streamed). Croissants are baked in the morning and sold all day (cached with a lifetime). The sign on the door, "Open 8–18", never changes (static). cacheLife is the note on the croissant tray: "best before 11:00, bake a new batch at 12:00, throw away at 18:00".

Cache lifetimes: cacheLife

cacheLife describes three times. The terms are worth learning, because they appear everywhere in the docs:

PropertyMeaning
staleHow long the browser may use its copy without asking the server.
revalidateAfter this, the next request still gets the cached value, but the server refreshes it in the background (stale-while-revalidate).
expireAfter this with no requests, the entry is dropped and the next request waits for fresh data.

The built-in profiles:

ProfileUse casestalerevalidateexpire
defaultStandard content5 minutes15 minutesnever
secondsReal-time data30 seconds1 second1 minute
minutesFrequently updated5 minutes1 minute1 hour
hoursUpdated several times a day5 minutes1 hour1 day
daysUpdated daily5 minutes1 day1 week
weeksUpdated weekly5 minutes1 week30 days
maxRarely changes5 minutes30 days1 year

You can also pass your own object, for example cacheLife({ stale: 60, revalidate: 600, expire: 3600 }) (seconds), or define named profiles in next.config.ts under cacheLife. Without a cacheLife call, the default profile applies.

⚠️ Very short lifetimes can't be prerendered. A cache with revalidate: 0 or expire under 5 minutes (of the presets, only seconds) is left out of the static shell and becomes a dynamic hole filled at request time, so it needs a <Suspense> boundary around it. A stale under 30 seconds is also excluded, because a prefetched copy would expire before the user could click.

Cache keys

Each cached function call is stored under a cache key made from the function's identity, its arguments, and any values it captures from enclosing scopes. Different inputs give separate entries: getBook("1") and getBook("2") are cached separately. Arguments and the return value must be serializable (the same rules as props to Client Components, Chapter 5).

Random values and the current time

Math.random(), Date.now(), new Date() and crypto.randomUUID() give a different value every time. If they ran during prerendering, every visitor would see the same "random" value baked into the HTML, which is rarely what you meant. So Next.js makes you choose:

The two server-side fixes are the most common. Per request: call await connection() (from next/server) first, which says "wait for a real request", and put the component in <Suspense>. Shared: compute it inside "use cache", so everyone sees the same value until the cache refreshes. (The [client] option renders the time in the browser instead.)

performance.now() is exempt: it's meant for measuring time (as in Chapter 6's timing page), not for rendering.

Request data and cached code

A cached function is shared between users, so it can't read cookies(), headers() or searchParams, directly or through any helper it calls. Read the value outside the cache and pass it in as an argument. The argument becomes part of the cache key, so each value gets its own entry:

Reading cookies() inside Recommendations instead would fail at request time with the next-request-in-use-cache error. For rare cases where you can't refactor, "use cache: private" caches per user in the browser only.

Predictable values are prerendered automatically

Not everything async is "uncached data". Module imports, pure computations and synchronous I/O (fs.readFileSync, synchronous SQLite) give the same result every time, so they simply run during prerendering. Asynchronous reads of local files (await readFile) count as uncached data: read config files once at module scope, or wrap the read in "use cache".

Where cached results live

A cached result is serialized as an RSC payload, and copies of it can live in three places:

  • Prerendered HTML on disk (self-hosting) or in your platform's storage behind a CDN: the static shell.
  • A server-side store. By default this is in memory, per server instance. On a long-running server it survives between requests; on serverless platforms each request may hit a fresh instance, so entries often don't survive. "use cache: remote" uses a shared cache handler (Redis, a KV store…) instead.
  • The browser, which keeps payloads for client navigations for their stale time (at least 30 seconds).

All of these are per deployment: the build ID is part of every cache key, so a new deploy starts with fresh caches.

If you read older code: the previous model

Apps without cacheComponents (and most articles before 2026) use the previous caching model. You'll recognise it by:

  • fetch(url, { cache: "force-cache" }) or { next: { revalidate: 60, tags: ["books"] } } options;
  • route segment exports such as export const dynamic = "force-dynamic", export const revalidate = 60 or dynamicParams;
  • unstable_cache(fn, keys, options) for non-fetch functions.

With Cache Components these segment exports are rejected by the build (you saw this for dynamicParams in Chapter 4), and "use cache" + cacheLife + cacheTag replace them. The docs' Migrating to Cache Components guide maps each one.

Recap

  • With Cache Components nothing is cached unless you add "use cache"; uncached data streams in <Suspense>.
  • "use cache" works on data functions and on components; cached results can join the static shell.
  • Pair it with cacheLife (stale/revalidate/expire); the seconds profile is a dynamic hole that needs <Suspense>.
  • Arguments and captured values form the cache key; inputs and outputs must be serializable.
  • Random values and the current time need connection() + <Suspense>, "use cache", or a Client Component.
  • Cached code can't read cookies()/headers()/searchParams: read them outside and pass values in.

Exercises

Exercise 1 🟢 easy recall

Give the three properties of a cache lifetime and what each controls.

Show solution

stale: how long the browser uses its copy without asking. revalidate: after this, the server serves the cached value but refreshes it in the background. expire: after this without requests, the next request waits for fresh data.

Exercise 2 🟢 easy choose a profile

Pick a cacheLife profile for: (a) a site's "About us" text, (b) the list of new books, updated a few times a day, (c) a live auction price, (d) today's reading tip, changed every morning.

Show solution

(a) max (or weeks). (b) hours. (c) seconds, inside <Suspense>, or no cache at all. (d) days, often with a tag so you can refresh it early (Chapter 9).

Exercise 3 🟢 easy true or false

True or false? (1) With Cache Components, fetch results are cached by default. (2) A cached function may call cookies(). (3) getBook("1") and getBook("2") share one cache entry. (4) A new deployment starts with empty caches.

Show solution

(1) False. (2) False: read cookies outside and pass the value as an argument. (3) False: arguments are part of the key. (4) True: the build ID is part of every key.

Exercise 4 🟢 easy read the error

A page shows Math.random() as a "lucky number" and the build fails. Give both fixes and say what users see with each.

Show solution

await connection() before the call and a <Suspense> boundary: every visitor gets a new number per request. Or "use cache" (with a cacheLife) around it: everyone sees the same number until the cache revalidates.

Exercise 6 🟡 medium cache keys

This cached function is called with getPrice({ id: "1", currency: "EUR" }) from two different components. How many cache entries are created? What if one call passes { currency: "EUR", id: "1" }?

Show solution

One entry: equal serialized arguments give the same key. Property order may change the serialized form, so it's safest to pass simple arguments (getPrice(id, currency)) and avoid relying on object key order. (Inside one request, the two calls are also de-duplicated.)

For each component, say whether it ends up in the static shell, in a cached part of the shell, or streamed: (a) <h1>Welcome</h1>; (b) an async component that awaits an uncached fetch, inside <Suspense>; (c) a component with "use cache" + cacheLife("days"); (d) the same with cacheLife("seconds"), inside <Suspense>.

Exercise 9 🔴 hard serverless

Your app runs on a serverless platform. A "use cache" function with cacheLife("hours") is called at request time (inside a Suspense boundary, after reading a cookie). Why might it run on almost every request anyway? What are your options?

Show solution

The default cache handler is in-memory and per instance. On serverless, requests often land on new, short-lived instances, so the entry usually isn't there. (Results that are part of the build-time static shell aren't affected: they're stored as files.) Options: "use cache: remote" with a durable cache handler shared by instances (costs a network round trip and storage, so it's worth it only at a high hit rate); moving the cached part out of the request-dependent branch so it joins the static shell; or self-hosting on a long-running server.

Exercise 10 🔴 hard design

Plan the caching for a book page in the Reading List app: title, author, description (edited by admins a few times a year); average rating (changes several times a day); "You marked this as read" (per user, from a cookie session); a random "You might also like" pick that should differ per visit. For each part give: cached or streamed, profile, and boundary.

Show solution
  • Book details: "use cache" + cacheLife("max") + a tag such as book-<id> to revalidate on edit (Chapter 9). Static shell.
  • Average rating: "use cache" + cacheLife("hours") (or a tag invalidated when someone rates). Static shell, refreshed in the background.
  • Read status: reads the session, so it's runtime data. Stream it in <Suspense>; optionally cache the lookup per user ID passed as an argument.
  • Random pick: await connection() + <Suspense>, so each visit is different; the candidates list itself can be cached.
