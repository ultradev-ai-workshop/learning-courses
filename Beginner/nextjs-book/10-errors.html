Error Handling

Things go wrong: a form is filled in badly, a book doesn't exist, a database is down, a component has a bug. The docs' Error Handling page splits errors into two kinds, expected errors and uncaught exceptions, and handles them differently. This chapter covers both: returning errors from actions, notFound() and not-found.tsx, error boundaries with error.tsx and catchError, global errors, and what production shows (and hides) from users.

You will learn

  • The difference between expected errors and uncaught exceptions.
  • Modelling expected errors as return values, not exceptions.
  • notFound(), not-found.tsx, and the HTTP status codes you actually get.
  • Error boundaries: error.tsx, retry(), nesting, and catchError.
  • global-error.tsx for errors in the root layout.
  • Why production hides server error messages, and how digest helps you find them.
  • Errors in event handlers, which boundaries don't catch.

Two kinds of errors

Expected errorsUncaught exceptions
ExamplesInvalid form input, "book not found", a failed payment, an API that returned 404A bug (undefined is not a function), the database is unreachable
Part of normal operation?YesNo
How to handleCheck for them and return a result the UI can show; call notFound()Throw, and let an error boundary show a fallback

🧠 Analogy: a shop. "We're out of that size" is an expected error: the assistant tells you politely and suggests another. A burst water pipe is an uncaught exception: you don't plan the conversation for it, you close that aisle (the error boundary), put up a sign, and keep the rest of the shop open.

Status codes and streaming

As you saw in Chapter 4, the HTTP status depends on when notFound() runs. If it runs before the response starts streaming, the status is 404. Once streaming has started (a Suspense fallback or the static shell has been sent), the status is already 200 and can't change. Next.js then streams the not-found UI and adds <meta name="robots" content="noindex">, so search engines don't index the page. The same applies to redirect(): before streaming it's an HTTP redirect; mid-stream it becomes a client-side redirect.

To return a real 404 status for a dynamic page, check for the missing record before any <Suspense> boundary or slow work, or prerender the valid IDs with generateStaticParams so unknown IDs are rare.

What production shows

The real error message ("Database connection lost") may contain sensitive details, so in production builds the message of an error thrown in a Server Component is never sent to the browser. The error that reaches error.tsx has a generic message (with React 19.3, a "minified React error") and a digest: a hash that the server also prints next to the real error in its log, so you can match a user's report to the real stack trace.

Meanwhile, the server log of next start shows the real error with the same digest:

In next dev you see the full message and stack in the error overlay. Errors thrown in Client Components keep their message, because their code is in the browser anyway.

⚠️ Don't use error messages to communicate with users. A message you throw on the server won't reach them in production. For anything the user should read, return a value (expected errors) or render it yourself.

Nested boundaries

An error bubbles up to the nearest error boundary above it. Put error.tsx files at different levels to control how much of the page is replaced: a boundary in app/dashboard/stats/ only replaces the stats panel, while one in app/ replaces everything below the root layout.

Component-level boundaries: catchError

error.tsx covers a whole route segment. To wrap any part of a page, Next.js 16 adds catchError (from next/error). It turns a fallback function into an error boundary component, and the fallback can receive its own props:

Only the wrapped part was replaced; the working widget is untouched. The message is visible here because the error was thrown by a Client Component in the browser.

⚠️ Errors during prerendering fail the build. Boundaries handle errors at request time and in the browser. If a component throws while next build prerenders it (here, if BrokenWidget threw on its first render), the build stops with "Error occurred prerendering page". That's why the examples above make their errors happen at request time, after connection() or after hydration. Fix errors that happen at build time; don't try to catch them.

Global errors

An error.tsx can't catch errors in the layout of its own segment, and so app/error.tsx can't catch errors in the root layout. For that, add app/global-error.tsx. Because it replaces the root layout when active, it must render its own <html> and <body>:

Recap

  • Expected errors (bad input, missing records, failed requests) are returned as values and shown by the UI; uncaught exceptions are thrown and caught by boundaries.
  • notFound() renders the nearest not-found.tsx; app/not-found.tsx handles unmatched URLs. After streaming starts, the status stays 200 with a noindex tag.
  • error.tsx (a Client Component) is a segment's error boundary; retry() re-fetches and re-renders. It sits inside the segment's layout.
  • In production, Server Component error messages are replaced by a generic message and a digest that matches the server log.
  • catchError creates boundaries for any part of a page; global-error.tsx covers the root layout.
  • Event handler errors need try/catch and state; errors in transitions and actions bubble to boundaries.

Exercise 1 🟢 easy classify

Expected error or uncaught exception? (a) The email is already registered. (b) Cannot read properties of undefined. (c) The payment provider declines the card. (d) The disk is full.

Show solution

(a) Expected: return a message. (b) Uncaught: a bug, let a boundary catch it and fix the code. (c) Expected: return a message so the user can try another card. (d) Uncaught: infrastructure failure.

Exercise 2 🟢 easy recall

Why must error.tsx be a Client Component? Which two props does it receive?

Show solution

It's a React error boundary that handles errors in the browser and offers interactivity (the retry button), so it needs client code. It receives error and retry (plus reset).

Exercise 3 🟢 easy true or false

True or false? (1) app/error.tsx catches errors thrown in app/layout.tsx. (2) Error boundaries catch errors in onClick handlers. (3) In production, the browser sees the message of an error thrown in a Server Component. (4) global-error.tsx must render <html> and <body>.

Show solution

(1) False: use global-error.tsx. (2) False. (3) False: it gets a generic message and a digest. (4) True.

Exercise 9 🔴 hard status codes

Search engines report many "soft 404s" (status 200 with a not-found page) for /books/[id] URLs of deleted books. Explain why this happens with Cache Components, and propose two improvements.

Show solution

Unlisted IDs are served the static shell first, which commits a 200 status before notFound() runs, so the first response is a 200 with the 404 UI and a noindex tag. Improvements: (1) check whether the book exists before any streaming starts, for example in proxy.ts (Chapter 15) or with a fast lookup before Suspense boundaries, so Next.js can send a real 404; (2) when a book is deleted, redirect its URL permanently (308) to the list, or keep returning notFound(): once the result is saved, later requests get a real 404, and the noindex tag already keeps the first one out of search results.

Exercise 10 🔴 hard design

Design the error handling for the Reading List's "Add a book" flow end to end: invalid input, a duplicate title, the data file being unreadable, and a bug in the list component. For each, say where it's detected and what the user sees.

Show solution
  • Invalid input: Zod in the Server Action; returned as field errors via useActionState; shown next to the fields.
  • Duplicate title: checked in the action against the store; returned as { message: "You already have that book" }.
  • Unreadable data file: unexpected, so let it throw. In the action, the error reaches the nearest boundary (app/books/error.tsx, "Couldn't load books · Try again"); log it on the server.
  • Bug in the list component: thrown during rendering; caught by app/books/error.tsx; the layout and navigation stay usable; the digest links the user's report to the log.
