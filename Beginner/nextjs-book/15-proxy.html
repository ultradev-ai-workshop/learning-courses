Proxy

Proxy is code that runs before a request reaches your routes. It can redirect, rewrite the URL to a different page, change request or response headers, or answer directly. Until Next.js 15 it was called Middleware (middleware.ts); in Next.js 16 it was renamed to make its purpose clear: a network boundary in front of your app, to be used sparingly. This chapter follows the docs' Proxy page.

You will learn

  • The proxy.ts convention and the proxy function.
  • Redirects, rewrites, headers and direct responses with NextResponse.
  • Targeting paths with matcher, including negative patterns.
  • Simple redirects in next.config.ts instead.
  • Optimistic auth checks, and why Proxy alone is never enough.
  • The execution order, and migrating from middleware.ts.

The convention

Create one proxy.ts file in the project root (next to app/, or inside src/ if you use it). Export a function named proxy (or a default export), and optionally a config object with a matcher. The function receives a NextRequest and returns a NextResponse, or nothing to let the request continue:

NextResponse.redirect answers with 307 Temporary Redirect, and the browser follows it to /books/dune. The matcher means Proxy only runs for /library/… paths; :path* matches zero or more segments.

📝 Since Next.js 16, Proxy runs in the Node.js runtime by default, so Node APIs are available. The runtime option isn't allowed in proxy.ts. Proxy isn't meant for slow data fetching, and fetch caching options have no effect in it.

The matcher is the docs' negative pattern: everything except Next.js's static files and the favicon. Without a matcher, Proxy runs on every request, including /_next/static scripts and images, which wastes time and can accidentally block your CSS and JavaScript.

💡 The matcher must be a constant (Next.js reads it at build time). It accepts a string, an array, regular-expression paths, and objects with has/missing conditions on headers or cookies.

Optimistic auth checks

A common use is to send anonymous visitors away from private pages before any rendering. The docs call this an optimistic check: Proxy only looks at whether a session cookie exists (fast, no database), not whether it's valid:

⚠️ Notice the second request: any cookie named session got through. Proxy is a fast first filter, not security. Always verify the session and the user's permissions where the data is: in the page's data access, in every Server Function and in every Route Handler (Chapter 16). The docs warn that Server Functions are POST requests to the page that uses them, so a change to the matcher or a moved action can silently lose Proxy coverage.

Execution order

For each request, Next.js applies these steps in order:

  1. headers from next.config
  2. redirects from next.config
  3. Proxy (rewrites, redirects, headers, responses)
  4. beforeFiles rewrites from next.config
  5. Filesystem routes: public/, _next/static/, app/…
  6. afterFiles rewrites
  7. Dynamic routes (/blog/[slug])
  8. fallback rewrites

🧠 Analogy: Proxy is the doorman of a building. He can point visitors to another door (redirect), quietly walk them to a different room while their ticket still says the same room number (rewrite), put a badge on them (request header), or turn them away (direct response). But he only glances at badges; the office with the safe still checks ID itself.

Recap

  • proxy.ts (formerly middleware.ts) at the project root runs before routes; it runs in Node.js by default.
  • NextResponse.redirect, .rewrite, .next({ request: { headers } }) and .json redirect, rewrite, pass headers or answer directly.
  • Always set a matcher, often the negative pattern that skips _next/static and _next/image.
  • Prefer redirects in next.config.ts for fixed redirects (308/307).
  • Use Proxy for optimistic checks only; verify sessions and permissions in data access, Server Functions and Route Handlers.

Exercises

Exercise 1 🟢 easy recall

What was Proxy called before Next.js 16, and why was it renamed?

Show solution

Middleware (middleware.ts). "Middleware" was often confused with Express middleware and encouraged overuse. "Proxy" describes what it is: a network boundary in front of the app, best used as a last resort.

Exercise 2 🟢 easy redirect or rewrite?

Redirect or rewrite? (a) /old-page moved to /new-page forever. (b) Show a "coming soon" page at /shop without changing the URL. (c) Send logged-out users from /account to /login.

Show solution

(a) Redirect, permanent (308), ideally in next.config.ts. (b) Rewrite. (c) Redirect (307), in Proxy because it depends on a cookie.

Exercise 3 🟢 easy matchers

Which paths does matcher: "/dashboard/:path*" match? /dashboard, /dashboard/stats, /dashboard/a/b, /dashboards.

Show solution

/dashboard, /dashboard/stats and /dashboard/a/b (* means zero or more segments). Not /dashboards.

Exercise 4 🟢 easy true or false

True or false? (1) You can have one proxy.ts per folder. (2) Proxy runs in the Edge runtime by default. (3) Without a matcher, Proxy runs for static files too. (4) Proxy is a good place to load a user's orders from the database.

Show solution

(1) False: one per project. (2) False: Node.js. (3) True. (4) False: it's not for slow data fetching.

Exercise 8 🟡 medium debug

After adding a Proxy that redirects anonymous users to /login with no matcher, the login page loads without any styling and the browser console shows errors loading /_next/static/…. What happened?

Show solution

Without a matcher, Proxy also runs for the CSS and JavaScript files under /_next/static (and images under /_next/image). Anonymous users are redirected for those too, so the login page's assets never load. Add a matcher, such as the negative pattern that skips _next/static, _next/image and favicon.ico, or limit it to the private paths.

Exercise 9 🔴 hard security

A team protects /admin only with Proxy (matcher: "/admin/:path*"). The admin page has a Server Action deleteBook. Later someone moves the delete form into a component also used on /books/[id]. What's the risk?

Show solution

Server Actions are POST requests to the page that renders them. On /books/[id], the Proxy matcher doesn't apply, so deleteBook can now be called without any check. Even before the move, the action's ID could be called from other pages. The fix is the one the docs insist on: verify the session and permissions inside deleteBook (and in the admin page's data access), and treat Proxy as a convenience only.

Exercise 10 🔴 hard design

Design an internationalised Reading List: /en/books and /fr/books. Visitors arriving at /books should be redirected to their language, from a lang cookie or the Accept-Language header, defaulting to English. Sketch the Proxy and the folder structure.

Show solution

Folders: app/[lang]/layout.tsx (the root layout, with <html lang={lang}>), app/[lang]/books/page.tsx, and generateStaticParams returning [{ lang: "en" }, { lang: "fr" }] so both languages are prerendered. The docs' Internationalization guide follows the same pattern.
