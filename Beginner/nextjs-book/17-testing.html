Testing with Vitest & Playwright

Tests let you change code without fear. The docs' Testing guide describes the kinds of tests and gives setup guides for four tools. This chapter uses two of them: Vitest for fast unit and component tests, and Playwright for end-to-end tests in a real browser, which is also how the docs recommend testing async Server Components. Every test run below was really executed against the chapter's app.

You will learn

  • The kinds of tests: unit, component, integration, end-to-end, snapshot.
  • Setting up Vitest with React Testing Library and jsdom, as in the docs.
  • Testing pure functions, Client Components with interactions, and Server Actions.
  • Why async Server Components are tested end to end.
  • Writing a Playwright test that clicks through the real app.

Types of tests

TypeTests…Tool in this chapter
UnitOne function, hook or component, in isolationVitest
ComponentHow a React component renders and reacts to props and eventsVitest + React Testing Library
IntegrationSeveral units working togetherVitest
End-to-end (E2E)A real user flow in a real browser against a production-like buildPlaywright
SnapshotRendered output compared with a saved copyVitest (toMatchSnapshot)

The docs also have guides for Jest (an older alternative to Vitest) and Cypress (an alternative to Playwright).

🧠 Analogy: building a car. Unit tests check each bolt and gear on the workbench. Component tests check the dashboard lights when you press each button. End-to-end tests are a test drive: start the engine, drive to the shop, park. You need many quick bench tests and a few test drives.

Testing Server Actions

A Server Action is an async function, so a unit test can call it directly with a FormData object, as long as it doesn't use request-only APIs like cookies() (those need a request, so test them end to end, or move the logic into a plain function you can test):

Async Server Components: test them end to end

async Server Components are new to the React ecosystem, and unit-testing tools don't fully support them yet. The docs recommend end-to-end tests for them. There's a second reason: their behaviour depends on Next.js itself (caching, streaming, Suspense, redirects), which only a real build reproduces.

End-to-end tests with Playwright

Playwright drives real browsers (Chromium, Firefox, WebKit). Install it with npm init playwright, or add @playwright/test and run npx playwright install to download the browsers. The config below uses the Chrome already installed on your computer (channel: "chrome") and the app's URL. The docs' setup adds a webServer entry so Playwright starts the app itself; here the app is already running.

Playwright's assertions like toBeVisible() and toHaveCount() wait and retry until they pass or time out, so the test doesn't need to know how long the streamed list takes. Run E2E tests against a production build (next build + next start), because development mode behaves differently (no prefetching, rendering on every request).

💡 In CI, a common pipeline is: npm ci → npm run lint → npx tsc --noEmit (or next typegen + tsc) → npx vitest run → npm run build → npx playwright test (with webServer starting npm run start).

Recap

  • Use many fast unit and component tests (Vitest + React Testing Library + jsdom) and a few end-to-end tests (Playwright).
  • The docs' Vitest config: plugins: [tsconfigPaths(), react()], environment: "jsdom"; npx vitest run runs once.
  • Find elements by role and name; fire events and assert on what the user sees.
  • Server Actions without request APIs can be called directly with FormData.
  • Test async Server Components (and streaming, caching, redirects) end to end, against a production build.
  • Playwright's web-first assertions wait and retry automatically.

Exercise 2 🟢 easy recall

What do environment: "jsdom" and tsconfigPaths() do in the Vitest config?

Show solution

jsdom gives tests a simulated browser (document, window) so components can render. tsconfigPaths() makes Vite resolve the paths from tsconfig.json, so @/lib/… imports work in tests.

Exercise 3 🟢 easy true or false

True or false? (1) npm run test with "test": "vitest" runs once and exits. (2) The docs recommend unit tests for async Server Components. (3) Playwright's toBeVisible() retries until it passes or times out. (4) E2E tests should run against next dev.

Show solution

(1) False: it watches; use vitest run in CI. (2) False: E2E. (3) True. (4) False: against a production build.

Exercise 4 🟢 easy queries

Write Testing Library queries for: the "Add book" button, the email input labelled "Email", and the page's main heading.

Show solution

Write a test for the Chapter 4 SearchBox? It uses useRouter and useSearchParams, which need Next.js's router. How can a unit test handle that?

Show solution

Mock the module: vi.mock("next/navigation", () => ({ useRouter: () => ({ replace: replaceMock }), usePathname: () => "/books", useSearchParams: () => new URLSearchParams("q=du") })). Exercise 8 🟡 medium refactor for testability

A Server Action reads cookies(), validates the form, computes a due date 14 days from today, and saves a loan. Which part would you extract to make it unit-testable, and how would you test the date logic without depending on today's date?

Show solution

Extract the pure parts: validateLoan(formData) and dueDate(from: Date) in lib/loans.ts. Test dueDate(new Date("2026-11-06")) → 2026-11-20, passing the date in instead of calling new Date() inside (or use vi.setSystemTime). Keep the action a thin shell that reads the session, calls these, and saves; cover the shell with an E2E test.

Exercise 9 🔴 hard explain

Your Vitest test of a Server Component passes, but the page fails in production with "Next.js encountered uncached or runtime data during prerendering". Why didn't the test catch it, and which test would have?

Show solution

Vitest only renders the component with React; it doesn't prerender, apply Cache Components rules, stream, or cache. The error comes from Next.js's build. npm run build itself is the first test that catches it (run it in CI), and an E2E test against next start checks the behaviour users actually get.

Exercise 10 🔴 hard strategy

Write a short test plan for the Reading List capstone: what you'd unit-test, what you'd component-test, and which three E2E flows matter most.

Show solution
  • Unit: validation schemas, readingStats, date and formatting helpers, the session encrypt/decrypt round trip, the store's read/write functions (with a temp file).
