Metadata & OG Images

Search engines, browser tabs and link previews in chat apps all read a page's <head>: its title, description, icons and preview image. Chapter 1 named this as one of the problems Next.js solves. This chapter follows the docs' Metadata and OG images page: static metadata, generateMetadata for data-driven pages, file-based metadata (icons, Open Graph images, robots.txt, sitemaps) and images generated from JSX.

You will learn

  • The two default meta tags, and why you never write <head> by hand.
  • The static metadata object, title templates, and how metadata merges from layouts to pages.
  • generateMetadata for pages whose title comes from data, without fetching twice.
  • Open Graph and Twitter fields for link previews.
  • File-based metadata: favicon.ico, icon, opengraph-image, robots, sitemap.
  • Generating OG images with ImageResponse.

Default fields

Every page gets two meta tags even without any metadata: the character set and the viewport (which makes pages scale properly on phones):

Everything else comes from the Metadata APIs. They're only supported in Server Components (layouts and pages), and Next.js generates the right <head> tags from them, handling streaming and de-duplication. That's why Chapter 3 said not to add <title> to the root layout by hand.

The full list of fields (keywords, authors, canonical URLs, robots, alternates for other languages…) is in the generateMetadata reference.

🧠 Analogy: metadata is the label on a jar. The layout prints the brand at the bottom of every label ("· Reading List"); each page writes its own contents above it. A shopper (search engine) or a friend you send a photo to (link preview) reads the label before opening the jar.

Generated metadata

When the title depends on data, as on a book's page, export an async function called generateMetadata instead. It receives the same params as the page. The page and the metadata need the same book, so the data function is cached and fetched once:

The title still uses the layout's template. (The og:image tags come from an opengraph-image.tsx file in the same folder, shown later in this chapter.) The openGraph fields become <meta property="og:…"> tags, which chat apps and social networks use for link previews (twitter fields work the same way for X).

💡 Fetching once. Here getBook is a "use cache" function, so the second call is a cache hit. For uncached data, wrap the function in React.cache (Chapter 6) so generateMetadata and the page share one request.

Streaming metadata

For pages rendered at request time, generateMetadata might be slow. Next.js doesn't make the page wait: it streams the metadata separately and injects it into the HTML when it's ready. Prerendered pages are unaffected, because their metadata was resolved at build time. Bots that need metadata in the initial <head> (Twitterbot, Slackbot, Bingbot…) are detected by their user agent and get the complete page; the htmlLimitedBots config option changes that list. With Cache Components, uncached data in generateMetadata triggers the same "use cache or Suspense" errors as in a page.

File-based metadata

Some metadata is easier to provide as a file in the app/ folder. Next.js finds these files and adds the right tags:

FileWhat it produces
favicon.ico (root of app/ only)The browser tab icon
icon.png|svg|ico, apple-icon.pngApp icons, including the iOS home-screen icon
opengraph-image.png|jpg, twitter-image.png|jpgLink preview images, for that segment and below
robots.txtInstructions for crawlers
sitemap.xmlThe list of URLs for search engines
manifest.jsonA web app manifest

Each can also be generated with code by using a .ts/.tsx file of the same name, which is useful when it depends on data.

robots.ts and sitemap.ts

In a real app, sitemap() would be async and list every book from your data (cache it, so the sitemap isn't rebuilt on every request).

Open Graph images

An Open Graph image is the picture shown in a link preview. For a fixed image, drop an opengraph-image.png into a folder: it applies to that route and everything below, and a deeper file takes precedence. For an image per book, generate it from JSX with ImageResponse (from next/og) in an opengraph-image.tsx file:

Next.js added the og:image tags automatically and serves a real 1200 × 630 PNG. ImageResponse turns JSX and a subset of CSS into a PNG (it uses satori and resvg under the hood). Only flexbox layout and common properties are supported: display: grid, for example, won't work. Try designs in the Vercel OG Playground.

📝 The og:image URL uses http://localhost:3000 because no base URL is set. In production, set metadataBase: new URL("https://your-site.example") in the root layout's metadata, so link previews get absolute, public URLs.

Recap

  • Use the Metadata APIs, not hand-written <head> tags; they work in Server Components (layouts and pages).
  • export const metadata for static values; title.template in a layout wraps page titles; fields merge from layouts down.
  • generateMetadata builds metadata from data and params; cache or React.cache the data so it's fetched once. For dynamic pages, metadata is streamed (but not to bots).
  • File conventions: favicon.ico, icon, apple-icon, opengraph-image, twitter-image, robots, sitemap, manifest, as files or code.
  • ImageResponse from next/og turns JSX into PNG images for OG cards and icons (flexbox only).
  • Set metadataBase for absolute URLs; viewport holds themeColor and similar settings.

Exercise 8 🟡 medium debug

A link preview in a chat app shows no image, although the page has an opengraph-image.png. The og:image tag reads http://localhost:3000/opengraph-image.png. What's wrong?

Show solution

metadataBase isn't set, so Next.js used a local URL that the chat app's servers can't reach. Set metadataBase: new URL("https://your-domain") in the root layout's metadata (some platforms set a sensible default from their deployment URL).

Exercise 9 🔴 hard Cache Components

A dynamic page's generateMetadata reads cookies() to put the user's name in the title. With Cache Components, what happens, and is it a good idea?

Show solution

Reading cookies() is runtime data, so the metadata can't be prerendered; Next.js reports the same kind of insight as in a page, and the metadata is streamed at request time. It's rarely a good idea: personal titles leak into shared screenshots and browser history, and search engines can't use them. Keep metadata about the content, and show personal information in the page body inside <Suspense>.

Exercise 10 🔴 hard design

Plan the complete metadata for the Reading List app: which fields go in the root layout, which in each page, which files you add, and how book pages get unique previews. Keep it under ten bullet points.

Show solution
  • Root layout: metadataBase, title template and default, description, openGraph.siteName.
  • app/icon.tsx (or icon.png) and apple-icon.png; favicon.ico.
  • app/opengraph-image.tsx: the default site card.
  • Static pages (/about, /books): export const metadata with title and description.
  • Book pages: generateMetadata with title, description and openGraph (type: "book"), reading the cached getBook.
  • app/books/[id]/opengraph-image.tsx: a card per book with title and author.
  • app/robots.ts: allow everything except /admin; link the sitemap.
  • app/sitemap.ts: home, list, and every book.
  • Admin pages: robots: { index: false } in their layout's metadata.
