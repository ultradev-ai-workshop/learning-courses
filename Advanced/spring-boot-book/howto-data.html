Add Flyway to an existing database

Production already has tables created by hand years ago. You want versioned migrations from now on, without re-running the original DDL.

FlywaybaselineChapter 13

Solution

  1. Dump the current schema into V1__baseline.sql (for new environments and tests).
  2. Tell Flyway that existing databases are already at version 1:

On the first start against production, Flyway creates flyway_schema_history with a baseline row and skips V1; new environments run V1 normally. Every later change is V2__…, V3__…. Remember the Boot 4 starter: spring-boot-starter-flyway (plus flyway-database-postgresql or the module for your database).

Pitfalls

  • Make sure V1 really matches production (indexes, constraints); ddl-auto=validate catches many differences at startup.
  • Remove baseline-on-migrate once all environments are baselined, so an accidental empty schema isn't silently treated as "version 1".

Load seed data only in development

Developers want 50 sample books on startup; production must never get them.

Flyway locationsprofilesChapters 4, 13

Solution

Keep schema migrations in db/migration and development data in a second folder that only the dev profile adds. Use repeatable migrations (R__) so editing the sample data re-applies it:

For tests, prefer creating exactly the data each test needs (repositories, @Sql, builders) over a big shared data set.

Pitfalls

  • Avoid mixing data.sql with Flyway: data.sql runs on every start and has no versioning.
  • Make seed scripts idempotent (MERGE/INSERT … ON CONFLICT DO NOTHING) or delete-then-insert in a repeatable migration.

Use two datasources

The main database is your own; reports must also be read from a legacy database.

DataSource@QualifierChapters 2, 13

Solution

Defining your own DataSource makes Boot's back off, so define both, mark the main one @Primary (JPA, Flyway and transactions use it), and bind each from its own properties prefix. Use a qualified JdbcClient for the second:

Note jdbc-url (Hikari's property name) rather than url when binding straight onto a DataSourceBuilder-created Hikari pool. For JPA on the second database too, you also need a second LocalContainerEntityManagerFactoryBean and JpaTransactionManager with their own packages (@EnableJpaRepositories(basePackages = …, entityManagerFactoryRef = …)).

Pitfalls

  • @Transactional uses the primary transaction manager; for the second database, name its manager: @Transactional("legacyTransactionManager").
  • A transaction spanning both databases is not atomic without XA — design for one database per operation or use events/outbox.

Prevent lost updates over HTTP (ETag / If-Match)

Two librarians edit the same book in their browsers; the second save silently overwrites the first.

@VersionETag412Chapters 9, 15

Solution

Expose the entity's @Version as the ETag; require clients to send it back in If-Match; reject a stale version with 412 Precondition Failed:

Pitfalls

  • The explicit version check covers the time between the client's GET and PUT; the JPA @Version check at flush still covers concurrent requests within the server.
  • Don't fall back to "last write wins" when If-Match is missing — answer 428 so clients learn to send it.

Deleted members must disappear from the app but stay in the database for auditing.

Solution

Pitfalls

  • Unique constraints still see deleted rows: a new member can't reuse a deleted member's e-mail unless the constraint includes the flag (or uses a partial index).
  • Soft delete isn't erasure — personal-data laws may require real deletion or anonymisation after a period.

Read only the columns you need

A list screen shows title and author name for 10 000 books; loading full entities (and their relations) is slow.

projectionsDTOChapter 14

Solution

Let the repository return a record; Spring Data selects only those properties — joins included — in one query:

The generated SQL selects two columns with a join — no description, no N+1 for authors, and no entities in the persistence context to dirty-check.

Pitfalls

  • Projections are read-only: to change data, load the entity.
  • Hibernate maps String to VARCHAR(255) unless told otherwise — long text needs @Column(length = …) (or @Lob), and with Flyway, the right column type in the migration.
  • Constructor expressions need the record's fully qualified name and a top-level (not nested) class.

See the SQL and its parameters

A query is slow or wrong and you want to see exactly what Hibernate sends.

loggingHibernateChapters 14, 18

Solution

Prefer logging over spring.jpa.show-sql=true, which bypasses the logging system (always to stdout, no levels). For production, use datasource-proxy or p6spy with Micrometer to time queries, or your database's slow-query log.

Pitfalls

  • Bind-parameter logging prints personal data and secrets — development only.
  • The SQL log shows what runs, not why it's slow: run EXPLAIN ANALYZE on the database for the plan.
