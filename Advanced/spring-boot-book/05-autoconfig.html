Auto-configuration & Starters

Auto-configuration is the "magic" of Spring Boot — and it isn't magic at all. It's ordinary @Configuration classes guarded by conditions. Once you can read those conditions, you can predict what Boot will create, find out why it did (or didn't), override any of it, and write your own auto-configuration and starter for code shared across teams.

You will learn

  • How Boot finds auto-configurations (the AutoConfiguration.imports file) and orders them.
  • The conditions: @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty, @ConditionalOnWebApplication and more.
  • Why your beans win, and how to exclude an auto-configuration.
  • Reading the condition evaluation report (--debug).
  • Writing and testing your own auto-configuration and starter with ApplicationContextRunner.

How auto-configuration works

@EnableAutoConfiguration (part of @SpringBootApplication) loads a list of class names from every META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports file on the classpath. Each listed class is an @AutoConfiguration — a @Configuration(proxyBeanMethods = false) class — whose beans are registered only if its conditions match. They're processed after your own configuration, so they can check what you've already defined.

Read it as a sentence: "If Jackson is on the classpath and the application hasn't defined a JsonMapper, create one, applying every customizer." Almost every auto-configuration follows that shape: a class-level condition on the classpath, bean-level @ConditionalOnMissingBean, and settings from @ConfigurationProperties.

🧠 Analogy: a hotel room checklist. Housekeeping has a checklist: "If the guest has a baby (condition), put a crib in the room — unless the guest brought their own (missing bean). If the guest asked for no turndown service (property), skip it." Boot's auto-configuration is that checklist, run against your classpath and configuration every time the application starts.

The conditions

AnnotationMatches when…
@ConditionalOnClass / @ConditionalOnMissingClassa class is (not) on the classpath — "is this library present?"
@ConditionalOnBean / @ConditionalOnMissingBeana bean of the type/name is (not) already defined
@ConditionalOnPropertya property has a value (optionally a specific one); matchIfMissing decides the default
@ConditionalOnBooleanPropertya boolean property is true (or false)
@ConditionalOnWebApplication / @ConditionalOnNotWebApplicationit's (not) a servlet or reactive web app
@ConditionalOnResourcea resource exists, e.g. classpath:banner.txt
@ConditionalOnSingleCandidateexactly one bean of a type (or one primary)
@ConditionalOnThreadingvirtual threads are (not) enabled (spring.threads.virtual.enabled)
@ConditionalOnExpression, @ConditionalOnJava, @ConditionalOnCloudPlatform…SpEL, Java version, Kubernetes/Cloud Foundry…
@Conditional(MyCondition.class)your own Condition implementation returns true

Conditions aren't only for auto-configuration — you can use them on your own @Bean methods and @Configuration classes:

caffeine isn't created: app.cache is set, but not to caffeine. With app.cache unset, matchIfMissing = true would create it.

⚠️ Class conditions on missing classes. @ConditionalOnClass(Gson.class) on a class is safe even when Gson is absent (Boot reads the annotation without loading the class). On a @Bean method, use the name = "…" form, or isolate the method in a nested configuration class — otherwise the JVM may fail to load your configuration class when Gson is missing.

Your beans win: backing off

Because auto-configurations run after your configuration and use @ConditionalOnMissingBean, defining a bean of the same type replaces the default. Boot calls this backing off:

💡 Customise, don't replace. Replacing a bean means you also lose everything Boot configured on it (the spring.jackson.* properties, registered modules…). Most auto-configurations offer a lighter hook: a property (spring.jackson.serialization.indent-output=true) or a customizer bean (JsonMapperBuilderCustomizer, RestClientCustomizer, WebServerFactoryCustomizer…). Prefer, in order: property → customizer → your own bean.

Starters

A starter is an (almost) empty jar whose only job is to bring in a set of dependencies: the library, its auto-configuration module, and anything else it needs. Spring Boot 4 made starters modular: each technology has its own auto-configuration module and starter, so your application only contains the auto-configuration it uses. Starters you'll meet in this book:

StarterBrings
spring-boot-starter-webmvcSpring MVC, embedded Tomcat, Jackson 3 (was -web in Boot 3)
spring-boot-starter-webfluxWebFlux, Reactor Netty
spring-boot-starter-restclient / -webclientauto-configured RestClient.Builder / WebClient.Builder, HTTP service clients
spring-boot-starter-validationHibernate Validator (Bean Validation)
spring-boot-starter-jdbc, -data-jpa, -flyway, -liquibaseHikariCP + JDBC, Spring Data JPA + Hibernate 7, migrations
spring-boot-starter-security, -security-oauth2-resource-serverSpring Security 7, JWT resource server
spring-boot-starter-actuator, -opentelemetryhealth, metrics, tracing

spring-boot-starter-xxx-testeach technology has a test starter (e.g. -webmvc-test, -data-jpa-test) with its test slice

Upgrading an old project? spring-boot-starter-classic (and -test-classic) bring back all auto-configuration modules at once, like Boot 3 — a stepping stone, not a destination (Appendix B).

Writing your own auto-configuration

When several applications share infrastructure — a company HTTP client, audit logging, a tenant resolver — package it as an auto-configuration so every app gets it by adding one dependency. The recipe:

  1. An @AutoConfiguration class with conditions, outside the packages of any application (it must not be component-scanned).
  2. A @ConfigurationProperties class for its settings.
  3. The class name listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports.
  4. Optionally a starter module that depends on it and the libraries it needs.

Testing an auto-configuration with ApplicationContextRunner

Starting a full application per scenario is slow. ApplicationContextRunner builds a tiny context in milliseconds, with exactly the configurations and properties you give it — ideal for testing conditions:

WebApplicationContextRunner and ReactiveWebApplicationContextRunner do the same for web conditions, and FilteredClassLoader simulates a missing library (runner.withClassLoader(new FilteredClassLoader(SomeLibrary.class))).

Ordering and naming tips

  • Use @AutoConfiguration(after = JacksonAutoConfiguration.class) when your conditions depend on beans another auto-configuration creates (for example @ConditionalOnBean(JsonMapper.class)).
  • Name modules acme-spring-boot-autoconfigure and acme-spring-boot-starter. The spring-boot-* prefix is reserved for the Spring Boot team.
  • Prefix your properties with your own namespace (acme.greeter.*), never spring.* or server.*.
  • Add spring-boot-configuration-processor so users get auto-completion and documentation for your properties.

Recap

  • Auto-configurations are @AutoConfiguration classes listed in META-INF/spring/…AutoConfiguration.imports, processed after your configuration.
  • Conditions decide everything: classpath (OnClass), existing beans (OnMissingBean), properties, web type, resources, threading, custom Conditions.
  • Your beans win (backing off). Prefer property → customizer → own bean. Exclude with exclude= or spring.autoconfigure.exclude.
  • --debug prints the condition evaluation report; ConditionEvaluationReport and /actuator/conditions expose it.
  • Own auto-configuration: conditions + properties + imports file, tested with ApplicationContextRunner. Boot 4 starters are modular, one per technology.

Exercises

Exercise 1 🟢 easy concept

Translate into a sentence: @ConditionalOnClass(DataSource.class) on the class, and @ConditionalOnMissingBean + @ConditionalOnProperty(name = "app.pool.enabled", matchIfMissing = true) on a @Bean HikariDataSource dataSource().

Show solution

"If JDBC's DataSource class is on the classpath, then — unless the application already defines a HikariDataSource bean, or app.pool.enabled is set to false — create a HikariDataSource." (A missing property counts as enabled because of matchIfMissing.)

Exercise 2 🟢 easy concept

You want all JSON output indented. List three ways to do it, from least to most invasive.

Show solution

(1) Property: spring.jackson.serialization.indent-output=true. (2) A JsonMapperBuilderCustomizer bean calling builder.enable(SerializationFeature.INDENT_OUTPUT). (3) Your own JsonMapper bean, which replaces Boot's (and loses its other settings).

Exercise 3 🟢 easy debug

You added a database driver but no DataSource bean appears. What's the fastest way to find out why?

Show solution

Run with --debug (or debug=true) and look for DataSourceAutoConfiguration in the condition evaluation report. Its Negative matches entry says exactly which condition failed — for example a missing spring-boot-starter-jdbc (in Boot 4 the auto-configuration lives in that module), or spring.datasource.url not set for a non-embedded database. With Actuator, /actuator/conditions shows the same.

Exercise 4 🟢 easy concept

Why must an auto-configuration class not live in a package that is component-scanned by the application?

Show solution

If it's scanned, it's registered as an ordinary configuration class, processed together with the user's configuration — before the user's beans are all known. Its @ConditionalOnMissingBean checks may then give the wrong answer, and ordering (after=) is ignored. Auto-configurations must only be loaded through the imports file.

Exercise 5 🟡 medium code

An application needs a default java.time.Clock (Clock.systemUTC()) that is replaced by a fixed Europe/Paris clock when app.fixed-clock=true. Implement both beans in one class, print the clock's zone with and without the property, and explain why @ConditionalOnMissingBean is not the right tool for the default here.

Show solution

Why not @ConditionalOnMissingBean? In application configuration, bean definitions are registered in an order you don't fully control, so "missing" may be evaluated before the other bean is registered. The docs recommend @ConditionalOnMissingBean only in auto-configurations. In application code, @Fallback (or @Primary) expresses "default unless replaced" reliably.

Exercise 6 🟡 medium code

Write an ApplicationContextRunner test for the greeter auto-configuration showing that greeter.prefix=Bonjour gives Bonjour, Ada! and that the GreeterProperties bean exists.

Show solution

Exercise 7 🟡 medium code

Use FilteredClassLoader in a test to prove that a configuration guarded by @ConditionalOnClass(name = "tools.jackson.databind.json.JsonMapper") backs off when Jackson is missing.

Show solution

Exercise 8 🟡 medium concept

Your company auto-configuration defines an AuditLogger that needs the application's JsonMapper bean, guarded by @ConditionalOnBean(JsonMapper.class). It sometimes isn't created even though Jackson is present. Why, and how do you fix it?

Show solution

@ConditionalOnBean only sees beans registered so far. If your auto-configuration is processed before JacksonAutoConfiguration, the JsonMapper isn't defined yet and the condition fails. Fix: @AutoConfiguration(after = JacksonAutoConfiguration.class) (or afterName = "…" to avoid a compile-time dependency).

Exercise 9 🔴 hard code

Write a custom condition annotation @ConditionalOnWeekend backed by a Condition that reads the day of week from the property app.today (e.g. SATURDAY; default: the real current day). Use it on a bean and test it with ApplicationContextRunner for SATURDAY and MONDAY.

Show solution

Meta-annotating with @Conditional is exactly how Boot's own @ConditionalOn… annotations are built. For better --debug output, extend SpringBootCondition and return a ConditionOutcome with a message.

Exercise 10 🔴 hard mini-project · playground

Create an audit auto-configuration in com.example.autoconfig.audit: AuditProperties("audit") with String appName (default app) and boolean enabled (default true); an AuditLog class with String entry(String action) returning "[appName] action"; an @AutoConfiguration that creates it unless disabled or already defined. Register it in the imports file (append a line to the existing one) and write four context-runner tests: default, custom name, disabled, user bean wins.

Show solution

To ship it, the imports file would get a second line, com.example.autoconfig.audit.AuditAutoConfiguration. The tests don't need it: AutoConfigurations.of(…) loads the class directly — which is why context-runner tests are fast and independent of the classpath.
