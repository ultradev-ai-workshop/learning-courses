Actuator, Observability & Logging

Running software you can't see into is guesswork. Spring Boot Actuator gives every application health checks, metrics and operational endpoints; Micrometer's Observation API turns one instrumentation call into both metrics and traces; and Boot's logging supports levels you can change at runtime and structured JSON logs. This chapter wires them all up.

You will learn

  • The Actuator endpoints (health, info, metrics, loggers, env…), how to expose and protect them.
  • Health: built-in indicators, custom HealthIndicators, liveness and readiness probes for Kubernetes.
  • Metrics with Micrometer: counters, timers, gauges, tags, and the automatic HTTP metrics.
  • Observations and tracing: Observation, @Observed, trace ids, OpenTelemetry.
  • Logging: levels and groups, runtime changes, MDC, and structured logging (ECS, Logstash, GELF).

The three signals

SignalAnswersExample
Metrics"how much, how often, how fast?" — aggregated numbers over timep99 latency of GET /books, error rate, pool usage
Traces"where did this request spend its time?" — across servicesa checkout that called 4 services; the slow span was the payment call
Logs"what exactly happened?" — detailed events"payment declined for order 42: insufficient funds"

🧠 Analogy: a hospital. Metrics are the monitors at the bedside: heart rate, blood pressure — numbers you watch and alert on. A trace is the patient's journey through departments, with times at each step. Logs are the doctors' detailed notes. The health endpoint is the nurse's quick check: "is the patient alive (liveness)? Ready to receive visitors (readiness)?"

Actuator endpoints

Add spring-boot-starter-actuator. Endpoints are served under /actuator; by default only health is exposed over HTTP (all are available over JMX if enabled). Expose more explicitly — and protect them:

EndpointShows
healthUP/DOWN status, components (db, disk, …), liveness/readiness groups
infoapplication info: build version, git commit, Java, OS, custom info.*
metrics, prometheusMicrometer metrics (JSON) / Prometheus scrape format
loggersview and change log levels at runtime
env, configpropsconfiguration properties and their sources (values masked by default)
beans, conditions, mappingsbeans, auto-configuration report (Chapter 5), request mappings
threaddump, heapdump, scheduledtasks, sbomdiagnostics, scheduled jobs, software bill of materials

Since Boot 3, the info.* properties only appear with management.info.env.enabled=true, and the Java and OS sections need management.info.java.enabled/os.enabled — a default that avoids leaking details by accident. The http.server.requests timer is recorded automatically for every request, tagged with method, uri (the template, e.g. /books/{id}, so the number of series stays bounded), status, outcome and exception. Similar automatic metrics exist for clients (http.client.requests), JVM memory and GC, Hikari pools, Tomcat, caches, executors and more.

⚠️ Actuator is an attack surface. env, heapdump and threaddump can reveal secrets. Expose only what you need (health,info,prometheus is a common choice), consider a separate management port (management.server.port=8081) that isn't reachable from the internet, and protect the rest with Spring Security (EndpointRequest.toAnyEndpoint() in a separate filter chain, as in Chapter 17).

Health, liveness and readiness

Health is the sum of health indicators: Boot adds them for the database, disk space, Redis, mail servers and so on. Add your own for dependencies that matter. Status aggregation is "the worst wins": one DOWN component makes the whole application DOWN (HTTP 503).

The last line matters: Kubernetes-style probes are separate health groups, enabled by default in Boot 4 at /actuator/health/liveness and /actuator/health/readiness:

  • Liveness — "is the process broken beyond repair?" A failed liveness probe makes Kubernetes restart the container. It should almost never depend on external systems: if the payment gateway is down, restarting your app won't fix it.
  • Readiness — "can I take traffic right now?" A failed readiness probe removes the instance from the load balancer until it recovers. It's DOWN during startup and graceful shutdown, and you can include dependencies here (management.endpoint.health.group.readiness.include=readinessState,db).

Your code can change these states by publishing AvailabilityChangeEvents, e.g. refusing traffic while a cache warms up (Exercise 9).

Metrics with Micrometer

Micrometer is a facade over monitoring systems (Prometheus, Datadog, OTLP, CloudWatch…), like SLF4J for metrics. Inject the MeterRegistry and record:

  • Counter: a number that only goes up (orders placed, errors). Rates are computed by the monitoring system.
  • Timer: count + total time + max of an operation, optionally percentiles/histograms.
  • Gauge: a current value sampled when read (queue size, active users).
  • DistributionSummary: distribution of non-time values (payload sizes, basket totals).

Without an exporter on the classpath, Boot uses an in-memory SimpleMeterRegistry (what /actuator/metrics shows). Add io.micrometer:micrometer-registry-prometheus for a /actuator/prometheus scrape endpoint, or micrometer-registry-otlp to push via OpenTelemetry. Apply common tags to everything with management.metrics.tags.region=eu-west-1.

⚠️ High-cardinality tags. Every distinct combination of tag values is a separate time series in your monitoring system. tag("channel", "web") is fine; tag("userId", id) or tag("isbn", isbn) creates millions of series and can take your metrics backend down. Put unbounded values in logs or traces, not metric tags.

Observations and tracing

Instrumenting the same operation separately for metrics, traces and logs is tedious. Micrometer's Observation API lets you instrument once: an observation has a name, low-cardinality key-values (become metric tags and span attributes) and high-cardinality ones (span attributes only); registered handlers turn it into a timer, a trace span, log context, or all three. Spring's own instrumentation (HTTP server and client, @Scheduled, messaging, JDBC with extra libraries) uses it too.

The high-cardinality query key-value never became a metric tag — exactly the protection described above. (Printing the third line has a precedence bug; you'll fix it in Exercise 1.)

Distributed tracing

Add spring-boot-starter-opentelemetry (Boot 4) and every incoming request gets a trace; each observation becomes a span; RestClient/WebClient calls propagate the trace context to downstream services in the traceparent header (W3C Trace Context); and the trace and span ids are added to your log lines. Spans are exported over OTLP to a collector (Grafana Tempo, Jaeger, Zipkin, a vendor):

For local development, Boot's Docker Compose support can start a Grafana LGTM container (logs, metrics, traces in one image) and configure these URLs automatically.

Logging

Boot uses SLF4J with Logback by default, logging to the console at INFO. Configure levels per logger or logger group, and write to a file if you need to:

Two production essentials: change levels at runtime via the loggers endpoint (turn on DEBUG for one package while investigating, no restart), and structured logging — JSON lines that log platforms can index without fragile regex parsing. Boot supports Elastic Common Schema (ecs), Logstash (logstash) and Graylog (gelf) formats:

Each log event is a single JSON line with standard field names; MDC entries (orderId) and SLF4J key-values (isbn) become fields. With tracing enabled, traceId and spanId appear too, so you can jump from a log line to its trace.

💡 Log for the reader at 3 a.m. Log business events at INFO with identifiers (order id, member id), unexpected failures at ERROR once with the stack trace (where you handle them, not at every layer), and never log secrets or personal data such as passwords, tokens or full card numbers.

Recap

  • Actuator: /actuator/*; only health exposed by default; expose with management.endpoints.web.exposure.include; protect or move to a management port.
  • Health = aggregated HealthIndicators (worst wins, 503 when DOWN). Liveness (restart) must not depend on externals; readiness (traffic) may.
  • Micrometer: counters, timers, gauges via MeterRegistry; automatic HTTP/JVM/pool metrics; bounded tag values only.
  • Observation API instruments once for metrics and traces (Observation.observe, @Observed); spring-boot-starter-opentelemetry for tracing, OTLP export and trace ids in logs.
  • Logging: levels and groups, runtime changes via /actuator/loggers, MDC and key-values, structured JSON with logging.structured.format.console=ecs.

Exercises

Exercise 1 🟢 easy debug

In the observation example, System.out.println("query tag on metric? " + registry.find(…).tagKeys("query").timer() != null) doesn't print what was intended. What does it print, why, and what's the fix?

Show solution

It prints just true: + binds tighter than !=, so Java compares the whole string "query tag on metric? " + timer with null. Add parentheses: "query tag on metric? " + (registry.find("library.search").tagKeys("query").timer() != null), which prints false — no timer has a query tag.

Exercise 2 🟢 easy concept

Your app's readiness group includes the database. The database has a 30-second outage. What happens with Kubernetes if the database is in (a) the readiness group, (b) the liveness group?

Show solution

(a) All instances become not-ready and are removed from the load balancer; when the database returns they become ready again — clients see errors or "service unavailable" for 30 s, which is honest. (b) Kubernetes restarts every instance repeatedly; startups hammer the recovering database and the outage gets longer. Keep external dependencies out of liveness.

Exercise 3 🟢 easy concept

Which metric type would you use for: (a) number of failed logins, (b) duration of report generation, (c) number of items currently in a retry queue, (d) size of uploaded files?

Show solution

(a) Counter (tagged with a bounded reason), (b) Timer, (c) Gauge, (d) DistributionSummary (with base unit bytes).

Exercise 4 🟢 easy code

Write a HealthIndicator that reports DOWN when free disk space in the temp directory is below a configured number of bytes (pass Long.MAX_VALUE to force DOWN) and print its status. (Hint: new java.io.File(System.getProperty("java.io.tmpdir")).getUsableSpace().)

Show solution

Health indicators are plain classes — easy to unit test without starting anything.

Exercise 5 🟡 medium code

Record a Timer with percentiles: build Timer.builder("report.time").publishPercentiles(0.5, 0.95) on a SimpleMeterRegistry, record durations 10, 20, …, 100 ms, and print the count and max.

Show solution

Client-side percentiles can't be aggregated across instances; with Prometheus prefer publishPercentileHistogram() and compute percentiles in the query (histogram_quantile).

Exercise 6 🟡 medium code

Wrap a failing operation in Observation.observe and show that the resulting timer is tagged with error=IllegalStateException.

Show solution

Successful runs are tagged error=none, so one timer gives you both latency and error rate.

Exercise 7 🟡 medium code

Expose info with custom properties and a custom InfoContributor that adds {"catalog":{"books":1234}}. Print the endpoint's catalog field.

Show solution

For build version and git commit, add the build-info goal of spring-boot-maven-plugin and the git-commit-id-maven-plugin; Boot then contributes build and git sections automatically.

Exercise 8 🟡 medium debug

A team tags their orders.placed counter with customerId. A month later the Prometheus server runs out of memory. Explain, and propose a better design for answering "which customers order the most?".

Show solution

Each customer id creates a new time series; with 2 million customers that's 2 million series for one metric (times every other tag combination). Metrics systems are built for bounded label sets. Keep the counter with low-cardinality tags (channel, country), and answer per-customer questions from the database or from logs/events in an analytics store, where high cardinality is normal.

Exercise 9 🔴 hard code

Write a custom readiness check: an application that starts not ready while a "cache warm-up" runs, by publishing AvailabilityChangeEvent with ReadinessState.REFUSING_TRAFFIC from an ApplicationRunner, then ACCEPTING_TRAFFIC when done. Read /actuator/health/readiness before and after.

Show solution

Timing matters: Boot itself publishes ACCEPTING_TRAFFIC when the application is ready (after the runners), so a REFUSING_TRAFFIC published from an ApplicationRunner would simply be overwritten — that's why the warm-up starts from ApplicationReadyEvent. Refusing traffic shows as OUT_OF_SERVICE (HTTP 503), so a load balancer won't send requests yet — but liveness stays UP, so nothing restarts the instance.

Exercise 10 🔴 hard mini-project · playground

Instrument the Library Loans service: a LoanService.borrow(isbn, member) that (1) runs inside an Observation named library.loans.borrow with a low-cardinality outcome of ok, limit or unavailable, (2) logs an INFO line with the member and isbn as key-values, and (3) exposes a gauge library.loans.open. Simulate 5 attempts and print the counts per outcome and the gauge.

Show solution

Starting and stopping the observation manually lets you add key-values that are only known at the end (the outcome). Note what went where: outcome (3 values) is a metric tag; member and isbn (unbounded) only go to the log line — and would go to the trace span as high-cardinality values.
