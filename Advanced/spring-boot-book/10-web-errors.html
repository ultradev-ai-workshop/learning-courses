Chapter 10 · Web

Errors, Validation & Web Infrastructure

A good API is judged by how it fails. This chapter shows how Spring MVC turns exceptions into HTTP responses, how to return consistent RFC 9457 Problem Details, how to validate request bodies and parameters, and the infrastructure around your controllers: servlet filters, CORS, and multipart uploads.

You will learn

  • What happens to an exception thrown from a controller, and Boot's default /error response.
  • ProblemDetail, ErrorResponseException and ResponseStatusException.
  • Local @ExceptionHandlers and a global @RestControllerAdvice.
  • Validating requests: @Valid @RequestBody, parameter constraints, and returning field errors.
  • Filters (OncePerRequestFilter), CORS and file uploads.

What happens when a controller throws

When a handler method throws, the DispatcherServlet asks a chain of HandlerExceptionResolvers to handle it:

  1. ExceptionHandlerExceptionResolver: your @ExceptionHandler methods (in the controller, then in @ControllerAdvice classes).
  2. ResponseStatusExceptionResolver: exceptions annotated @ResponseStatus and ResponseStatusException.
  3. DefaultHandlerExceptionResolver: Spring's own exceptions (missing parameter → 400, wrong method → 405…).

If none handles it, the exception reaches the servlet container, which forwards to /error. Boot's BasicErrorController answers there with a JSON body (or an HTML "Whitelabel" page for browsers):

(The example removes the timestamp field and silences Spring's WARN log lines so the output is stable; the container also logs the stack trace of the 500.) Notice what's not there: the exception message. Boot hides messages, exception class names and stack traces by default, because they can leak internals to attackers. You can opt in with server.error.include-message=always — but a better approach is to design your error responses explicitly.

Problem Details (RFC 9457)

RFC 9457 "Problem Details for HTTP APIs" is a standard JSON shape for errors, with the media type application/problem+json:

Spring represents it as ProblemDetail. Turn on spring.mvc.problemdetails.enabled=true and all of Spring MVC's own exceptions (400, 404, 405, 415…) are rendered this way. For your own errors, throw an ErrorResponseException (or a subclass) or ResponseStatusException, or return a ProblemDetail from an exception handler:

Three details of the JSON Spring writes: type is left out when it is the default about:blank (RFC 9457 says a missing type means exactly that); extra properties such as balance appear at the top level, as the RFC requires; and instance is filled in with the request path automatically. The last line shows Spring's own MissingServletRequestParameterException rendered as a problem — with a helpful, safe detail.

🧠 Analogy: a standard accident report form. Without a standard, every driver describes an accident differently — one writes a novel, another just says "bad". Insurance companies use one form with fixed boxes: what happened, where, how serious, plus a free-text box for details. Problem Details is that form for APIs: clients always know where to look for the status, the title and the details, and can still read your extra fields.

Exception handlers and @RestControllerAdvice

Domain code shouldn't know about HTTP. Throw plain domain exceptions in services, and translate them to responses in one place: a @RestControllerAdvice class with @ExceptionHandler methods. Extending ResponseEntityExceptionHandler also gives you Problem Details for all of Spring MVC's exceptions, with hooks to customise them:

The @ExceptionHandler methods declare the exception type as their parameter; Spring picks the closest match in the class hierarchy, so the Exception handler only gets what nothing else handles. An @ExceptionHandler inside a controller class applies only to that controller and takes precedence over the advice.

💡 Choosing status codes. 400 malformed request; 401 not authenticated; 403 authenticated but not allowed; 404 not found; 409 conflicts with current state (duplicate, version mismatch); 422 well-formed but violates a business rule; 429 rate-limited; 500 your bug; 503 a dependency is down. Pick one convention per API and document it.

Validating requests

Add @Valid (or @Validated for groups) to a @RequestBody. Invalid input throws MethodArgumentNotValidException, which ResponseEntityExceptionHandler turns into a 400 problem. Constraints directly on @PathVariable/@RequestParam parameters are validated too — Spring MVC has built-in method validation for controllers — and raise HandlerMethodValidationException. ⚠️ Malformed JSON is not a validation error. A body like {"age": "old"} or a truncated document fails before validation with HttpMessageNotReadableException (400, "Failed to read request"). Handle it separately if you want a friendlier message, and never echo the raw parser message to clients — it can contain internal class names.

Servlet filters

A filter wraps the whole request processing — even requests that never reach a controller (404s, static files) and code that runs before Spring MVC (Spring Security is a filter chain). Extend OncePerRequestFilter, which guarantees one execution per request even with internal forwards like /error. Any Filter bean is registered automatically; @Order sets its position:

The filter sees the 404 for /missing even though no controller handled it. Use filters for cross-cutting HTTP concerns (request ids, logging, compression, CORS, security); use interceptors (Chapter 9) when you need to know which handler method was chosen.

CORS

Browsers block JavaScript on https://app.example.com from reading responses from https://api.example.com unless the API allows it with CORS headers. Server-to-server calls (and curl) are not affected — CORS is a browser rule. Configure it globally:

File uploads

Spring MVC handles multipart/form-data out of the box. Accept a MultipartFile with @RequestParam (or @RequestPart for a JSON part next to the file). Limits are properties:

The client sent the file part as image/png because RestClient guesses the part's content type from the .png file name. Never trust it on the server for security decisions: check the bytes (magic numbers) and the size, and generate your own storage name instead of using getOriginalFilename(), which can contain ../. Recap

  • Exceptions go through HandlerExceptionResolvers (@ExceptionHandler → @ResponseStatus/ResponseStatusException → Spring's defaults), then to Boot's /error, which hides messages by default.
  • Use Problem Details (application/problem+json): spring.mvc.problemdetails.enabled=true, ProblemDetail, ErrorResponseException, custom type and extra properties.
  • Keep domain exceptions HTTP-free; map them in one @RestControllerAdvice extending ResponseEntityExceptionHandler, with a safe catch-all for 500s.
  • @Valid @RequestBody → MethodArgumentNotValidException; parameter constraints → HandlerMethodValidationException. Override the handler hooks to return field errors.
  • Filters (OncePerRequestFilter beans with @Order) wrap everything; CORS via addCorsMappings/@CrossOrigin; uploads with MultipartFile and spring.servlet.multipart.* limits.

Exercises

Exercise 1 🟢 easy concept

Name the five standard fields of an RFC 9457 problem and say which ones Spring fills in automatically for ProblemDetail.forStatusAndDetail(NOT_FOUND, "…").

Show solution

type (a URI identifying the problem kind), title (short summary), status, detail (this occurrence), instance (URI of this occurrence). Spring sets status and detail from the arguments, defaults type to about:blank, sets title from the status reason ("Not Found"), and fills instance with the request path when rendering.

Exercise 2 🟢 easy concept

Why does Boot not include the exception message in the default error response? When is it acceptable to include it?

Show solution

Messages often contain internal details: SQL fragments, host names, file paths, class names — useful to attackers and confusing to users. Include messages only when you wrote them for clients (your own domain exceptions mapped explicitly, as in this chapter). server.error.include-message=always exposes all messages and is best limited to development.

Show solution

Exercise 4 🟢 easy concept

A React app on http://localhost:5173 calls your API on http://localhost:8080. It works with curl but fails in the browser. What's wrong, and what's the minimal fix?

Show solution

A different port is a different origin, so the browser enforces CORS and blocks the response (or the preflight). curl doesn't implement CORS. Fix: allow that origin, e.g. registry.addMapping("/api/**").allowedOrigins("http://localhost:5173"), ideally only in the dev profile — or use the dev server's proxy so the browser sees one origin.

Exercise 8 🟡 medium predict

A controller has @ExceptionHandler(IllegalArgumentException.class) returning 400, and a global advice has @ExceptionHandler(RuntimeException.class) returning 500. Which handler runs when the controller throws IllegalArgumentException? When it throws NumberFormatException? When another controller throws IllegalArgumentException?

Show solution

The local handler (400) — local handlers are tried first. NumberFormatException extends IllegalArgumentException, so the local handler again (400). In another controller, only the advice applies: 500 from the RuntimeException handler.

Exercise 9 🔴 hard code

Make malformed JSON friendly: override handleHttpMessageNotReadable to return a 400 problem with detail "Malformed JSON request" and, if the cause is a Jackson MismatchedInputException, a property field holding the name of the offending property (the last element of the exception's path). Send {"name":"Ada","age":"old"} to an endpoint expecting int age.

Show solution

Jackson 3's exceptions live in tools.jackson.databind.exc. A type mismatch tells you where it happened; a truncated document doesn't have a field to blame.
