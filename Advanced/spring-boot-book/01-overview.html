Chapter 1 · Foundations

Spring & Spring Boot: the Big Picture

Spring Framework is the toolkit; Spring Boot is the opinionated way to assemble it into a running application in minutes. This chapter maps the territory: what each project does, how they fit together, what's new in Spring Framework 7 and Spring Boot 4, and what really happens when you call SpringApplication.run.

You will learn

  • What the Spring Framework provides: the container, AOP, data access, web stacks, integration and testing.
  • What Spring Boot adds on top: starters, auto-configuration, an embedded server and production features.
  • The current generation: Spring Framework 7 + Spring Boot 4, Java 17+ (this book uses Java 25), Jakarta EE 11.
  • The anatomy of a Boot project: the build file, the main class and @SpringBootApplication.
  • What happens at startup, and how to look inside the ApplicationContext.

What is the Spring Framework?

The Spring Framework is a set of libraries for building Java applications. At its centre is an Inversion of Control (IoC) container: you describe the objects your application needs (called beans) and how they depend on each other, and the container creates them, wires them together and manages their lifecycle. Everything else in Spring is built on top of that container.

The reference documentation groups the framework into these areas:

AreaWhat it gives youChapter
CoreIoC container, resources, validation, data binding, type conversion, SpEL, AOP, null safety2–8
Data Accesstransactions, DAO support, JDBC (JdbcClient), R2DBC, ORM integration13–15
Web ServletSpring MVC, REST clients, WebSocket9–11
Web ReactiveSpring WebFlux, WebClient, reactive WebSocket12
IntegrationREST clients, JMS, email, scheduling, caching, observability, JVM checkpoint restore8, 11, 18
Testingthe TestContext framework, MockMvc, RestTestClient, WebTestClient16

Other Spring projects build on the framework: Spring Data (repositories for JPA, MongoDB, Redis…), Spring Security, Spring Batch, Spring Cloud, Spring AI and more. They all follow the same model: beans in a container.

What does Spring Boot add?

Using the framework directly means making many decisions: which server, which JSON library, how to configure a connection pool, which logging setup. Spring Boot makes those decisions for you with sensible defaults, and lets you change any of them. Its main features:

  • Starters: one dependency per capability. spring-boot-starter-webmvc brings Spring MVC, Jackson, an embedded Tomcat and logging, all in versions that work together.
  • Auto-configuration: Boot looks at your classpath and your configuration, then creates the beans you would otherwise write by hand: a DataSource if there's a database driver, a JsonMapper if Jackson is present, and so on. Your own beans always win (Chapter 5).
  • Embedded server: the application is a plain main method. There's no WAR file to deploy into an external Tomcat; the server lives inside your jar.
  • Externalized configuration: application.properties/.yml, environment variables and command-line arguments, with a clear order of precedence (Chapter 4).
  • Production features: health checks, metrics, tracing and info endpoints through Actuator (Chapter 18), plus layered jars, container images and native images (Chapter 19).

🧠 Analogy: a kitchen and a meal kit. Spring Framework is a professional kitchen: every tool you could want, but you choose the pans, buy the ingredients and decide the recipe. Spring Boot is a meal kit delivered to that kitchen: the ingredients are measured, the recipe card is written, and the oven is preheated. You can still swap any ingredient — the kit just stops you from starting with an empty counter.

The current generation: Framework 7 and Boot 4

Spring Boot 4.0 (November 2025) and Spring Framework 7.0 are a major generation. This book uses Spring Boot 4.1 on Java 25. The important facts:

  • Java 17 is the minimum; Java 21 and 25 (LTS releases) are recommended. Virtual threads (Java 21+) are a one-line switch.
  • Jakarta EE 11: Servlet 6.1, JPA 3.2, Bean Validation 3.1. Packages are jakarta.*, not javax.*.
  • Modular Boot: auto-configuration is split into small modules and starters are named after the technology (spring-boot-starter-webmvc, -flyway, -restclient…).
  • Jackson 3 (package tools.jackson), JSpecify null-safety annotations, built-in API versioning, HTTP service clients and retry in the core framework.

☕ Coming from Boot 2 or 3? Most code still compiles, but some starters, packages and test annotations changed. Appendix B lists everything you need when you upgrade.

What @SpringBootApplication means

@SpringBootApplication is a shortcut for three annotations:

AnnotationEffect
@SpringBootConfigurationThis class is a configuration class (a specialised @Configuration): its @Bean methods define beans.
@EnableAutoConfigurationTurn on Boot's auto-configuration.
@ComponentScanFind @Component, @Service, @Repository, @Controller, @Configuration classes in this package and its sub-packages.

That last line is why the main class belongs in a root package such as com.example.shop, with everything else below it (com.example.shop.orders, com.example.shop.web…). A class in a sibling package like com.example.other is simply not found.

⚠️ Don't put the main class in the default package (a file with no package line). Component scanning would then scan every jar on the classpath, which is slow and usually fails with confusing errors.

What happens in SpringApplication.run

Startup follows a fixed sequence. Knowing it makes most error messages easy to read:

  1. Create the Environment: read command-line arguments, environment variables, application.properties and profiles (Chapter 4).
  2. Create the ApplicationContext, the container. Its type depends on the classpath: servlet web, reactive web, or none.
  3. Register bean definitions: component scanning, your @Bean methods, then auto-configuration (which backs off where you defined your own beans).
  4. Refresh the context: create all singleton beans in dependency order, inject them, run initialisation callbacks, and start the web server.
  5. Call runners: every CommandLineRunner and ApplicationRunner bean.
  6. Publish events such as ApplicationReadyEvent; the application is now live.

The ApplicationContext returned by run is the container itself. You rarely use it directly in application code (you inject beans instead, Chapter 2), but it's very useful for learning and debugging:

Even a small application has dozens of beans, most created by auto-configuration. Your beans are named after their class with a lower-case first letter. Why a container at all?

Without Spring you'd wire objects by hand in main:

That's fine for three classes. With three hundred, plus transactions, security, caching and configuration that differs per environment, the main method becomes a maze. Spring keeps the good part — CheckoutService still receives its dependency through the constructor and knows nothing about Spring — and takes over the wiring. That idea, dependency injection, is the subject of Chapter 2.

🧠 Analogy: a theatre's stage manager. Actors (your classes) shouldn't have to find their own props and fellow actors before each scene. The stage manager (the container) reads the script (your configuration), places every prop and calls every actor at the right moment. The actors just perform.

Recap

  • Spring Framework = an IoC container plus modules (AOP, data access, MVC/WebFlux, integration, testing). Other Spring projects build on the container.
  • Spring Boot = starters + auto-configuration + embedded server + externalized config + production features. It configures the framework; it doesn't replace it.
  • Current generation: Boot 4 / Framework 7, Java 17+ (25 recommended), Jakarta EE 11, Jackson 3, modular starters.
  • @SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan (current package and below).
  • Startup: environment → context → bean definitions → refresh (create beans, start server) → runners → ApplicationReadyEvent.

Exercises

Exercise 1 🟢 easy concept

Name the three annotations combined in @SpringBootApplication and say in one line what each does.

Show solution

@SpringBootConfiguration marks the class as a configuration class (its @Bean methods define beans). @EnableAutoConfiguration turns on Boot's classpath-driven auto-configuration. @ComponentScan registers components found in the class's package and its sub-packages.

Exercise 2 🟢 easy concept

Your main class is com.acme.shop.ShopApplication. Which of these @Service classes are found by component scanning? com.acme.shop.orders.OrderService, com.acme.billing.InvoiceService, com.acme.shop.ShopService, com.acme.shopping.CartService.

Show solution

OrderService (a sub-package) and ShopService (the same package) are found. InvoiceService (sibling package) and CartService are not: com.acme.shopping is a different package from com.acme.shop, even though the name starts the same way. Scanning works on package segments, not string prefixes.

Exercise 3 🟢 easy code

Write a non-web Boot application whose CommandLineRunner prints Total: 6, the sum of the integers passed as arguments 1 2 3.

Show solution

CommandLineRunner receives the raw String[], exactly as passed to main.

Exercise 4 🟢 easy concept

Which starter would you add for (a) a Spring MVC REST API, (b) JPA with Hibernate, (c) Actuator endpoints? Why don't the starters in pom.xml need a <version>?

Show solution

(a) spring-boot-starter-webmvc, (b) spring-boot-starter-data-jpa, (c) spring-boot-starter-actuator. Versions come from spring-boot-starter-parent, which imports Boot's dependency management (a bill of materials): one Boot version pins hundreds of library versions that are tested together.

Exercise 5 🟡 medium code

Add a @RestController with GET /square/{n} that returns n * n as JSON {"n":7,"square":49}. Use a record for the response, and make main call it with RestClient and print the body.

Show solution

uri("/square/{n}", 7) expands the URI template and encodes the value for you.

Exercise 6 🟡 medium code

Write an application with two runners: an ApplicationRunner that prints second and a CommandLineRunner that prints first. Make them run in that order using @Order. Which order do they run in without it?

Show solution

Lower @Order values run first. Without an order, runners have the lowest precedence and their relative order is not something you should rely on — so add @Order whenever order matters.

Exercise 7 🟡 medium debug

A teammate's application has the main class in com.acme.app and a controller in com.acme.web.StatusController. Requests to /status return 404, and there's no error at startup. What's wrong, and what are two ways to fix it?

Show solution

The controller is outside the scanned packages (com.acme.app and below), so it is never registered and the URL isn't mapped. Fix 1 (best): move the main class up to com.acme, or move the controller to com.acme.app.web. Fix 2: widen the scan with @SpringBootApplication(scanBasePackages = "com.acme"). Prefer fix 1: a single root package keeps scanning predictable.

Exercise 8 🟡 medium code

Print the type of ApplicationContext Boot creates for a non-web application and for a servlet web application (use getClass().getSimpleName()).

Show solution

Boot normally picks the type by looking at the classpath (Spring MVC → SERVLET, only WebFlux → REACTIVE, neither → NONE). The web context's extra job is to create and start the embedded server during refresh.

Exercise 9 🔴 hard code

Write an application that measures its own startup: record System.nanoTime() in main before run, and print ready plus whether startup took less than 10 seconds from an ApplicationReadyEvent listener (use @EventListener).

Show solution

ApplicationReadyEvent.getTimeTaken() gives Boot's own measurement (the same number logged as "Started … in 1.2 seconds"). @EventListener methods on any bean receive application events — Chapter 8 covers events in depth.

Exercise 10 🔴 hard mini-project · playground

Build a tiny "status" service: GET /status returns {"app":"…","javaVersion":…,"beans":…} where app comes from the property app.name (default demo), and beans is the bean count, read by injecting the ApplicationContext into the controller's constructor. Call it once and print app and whether beans > 50.

Show solution

The container can inject itself (ApplicationContext) like any other bean. A web app with Spring MVC has well over 50 beans, almost all from auto-configuration. In the Chapter 18 you'll get this for free from Actuator's /actuator/info and /actuator/beans.
