Transactions in Depth

A transaction makes several changes succeed or fail together. Spring's @Transactional makes that a one-word decision — and hides a lot of behaviour behind it: which exceptions roll back, what happens when one transactional method calls another, what "read-only" means, and how concurrent users can still overwrite each other's work. This chapter makes all of it explicit.

You will learn

  • What a transaction guarantees (ACID) and how @Transactional works as a proxy around a PlatformTransactionManager.
  • Rollback rules: unchecked vs checked exceptions, rollbackFor, noRollbackFor, and "rollback-only".
  • Propagation: REQUIRED, REQUIRES_NEW, NESTED, MANDATORY and friends.
  • readOnly, timeouts, isolation levels and the programmatic TransactionTemplate.
  • Concurrency control: optimistic locking with @Version, pessimistic locks, and after-commit events.

Why transactions

Borrowing a book means two writes: decrement the stock, insert a loan. If the second fails after the first succeeded, the database is inconsistent — a copy vanished. A database transaction guarantees ACID:

  • Atomicity: all changes commit, or none do.
  • Consistency: constraints hold before and after.
  • Isolation: concurrent transactions don't see each other's half-done work (to a configurable degree).
  • Durability: once committed, it survives crashes.

🧠 Analogy: a shopping basket at the till. You put items in your basket (changes), but nothing is yours until you pay (commit). If your card is declined (an exception), all items go back on the shelves (rollback) — the shop never ends up with half of your basket sold. Other shoppers don't see the items you're holding as sold until you've paid (isolation).

How @Transactional works

Boot auto-configures a PlatformTransactionManager (a JpaTransactionManager with JPA, DataSourceTransactionManager with plain JDBC) and enables annotation-driven transactions. @Transactional on a public method of a bean makes Spring wrap the bean in a proxy (Chapter 7) that:

  1. gets or begins a transaction — binding a connection to the current thread,
  2. calls your method; every repository or JdbcClient call on that thread uses the bound connection,
  3. commits if the method returns normally, or rolls back if it throws an unchecked exception.

💡 Where to put @Transactional. On service methods that represent one business operation ("borrow a book", "place an order") — not on controllers (too wide, includes serialisation) and not only on repositories (too narrow: each call would be its own transaction). Spring Data repository methods are already transactional individually; your service method makes several of them one unit.

Rollback rules

By default Spring rolls back on unchecked exceptions (RuntimeException and Error) and commits on checked exceptions — a convention from EJB that surprises many people. Change it per method:

The checked PaymentDeclined committed the audit row by default. Many teams make domain exceptions unchecked (extending RuntimeException) precisely so the default does what people expect.

⚠️ Catching an exception doesn't undo "rollback-only". If an inner @Transactional method (joining your transaction) throws an unchecked exception, the shared transaction is marked rollback-only — even if you catch the exception in the outer method. When the outer method then returns normally, the commit fails with UnexpectedRollbackException. Either let the exception propagate, or run the inner work in its own transaction (REQUIRES_NEW, next section).

readOnly, timeouts and isolation

  • @Transactional(readOnly = true) is a hint: Hibernate skips dirty checking and flushing (faster for big reads), the JDBC connection is set read-only, and some databases or routing data sources send it to a replica. Use it on query methods. A common pattern is @Transactional(readOnly = true) on the class and @Transactional on the writing methods.
  • timeout = 5 (seconds) rolls back a transaction that runs too long — a safety net against runaway queries.
  • isolation chooses how much concurrent transactions see of each other. Most applications use the database default (READ COMMITTED on PostgreSQL, Oracle and SQL Server; REPEATABLE READ on MySQL):
Isolation levelDirty readNon-repeatable readPhantom read
READ_UNCOMMITTEDpossiblepossiblepossible
READ_COMMITTED—possiblepossible
REPEATABLE_READ——possible
SERIALIZABLE———

Higher isolation means fewer anomalies but more blocking or serialization failures that you must retry. For most "two users edit the same thing" problems, optimistic locking is the better tool.

Concurrent updates: optimistic and pessimistic locking

Transactions don't stop the lost update: Ada and Bob both load a book with stock 3, each subtracts one in memory, and both save 2 — one copy vanished. Two fixes:

  • Optimistic locking: add a @Version field. Every update runs UPDATE … SET …, version = version + 1 WHERE id = ? AND version = ?; if another transaction changed the row in between, zero rows match and Spring throws ObjectOptimisticLockingFailureException. No locks are held — ideal when conflicts are rare.
  • Pessimistic locking: @Lock(LockModeType.PESSIMISTIC_WRITE) on a repository query issues SELECT … FOR UPDATE, so others wait until you commit. Use it for short, hot rows where conflicts are frequent.

On a conflict, the usual responses are: retry the whole operation with fresh data (automatic for simple counters — @Retryable(includes = ObjectOptimisticLockingFailureException.class) on the service method, Chapter 11), or tell the user "someone else changed this — reload". In REST APIs, expose the version as an ETag and require If-Match on updates (How-To H3).

Recap

  • @Transactional is a proxy around a PlatformTransactionManager: begin, call, commit — or roll back. Put it on service methods; self-invocation and private methods bypass it.
  • Default rollback: unchecked exceptions roll back, checked exceptions commit. Use rollbackFor/noRollbackFor; beware "rollback-only" after a caught inner exception.
  • Propagation: REQUIRED joins; REQUIRES_NEW is independent (needs a second connection); NESTED uses savepoints; MANDATORY demands a caller transaction.
  • readOnly = true for queries, timeout as a safety net, database-default isolation for most apps; TransactionTemplate for programmatic control.
  • Lost updates: @Version optimistic locking (retry or report conflicts) or PESSIMISTIC_WRITE locks. Side effects go in @TransactionalEventListener (after commit).

Exercises

Exercise 1 🟢 easy predict

A @Transactional method saves an order and then throws java.io.IOException (checked). Is the order in the database afterwards? How do you change that?

Show solution

Yes — by default checked exceptions commit. Add @Transactional(rollbackFor = IOException.class) (or rollbackFor = Exception.class), or wrap it in an unchecked exception.

Exercise 2 🟢 easy concept

A controller method calls service.reserve() and then service.charge(), each @Transactional. charge() fails. Is the reservation rolled back? How should this be structured?

Show solution

No: they are two separate transactions; reserve() already committed. Make one service method, e.g. checkout(), annotated @Transactional, that calls both — the inner calls join it (REQUIRED) and everything commits or rolls back together.

Exercise 3 🟢 easy code

Use TransactionTemplate.execute to insert an account and return its balance from inside the transaction, then show that calling status.setRollbackOnly() in a second template call leaves no row behind.

Show solution

Exercise 4 🟢 easy concept

What does @Transactional(readOnly = true) do with JPA/Hibernate, and does it prevent writes?

Show solution

It sets the Hibernate session to read-only/flush mode MANUAL (no dirty checking, no automatic flush, less memory for snapshots), marks the JDBC connection read-only, and can route to a replica. Whether writes are actually blocked depends on the driver/database: some reject them on a read-only connection, others don't. Treat it as an optimisation hint, not a security feature.

Exercise 5 🟡 medium code

Demonstrate UnexpectedRollbackException: an outer @Transactional method calls an inner @Transactional (REQUIRED) method on another bean that throws IllegalStateException; the outer method catches it and returns normally. Print what the caller sees.

Show solution

The inner proxy marked the shared transaction rollback-only when the exception passed through it. The outer method's "success" can't commit, so Spring tells you loudly instead of silently rolling back.

Exercise 6 🟡 medium code

Write a service method that retries an optimistic-lock conflict: decrement(String sku) with @Retryable(includes = ObjectOptimisticLockingFailureException.class, maxRetries = 3) and @Transactional. Simulate a conflict on the first attempt by updating the row with JdbcClient (bumping the version) after loading the entity.

Show solution

Both decrements counted: the other user's (10 → 9) and ours on the retry with fresh data (9 → 8). The retry must wrap the whole transaction — that's why @Retryable sits outside @Transactional on the same method (the resilience interceptor runs first by default); retrying inside a failed transaction can't work.

Exercise 7 🟡 medium debug

A batch job loops over 10 000 records and calls this.processOne(record), which is annotated @Transactional(propagation = REQUIRES_NEW), so that one failure doesn't undo the others. After one failure, everything processed so far is rolled back anyway. Why?

Show solution

Self-invocation: this.processOne() doesn't go through the proxy, so the annotation is ignored and everything runs in the outer transaction (or none). Fix: move processOne to another bean, or use a TransactionTemplate per record as in this chapter's importer example.

Exercise 8 🟡 medium concept

Your service sends an order-confirmation e-mail inside the @Transactional method that saves the order. Name two things that can go wrong and the fix.

Show solution

(1) The e-mail is sent, then the transaction rolls back (a later statement fails, or the commit fails) — the customer is told about an order that doesn't exist. (2) The SMTP call is slow, keeping the transaction and its locks and connection open for seconds. Fix: publish an event and send the mail in a @TransactionalEventListener (after commit), ideally @Async — or use an outbox table for guaranteed delivery.

Exercise 9 🔴 hard code

Show a pessimistic lock preventing a lost update: two threads each run a transaction that loads a Counter entity with @Lock(PESSIMISTIC_WRITE), sleeps 50 ms, increments and commits. Run 4 such threads; the final value must be 4.

Show solution

A field named value would fail at startup: Hibernate creates a column value, a reserved word in H2 — rename the field or map it with @Column(name = "…"). Without the lock (a plain findById), all four threads would read 0 and write 1. The lock serialises them: each waits for the previous commit. Note the pool size (default 10) must exceed the number of threads waiting, and lock waits should have a timeout (jakarta.persistence.lock.timeout hint) in production.

Exercise 10 🔴 hard mini-project · playground

Fix the Chapter 13 Library Loans flaw: a LoanService.borrow(isbn, member) that, in one transaction, decrements stock with the atomic UPDATE … WHERE stock > 0, inserts a loan, and enforces "at most 2 open loans per member" by counting after the insert and throwing LoanLimitReached (unchecked) if exceeded. Also record every attempt in the audit table with REQUIRES_NEW. Show that a rejected third loan leaves stock and loans unchanged but is audited.

Show solution

"Check after write, inside the transaction" closes the race where two concurrent requests both see one open loan and both insert. (Strictly, under READ COMMITTED two concurrent transactions could still both count 2 before either commits; for a hard guarantee, lock the member row first with SELECT … FOR UPDATE.) Chapter 20 builds this into the full project with JPA, a REST API and tests.
