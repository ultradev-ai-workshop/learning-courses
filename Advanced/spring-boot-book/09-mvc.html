Chapter 9 · Web

Building REST APIs with Spring MVC

Spring MVC is the servlet-based web framework at the heart of most Spring Boot applications. This chapter follows a request from the socket to your method and back, then covers everything you need for a JSON API: mappings, path variables and parameters, request bodies, response status and headers, JSON customisation with Jackson 3, content negotiation and Spring Framework 7's built-in API versioning.

You will learn

  • How the DispatcherServlet routes a request to a handler method and turns the return value into a response.
  • Mapping requests: @GetMapping & co., path patterns, produces/consumes, headers and parameters.
  • Method arguments: @PathVariable, @RequestParam, @RequestHeader, @RequestBody, and more.
  • Responses: return values, ResponseEntity, 201 Created with a Location, 204 No Content.
  • JSON with Jackson 3, and API versioning with @GetMapping(version = …).

The request journey

Every request to a Spring MVC app enters one servlet, the DispatcherServlet (the front controller). It asks its HandlerMappings which method handles the request, runs interceptors, calls the method through a HandlerAdapter (which resolves its arguments), and finally writes the return value with an HttpMessageConverter — Jackson for JSON.

🧠 Analogy: a hotel reception. Every guest comes through one front desk (the DispatcherServlet). Security at the entrance (filters) checks everyone first. The receptionist looks up which department handles the request (handler mapping), fills in the forms the department needs (argument resolvers), sends the guest there (your method), and translates the department's answer into the guest's language on the way out (message converters).

Things to notice:

  • @RestController = @Controller + @ResponseBody: return values are written to the response body (as JSON), not resolved as view names.
  • Separate request and response types (BookRequest vs Book): clients can't set the id, and your API isn't tied to your persistence model.

☕ Coming from JAX-RS? @RequestMapping ≈ @Path, @GetMapping ≈ @GET, @PathVariable ≈ @PathParam, @RequestParam ≈ @QueryParam, ResponseEntity ≈ Response.

Request mapping in detail

Path patterns

Spring MVC parses mappings with PathPatternParser:

PatternMatches
/books/{id}/books/42 — captures one segment as id
/books/{id:\d+}only digits: /books/42 but not /books/abc
/files/{*path}the rest of the path: /files/a/b/c.txt → path = "/a/b/c.txt"
/img/*.pngone segment ending in .png
/docs/**anything under /docs/

When several patterns match, the most specific wins: /books/new beats /books/{id} (a literal beats a variable), and a pattern with fewer variables and wildcards beats one with more.

⚠️ Regex constraints don't make a pattern more specific. With /books/{id:\d+} and a plain /books/{slug}, the URL /books/42 matches both equally well, and Spring fails the request with "IllegalStateException: Ambiguous handler methods mapped for '/books/42'" — a 500 error, not a startup error. That's why the slug pattern above must start with a letter, so the two never overlap.

Narrowing by method, headers, parameters and media types

Besides path and HTTP method, a mapping can require params (params = "debug"), headers (headers = "X-Tenant"), a request Content-Type (consumes) and an acceptable response type (produces). A request that matches the path but not these conditions gets 405, 415 Unsupported Media Type or 406 Not Acceptable — Spring answers with the right status code for you.

Without the logging setting you'd also see lines such as WARN … DefaultHandlerExceptionResolver : Resolved [HttpMediaTypeNotAcceptableException: No acceptable representation] — Spring tells you which client error it turned into which status. They're useful while developing.

Handler method arguments

ArgumentSource
@PathVariable long idURI template variable
@RequestParam(defaultValue = "0") int pagequery string or form field; List<String> for repeated params
@RequestHeader("X-Request-Id") String ida request header (HttpHeaders for all)
@CookieValue("session") String sa cookie
@RequestBody Order orderthe body, converted by a message converter (JSON)
@ModelAttribute Filter f / plain objectrequest parameters bound onto an object's properties
@Valid on any of the aboverun Bean Validation (Chapter 10)
HttpServletRequest, Principal, Locale, UriComponentsBuilderinjected by type

A record without an annotation is treated like @ModelAttribute: its constructor parameters are bound from request parameters by name. That keeps search endpoints with many optional filters tidy.

⚠️ Primitive parameters and missing values. @RequestParam int page without a default is required: a missing page gives 400 Bad Request. A value like page=abc also gives 400 (type mismatch). Use defaultValue, required = false with a wrapper type, or Optional<Integer>.

Responses

What you return decides the response:

  • An object (record, list, map): status 200, written as JSON.
  • ResponseEntity<T>: full control over status, headers and body. Builders: ok(), created(uri), accepted(), noContent(), notFound(), badRequest(), status(…).
  • void with @ResponseStatus(NO_CONTENT): no body.
  • String: written as text/plain (the string converter comes before JSON).
  • ProblemDetail or a thrown ErrorResponseException: an RFC 9457 error response (Chapter 10).

JSON with Jackson 3

Boot 4 uses Jackson 3. The core classes moved to the tools.jackson package (tools.jackson.databind.json.JsonMapper), but the annotations stay in com.fasterxml.jackson.annotation, so @JsonProperty, @JsonIgnore and @JsonFormat look exactly as before. Java time types (LocalDate, Instant) are supported out of the box and written as ISO-8601 strings.

Two safety details: @JsonIgnore works in both directions (the incoming passwordHash is ignored), and unknown fields in the request (unknownField) don't cause an error — Boot disables FAIL_ON_UNKNOWN_PROPERTIES, so old clients and new servers can evolve independently. Common settings:

API versioning Spring 7

Spring Framework 7 has first-class API versioning. You choose where clients send the version (a header, a query parameter, a path segment or a media-type parameter) with a property, then add version to your mappings. "1.1+" means "1.1 and later, until a newer mapping exists" — so you only write a new method when the behaviour changes:

An unsupported version is rejected with 400 Bad Request. Other strategies: spring.mvc.apiversion.use.query-parameter=version, use.path-segment=1 (for /api/v2/… with a {version} in the mapping) and use.media-type-parameter[application/json]=v. You can also mark old versions as deprecated so responses carry Deprecation and Sunset headers.

Recap

  • The DispatcherServlet maps a request to a handler, resolves its arguments, calls it, and writes the result with message converters (Jackson for JSON). Filters run before it; interceptors around handlers.
  • Mappings: @GetMapping etc. with path patterns ({id:\d+}, {*path}), plus params, headers, consumes, produces. Mismatches give 405/406/415 automatically.
  • Arguments: @PathVariable, @RequestParam (defaults!), @RequestHeader, @RequestBody, records bound from query params.
  • ResponseEntity for status and headers: created(location), noContent(), notFound(), ETags, cache control.
  • Jackson 3: tools.jackson core, unchanged annotations, spring.jackson.* settings. API versioning: spring.mvc.apiversion.* + @GetMapping(version = "2.0+").

(a) 404 Not Found, (b) 405 Method Not Allowed (with an Allow header), (c) 415 Unsupported Media Type, (d) 406 Not Acceptable.

Exercise 3 🟢 easy concept

Why is it a good idea to use a separate CreateUserRequest record for POST /users instead of accepting your User entity directly?

Show solution

The request type contains only what clients may set: no id, no role, no createdAt. Binding directly to the entity invites mass assignment (a client sending "role":"ADMIN"), couples your API to your database model, and makes validation rules for "create" and "update" collide. Map the request to the entity in the service.

Exercise 4 🟢 easy predict

Mappings: /users/{id}, /users/me, /users/**. Which handles /users/me, /users/42 and /users/42/orders?

Show solution

/users/me → /users/me (a literal beats a variable). /users/42 → /users/{id} (a variable is more specific than **). /users/42/orders → /users/** (the only one matching two segments).

Exercise 8 🟡 medium debug

A developer added @EnableWebMvc to a configuration class to register an interceptor. Suddenly spring.jackson.* settings and static resources from classpath:/static stop working. Why?

Show solution

@EnableWebMvc imports Spring MVC's full configuration, and Boot's WebMvcAutoConfiguration backs off when it sees it (@ConditionalOnMissingBean(WebMvcConfigurationSupport.class)). You lose Boot's message-converter setup, static resource handling, formatters and more. Remove @EnableWebMvc: implementing WebMvcConfigurer in a plain @Configuration class is all you need to add interceptors.

Exercise 9 🔴 hard code

Implement conditional GET: GET /config returns a JSON document with an ETag computed from its content. If the client sends If-None-Match with the same ETag, return 304 Not Modified with no body. Use WebRequest.checkNotModified(etag). Show the first request (200), a repeat with the ETag (304), and a request after the config changed (200 with a new ETag).

Show solution

Conditional requests save bandwidth for clients that poll. For simple cases, Spring's ShallowEtagHeaderFilter computes ETags from the response body automatically (but still runs your method every time).

Exercise 10 🔴 hard mini-project · playground

Start the Library Loans API (the Chapter 20 project) in memory: Member(id, name) and Loan(id, memberId, isbn, dueDate). Endpoints: POST /members (201 + Location), POST /members/{id}/loans with {"isbn":"…"} (201, due date = today + 14 days, 404 if the member doesn't exist, 409 Conflict if the member already has 3 loans), GET /members/{id}/loans. Exercise all paths in main and print the status codes.

Show solution

The synchronized on borrow makes "check the count, then add" atomic; without it, two concurrent requests could both see 2 loans and both succeed.
