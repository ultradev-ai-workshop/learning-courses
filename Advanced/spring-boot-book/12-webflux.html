Reactive Web with WebFlux

Spring WebFlux is Spring's second web stack: fully non-blocking, built on Project Reactor and usually running on Netty. It shines when an application spends most of its time waiting — on other services, streams or slow clients — and needs to do that with very few threads. This chapter teaches the reactive model, Mono and Flux, annotated and functional endpoints, WebClient, streaming, and how to decide between WebFlux, Spring MVC and virtual threads.

You will learn

  • The reactive model: publishers, subscribers, laziness and backpressure.
  • Mono and Flux and the operators you'll use daily: map, flatMap, filter, zip, onErrorResume, timeout, retryWhen.
  • WebFlux annotated controllers and functional endpoints (RouterFunction).
  • WebClient, server-sent events, and testing with StepVerifier and WebTestClient.
  • The golden rule (never block) and when to choose WebFlux vs MVC with virtual threads.

The reactive model

In Spring MVC, each request gets a thread, and that thread waits whenever your code waits (for the database, for another service). In WebFlux, a small number of event-loop threads (typically one per CPU core) handle all requests. Your code doesn't wait; it describes what to do when data arrives, and the thread moves on to other work in the meantime.

That description is a reactive pipeline built from publishers (Reactive Streams): a Mono<T> emits 0 or 1 item, a Flux<T> emits 0 to N items, and either can end with completion or an error. Three properties matter most:

  • Lazy: nothing happens until something subscribes. In WebFlux, the framework subscribes to what your controller returns.
  • Asynchronous: items may arrive later, on another thread.
  • Backpressure: the subscriber says how many items it can take (request(n)), so a fast producer can't overwhelm a slow consumer.

🧠 Analogy: a restaurant with pagers. In a thread-per-request restaurant, each waiter takes an order and stands at the kitchen window until the dish is ready — with 200 waiters, the 201st guest waits. In a reactive restaurant, a few waiters take orders, hand customers a pager and keep serving others. When the kitchen buzzes, whichever waiter is free brings the dish. It's very efficient — but only if nobody stands at the window. One waiter who blocks freezes a whole section.

Mono and Flux

map vs flatMap

map transforms each item synchronously (T → R). flatMap transforms each item into another publisher (T → Mono<R>) — for example a call to another service — and merges the results as they arrive, concurrently. concatMap does the same but one at a time, preserving order. Mono.zip waits for several publishers in parallel:

flatMap ran the three "calls" at once and returned them in completion order (≈120 ms total); concatMap ran them one after another (≈200 ms) in input order. zip was concurrent and kept positions. Use flatMap(fn, concurrency) to cap how many inner calls run at once.

WebClient

WebClient is the reactive HTTP client. It works in WebFlux apps (where you return its Monos) and is also useful in MVC apps when you need to fan out many concurrent calls. The golden rule: never block

An event-loop thread that blocks — Thread.sleep, JDBC, a blocking HTTP call, .block() — can't serve any other request on that loop. A handful of blocking calls can freeze the whole server. Reactor Netty even refuses block() on its threads. If you must call blocking code, move it to a thread pool meant for it:

⚠️ "Reactive all the way down." WebFlux pays off only if every I/O call is non-blocking: R2DBC or reactive MongoDB/Redis drivers instead of JDBC/JPA, WebClient instead of blocking clients. Mixing in JPA via boundedElastic works, but then you have the complexity of reactive code and a thread per request. Tools like BlockHound detect blocking calls on event-loop threads in tests.

WebFlux, MVC or virtual threads?

Spring MVC (platform threads)Spring MVC + virtual threadsWebFlux
Programming modelimperative, easy to debugimperative, easy to debugreactive pipelines, steeper learning curve
Concurrency~ thread pool size (200)very high: blocking is cheapvery high: no blocking
Database accessJDBC/JPAJDBC/JPAR2DBC, reactive NoSQL
Streaming, backpressurelimited (SSE emitters)limitedfirst-class
Best fortypical CRUD servicesI/O-heavy services that call many dependenciesstreaming, gateways, very high fan-out, reactive data stores

Since Java 21, spring.threads.virtual.enabled=true gives MVC applications most of the scalability benefit of WebFlux while keeping simple blocking code. The Spring team's advice: if you have a working MVC application, don't rewrite it; use WebFlux when you need streaming and backpressure, or when your whole stack is already reactive.

Recap

  • WebFlux: non-blocking, few event-loop threads, Reactor Netty. Pipelines are lazy, asynchronous and backpressure-aware.
  • Mono = 0..1, Flux = 0..N. map (sync), flatMap (async, concurrent), concatMap (async, ordered), zip, onErrorResume, timeout, retryWhen.
  • Annotated controllers look like MVC; functional endpoints use RouterFunction. SSE with text/event-stream. WebClient for reactive HTTP.
  • Never block on event-loop threads; offload with Schedulers.boundedElastic() if you must. Reactive pays off only end to end.
  • Choose MVC (+ virtual threads) by default; WebFlux for streaming, backpressure and reactive stacks. Test with StepVerifier and WebTestClient.

Exercise 1 🟢 easy predict

What does this print? Mono.fromSupplier(() -> { System.out.println("A"); return 1; }).map(x -> x + 1); System.out.println("B");

Show solution

Only B. The Mono is never subscribed to, so the supplier never runs. A reactive pipeline without a subscriber does nothing — a common bug when people call a method returning Mono<Void> and ignore the result.

Exercise 3 🟢 easy concept

When should you use flatMap instead of map? And concatMap instead of flatMap?

Show solution

flatMap when the transformation itself is asynchronous (returns a Mono/Flux, e.g. a database or HTTP call); with map you'd get a Flux<Mono<T>> that nobody subscribes to. concatMap when order matters or calls must not run concurrently (e.g. applying events to an account in sequence).

Exercise 4 🟢 easy concept

A WebFlux controller calls a JPA repository directly. Under load, latency explodes even though CPU is low. Why?

Show solution

JPA/JDBC calls block. They run on the few Netty event-loop threads, so while one request waits for the database, every other request assigned to that loop waits too. Either use a reactive driver (R2DBC), offload the calls with subscribeOn(Schedulers.boundedElastic()), or — usually simplest — use Spring MVC (with virtual threads).

Exercise 8 🟡 medium code

Process ids 1..20 with a fake async lookup (Mono.delay(20ms)), using flatMap(fn, 5) to allow at most 5 concurrent lookups. Track the maximum number in flight and print it.

Show solution

Decrementing in doFinally instead would report 6: it runs after the completion has reached flatMap, which has already subscribed to the next lookup — counting concurrency correctly in async code needs care. The second argument of flatMap is the concurrency. Always bound it when calling other services, or a big Flux fires thousands of requests at once.

Exercise 10 🔴 hard mini-project · playground

Build a reactive availability aggregator for the library: GET /availability/{isbn} queries three "branch" services (simulate them as Monos with delays 30, 50 and 500 ms; the last one is slow). Give each branch a 200 ms timeout and treat a timeout as "unknown". Return JSON like {"isbn":"…","branches":{"north":2,"south":0,"east":"unknown"}} within ~200 ms.

Show solution

A slow branch costs at most its timeout, not its full latency, and never fails the whole response. That's the core of every "scatter-gather" API: concurrent calls, per-call timeouts, partial results.
