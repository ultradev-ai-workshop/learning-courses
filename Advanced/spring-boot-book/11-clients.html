Chapter 11 · Web

Calling HTTP Services

Most services call other services. Spring gives you RestClient, a fluent synchronous client; HTTP service clients, where you declare a Java interface and Spring implements it; and, new in Spring Framework 7, resilience annotations — @Retryable and @ConcurrencyLimit — in the core framework. This chapter covers all three, plus timeouts and error handling, the things that decide whether a slow dependency takes your service down with it.

You will learn

  • RestClient: the auto-configured builder, requests, typed responses, headers and generic types.
  • Handling errors: default exceptions, onStatus, and exchange for full control.
  • Configuring timeouts and the underlying HTTP library.
  • HTTP service clients: @HttpExchange interfaces, @ImportHttpServices and per-group configuration.
  • Resilience: @Retryable with back-off and jitter, RetryTemplate, @ConcurrencyLimit.

How the examples work

Every example in this chapter starts two Spring applications in one JVM: a small remote service on a random port (playing the part of another team's API), and a client application without a web server that calls it. That's exactly the situation in production — just with both processes squeezed into one main.

Handling errors

By default, retrieve() throws on error statuses: HttpClientErrorException for 4xx (with subclasses like HttpClientErrorException.NotFound) and HttpServerErrorException for 5xx. Connection problems and timeouts throw ResourceAccessException. Both are RestClientExceptions. You can replace the default with onStatus, or take full control with exchange:

⚠️ Don't let remote errors leak through your API. An uncaught HttpClientErrorException.NotFound from a downstream call becomes a 500 in your API (or worse, a misleading 404). Translate downstream failures into your own domain exceptions at the client boundary, then map those in your @RestControllerAdvice (Chapter 10).

Timeouts

Without timeouts, a dependency that stops answering keeps your request threads waiting until they're all used up — and then your service stops answering too. Always set a connect timeout (establishing the TCP connection) and a read timeout (waiting for data). In Boot 4 they're shared settings for all auto-configured HTTP clients:

The JDK's java.net.http.HttpClient is used here; its timeout exception is HttpTimeoutException. Pick a read timeout from the dependency's real latency (for example its p99 plus a margin), not a round number like 30 s.

🧠 Analogy: waiting on hold. You call a supplier and get put on hold. Without a timeout you'd hold forever, while your own customers queue up behind you. A read timeout is deciding up front: "If nobody answers within five minutes, I hang up and tell my customer we'll call back." A retry is calling again; a concurrency limit is having only three phone lines, so you never have every employee on hold at once.

HTTP service clients: declare an interface

Instead of writing request code, describe the remote API as a Java interface with @HttpExchange annotations — like a controller, but from the client side. Spring generates the implementation. @ImportHttpServices registers interfaces in a named group, and Boot configures each group from spring.http.serviceclient.<group>.* properties:

The remote service required the X-Api-Key header, which the group's default-header property added to every call. Method parameters use the same annotations as controllers: @PathVariable, @RequestParam, @RequestHeader, @RequestBody, plus URI for a dynamic base URL. Return types can be a body type, ResponseEntity<T>, HttpHeaders or void. Errors behave exactly like retrieve().

☕ Coming from OpenFeign? HTTP service clients are Spring's built-in answer to Feign: an annotated interface, configured per group. For new code you don't need Spring Cloud OpenFeign; Feign's interceptors map to RestClientHttpServiceGroupConfigurer beans or RestClientCustomizers.

Resilience: retries and concurrency limits Spring 7

Spring Framework 7 moved retry support into the core (the separate Spring Retry project is in maintenance mode). Add @EnableResilientMethods and annotate methods:

  • @Retryable retries a method that throws, with a configurable number of retries, delay, exponential multiplier, maxDelay and random jitter. includes/excludes choose which exceptions are retried.
  • @ConcurrencyLimit caps how many threads can be inside a method at once — a bulkhead that protects a fragile dependency (and is especially useful with virtual threads, which are otherwise unlimited).

The delays here grow 20 ms → 40 ms → 80 ms (capped at 200 ms). In production, add jitter so a thousand clients that failed at the same moment don't all retry at the same moment.

⚠️ Only retry what is safe to repeat. GET is safe; a POST /payments that timed out may have succeeded on the server — retrying charges the customer twice. Retry non-idempotent calls only with an idempotency key the server deduplicates. And never retry 4xx errors: the request is wrong, and sending it again won't fix it.

Limiting concurrency

Both annotations are proxy-based (Chapter 7): they only apply to calls from other beans. For circuit breakers and rate limiters, use Resilience4j (with Spring Cloud Circuit Breaker) — Spring's core covers the two most common needs.

Recap

  • Inject Boot's RestClient.Builder, build one client per service; use URI templates and ParameterizedTypeReference for generic types.
  • Errors: 4xx → HttpClientErrorException, 5xx → HttpServerErrorException, I/O and timeouts → ResourceAccessException. Customise with onStatus; use exchange for full control. Translate to domain exceptions.
  • Always set spring.http.clients.connect-timeout and read-timeout.
  • HTTP service clients: @HttpExchange interfaces + @ImportHttpServices(group = …) + spring.http.serviceclient.<group>.base-url, timeouts and default headers.
  • Spring 7 resilience: @EnableResilientMethods, @Retryable (retries, delay, multiplier, jitter, includes), RetryTemplate, @ConcurrencyLimit. Retry only idempotent calls and 5xx/I/O errors.

Exercises

Exercise 1 🟢 easy concept

Why should you inject RestClient.Builder instead of calling RestClient.create() in a Spring Boot application?

Show solution

The auto-configured builder carries Boot's setup: the application's message converters (with your spring.jackson.* settings), the configured HTTP library and timeouts, SSL bundles, observability (metrics and tracing of every call) and every RestClientCustomizer. RestClient.create() gets none of that.

Exercise 2 🟢 easy concept

Which exception does retrieve().body(…) throw for (a) a 404, (b) a 502, (c) a read timeout, (d) a connection refused?

Show solution

(a) HttpClientErrorException.NotFound, (b) HttpServerErrorException.BadGateway, (c) and (d) ResourceAccessException (wrapping the I/O exception). All extend RestClientException.

Exercise 3 🟢 easy concept

Which of these calls is safe to retry automatically after a timeout? GET /orders/7, PUT /orders/7 with the full order, POST /orders, DELETE /orders/7, POST /payments with an Idempotency-Key header.

Show solution

GET, PUT and DELETE are idempotent by HTTP semantics — repeating them leaves the same state. POST /orders isn't: it may create two orders. POST /payments with an idempotency key is safe if the server stores keys and returns the original result for repeats.

Exercise 7 🟡 medium debug

A service annotates a private method fetchRates() with @Retryable and calls it from a public method of the same class. Retries never happen. Give two fixes.

Show solution

@Retryable is applied by a proxy, which can't intercept private methods or self-invocation (Chapter 7). Fix 1: move fetchRates() to a separate bean (for example the HTTP client class) as a public method. Fix 2: use a RetryTemplate inside the method instead of the annotation. (Also check that @EnableResilientMethods is present.)

Exercise 8 🟡 medium concept

Your service handles 200 requests/s; each calls a dependency that normally answers in 50 ms. The dependency becomes slow: every call hangs for 30 s until the default timeout. Using Little's law (concurrent requests = arrival rate × time in system), how many requests are in flight on your side? What happens to Tomcat's default 200 worker threads?

Show solution

Normally 200 × 0.05 s = 10 concurrent calls. With 30 s waits, 200 × 30 = 6000 — far more than 200 threads, so all workers block within about a second, and every other endpoint (even ones that don't use the dependency) stops responding. A 500 ms read timeout would cap it at 200 × 0.5 = 100; a @ConcurrencyLimit on the client call would protect the rest of the service even more directly.

Exercise 9 🔴 hard code

Combine a timeout and a retry: a remote endpoint /maybe-slow takes 1 s on the first call and 10 ms afterwards. With read-timeout=200ms and @Retryable(includes = ResourceAccessException.class, maxRetries = 2, delay = 10), show that the second attempt succeeds and the whole call takes well under 1 s.

Show solution

Timeout + retry is the classic pair against occasional slow responses ("tail latency"). The timeout should be small enough that timeout × (retries + 1) still fits within your callers' timeout.

Exercise 10 🔴 hard mini-project · playground

For the Library Loans project, write an ISBN lookup client as an HTTP service interface BookInfoClient (@GetExchange("/isbn/{isbn}") BookInfo lookup(@PathVariable String isbn)), wrapped in a BookInfoService that (1) retries 5xx up to 2 times, (2) returns Optional.empty() on 404, and (3) falls back to BookInfo(isbn, "unknown title") when the remote service stays unavailable. Demonstrate the three cases.

Show solution

Six remote calls: 2 for the flaky one (fail, then succeed), 1 for the 404 (never retried) and 3 for the dead one (1 + 2 retries). Notice the layering: retry inside, fallback outside, and each in its own bean so the proxy sees the call.
