Chapter 8 · Core Framework

Events, Async, Scheduling & Caching

Four everyday tools from Spring's core, each enabled with an annotation: application events to decouple components, @Async to run work on another thread, @Scheduled for recurring jobs, and the cache abstraction to avoid repeating expensive work. Three of them are proxies (Chapter 7) — so you already know their limits.

You will learn

  • Publishing and listening to application events: @EventListener, conditions, ordering, chaining and transaction-bound listeners.
  • @Async: return types, the executor Boot configures, error handling and virtual threads.
  • @Scheduled: fixed rate vs fixed delay, cron expressions, time zones and the scheduler thread pool.
  • The cache abstraction: @Cacheable, @CachePut, @CacheEvict, keys, conditions and cache providers.

Application events

An event is an ordinary object (a record is ideal) that one bean publishes and any number of others receive. The publisher doesn't know who listens; listeners don't know who published. That makes events the standard way to keep modules independent — "an order was placed" instead of the order service calling the email, stock and analytics services directly.

Notice that "place() returns" comes after the listeners: by default events are delivered synchronously, on the publisher's thread. A listener that throws makes publishEvent throw too, and a slow listener slows the publisher. Make a listener asynchronous with @Async (next section) when that matters.

🧠 Analogy: a radio station. The station broadcasts "order placed" without knowing who's tuned in. Any number of radios (listeners) can be switched on or off without the station changing anything. By default, though, this is a very polite station: it waits until every radio has finished reacting before it plays the next song (synchronous delivery).

Errors in async methods

An exception in an @Async method can't reach the caller's try/catch — the caller has already moved on. With CompletableFuture, the exception completes the future exceptionally. With void, it goes to an AsyncUncaughtExceptionHandler (by default it's only logged):

⚠️ What's lost on another thread. An @Async method runs outside the caller's transaction and, by default, without its security context, MDC logging context or request scope. Pass what it needs as parameters. Boot can propagate some context through a TaskDecorator bean (for example for tracing, Chapter 18).

Scheduled tasks

With @EnableScheduling, methods annotated @Scheduled run on a schedule. They take no arguments and return void:

AttributeMeaning
fixedRate = 5000start every 5 s, measured from the previous start
fixedDelay = 5000wait 5 s after the previous run finishes
initialDelay = 1000wait before the first run
timeUnit = TimeUnit.SECONDSunit for the numbers above (default milliseconds)
fixedRateString = "${jobs.rate:PT30S}"from configuration; ISO-8601 or simple durations like 30s
cron = "0 0 3 * * MON-FRI", zone = "Europe/Paris"cron expression with seconds field, optional time zone

Boot's scheduler has one thread by default (spring.task.scheduling.pool.size=1), so a slow job delays every other job. Increase the pool, or enable virtual threads, if you have several jobs.

Cron expressions

Spring's cron format has six fields: second, minute, hour, day of month, month, day of week. Macros like @daily and @hourly are also accepted. CronExpression lets you check an expression before deploying it:

⚠️ Scheduled jobs and multiple instances. Run three instances of your app and each @Scheduled job runs three times. For jobs that must run once per cluster, use a distributed lock (ShedLock is popular), a dedicated single-instance worker, or the platform's scheduler (a Kubernetes CronJob).

The cache abstraction

@EnableCaching plus @Cacheable on a method: the first call runs the method and stores the result; later calls with the same arguments return the stored value without running the method. Boot auto-configures a CacheManager for the first provider it finds (Caffeine, Redis, Hazelcast, JCache…), falling back to a simple in-memory ConcurrentHashMap.

⚠️ Never read fields of a proxied bean directly. books is a CGLIB proxy — a subclass instance whose own copy of every field is empty. Writing books.lookups would read the proxy's field (null here) instead of the target's. Method calls are forwarded to the target; field access isn't. Expose state through methods.

Keys, conditions and unless

The default key is built from all arguments. Use SpEL to choose: key = "#user.id", key = "#country + ':' + #page". condition is checked before the call (don't cache at all if false), unless after it, with access to #result:

Only U100 was served from the cache (same lower-cased key as u100). x999 returned empty and wasn't cached (unless); u1 failed the condition. Spring unwraps Optional: the cache stores the value inside it, and #result is that value — null for an empty Optional, which is why the test is #result == null (writing #result.isEmpty() fails with "method call on null context object").

Choosing a cache provider

The default ConcurrentMapCacheManager never expires entries — fine for tests, dangerous in production. Add Caffeine for a local cache with size limits and expiry, or Redis for a cache shared by all instances:

💡 Cache what's expensive and stable. Good candidates: reference data, remote lookups, computed reports. Bad candidates: anything that must always be fresh, or per-user data with a huge key space. Always decide how entries become stale (TTL or explicit eviction) before adding @Cacheable.

Recap

  • Events: publish any object with ApplicationEventPublisher; receive with @EventListener (with condition, @Order, return values as new events). Delivery is synchronous unless the listener is @Async; use @TransactionalEventListener for after-commit work.
  • @EnableAsync + @Async: return CompletableFuture for results; void errors go to AsyncUncaughtExceptionHandler. Configure with spring.task.execution.* or spring.threads.virtual.enabled.
  • @EnableScheduling + @Scheduled: fixedRate (from start), fixedDelay (from end), 6-field cron with zone. One scheduler thread by default; every instance runs every job.
  • @EnableCaching + @Cacheable/@CachePut/@CacheEvict with SpEL keys, condition and unless. Use a real provider (Caffeine, Redis) with expiry in production.

Exercises

Exercise 1 🟢 easy predict

A listener for UserRegistered throws an exception. The publisher calls publishEvent inside register(). What does the caller of register() see, with a plain @EventListener? And with @Async @EventListener?

Show solution

Plain listener: the exception propagates out of publishEvent, so register() throws (and, inside a transaction, it would roll back). Async listener: the caller sees nothing; the exception happens on another thread and goes to the AsyncUncaughtExceptionHandler (logged by default).

Exercise 2 🟢 easy concept

A job takes 3 seconds. What's the difference between @Scheduled(fixedRate = 2000) and @Scheduled(fixedDelay = 2000)?

Show solution

fixedDelay waits 2 s after each run ends: runs start every 5 s. fixedRate aims to start every 2 s from the previous start; since the job takes longer, the next run starts as soon as the previous one finishes (with the default single thread, runs never overlap; they just run back to back).

Exercise 3 🟢 easy code

Write cron expressions and verify their next run from Friday 2026-03-06 14:07:30 with CronExpression: (a) every day at 18:45, (b) every 10 seconds, (c) at 08:00 on the first Monday of each month (MON#1).

Show solution

March 2026's first Monday (the 2nd) has already passed, so the next one is April 6.

Exercise 4 🟢 easy concept

Which key does @Cacheable("prices") Price price(String sku, Locale locale) use? How would you cache by sku only?

Show solution

The default SimpleKeyGenerator combines all arguments into a SimpleKey(sku, locale). To ignore the locale: @Cacheable(cacheNames = "prices", key = "#sku") — only correct if the price really doesn't depend on the locale.

Exercise 8 🟡 medium debug

Every @Scheduled job in an app sometimes runs minutes late. One job calls a slow external API. What's happening, and what are two fixes?

Show solution

Boot's scheduler has a single thread by default, so while the slow job is running, every other job waits. Fixes: increase spring.task.scheduling.pool.size; enable virtual threads (spring.threads.virtual.enabled=true); or have the slow job hand its work to @Async so the scheduler thread returns quickly. Also add a timeout to the API call.

Exercise 9 🔴 hard code

Implement a generic event EntityChanged<T> implementing ResolvableTypeProvider, so a listener for EntityChanged<Customer> doesn't receive EntityChanged<Invoice>. Publish one of each and show which listeners fire.

Show solution

Because of type erasure, an EntityChanged object doesn't know its T at runtime. ResolvableTypeProvider tells Spring the full generic type so it can route the event correctly.

Exercise 10 🔴 hard mini-project · playground

Build a digest mailer: CommentPosted(String author, String text) events are collected by a listener into a thread-safe queue; a @Scheduled(fixedDelay = 100ms) job drains the queue and, if not empty, prints one digest line digest: N comments (authors…). Publish 3 comments, wait for one digest, publish 1 more, wait for the second digest.

Show solution

The three events are published before the job's first run (it starts right after startup, but the context is published synchronously in main faster than 100 ms). Batching like this turns many small notifications into one — a common pattern for e-mails and webhooks. In a cluster, the queue would live in a database or message broker instead of memory.
