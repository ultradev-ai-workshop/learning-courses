Testing Spring Boot Applications

Spring's design — constructor injection, small beans, configuration you can swap — makes code easy to test. Spring Boot adds a testing toolkit on top: full-application tests on a random port, test slices that start only the web layer or only the persistence layer, mock beans, a mock HTTP server for clients, and context caching that keeps big test suites fast. This chapter tests one small application at every level.

You will learn

  • The test pyramid for Spring apps: plain unit tests, slice tests, full integration tests.
  • Unit tests with JUnit 6 and Mockito — no Spring at all.
  • Slices: @WebMvcTest with MockMvcTester, @DataJpaTest, @RestClientTest, @JsonTest.
  • @SpringBootTest with a real server and RestTestClient; @MockitoBean to replace beans.
  • Test configuration: properties, profiles, @TestConfiguration, context caching, and Testcontainers with @ServiceConnection.

The test pyramid

  • Unit tests create classes with new and mocks. Milliseconds each; test business rules thoroughly here.
  • Slice tests start only part of the context (web layer, JPA layer, an HTTP client) — they test the Spring-specific behaviour: mappings, validation, JSON, queries.
  • Integration tests start the whole application, ideally against real infrastructure (Testcontainers). A few per feature, testing that the pieces fit.

Boot 4 has a test starter per technology: spring-boot-starter-webmvc-test, -data-jpa-test, -restclient-test, -security-test… each brings the matching slice plus the common spring-boot-starter-test (JUnit Jupiter, AssertJ, Mockito, Hamcrest, JSONassert, JsonPath, Awaitility).

🧠 Analogy: testing a car. Unit tests check each part on a workbench (does the brake pad grip?). Slice tests mount a subsystem on a test rig (the whole brake system, with a fake wheel). Integration tests drive the finished car around the track. You need all three — but you can't afford to drive a full lap for every brake-pad variant.

The application under test

A tiny book service: an entity, a repository, a client for a remote price service, a service, and a controller with an error handler.

Unit tests: no Spring needed

Because BookService receives its collaborators through the constructor, a unit test just creates it with mocks. No context, no annotations scanning, runs in milliseconds:

💡 Given / when / then. Structure each test in three blocks — arrange the inputs and mocks, call the one method under test, assert the outcome — and name the test after the behaviour (unknownBookFailsWithoutCallingThePriceService), not the method. A failing test name should read like a bug report.

Web slice: @WebMvcTest

@WebMvcTest(BookController.class) starts Spring MVC with only that controller, controller advice, filters, converters and validation — no services, no repositories, no server. Dependencies the controller needs are replaced with @MockitoBean. Requests go through MockMvc; its AssertJ flavour MockMvcTester reads nicely:

This tests everything the unit test couldn't: the URL mapping, path variables, JSON serialisation, validation and the exception handler. @MockitoBean (Spring Framework 6.2+) replaces Boot's old @MockBean, which was removed in Boot 4; @MockitoSpyBean wraps the real bean instead.

Persistence slice: @DataJpaTest

@DataJpaTest configures JPA, repositories and an embedded database (replacing your configured one unless you say otherwise), and runs each test in a transaction that is rolled back at the end — tests can't affect each other. TestEntityManager sets up data directly:

⚠️ Flush before you trust a repository test. Inside the test transaction, save may not send any SQL yet (write-behind, Chapter 14). Constraint violations and query behaviour only show up when Hibernate flushes — call flush()/saveAndFlush(), or query, before asserting. Otherwise a test can pass while the real code fails at commit.

Full integration: @SpringBootTest

@SpringBootTest starts the whole application context. With webEnvironment = RANDOM_PORT it also starts the real embedded server, and RestTestClient (Boot 4, with @AutoConfigureRestTestClient) sends real HTTP requests to it. External dependencies you can't run in a test are still replaced with @MockitoBean:

This test goes through Tomcat, the controller, the service, the transaction and H2 — but data persists between tests (no rollback across a real HTTP call), so give each test its own ISBNs or clean up. Boot 4 changes to remember: @SpringBootTest no longer provides a MockMvc on its own (add @AutoConfigureMockMvc), and TestRestTemplate needs @AutoConfigureTestRestTemplate.

Test configuration and context caching

  • Properties: @SpringBootTest(properties = "prices.url=http://localhost:9"), @TestPropertySource, or @DynamicPropertySource for values known only at runtime (a container's port).
  • Profiles: @ActiveProfiles("test") loads application-test.properties.
  • Extra or replacement beans: a nested @TestConfiguration class adds beans to the context (a fixed Clock, a fake mailer) without disabling the application's configuration.
  • Context caching: Spring caches application contexts across test classes with the same configuration. Every different set of @MockitoBeans, properties or profiles creates a new context (seconds each). Keep test configurations uniform — e.g. a shared base class — and avoid @DirtiesContext unless a test really corrupts shared state.

Injecting a Clock into code that needs "now" is the single most useful trick for testable time logic (due dates, expiries, schedules).

Real databases with Testcontainers

H2 is convenient, but it isn't PostgreSQL: SQL dialects, types, locking and constraint behaviour differ. Testcontainers starts real services in Docker for your tests, and Boot's @ServiceConnection wires the connection details automatically (no URL properties needed). Add spring-boot-testcontainers and org.testcontainers:postgresql:

You can also use containers while developing: a TestApplication main class in src/test/java that calls SpringApplication.from(LibraryApp::main).with(ContainersConfig.class).run(args) starts your app with a PostgreSQL container — no local database install. (These examples need Docker, so they aren't run by this book's checker.)

Recap

  • Pyramid: many plain unit tests (JUnit + Mockito, constructor injection), fewer slice tests, a few @SpringBootTests.
  • @WebMvcTest + MockMvcTester + @MockitoBean for mappings, JSON, validation and error handling.
  • @DataJpaTest (rolled-back transactions, embedded DB, TestEntityManager; flush before asserting); @RestClientTest + MockRestServiceServer; @JsonTest.
  • @SpringBootTest(webEnvironment = RANDOM_PORT) + @AutoConfigureRestTestClient for end-to-end HTTP. Boot 4: add @AutoConfigureMockMvc/@AutoConfigureTestRestTemplate explicitly.
  • Keep configurations uniform for context caching; @TestConfiguration, @ActiveProfiles, @DynamicPropertySource; Testcontainers + @ServiceConnection for real infrastructure.

Exercises

Exercise 1 🟢 easy concept

Which test type would you choose for each? (a) "a 15% discount applies to orders over €100", (b) "POST /orders with a missing customerId returns 400", (c) "the native query for monthly revenue works on PostgreSQL", (d) "placing an order sends a confirmation e-mail after commit".

Show solution

(a) A plain unit test of the pricing class. (b) @WebMvcTest with a mocked service. (c) @DataJpaTest against a Testcontainers PostgreSQL (H2 may accept or reject different SQL). (d) @SpringBootTest (real transactions and events), with the mail sender replaced by a @MockitoBean or a fake.

Exercise 2 🟢 easy concept

A test suite has 40 @SpringBootTest classes and takes 6 minutes. Most of the time is spent starting contexts. What's the likely cause and fix?

Show solution

Each class has a slightly different configuration (different @MockitoBeans, properties, profiles, or @DirtiesContext), so the context cache can't reuse contexts — dozens of startups. Fix: unify configuration (an abstract base class with the common mocks and properties), remove unnecessary @DirtiesContext, and move tests that only need the web or JPA layer to slices or unit tests.

Exercise 3 🟢 easy code

Write a unit test for BookService.add that uses Mockito's ArgumentCaptor to check the Book passed to save has the right title and copies.

Show solution

Exercise 4 🟢 easy debug

A @WebMvcTest(BookController.class) fails at startup with "No qualifying bean of type 'BookService'". Why, and what's the fix?

Show solution

The web slice doesn't create @Service beans, but the controller's constructor needs one. Provide it: @MockitoBean BookService service; in the test (or import a real configuration with @Import if you want the real service).

Exercise 7 🟡 medium code

Exercise 8 🟡 medium concept

Your @DataJpaTest passes, but in production the same repository method fails with a unique-constraint violation at commit. How can the test have missed it?

Show solution

The test never flushed: save queued the INSERT, the assertions ran against the persistence context, and the test transaction was rolled back without ever sending SQL. Use saveAndFlush or em.flush() before asserting. (Another cause: H2 vs the production database behaving differently — use Testcontainers for database-specific behaviour.)

Exercise 9 🔴 hard code

Write a full @SpringBootTest with @AutoConfigureMockMvc (no real server) and MockMvcTester that adds a book via POST, then reads it via GET with a mocked price, and checks the whole JSON with isStrictlyEqualTo.

Show solution

MockMvc-based integration tests run in the test's thread, so — unlike the RANDOM_PORT variant — you could even add @Transactional to the test to roll back its data.

Exercise 10 🔴 hard mini-project · playground

Test the Library Loans rule "a member can have at most 2 open loans" from Chapter 15 at the unit level: extract the rule into a LoanPolicy class with void check(int openLoans, boolean hasOverdue) that throws LoanRefused(reason) for "limit reached" or "has overdue loans". Write a parameterised test covering allowed and refused cases, and assert the reason.

Show solution

Pulling rules out of the service into a small class with no dependencies makes them trivially testable — dozens of cases in milliseconds — while one integration test checks the service applies the policy. Chapter 20's project is built this way.
