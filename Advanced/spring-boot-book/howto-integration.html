Call a slow, flaky API safely

A partner's currency API sometimes answers in 10 seconds and sometimes returns 503. Your endpoint must stay fast.

timeouts@RetryablefallbackChapter 11

Solution

Three layers: a short read timeout, a few retries with back-off for 5xx and I/O errors, and a fallback when it still fails:

Calls 1–2 got 503, call 3 timed out after 500 ms instead of waiting 2 s, call 4 succeeded. Set the timeouts globally with spring.http.clients.connect-timeout/read-timeout, or per HTTP service group.

Pitfalls

  • Worst-case latency = attempts × (timeout + delay). Make sure it fits within your callers' timeouts.
  • Never retry non-idempotent calls (payments) without an idempotency key; never retry 4xx.
  • @Retryable is a proxy: it must be on a public method of another bean, as here.

Add a token to every outgoing request

Every call to the partner API needs Authorization: Bearer …, and the token expires every hour.

ClientHttpRequestInterceptorRestClientCustomizerChapter 11

Solution

An interceptor fetches the current token per request (from a cache that refreshes it), so no call site has to remember it:

For standard OAuth2 client credentials, Spring Security's OAuth2ClientHttpRequestInterceptor with spring.security.oauth2.client.registration.* properties does all of this, including refresh. Apply an interceptor to all builders with a RestClientCustomizer bean — only if every call should get it.

Pitfalls

  • Don't share one builder customised for partner A with calls to partner B — you'd send A's token to B.
  • Never log the Authorization header.

Run a job every night

Overdue reminders must go out at 02:30 Paris time, once — even with three instances running.

@ScheduledcronChapter 8

Solution

Notice the daylight-saving switch: on 29 March 2026 the clocks jump from 02:00 to 03:00 in Paris, so 02:30 doesn't exist — and Spring's cron skips that day entirely: the next run is on the 30th. Avoid scheduling between 02:00 and 03:00 local time (use 03:30, or UTC). The cron comes from a property, so operations can change it without a release.

Pitfalls

  • Every instance runs every job. For "once per cluster", use a lock (ShedLock: @SchedulerLock(name = "reminders") with a database table) or a platform scheduler (Kubernetes CronJob).
  • Make jobs idempotent and resumable (record what was sent): instances die mid-job.
  • The scheduler has one thread by default; long jobs delay others — spring.task.scheduling.pool.size or virtual threads.

Send an e-mail

Members get a confirmation e-mail when they borrow a book.

JavaMailSenderspring-boot-starter-mailChapters 8, 15

Solution

With spring-boot-starter-mail and spring.mail.* properties, Boot provides a JavaMailSender. Send after commit, in the background:

In development, run a fake SMTP server such as Mailpit (docker run -p 1025:1025 -p 8025:8025 axllent/mailpit) and point spring.mail.host at it — you can read every mail in its web UI. In tests, replace JavaMailSender with a @MockitoBean.

Pitfalls

  • Escape user-provided text in HTML mails (titles can contain <) or use a template engine (Thymeleaf) that escapes by default.
  • SMTP is slow and can fail: @Async keeps requests fast; for guaranteed delivery, store mails in an outbox table and retry.

Cache a lookup with expiry and a size limit

Book details from a remote catalogue rarely change; you want them cached for 10 minutes, at most 10 000 entries.

@CacheableCaffeineChapter 8

Solution

Add com.github.ben-manes.caffeine:caffeine; Boot then uses a Caffeine cache manager configured by a spec string:

With Actuator, recordStats also publishes cache.gets{result=hit|miss} metrics — watch the hit ratio to see whether the cache earns its keep. Use Redis (spring-boot-starter-data-redis) instead when several instances must share one cache.

Pitfalls

  • Caffeine's spec accepts durations in d, h, m or s only — expireAfterWrite=200ms fails at startup. For finer control, define a Caffeine builder bean.
  • Cached objects are shared: never mutate a returned object; prefer immutable records.
  • Self-invocation bypasses the cache (Chapter 7).
