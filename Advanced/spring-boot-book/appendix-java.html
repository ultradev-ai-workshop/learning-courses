Appendix A

Modern Java for Spring Developers

This book uses Java 25 freely: records for DTOs and configuration, text blocks for SQL and JSON, pattern matching, sequenced collections, virtual threads. If your Java habits come from Java 8 or 11, this appendix covers everything the chapters assume — each feature with the Spring situation where you'll meet it.

You will learn

  • Records, and why they're ideal for DTOs, projections, events and @ConfigurationProperties.
  • Sealed types and pattern matching (instanceof, switch, record patterns, unnamed _).
  • Text blocks, var, and modern collection and stream APIs (toList(), sequenced collections).
  • Virtual threads and scoped values — the concurrency model behind spring.threads.virtual.enabled.
  • Java 25 conveniences: flexible constructor bodies, compact source files, module imports.

Records

A record is a transparent, immutable data carrier: you declare the components, Java generates the constructor, accessors (title(), not getTitle()), equals, hashCode and toString. A compact constructor validates or normalises the values:

Where Spring uses them: request/response DTOs (Jackson reads and writes records), @ConfigurationProperties (constructor binding, Chapter 4), Spring Data projections (Chapter 14), application events (Chapter 8), JdbcClient row mapping (Chapter 13). Not as JPA entities: those need a no-arg constructor and mutability.

🧠 Analogy: a printed receipt. A record is like a receipt: it states its contents, can be compared with another receipt line by line, and nobody edits it after printing — if something changes, you print a new one.

Sealed types and pattern matching

A sealed interface lists exactly which classes may implement it. Combined with records and pattern matching for switch, the compiler checks that you've handled every case — no default needed, and adding a new case breaks the build where it's not handled:

Where it helps in Spring code: modelling outcomes of a service method instead of exceptions for expected cases, mapping them to HTTP statuses in one exhaustive switch, handling different event types, and parsing polymorphic JSON (Jackson's @JsonTypeInfo/@JsonSubTypes work with sealed records).

Text blocks, var and small conveniences

Text blocks appear in this book for SQL in @Query and JdbcClient, JSON in tests (isLenientlyEqualTo("""…""")) and multi-line messages. Use var where the type is obvious from the right-hand side; spell it out where it documents intent.

Sequenced collections and streams

Java 21 added sequenced collections: getFirst(), getLast(), reversed(), addFirst() on lists, deques, LinkedHashSet/LinkedHashMap and sorted collections. Combined with modern stream collectors, many loops disappear:

Stream gatherers (Java 24) add custom intermediate operations — windowFixed above batches items, useful when calling JdbcTemplate.batchUpdate or an API that accepts at most N items per request.

Virtual threads and scoped values

A virtual thread is a lightweight thread managed by the JVM rather than the OS. Blocking (waiting for I/O, sleeping) unmounts it from its carrier OS thread, so you can have hundreds of thousands. That's what makes "one thread per request" scale again — the model Spring MVC and JDBC are built on:

With 200 platform threads, the same work would take about 5 seconds (10 000 / 200 × 100 ms). Scoped values (final in Java 25) are the virtual-thread-friendly replacement for many ThreadLocal uses: an immutable value bound for the duration of a call, visible to everything it calls:

⚠️ Spring still uses ThreadLocal for context — transactions, the security context, request attributes. They work with virtual threads (each request still runs on one thread), but the context doesn't flow to threads you start yourself. Use Spring's executors (which can propagate context) instead of raw new Thread.

Java 25 conveniences

Flexible constructor bodies let you validate arguments before calling super(…) or this(…) — handy in exception classes and entity hierarchies:

Compact source files and instance main (void main() { IO.println("hi"); } in a file without a class) and module imports (import module java.base;) make small scripts and experiments shorter — great for trying an API quickly, while Spring applications keep their normal class structure.

More examples

Records as configuration properties and JSON

Jackson 3 reads and writes records out of the box — properties in declaration order, created through the canonical constructor — so a record is all a DTO needs.

Optional done right

Return Optional from lookups (Spring Data does: findById); don't use it for fields, parameters or collections (return an empty list instead).

Recap

  • Records: immutable data carriers with compact constructors — DTOs, properties, projections, events; not JPA entities.
  • Sealed interfaces + record patterns + switch give exhaustive, compiler-checked handling of alternatives; _ for unused parts.
  • Text blocks for SQL/JSON, var for obvious types, Stream.toList(), sequenced collections (getFirst, reversed), gatherers.
  • Virtual threads make blocking cheap; scoped values replace many thread-locals; Spring's own context still lives in thread-locals.
  • Java 25: statements before super(…), compact source files, module imports.

Exercises

Exercise 1 🟢 easy code

Write a record Isbn(String value) whose compact constructor removes dashes and rejects anything that isn't 13 digits. Print new Isbn("978-0-441-01359-3").

Show solution

Exercise 2 🟢 easy concept

Why can't a record be a JPA entity? Name two record features that conflict with JPA's requirements.

Show solution

JPA needs a no-argument constructor to instantiate entities and mutable, non-final fields for dirty checking, lazy-loading proxies (subclasses) and id generation after insert. Records have only the canonical constructor, final fields, and are implicitly final classes (no proxy subclass). Use records for projections and DTOs instead.

Exercise 3 🟢 easy code

Rewrite this with a text block and formatted: "SELECT * FROM book\n" + "WHERE author = '" + a + "'" — and explain why the result is still wrong for SQL.

Show solution

The quote in O'Brien breaks the statement — and a malicious value could inject SQL. Text blocks make SQL readable, but values must still be passed as parameters (WHERE author = :author with .param("author", a)), never formatted in.

Exercise 4 🟢 easy predict

What does List.of(1, 2, 3).stream().map(i -> i * 2).toList().add(8) do?

Show solution

It throws UnsupportedOperationException: Stream.toList() returns an unmodifiable list (unlike collect(Collectors.toList()), which in practice returns an ArrayList). Copy it into new ArrayList<>(…) if you need to modify it.

Exercise 5 🟡 medium code

Model payment methods as a sealed interface Payment with records Card(String last4), Iban(String country) and Voucher(int value). Write an exhaustive switch computing a fee: card 1.5%, IBAN 0 except outside DE 1.00, voucher 0. Print fees for an amount of 100.

Show solution

The guarded case must come before the general Iban _ case — the compiler rejects the reverse order as dominated.

Exercise 6 🟡 medium code

Given loans with member and days, compute the member with the most borrowing days using streams (groupingBy + summingInt, then max by value).

Show solution

In a real application, let the database do this (GROUP BY member ORDER BY SUM(days) DESC LIMIT 1) instead of loading every loan.

Exercise 7 🟡 medium code

Use a virtual-thread executor to "fetch" prices for 5 shops concurrently (each a Thread.sleep(200) returning a price), and show the total time is well under 1 second.

Show solution

Exercise 8 🟡 medium concept

A teammate replaces a ThreadLocal<Tenant> in a Spring MVC app with a ScopedValue. Where must ScopedValue.where(...).run(...) be called so that controllers, services and repositories all see the tenant?

Show solution

Around the whole request processing — in a servlet Filter (OncePerRequestFilter) that reads the tenant from the request and calls ScopedValue.where(TENANT, t).run(() -> chain.doFilter(req, res)) (rethrowing checked exceptions). Everything called within chain.doFilter on that thread sees the value, and it's automatically unbound afterwards — no clean-up needed, unlike a ThreadLocal.

Exercise 9 🔴 hard code

Write a small "result" type for service methods: a sealed interface Result<T> with records Ok<T>(T value) and Err<T>(String code, String message), plus a map method. Use it for a borrow function and translate results to HTTP status codes with a switch.

Show solution

Result types make expected failures explicit in the signature. In Spring applications, exceptions mapped by @RestControllerAdvice are more common — and transactions roll back on exceptions, not on Err values, so choose deliberately.

Exercise 10 🔴 hard mini-project · playground

Use gatherers to process a list of 10 ISBNs in batches of 4, "saving" each batch (print its size and contents), and use a sequenced collection to report the first and last batch.

Show solution

Each batch would be one JdbcTemplate.batchUpdate or saveAll call (Chapter 13) — batching keeps memory and round trips under control for large imports.
