Chapter 13 · Data

JDBC, JdbcClient & Flyway

Before reaching for JPA, learn the layer underneath: a DataSource with a connection pool, plain SQL through Spring's JdbcClient, Spring's consistent exception hierarchy, and versioned schema changes with Flyway. Many services need nothing more — and every JPA application still depends on all of it.

You will learn

  • How Boot configures a DataSource and the HikariCP connection pool, and the spring.datasource.* properties.
  • JdbcClient: queries with named and positional parameters, mapping rows to records, inserts with generated keys, updates.
  • JdbcTemplate for batch updates and when you meet it in existing code.
  • The DataAccessException hierarchy: DuplicateKeyException, EmptyResultDataAccessException…
  • Flyway migrations: naming, ordering, the history table, repeatable migrations and the rules for changing a schema safely.

DataSource and connection pool

Opening a database connection takes milliseconds — far too slow to do per request. A connection pool keeps a set of open connections and lends them out. Boot auto-configures HikariCP as a DataSource as soon as spring-boot-starter-jdbc (or -data-jpa) and a driver are on the classpath:

With an embedded database driver (H2, HSQLDB, Derby) and no URL, Boot creates an in-memory database with a unique name (and flags that keep it alive while the pool has no open connection) — that's what the examples in this chapter use. Everything else works identically with PostgreSQL or MySQL.

💡 Pool size is not "the more the better". A database can only work on a few queries at once (roughly CPU cores × 2). A small pool with requests waiting briefly for a connection is usually faster than a big pool where the database thrashes. Start with the default 10 and measure. Remember that the total is pool size × number of app instances.

Schema migrations with Flyway

Your schema evolves with your code, so it belongs in version control, applied automatically and in order. With spring-boot-starter-flyway (required in Boot 4; the plain flyway-core library is no longer enough), Boot runs Flyway at startup, before any other bean uses the database. Migrations are SQL files in src/main/resources/db/migration named V<version>__<description>.sql:

With H2 you'll also see a startup WARN that H2 is newer than the version Flyway was verified with; it's harmless (the book's examples hide it) and doesn't appear with PostgreSQL or MySQL. (V4 is a Java-based migration you'll write in Exercise 9 — Flyway runs SQL and Java migrations together, in version order.)

The first row is a marker Flyway writes when it creates the history table itself. Flyway records each applied migration — with a checksum — in flyway_schema_history. On the next start it applies only new versions. The rules that keep this safe:

  • Never edit a migration that has run anywhere shared. Flyway detects the changed checksum and refuses to start. Fix mistakes with a new migration.
  • Versions are ordered numerically: V1, V2, V2_1, V10. Teams often use timestamps (V20260301_1200__…) to avoid clashes between branches.
  • Repeatable migrations (R__views.sql) are re-applied whenever their checksum changes — good for views and stored procedures.
  • Make changes backwards compatible so old and new app versions can run side by side during a rolling deployment: add a nullable column, deploy, backfill, then add the constraint in a later release.

🧠 Analogy: a building's renovation log. Every change to the building is a numbered work order: "1. lay foundations, 2. add walls, 3. add a window". The log on the wall says which orders are done. A new crew reads the log and continues from the next number. Nobody rewrites order 2 after the walls are up — you file order 4: "move the window".

Boot alternatively supports Liquibase (spring-boot-starter-liquibase, changelogs in XML/YAML/SQL) and simple schema.sql/data.sql scripts (spring.sql.init.mode=always), which are fine for demos and tests but have no versioning.

JdbcClient

JdbcClient (Spring 6.1+) is the modern fluent API over JDBC. Boot auto-configures one. You write SQL; it handles connections, statements, parameter binding, result-set iteration, resource cleanup and exception translation:

(The Hobbit isn't by Frank Herbert, of course — the foreign key only checks that author 1 exists.) Result methods: list(), optional(), single() (exactly one row, else an exception), set() and stream() (close it!). Map with query(Record.class), a RowMapper lambda, or query(Integer.class) for a single column.

⚠️ Never concatenate input into SQL. "... WHERE isbn = '" + isbn + "'" is an SQL injection hole: an isbn of ' OR '1'='1 returns every row, and worse is possible. Always use parameters (:name or ?) — the value is sent separately and can never change the SQL's structure. If you need a dynamic column or sort direction, choose it from a fixed allow-list.

Spring's data access exceptions

Every database reports errors differently (vendor codes, SQL states). Spring translates them into one unchecked hierarchy rooted at DataAccessException, so your code can catch "duplicate key" the same way on PostgreSQL, MySQL and H2:

Order matters in the checks: DuplicateKeyException is a subclass of DataIntegrityViolationException, and EmptyResultDataAccessException a subclass of IncorrectResultSizeDataAccessException. A typical use: catch DuplicateKeyException in a service and throw your domain's EmailAlreadyRegistered, which the web layer maps to 409 (Chapter 10). @Repository beans get the same translation for JPA and other technologies.

Paging with LIMIT/OFFSET

Always ORDER BY when paging, or rows may move between pages. For deep pages on big tables, keyset pagination (WHERE title > :lastTitle ORDER BY title LIMIT :size) is much faster than large offsets.

Recap

  • Boot auto-configures a HikariCP DataSource from spring.datasource.*, or an embedded in-memory database. Keep the pool small.
  • Flyway (spring-boot-starter-flyway) runs db/migration/V<n>__name.sql at startup and records them in flyway_schema_history. Never edit an applied migration; make changes backwards compatible.
  • JdbcClient: sql(…).param(…).query(Type.class).list()/optional()/single(), update(), update(keyHolder, "id"). Records map from snake_case columns.
  • Always use parameters — never concatenate input into SQL.
  • Errors become unchecked DataAccessExceptions: DuplicateKeyException, DataIntegrityViolationException, EmptyResultDataAccessException, BadSqlGrammarException. JdbcTemplate.batchUpdate for bulk work.

Exercises

Exercise 1 🟢 easy concept

A teammate fixed a typo in V2__seed_books.sql after it was deployed to staging. The staging app now fails to start. Why, and what should they have done?

Show solution

Flyway stores a checksum of each applied migration. At startup it validates them; the edited file no longer matches, so validation fails ("Migration checksum mismatch"). They should have added a new migration (V4__fix_title_typo.sql with an UPDATE). Only for local databases is flyway repair (or recreating the DB) acceptable.

Exercise 2 🟢 easy concept

Which JdbcClient result method would you use for: (a) "find by id, may not exist", (b) "count rows", (c) "all books by an author", (d) processing 10 million rows without loading them all into memory?

Show solution

(a) optional(); (b) query(Long.class).single(); (c) list(); (d) stream() in a try-with-resources block (it holds a connection and cursor open until closed), or the RowCallbackHandler form. Set a fetch size on the driver so rows are streamed, not buffered.

Exercise 3 🟢 easy code

Print the number of books and the sum of all stock values with a single query, mapping the result to a record Totals(long books, long copies).

Show solution

Column aliases (AS books) must match the record component names. Every book has stock = 1 thanks to the DEFAULT 1 in V3.

Exercise 4 🟢 easy predict

What does jdbc.sql("SELECT title FROM book WHERE published > 3000").query(String.class).single() do? And with .optional()? And .list()?

Show solution

single() throws EmptyResultDataAccessException (an IncorrectResultSizeDataAccessException expecting 1, got 0). optional() returns Optional.empty(). list() returns an empty list. (optional() would also throw if there were two or more rows.)

Exercise 5 🟡 medium code

Write an AuthorRepository.create(String name) that returns the new id, and translates DuplicateKeyException into your own AuthorExists(name) exception. Try to create Jane Austen and Mary Shelley.

Show solution

Why id 5 and not 4? The failed insert for Jane Austen had already taken identity value 4 from the sequence, and sequences are never rolled back — gaps in generated ids are normal, so never use them as "row counts" or show them as consecutive numbers. Relying on the database's unique constraint (instead of "SELECT first, then INSERT") is correct even under concurrency: two simultaneous requests can't both pass a check that the database enforces atomically.

Exercise 6 🟡 medium code

Implement a search with optional filters: search(String titleContains, Integer publishedAfter), where null means "no filter". Build the SQL with fixed fragments and parameters only. Run it with ("e", 1900), (null, 1960) and (null, null).

Show solution

Only fixed SQL fragments are concatenated; every user value travels as a parameter. For many optional filters, Spring Data's Specifications or Querydsl/jOOQ (Chapter 14) scale better.

Exercise 7 🟡 medium code

Write a "decrement stock" method that never lets stock go below zero, using a single conditional UPDATE … WHERE stock > 0, and returns whether it succeeded. Call it twice for Dune (stock 1).

Show solution

The check and the change happen in one atomic statement, so two concurrent borrowers can never both take the last copy — no explicit lock, no read-then-write race.

Exercise 8 🟡 medium concept

You must rename the column book.published to published_year in a system that is deployed with zero downtime (old and new app versions run side by side for a few minutes). Plan the migrations and releases.

Show solution

Expand–contract: (1) release N: migration adds published_year, copies data; the app writes both columns and reads the new one (a trigger or dual writes keeps them in sync). (2) release N+1: the app no longer uses published. (3) release N+2: migration drops published. A single ALTER TABLE … RENAME COLUMN would break the old version still running during the rollout.

Exercise 9 🔴 hard code

Write a Java-based Flyway migration V4__add_slugs (a class extending BaseJavaMigration in the package db.migration) that adds a slug column to book and fills it in Java: the lower-case title with every run of non-alphanumeric characters replaced by -. Print all slugs in id order.

Show solution

Flyway finds Java migrations in the db.migration package on the classpath, alongside SQL ones, and orders them by version. Use them for data transformations that are awkward in SQL. (This migration now runs for every example on this page — that's why it doesn't break any of them: it only adds a column.)

Exercise 10 🔴 hard mini-project · playground

For the Library Loans project, write migration-free JDBC code against a loan table you create with JdbcClient at the start of main (id identity, book_id, member, due_date, returned_at nullable). Implement LoanRepository with borrow(isbn, member, dueDate) (fails with IllegalStateException if no copy is left — reuse the atomic stock update), giveBack(loanId) and overdue(LocalDate today). Demonstrate them.

Show solution

There's a real flaw left: borrow runs two statements without a transaction. If the insert failed, the stock would already be decremented. Chapter 15 fixes it with @Transactional. (And in the real project, the loan table would of course be a Flyway migration.)
