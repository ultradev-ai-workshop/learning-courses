Packaging & Deployment

A Spring Boot application ships as one executable jar — or one container image — that contains your code, every dependency and the web server. This chapter looks inside that jar, builds efficient container images, configures the app for containers and Kubernetes (probes, graceful shutdown, memory), and makes it start faster with virtual threads, class-data sharing / AOT caches and GraalVM native images.

You will learn

  • What's inside an executable jar (BOOT-INF, the loader, Start-Class) and how to run it.
  • Layered jars and the tools jar mode: list-layers and extract.
  • Building container images with Cloud Native Buildpacks or a layered Dockerfile.
  • Running well in containers and Kubernetes: configuration, probes, graceful shutdown, memory.
  • Faster startup: virtual threads, CDS / AOT cache, and GraalVM native images.

The application we'll package

The executable jar

spring-boot-maven-plugin (or the Gradle plugin) repackages the normal jar into an executable one during package:

(The book's examples run with logging at WARN; normally you'd also see the banner and "Started InventoryApp in 1.2 seconds".) A plain jar can't contain other jars, so how does this work? Look inside:

  • Your classes and resources are in BOOT-INF/classes, every dependency jar in BOOT-INF/lib — stored uncompressed so they can be read in place.
  • The JVM starts JarLauncher (the Main-Class), a small loader at the jar's root that knows how to load classes from nested jars, and then calls your Start-Class.

🧠 Analogy: a removal box with a packing list. The jar is one big box; inside are smaller sealed boxes (dependency jars) and your own items. Taped on top is a note for the movers (the manifest): "open with the box-opener in the lid (JarLauncher), then hand everything to InventoryApp". The JVM can't open nested boxes by itself — the box-opener can.

Layers

Dependencies change rarely; your code changes on every commit. Boot jars are layered (see BOOT-INF/layers.idx) so container images can cache the slow-changing parts. The tools jar mode lists and extracts them:

extract unpacks the jar into an ordinary application jar plus a lib/ folder referenced from its manifest's Class-Path. Running the extracted form starts faster (no nested-jar loading) and is what the AOT cache below needs.

Graceful shutdown

When Kubernetes stops a pod, it sends SIGTERM. Boot's graceful shutdown (on by default since Boot 3.4) then stops accepting new requests, lets in-flight requests finish for up to spring.lifecycle.timeout-per-shutdown-phase (30 s default), and closes the context — running @PreDestroy and stopping SmartLifecycle beans in phase order (Chapter 3). Readiness switches to refusing traffic during shutdown, so load balancers stop routing to the instance:

⚠️ Make sure the JVM actually receives SIGTERM. Starting the app via a shell script (ENTRYPOINT ["sh", "-c", "java …"]) makes the shell PID 1, and it may not forward signals — Kubernetes then kills the JVM hard after the grace period. Use the exec form (["java", …]) or exec java … in scripts.

Faster startup and better throughput

Virtual threads

On Java 21+, spring.threads.virtual.enabled=true makes Tomcat handle each request on a virtual thread, and switches @Async, @Scheduled and other executors to virtual threads too. Blocking I/O (JDBC, RestClient) no longer ties up an OS thread, so an I/O-heavy MVC service can handle far more concurrent requests with the same memory. Watch out for the limits that remain: the database pool (still 10 connections!), and code that keeps a synchronized block around blocking I/O (much improved in Java 24+, but still worth reviewing).

CDS and the AOT cache

Much of a JVM's startup time goes into loading and linking classes. Java's class data sharing stores that work in an archive; Java 25's AOT cache (JEP 483/514/515) goes further, also caching linked classes and method profiles. Create the cache with a training run: -Dspring.context.exit=onRefresh starts the context and exits immediately:

Typical gains are 30–50% faster startup, with no code changes — but the cache must be created with the same JDK and the same classpath (that's why it uses the extracted form). Buildpacks can do this for you (BP_JVM_AOTCACHE_ENABLED=true).

GraalVM native images

A native image compiles your application ahead of time into a platform executable: startup in tens of milliseconds and a much smaller memory footprint, ideal for scale-to-zero and CLI-like services. The trade-offs: a slow build (minutes), a "closed world" (reflection, proxies and resources must be known at build time — Spring's AOT engine generates that metadata for you), and lower peak throughput than a warmed-up JIT. Things that can break: libraries that use reflection without metadata, @Profile/@ConditionalOnProperty decisions (they're evaluated at build time in native mode), and dynamic class loading. Run your tests in native mode too: ./mvnw -PnativeTest test.

Recap

  • The executable jar: JarLauncher (Main-Class) loads your Start-Class from BOOT-INF/classes and nested jars in BOOT-INF/lib.
  • Layers (dependencies, spring-boot-loader, snapshot-dependencies, application) make image rebuilds fast; -Djarmode=tools … list-layers / extract.
  • Images: spring-boot:build-image (buildpacks) or a multi-stage layered Dockerfile; non-root, JRE base, MaxRAMPercentage, config via env vars.
  • Kubernetes: liveness/readiness/startup probes on Actuator health groups; graceful shutdown (default) with a preStop delay; exec-form entrypoints so SIGTERM arrives.
  • Performance: virtual threads for I/O-bound MVC apps; Java 25 AOT cache (-XX:AOTCacheOutput, spring.context.exit=onRefresh); GraalVM native images for instant startup and low memory.

Exercises

Exercise 1 🟢 easy concept

Why can't you run a Boot application with java -cp target/app.jar com.example.InventoryApp?

Show solution

The application classes are under BOOT-INF/classes (not at the jar root) and the dependencies are nested jars in BOOT-INF/lib, which the standard class loader can't read. Only JarLauncher knows that layout. Use java -jar, or extract the jar first and use the extracted form.

Exercise 2 🟢 easy concept

In the layered Dockerfile, why are the layers copied in the order dependencies → loader → snapshot-dependencies → application?

Show solution

Docker caches layers in order; changing a layer invalidates it and every layer after it. Release dependencies change least often, your application code most often. With this order, a typical commit only rebuilds and re-pushes the small application layer (a few hundred KB) instead of 80 MB of libraries.

Exercise 3 🟢 easy code

Run the packaged jar with the profile batch set through the SPRING_PROFILES_ACTIVE environment variable and app.mode set as a JVM system property, and confirm the output.

Show solution

JVM options (-D…) must come before -jar; application arguments (--…) after the jar name.

Exercise 4 🟢 easy concept

A container with a 1 GiB memory limit keeps getting OOM-killed, although the JVM heap is only 256 MiB. Or it never uses more than 256 MiB of heap and throws OutOfMemoryError. Explain both and the setting involved.

Show solution

By default the JVM sizes the maximum heap at 25% of the container's memory, so 256 MiB of a 1 GiB limit — leaving the app starved (OutOfMemoryError) while 750 MiB sit unused. Raise it with -XX:MaxRAMPercentage=75. The opposite problem — being OOM-killed — happens when heap + metaspace + thread stacks + direct buffers + code cache exceed the limit (e.g. MaxRAMPercentage=95, or -Xmx set to the full limit): leave 20–30% for non-heap memory.

Exercise 5 🟡 medium code

Use -Dspring.context.exit=onRefresh to show that the application starts the context and exits without running the CommandLineRunner. Why is that useful for training runs?

Show solution

Nothing is printed by the runner: the context is refreshed (all beans created, so their classes are loaded and linked) and the JVM exits right after. That's ideal for creating CDS archives or AOT caches without side effects like processing data or connecting to queues.

Exercise 6 🟡 medium concept

Kubernetes sends SIGTERM, but the load balancer keeps sending requests to the pod for a few seconds, and some fail with "connection refused". What two settings fix it?

Show solution

Removing the pod from the Service's endpoints is asynchronous; the app shut its connector while traffic was still arriving. (1) A preStop hook (sleep: 10) delays SIGTERM so routing updates first. (2) Graceful shutdown (server.shutdown=graceful, the default) lets requests already in progress finish. Also make sure terminationGracePeriodSeconds exceeds preStop + shutdown timeout.

Exercise 7 🟡 medium code

List the dependency jars inside the packaged jar whose name starts with tomcat-embed, using jar tf and grep.

Show solution

The embedded Tomcat is just three jars in your application. To switch to Jetty, exclude spring-boot-starter-tomcat from the web starter and add spring-boot-starter-jetty. (Undertow is no longer supported in Boot 4.)

Exercise 8 🟡 medium concept

A service runs on Kubernetes with 4 replicas and scales to 0 at night; users complain the first request in the morning takes 8 seconds. Rank three options to fix it by effort.

Show solution

(1) Least effort: keep a minimum of 1 replica (costs money, no code change). (2) JVM AOT cache / CDS with a training run in the image build: often halves startup, no code changes. (3) GraalVM native image: startup in tens of milliseconds, but needs GraalVM in CI, native-compatible libraries and native tests. Also check the startup itself — lazy initialization of rarely used beans, or a slow connection at startup, may be the real cause.

Exercise 9 🔴 hard code

Measure the effect of the AOT cache yourself: time three runs of java -Dspring.context.exit=onRefresh -jar … with and without -XX:AOTCache=app.aot in the extracted directory. (The book only checks that both run; the numbers depend on your machine.)

Show solution

Remove | wc -l to see the times. On a typical laptop the cached runs are roughly 40% faster. If the JVM prints a warning that the cache can't be used, the classpath or JDK differs from the training run — rebuild the cache.

Write a production-ready application-prod.yml for the Library Loans API: database from environment variables, Flyway on with Hibernate validation, graceful shutdown with a 20 s timeout, virtual threads, Actuator exposing health,info,prometheus on management port 8081 with probes, structured JSON console logs, and no Open Session in View.
