Chapter 2 · Foundations

The IoC Container & Dependency Injection

Everything in Spring is a bean in a container. This chapter shows how the container learns about your beans (component scanning, @Bean methods, programmatic registration), how it injects them into each other, and how to resolve the classic problems: two candidates for one dependency, optional dependencies and circular references.

You will learn

  • What Inversion of Control and dependency injection mean, and what a bean definition is.
  • Three ways to define beans: stereotype annotations, @Bean methods and Spring 7's BeanRegistrar.
  • Why constructor injection is the default, and when setter or field injection appear.
  • Full vs lite @Configuration classes and what proxyBeanMethods changes.
  • How to choose between candidates: @Primary, @Qualifier, @Fallback, parameter names, collections and ObjectProvider.

Inversion of Control in one example

In ordinary code, an object creates or looks up what it needs. With Inversion of Control, the object just declares what it needs (usually as constructor parameters) and something outside — the container — provides it. Supplying dependencies that way is called dependency injection (DI).

The container's interface is BeanFactory; in practice you always use its richer sub-interface ApplicationContext, which adds events, resources, internationalisation and environment support. You don't need Spring Boot to use it:

Greeter has no idea where its Clock comes from. In a test you'd pass a different Clock; in production the container passes the real one. That is the whole point: classes depend on abstractions, and the wiring lives in one place.

🧠 Analogy: a staffing agency. Without IoC, every manager recruits their own staff — each department has its own hiring process. With IoC, managers send the agency a job description ("I need a Clock"), and the agency (the container) finds a matching person, hires them once, and sends the same person to whoever asks. Managers never deal with hiring again.

What the container knows: bean definitions

Before creating any object, the container builds a bean definition for each bean: its class (or factory method), its name, its scope (singleton by default), whether it's lazy, its dependencies and its lifecycle callbacks. Three ways to define beans

1. Stereotype annotations + component scanning

Annotate your own classes and let scanning find them. The stereotypes are all @Component with a more specific meaning:

AnnotationUse forExtra behaviour
@Componentany bean—
@Servicebusiness logicnone (documents intent)
@Repositorydata accesspersistence exceptions translated to Spring's DataAccessException
@Controller / @RestControllerweb endpointsdetected by Spring MVC as handlers
@Configurationclasses with @Bean methodsproxied so @Bean methods return singletons (below)

2. @Bean methods

Use @Bean methods for classes you don't own (a library's client, a Clock, an ObjectMapper) or when creating the object takes logic. The method's return value is the bean; its parameters are injected.

Constructor injection (and the alternatives)

If a class has one constructor, Spring uses it and injects every parameter. No @Autowired is needed. If it has several, mark the one to use with @Autowired.

Why constructor injection is the recommended default:

  • Dependencies are explicit: the constructor is the list of what the class needs. Too many parameters is a visible signal the class does too much.
  • Fields can be final, so the object is never half-built.
  • It's testable without Spring: new OrderService(fakeRepo) in a unit test.
  • Cycles fail fast at startup instead of silently working with half-initialised objects.

Field injection (@Autowired private OrderRepository orders;) still works but hides dependencies and needs reflection to test. You'll see it in older code and in test classes, where it's fine.

☕ Records and Lombok. A record's canonical constructor is a single constructor, so records can be beans with constructor injection too. Lombok's @RequiredArgsConstructor generates a constructor for final fields — popular in Spring code, but plain Java constructors work just as well.

Full vs lite @Configuration

When one @Bean method calls another, what happens depends on the class. A @Configuration class is subclassed with CGLIB (proxyBeanMethods = true, the default) so the call is intercepted and returns the existing singleton. In lite mode (proxyBeanMethods = false, or @Bean methods in a @Component), the call is just a Java method call and creates a new object:

Lite mode starts faster and works better with native images, which is why Boot's own auto-configurations use proxyBeanMethods = false. The safe habit in lite mode is to ask for collaborators as method parameters (Dao dao(Pool pool)) instead of calling other @Bean methods — then both modes behave the same.

Choosing between candidates

Injection is by type. If exactly one bean matches, it's injected. If none match, startup fails with NoSuchBeanDefinitionException. If several match, Spring tries, in order:

  1. a @Qualifier on the injection point,
  2. a bean marked @Primary (and ignores beans marked @Fallback if exactly one other is left),
  3. a bean whose name equals the parameter name,
  4. otherwise it fails with NoUniqueBeanDefinitionException.

Watch the third line: @Primary beats a matching parameter name. Parameter-name matching is only a last resort for when nothing is primary. Be explicit with @Qualifier when it matters.

@Fallback: the bean to use only if nothing else exists

@Fallback is the opposite of @Primary: "use me only if there's no other candidate". It's ideal for defaults that users may replace:

Injecting all candidates

Ask for a List to get every bean of a type (sorted by @Order/Ordered, otherwise in registration order) or a Map<String, T> keyed by bean name. This is the Spring way to build plug-in style designs:

To add a rule, you add a class. PasswordPolicy never changes — the open/closed principle, powered by the container.

⚠️ Bean names follow class names. A scanned component is named after its short class name with a lower-case first letter (DigitCheck → digitCheck). Rename the class and the map key changes too, so if anything depends on the key (a URL, a config value), give the component an explicit name: @Component("digit").

Optional dependencies: ObjectProvider, Optional and @Nullable

ObjectProvider is the most flexible: it's resolved lazily (when you call it), it has getIfAvailable, getIfUnique, ifAvailable, orderedStream(), and it works for prototype beans too. Boot's auto-configurations use it everywhere.

Circular dependencies

If A needs B in its constructor and B needs A, neither can be created first. Spring detects the cycle and fails at startup:

(The ... stands for a WARN log line in which the context reports that it cancelled the refresh.) Spring Boot goes further: it sets spring.main.allow-circular-references=false, so even setter/field cycles fail. The right fix is nearly always design: extract the shared logic into a third bean, publish an event instead of calling back (Chapter 8), or inject an ObjectProvider and resolve lazily.

Recap

  • IoC: objects declare dependencies; the container (ApplicationContext) creates and injects them from bean definitions.
  • Define beans with stereotypes + scanning, @Bean methods, or programmatically with BeanRegistrar (Spring 7).
  • Prefer constructor injection: explicit, final, testable, cycle-detecting. A single constructor needs no @Autowired.
  • @Configuration (full) proxies @Bean method calls; lite mode (proxyBeanMethods = false) doesn't — take collaborators as parameters.
  • Resolution order: @Qualifier → @Primary/@Fallback → parameter name → error. Inject List/Map for all candidates, ObjectProvider for optional or lazy ones.

Exercises

Exercise 1 🟢 easy concept

Explain the difference between BeanFactory and ApplicationContext. Which one does Spring Boot create?

Show solution

BeanFactory is the basic container: bean definitions, creation and injection. ApplicationContext extends it with event publishing, resource loading, message sources (i18n), the Environment, and automatic registration of post-processors. Boot always creates an ApplicationContext (for example AnnotationConfigServletWebServerApplicationContext for a web app).

Exercise 2 🟢 easy code

Without Spring Boot, create an AnnotationConfigApplicationContext from a @Configuration class that defines a List<String> bean named colors containing red, green, and print it.

Show solution

A trap worth knowing: if the configuration class itself were called Colors, its bean name would be colors too, and Spring refuses to start with "Bean name derived from @Bean method 'colors' clashes with bean name for containing configuration class".

Exercise 3 🟢 easy concept

Give three reasons to prefer constructor injection over field injection.

Show solution

(1) Dependencies are visible in the constructor signature and can be final. (2) The class can be created in a plain unit test with new, no reflection or Spring. (3) Required dependencies can't be missing (the object can't exist without them), and circular dependencies fail fast at startup.

Exercise 4 🟢 easy predict

Two beans implement Notifier, neither is @Primary, and a constructor asks for Notifier notifier. Neither bean is named notifier. What happens? Give two fixes.

Show solution

Startup fails with NoUniqueBeanDefinitionException ("expected single matching bean but found 2"). Fixes: mark one bean @Primary; add @Qualifier("beanName") to the parameter; rename the parameter to match one bean's name; or inject List<Notifier> if you actually need both.

Exercise 7 🟡 medium code

Write a library-style default: a @Bean @Fallback Greeting that returns "Hello". Then, controlled by the property app.formal=true, add a @Bean returning "Good day" using @ConditionalOnProperty. Run once with and once without the property.

Show solution

Exercise 8 🟡 medium debug

InvoiceService needs EmailService, and EmailService needs InvoiceService to look up the invoice total when it builds an email. Startup fails with a circular reference. Propose a design that removes the cycle.

Show solution

Pass the data instead of the service: emailService.sendInvoice(invoice) gives EmailService everything it needs, so it no longer depends on InvoiceService. Alternatives: extract the shared logic (e.g. InvoiceTotals) into a third bean both depend on; or have InvoiceService publish an InvoiceCreated event that an email listener handles (Chapter 8). @Lazy or ObjectProvider also break the cycle technically, but they hide the design problem.

Exercise 9 🔴 hard code

Write a BeanRegistrar that registers one Tenant bean per entry in the property app.tenants (e.g. acme,globex), marks the first one primary(), and print the primary tenant plus all tenants.

Show solution

Copy the loop variables into effectively-final locals (id, first) before using them in the lambdas.

Exercise 10 🔴 hard mini-project · playground

Build a tiny command dispatcher: an interface Command with String name() and String run(String arg); beans upper, reverse and count; and a Dispatcher that receives List<Command>, indexes them by name(), and runs "upper spring", "reverse spring", "count spring" and "nope x" (print unknown command: nope).
