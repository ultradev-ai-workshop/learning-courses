Chapter 4 · Foundations

Externalized Configuration

The same jar should run on your laptop, in CI and in production, with only its configuration changing. Spring Boot reads configuration from a dozen places in a well-defined order, binds it to typed Java objects, and validates it at startup. This chapter shows how, and how to keep secrets out of your code.

You will learn

  • The Environment, property sources and their precedence order.
  • application.properties vs YAML, profile-specific files, multi-document files and spring.config.import.
  • Injecting single values with @Value and placeholders with defaults.
  • Type-safe @ConfigurationProperties with records: nested objects, lists, maps, Duration and DataSize, defaults and validation.
  • Relaxed binding: how APP_MAIL_HOST becomes app.mail.host.

The Environment and property sources

All configuration ends up in one object, the Environment. It's a list of property sources searched in order: the first source that has a key wins. Boot registers them in this order (highest priority first; the full list has 15 entries):

  1. properties in tests (@SpringBootTest(properties=…), @TestPropertySource, @DynamicPropertySource),
  2. command-line arguments (--server.port=9000),
  3. SPRING_APPLICATION_JSON (inline JSON in an environment variable or system property),
  4. Java system properties (-Dserver.port=9000),
  5. OS environment variables (SERVER_PORT=9000),
  6. random.* values,
  7. config files: profile-specific application-{profile}.properties before application.properties; files outside the jar before files inside it,
  8. @PropertySource on configuration classes,
  9. default properties (SpringApplication.setDefaultProperties).

The rule of thumb: the closer to the deployment, the higher the priority. Defaults live in the jar, the environment overrides them, and an explicit command-line flag overrides everything.

🧠 Analogy: a stack of transparent sheets. Imagine each property source as a transparent sheet with a few values written on it, stacked on top of each other: application.properties at the bottom, environment variables above it, command-line arguments on top. Looking down through the stack, you see the top-most value for each key. Values not overridden show through from the sheets below.

Configuration files

Properties or YAML

Boot reads application.properties and application.yml (or .yaml). They're equivalent; choose one style per project. YAML is easier to read for nested structures, properties files are harder to get wrong (indentation matters in YAML).

Where files are found

Boot looks in four locations, later ones overriding earlier ones: classpath:/, classpath:/config/, the current directory ./, and ./config/ (plus its sub-directories). So a config/application.properties next to the jar overrides the one inside it — no rebuild needed. You can change this with spring.config.location or add more with spring.config.additional-location.

Profile-specific files and documents

Importing more configuration

spring.config.import pulls in other files or sources. Prefix a location with optional: so a missing file isn't an error:

configtree: reads a directory where each file name is a key and its content is the value — exactly how Kubernetes and Docker mount secrets. Other importers come from Spring Cloud (Config Server, Vault, Consul).

Single values with @Value

@Value("${key:default}") injects one property, converted to the parameter's type. It's fine for one or two values; for groups of related settings, use @ConfigurationProperties (next section).

⚠️ ${…} vs #{…}. ${key} is a property placeholder. #{expr} is a SpEL expression. Without a default, a missing ${key} fails startup with Could not resolve placeholder — which is usually what you want for required settings.

Relaxed binding

@ConfigurationProperties binding is forgiving about how names are written, so each source can use its natural style. The canonical form is lower-case kebab-case (mail.max-attachment-size):

SourceWrite it as
properties / YAMLmail.max-attachment-size (recommended), also maxAttachmentSize, max_attachment_size
environment variableMAIL_MAXATTACHMENTSIZE — upper case, dots become _, dashes removed (MAIL_MAX_ATTACHMENT_SIZE is also accepted)
list index in envMAIL_RECIPIENTS_0_ or MAIL_RECIPIENTS_0

The source must be named systemEnvironment: that name is what tells Boot to apply the environment-variable naming rules. DB_POOL_MAXSIZE from the environment beats db.pool.max-size=10 from the file — the same key in a different spelling. The Binder used here is the engine behind @ConfigurationProperties; you can use it directly in code that runs before the context exists.

⚠️ Use kebab-case in @Value placeholders. Relaxed binding is a @ConfigurationProperties feature; @Value only gets part of it. With APP_MAX_USERS=50 in the environment, @Value("${app.max-users}") resolves to 50 but @Value("${app.maxUsers}") finds nothing. The canonical kebab-case form is the only one that matches every spelling — another reason to prefer @ConfigurationProperties.

Secrets

Never commit passwords or API keys in application.properties. Common approaches, from simplest to most robust:

  • Environment variables set by the platform (SPRING_DATASOURCE_PASSWORD); reference them from files with placeholders: spring.datasource.password=${DB_PASSWORD}.
  • Mounted secret files read with spring.config.import=configtree:/run/secrets/.
  • A secret store (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault) via Spring Cloud integrations.
  • For local development, an untracked dev.properties imported with optional:file: and listed in .gitignore.

Actuator's /env and /configprops endpoints mask values by default (Chapter 18) — keep it that way.

Recap

  • All configuration flows into the Environment: an ordered list of property sources. Command line > system properties > env vars > profile files > application.properties > defaults.
  • Files: properties or YAML in classpath:/, classpath:/config/, ./, ./config/; application-{profile} files; #--- documents with spring.config.activate.on-profile; spring.config.import (with optional: and configtree:).
  • @Value("${key:default}") for single values; @ConfigurationProperties records for groups (immutable, typed, @DefaultValue, Duration, DataSize).
  • @Validated + constraints fail startup with a clear report showing each property's origin.
  • Relaxed binding maps MAIL_MAXATTACHMENTSIZE to mail.max-attachment-size. Keep secrets in the environment or a secret store, never in the repository.

Exercise 1 🟢 easy predict

application.properties has server.port=8080, the environment has SERVER_PORT=9090, and the app starts with java -jar app.jar --server.port=7070. Which port is used? And without the argument?

Show solution

7070: command-line arguments beat environment variables. Without the argument, 9090: environment variables beat application.properties.

Exercise 2 🟢 easy concept

Translate these keys into environment variable names: spring.datasource.url, app.max-retries, app.servers[2].

Show solution

SPRING_DATASOURCE_URL, APP_MAXRETRIES (dashes are removed; APP_MAX_RETRIES is also accepted for compatibility), APP_SERVERS_2_ (or APP_SERVERS_2).

Exercise 3 🟢 easy code

Inject app.title with @Value, defaulting to Untitled, and print it with and without --app.title=Library.

Show solution

Exercise 4 🟢 easy concept

Your jar contains application.properties with app.mode=test. In production you can't rebuild the jar. Name two ways to set app.mode=live without code changes.

Show solution

Any higher-priority source works: an environment variable APP_MODE=live; a command-line argument --app.mode=live; a system property -Dapp.mode=live; or a config/application.properties file next to the jar (files outside the jar override those inside).

Exercise 5 🟡 medium code

Create a record @ConfigurationProperties("upload") with DataSize maxFileSize (default 5MB), List<String> allowedTypes, and Duration retention (default 7d). Bind it from --upload.allowed-types=png,pdf --upload.max-file-size=20MB and print it.

Show solution

Duration accepts simple units (ns us ms s m h d) and ISO-8601 (PT7H); DataSize accepts B KB MB GB TB (powers of 1024).

Exercise 6 🟡 medium code

Bind a Map<String, Integer> of per-plan rate limits from YAML-style keys limits.plans.free=10, limits.plans.pro=100, limits.plans.enterprise=1000 (pass them on the command line). Print the limit for pro and the plan names in sorted order.

Show solution

Exercise 7 🟡 medium debug

The environment has APP_MAX_USERS=50. A @ConfigurationProperties("app") record with int maxUsers gets 50, but a teammate's @Value("${app.maxUsers:0}") int maxUsers in another bean gets 0. Why, and what's the fix?

Show solution

@ConfigurationProperties uses relaxed binding: it maps APP_MAX_USERS (and APP_MAXUSERS) to app.max-users, which matches maxUsers. @Value does a plain lookup of the exact key in the placeholder; the camelCase key app.maxUsers doesn't match the environment variable, so the default 0 is used. Fix: write the placeholder in canonical form, @Value("${app.max-users:0}") — or better, inject the properties record.

Exercise 8 🟡 medium code

With a properties file containing a default document and a prod document (via #--- and spring.config.activate.on-profile), create a profile group production = prod,audit. Show that activating production activates both profiles and picks up the prod document. (Use setDefaultProperties to define the group in code for this exercise.)

Show solution

The pool.size=50 comes from the prod document of the application.properties shown earlier in this chapter. In a real project you'd write spring.profiles.group.production=prod,audit in application.properties.

Exercise 9 🔴 hard code

Write a validated properties record @ConfigurationProperties("retry") with @Min(1) @Max(10) int attempts, @NotNull Duration backoff and a cross-field rule: the total wait (attempts × backoff) must be at most 1 minute. Express the rule with an @AssertTrue method. Show that --retry.attempts=5 --retry.backoff=20s fails with the rule's message.

Show solution

@AssertTrue on a getter-style method (isXxx) validates the whole object. --logging.level.root=OFF silences the failure report so only our line is printed. With --retry.backoff=10s the app starts.

Exercise 10 🔴 hard mini-project · playground

Build a feature-flag service: @ConfigurationProperties("flags") with Map<String, Flag> features, where Flag is a record with boolean enabled and @DefaultValue("100") int rolloutPercent. A FeatureFlags bean has boolean isOn(String feature, String userId): on if enabled and Math.floorMod(userId.hashCode(), 100) < rolloutPercent. Configure search (enabled, 100%), beta (enabled, 0%) and dark-mode (disabled), and print the flags for user u1 plus an unknown feature.

Show solution

Map keys with dashes (dark-mode) are kept as-is. Hashing the user id makes rollout sticky: the same user always gets the same answer for a given percentage. Real projects often move flags to a dedicated service, but configuration-backed flags are a great start.
