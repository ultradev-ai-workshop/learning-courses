Securing Applications with Spring Security

Add spring-boot-starter-security and your application is locked down: every endpoint needs a login. Spring Security 7 then lets you describe exactly who may do what — with a filter chain for URLs, annotations for methods, password hashing, and JWT-based authentication for APIs. This chapter builds that up step by step, and tests it.

You will learn

  • Authentication vs authorization, and how Spring Security's filter chain sits in front of your controllers.
  • Configuring a SecurityFilterChain: URL rules, HTTP Basic, stateless sessions, CSRF.
  • Users and passwords: UserDetailsService, PasswordEncoder and BCrypt.
  • Method security with @PreAuthorize, and reading the current user.
  • JWT resource servers (OAuth2) with scopes, and testing security with @WithMockUser and jwt().

Concepts

  • Authentication answers who are you? — a password, a token, a certificate. The result is an Authentication object (the principal plus its authorities) stored in the SecurityContext for the current request.
  • Authorization answers are you allowed to do this? — based on authorities such as ROLE_ADMIN or SCOPE_books:write.
  • Failing authentication gives 401 Unauthorized; being authenticated but not allowed gives 403 Forbidden.

Spring Security is implemented as a chain of servlet filters (Chapter 10) that runs before the DispatcherServlet: one filter reads credentials, another checks authorization rules, another turns security exceptions into 401/403 responses. Your controllers only see requests that passed.

🧠 Analogy: an office building. At reception (authentication) you show your ID and get a badge listing your access levels (authorities). Each door has a reader (authorization) that checks your badge: the lobby is open to everyone, floor 3 needs "staff", the server room needs "admin". No badge → back to reception (401). Badge without the right level → the door stays shut (403).

The defaults

With the starter on the classpath and no configuration, Boot secures everything, enables form login and HTTP Basic, and creates one user named user with a random password printed at startup ("Using generated security password: …"). You can set it with spring.security.user.name/password/roles. That's fine for a first run — every real application defines its own rules.

Rules are checked top to bottom; the first match wins — put specific matchers first and anyRequest() last. hasRole("ADMIN") checks for the authority ROLE_ADMIN; hasAuthority("…") checks an authority by its exact name. Ending with .anyRequest().authenticated() (or denyAll()) makes the configuration secure by default: a new endpoint someone forgets to mention is still protected.

CSRF, sessions and CORS

  • CSRF (cross-site request forgery) tricks a logged-in browser into sending a request with its cookies. Protection is on by default and must stay on for browser apps with session cookies. For a stateless API authenticated by an Authorization header (Basic or Bearer), browsers don't attach credentials automatically, so disabling CSRF is the standard choice.
  • Sessions: STATELESS means Spring Security never creates an HTTP session; every request carries its credentials. That's what you want for APIs behind a load balancer.
  • CORS: enable it in the chain with http.cors(Customizer.withDefaults()) and a CorsConfigurationSource bean, so that pre-flight OPTIONS requests are answered before authentication.

Passwords

Never store passwords in plain text — or with a fast hash like SHA-256. Use a slow, salted password hash such as BCrypt, Argon2 or scrypt. The delegating password encoder stores the algorithm as a prefix ({bcrypt}…), so you can upgrade algorithms later while old hashes keep working:

In a real application, UserDetailsService loads users from your database (implement loadUserByUsername with a repository), or — more often today — you don't store passwords at all and delegate login to an identity provider (Keycloak, Auth0, Entra ID, Okta) with OAuth2/OpenID Connect.

Method security

URL rules are coarse. For rules that depend on the data ("users can only read their own loans"), enable method security and annotate service methods. @PreAuthorize takes a SpEL expression with access to the method arguments and the authentication:

Like every annotation in Chapter 7, method security is a proxy: it protects calls into the bean, not self-invocation. Other options: @PostAuthorize (check the return value, returnObject), @PreFilter/@PostFilter for collections, and your own meta-annotations (@IsLibrarian) so expressions aren't copy-pasted. In a web app, denied method calls become 403 responses.

The current user

In a controller, inject Principal, Authentication or @AuthenticationPrincipal UserDetails user (or @AuthenticationPrincipal Jwt jwt for tokens). Elsewhere, SecurityContextHolder.getContext().getAuthentication() — the context is thread-bound, so it isn't automatically available on @Async threads.

JWT resource servers

Modern APIs don't check passwords themselves. An authorization server (Keycloak, Auth0, Spring Authorization Server…) logs the user in and issues a signed JWT access token; the API — a resource server — verifies the signature and expiry on each request and reads the claims. The resource server never stored any user: everything it needs is in the signed token. That's why JWTs scale well across many services — and why their lifetime should be short (minutes), since a stolen token is valid until it expires. Use a JwtAuthenticationConverter to map other claims (for example Keycloak's realm_access.roles) to authorities.

⚠️ Don't invent your own security. Shared HMAC secrets (as in this demo) mean every service that can verify tokens can also forge them. In production, use asymmetric keys (RS256/ES256) from a real authorization server, validate the iss and aud claims, keep tokens short-lived, and never put secrets in a JWT — its payload is only Base64, not encrypted.

Recap

  • Authentication = who (401 when missing/invalid); authorization = what (403 when not allowed). Spring Security is a filter chain in front of MVC.
  • Define a SecurityFilterChain bean: ordered requestMatchers rules ending with anyRequest(), HTTP Basic or a resource server, STATELESS sessions and CSRF off for token APIs.
  • Hash passwords with the delegating encoder (BCrypt by default); load users with a UserDetailsService — or delegate login to an identity provider.
  • @EnableMethodSecurity + @PreAuthorize("#member == authentication.name or hasRole('X')"); @PostFilter; proxy rules apply.
  • JWT resource server: issuer-uri, SCOPE_ authorities, short-lived tokens. Test with @WithMockUser, jwt() and httpBasic().

Exercises

Exercise 1 🟢 easy predict

The rules are requestMatchers("/admin/**").authenticated(), then requestMatchers("/admin/users/**").hasRole("ADMIN"), then anyRequest().permitAll(). Can a plain logged-in user call DELETE /admin/users/7? Fix the configuration.

Show solution

Yes — the first matching rule wins, and /admin/** (any authenticated user) matches before the admin rule is reached. Put the more specific matcher first: /admin/users/** → hasRole("ADMIN"), then /admin/** → authenticated(). And consider ending with anyRequest().authenticated() rather than permitAll().

Exercise 2 🟢 easy concept

What's the difference between hasRole("ADMIN") and hasAuthority("ADMIN")? Which authorities does a JWT with "scope": "orders:read orders:write" produce by default?

Show solution

hasRole("ADMIN") checks for the authority ROLE_ADMIN (the prefix is added for you); hasAuthority("ADMIN") checks for exactly ADMIN. The JWT produces SCOPE_orders:read and SCOPE_orders:write.

Exercise 3 🟢 easy code

Use a BCryptPasswordEncoder with strength 12 to hash "hunter2", then print whether the hash starts with $2a$12$ and whether it matches.

Show solution

Each strength step doubles the work: 12 is about 4× slower than the default 10. Choose the highest value that keeps login acceptably fast on your servers (~100–300 ms).

Exercise 4 🟢 easy concept

A colleague disables CSRF in a server-rendered web shop that uses session cookies, "because the forms stopped working". Why is that dangerous, and what's the real fix?

Show solution

With cookie-based sessions, any website the user visits can submit a form to the shop and the browser will attach the session cookie — e.g. changing the delivery address or placing an order. The fix is to include the CSRF token in the forms (Thymeleaf does it automatically with th:action; JavaScript clients read the XSRF-TOKEN cookie and send the header). CSRF may only be disabled for APIs that don't use cookies for authentication.

Exercise 8 🟡 medium debug

After adding Spring Security, a browser single-page app on another origin gets CORS errors on every API call, even though WebMvcConfigurer.addCorsMappings is configured. Why?

Show solution

The browser's preflight OPTIONS request carries no credentials, so the security filter chain rejects it with 401 before Spring MVC's CORS handling runs. Enable CORS in the security chain — http.cors(Customizer.withDefaults()) — which uses the MVC configuration or a CorsConfigurationSource bean and answers preflights before authentication.

Exercise 9 🔴 hard code

Map custom JWT claims to roles: tokens carry "roles": ["librarian", "user"]. Configure a JwtAuthenticationConverter (with a JwtGrantedAuthoritiesConverter using setAuthoritiesClaimName("roles") and prefix ROLE_, upper-casing is up to you) and decode a token with NimbusJwtDecoder to print the resulting authorities — no web server needed.

Show solution

FACTOR_BEARER is new in Spring Security 7: alongside your own authorities, an authentication records how the user proved their identity (FACTOR_PASSWORD, FACTOR_BEARER, FACTOR_OTT…). That's the basis of its multi-factor authentication support — rules can require, say, both a password and a one-time token. Register the converter in the chain with .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(converter))); then hasRole('LIBRARIAN') works with your identity provider's role claim.
