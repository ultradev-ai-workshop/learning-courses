Bean Scopes, Lifecycle & Profiles

A bean isn't just an object: it has a scope (how many instances exist and for how long), a lifecycle (callbacks when it's ready and when it's destroyed) and sometimes a profile (the environments it exists in). Getting these right is the difference between "works on my machine" and a predictable production app.

You will learn

  • The bean scopes: singleton, prototype, and the web scopes request, session and application.
  • The scoped-dependency problem (a short-lived bean inside a singleton) and three ways to solve it.
  • The full lifecycle: construction, injection, Aware callbacks, @PostConstruct, post-processors, @PreDestroy.
  • SmartLifecycle for things that start and stop (consumers, schedulers), and lazy initialisation.
  • Profiles: @Profile, profile expressions, activating profiles and the default profile.

Bean scopes

ScopeInstancesTypical use
singleton (default)one per containerservices, repositories, controllers, clients — stateless objects
prototypea new one every time it's requestedstateful helpers, builders, objects with per-use state
requestone per HTTP requestper-request context (correlation id, current tenant)
sessionone per HTTP sessionshopping cart in a server-rendered app
applicationone per ServletContextrare; like singleton but visible as a servlet attribute

⚠️ Singletons are shared by every thread. A web server handles requests on many threads at once, all calling the same controller and service instances. Never keep per-request data in a field of a singleton; use local variables, method parameters, or a request-scoped bean. Mutable shared state must be thread-safe (AtomicInteger, ConcurrentHashMap…).

🧠 Analogy: the office printer and paper cups. A singleton is the office printer: one machine, everybody uses it, so it must cope with many people at once. A prototype is a paper cup: you take a fresh one each time and nobody else drinks from it. Request scope is a visitor badge: issued at the door, valid for one visit, collected on the way out.

Injection happens once, when the singleton is created. If a singleton has a prototype dependency injected into its constructor, it keeps that one instance forever — the prototype scope is silently lost:

Three ways to get a fresh instance each time:

  • ObjectProvider<T> (shown above): explicit and simple. The recommended choice.
  • A scoped proxy: @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS) injects a proxy that fetches a new target on every method call. That's how request and session scopes work.
  • @Lookup methods: an abstract method that Spring overrides to return a new bean. It works, but it's less obvious to readers.

In practice you use @PostConstruct and @PreDestroy (or initMethod/destroyMethod for third-party classes). InitializingBean and DisposableBean tie your class to Spring, so the docs recommend against them for application code.

💡 Automatic close. For @Bean methods, Spring infers the destroy method: if the returned object has a public close() or shutdown() method (or is AutoCloseable), it is called on shutdown without any configuration. Use @Bean(destroyMethod = "") to turn that off.

⚠️ Prototype beans aren't destroyed. The container creates and initialises prototypes, then hands them over and forgets them: @PreDestroy is never called on a prototype. If it holds resources, the code that requested it must clean up.

Things that start and stop: SmartLifecycle

Some beans need to run while the application is up: a message-queue consumer, a polling loop, an embedded server. Implement SmartLifecycle: start() is called after all singletons are created, stop() before they're destroyed, ordered by getPhase() (lower starts first and stops last):

The pool starts before the consumer that needs it, and stops after it. During graceful shutdown (Chapter 19) Boot uses phases to stop accepting web requests first.

Lazy initialisation

Singletons are created eagerly at startup by default, so configuration errors appear immediately. @Lazy on a bean (or spring.main.lazy-initialization=true for all beans) delays creation until first use: faster startup, but errors show up later, on the first request. A common compromise is lazy in development, eager in production.

Profiles

A profile is a named set of beans and configuration that is active only in some environments. Mark beans (or whole @Configuration classes) with @Profile, and activate profiles with spring.profiles.active:

Profile expressions support ! (not), & (and) and | (or), with parentheses. The special default profile is active only when no other profile is. Ways to activate profiles, from most to least common:

  • environment variable SPRING_PROFILES_ACTIVE=prod (the usual choice in containers),
  • command line --spring.profiles.active=prod or JVM option -Dspring.profiles.active=prod,
  • in tests, @ActiveProfiles("test") (Chapter 16),
  • in code, SpringApplication.setAdditionalProfiles("…").

Profiles also select configuration files (application-prod.properties) and support profile groups — both in Chapter 4.

💡 Prefer properties to profiles for small differences. Use a profile when the set of beans differs (a fake mailer vs a real one). When only a value differs (a URL, a timeout), keep one bean and change the property per environment. Too many @Profile annotations make it hard to know what actually runs in production.

Recap

  • Default scope is singleton (one shared, thread-safe instance). prototype = new per request to the container; request/session live with HTTP.
  • Injecting a shorter-lived bean into a singleton captures one instance. Use ObjectProvider, or a scoped proxy (which web scopes use automatically with @RequestScope).
  • Lifecycle: constructor → injection → Aware → @PostConstruct → afterPropertiesSet/initMethod → post-processors (proxies) → ready → @PreDestroy → destroy. Prototypes are never destroyed by the container.
  • SmartLifecycle beans start after all singletons exist and stop first on shutdown, ordered by phase.
  • @Profile("prod & !eu") selects beans per environment; activate with SPRING_PROFILES_ACTIVE or --spring.profiles.active; default applies when none is active.

Exercises

Exercise 1 🟢 easy concept

A @Service stores the current user's id in a field set at the start of each request. Under load, users occasionally see each other's data. Why?

Show solution

The service is a singleton shared by all request threads. Two concurrent requests write the same field, and one reads the other's value. Per-request data must be passed as parameters, kept in local variables, or stored in a request-scoped bean (or Spring Security's SecurityContextHolder, which is per-thread).

Exercise 2 🟢 easy predict

A prototype bean has a @PreDestroy method that prints bye. You call getBean three times and then close the context. How many times is bye printed?

Show solution

Zero. The container doesn't keep track of prototype instances after handing them out, so their destruction callbacks are never invoked.

Exercise 3 🟢 easy code

Write a bean with @PostConstruct printing ready and @PreDestroy printing closing, and a main that prints working between start and close.

Show solution

Exercise 4 🟢 easy concept

Which beans exist when the active profiles are prod,eu? Beans: @Profile("prod") A, @Profile("!prod") B, @Profile("eu | us") C, @Profile("default") D, no profile E.

Show solution

A (prod is active), C (eu is active) and E (beans without @Profile always exist). Not B (prod is active) and not D (default is only active when no profile is set).

Exercise 5 🟡 medium code

A singleton ReportService needs a new ReportBuilder (prototype, holds a StringBuilder) for each report. Implement String report(String... lines) with ObjectProvider, and show that two reports don't mix their lines.

Show solution

Exercise 6 🟡 medium code

Create a @Bean of a class with a public close() method (but no @PreDestroy and not AutoCloseable) and show that close() is still called on shutdown. Then switch it off with destroyMethod = "".

Show solution

The default destroyMethod is the special value "(inferred)", which looks for a public close or shutdown method. Inference applies to @Bean methods, not to scanned @Component classes (those need @PreDestroy or AutoCloseable).

Exercise 7 🟡 medium code

Define a StorageService with two implementations: LocalStorage in profiles dev and default, S3Storage in prod. Use one @Profile annotation per class. Print the implementation for no profile, dev and prod.

Show solution

@Profile({ "dev", "default" }) means "dev OR default" — the same as @Profile("dev | default").

Exercise 8 🟡 medium predict

Three SmartLifecycle beans have phases 0, -100 and Integer.MAX_VALUE. In what order do they start and stop?

Show solution

Start: -100, 0, MAX_VALUE (lowest first). Stop: MAX_VALUE, 0, -100 (reverse). The default phase for SmartLifecycle is Integer.MAX_VALUE, i.e. "start last, stop first" — which suits most consumers.

Exercise 9 🔴 hard code

Write a BeanPostProcessor that wraps every bean implementing Greeter in a decorator that upper-cases its result — without changing the Greeter classes. Show that the injected Greeter is the decorated one.

Show solution

Whatever a post-processor returns becomes the bean. This is exactly how Spring's AOP proxies (transactions, caching, security) are applied — Chapter 7. Declare post-processor @Bean methods static so their configuration class isn't created too early.

Exercise 10 🔴 hard mini-project · playground

Build a Poller that implements SmartLifecycle: start() launches a virtual thread that increments a counter every 20 ms; stop() interrupts it and waits for it to finish. Let the application run ~200 ms, then close it and print whether the counter is greater than 3 and whether the thread has ended.

Show solution

isRunning() matters: the container only calls stop() on components that report they're running. In real code you'd usually use @Scheduled (Chapter 8) instead of a hand-written loop — but this is how such infrastructure works under the hood.
