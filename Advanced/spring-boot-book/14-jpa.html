Spring Data JPA

JPA maps Java objects to tables, and Spring Data JPA writes the repository code for you: declare an interface, and you get CRUD, paging, sorting and queries derived from method names. It's enormously productive — as long as you understand what JPA does behind your back: the persistence context, dirty checking, lazy loading and the N+1 problem. This chapter covers both sides.

You will learn

  • Mapping entities: ids, columns, relationships (@ManyToOne, @OneToMany), and equals/hashCode.
  • Repositories: JpaRepository, derived queries, @Query (JPQL and native), @Modifying.
  • Paging and sorting with Pageable, Page and Slice; projections with interfaces and records.
  • The persistence context: managed entities, dirty checking, flush and the first-level cache.
  • Lazy loading and N+1: detecting it, fixing it with fetch joins and @EntityGraph; plus auditing.

Entities

An entity is a class whose instances are rows. It needs @Entity, an @Id, and a no-argument constructor (it may be protected) because Hibernate creates instances by reflection. Entities are mutable classes — records can't be entities (but they're perfect for projections, below).

Key mapping decisions:

  • @GeneratedValue: IDENTITY uses the database's auto-increment; SEQUENCE (the default with AUTO on most databases) allows Hibernate to batch inserts.
  • Relationships: @ManyToOne is the owning side (it has the foreign key column); @OneToMany(mappedBy = …) is the inverse side. Always make @ManyToOne LAZY — the JPA default is EAGER, which loads the parent in every query.
  • equals/hashCode: don't use the generated id (it's null before saving, so a new entity's hash changes after persist). A natural business key (ISBN) is ideal; otherwise compare ids but use a constant hashCode.

A typo in a property name fails at startup — one of Spring Data's best features. When a name gets longer than a sentence, switch to @Query.

🧠 Analogy: ordering from a menu in plain words. A derived query is like telling a waiter "the pasta, without onions, extra cheese". The kitchen (Spring Data) understands the sentence and cooks the SQL. For an unusual dish you hand over a written recipe (@Query). If you ask for "the spagetti", the waiter tells you immediately that it's not on the menu — at startup, not when the plate arrives.

Page vs Slice, and sorting from the web

A Page runs an extra COUNT query to know the total; a Slice only knows whether there's a next page (it fetches one extra row) — cheaper for infinite scrolling. In a controller, accept a Pageable parameter: Spring Data's web support binds ?page=1&size=20&sort=title,desc automatically. Return a PagedModel (or your own DTO) rather than the raw PageImpl, whose JSON structure isn't guaranteed stable.

The persistence context

Inside a transaction, JPA keeps a persistence context: a map of every entity loaded or saved, keyed by id. It gives you three behaviours that surprise newcomers:

  • Identity: loading the same row twice returns the same object (the first-level cache) — the second load doesn't even hit the database.
  • Dirty checking: change a field of a managed entity and the UPDATE is written at commit — no save() call needed.
  • Write-behind: SQL is sent at flush time (before commit, before queries that need it, or on flush()), not when you call save.

Two statements: one SELECT by ISBN (the findById was answered from the persistence context) and the UPDATE generated by dirty checking at commit. Because @SpringBootApplication scans only its own package, this example points scanning, @EntityScan and @EnableJpaRepositories at the shared library package — in a normal project with one root package you need none of these.

⚠️ Outside a transaction, entities are detached. Changes to a detached entity are not saved, and touching a lazy relationship throws LazyInitializationException. Do your loading and changing inside a @Transactional service method, and return DTOs to the web layer. (Boot's spring.jpa.open-in-view keeps a session open during web requests to hide this, and warns at startup when enabled; this book turns it off, as most teams do.)

Lazy loading and the N+1 problem

With LAZY relationships, Hibernate loads a book's author only when you call book.getAuthor().getName(). Loop over 100 books and print their authors, and you run 1 query for the books + N queries for the authors — the infamous N+1 problem. It's invisible in development with five rows and crippling in production with five thousand. Count the queries to see it:

(The derived query has no OrderBy, so rows come back in whatever order the database chooses — never rely on it.) Here N+1 is "only" 1 + 3 (one query per distinct author — the persistence context caches each author once loaded). Fixes, in order of preference:

  1. Fetch what the use case needs: JOIN FETCH in a @Query, or @EntityGraph(attributePaths = …) on the repository method.
  2. Use a DTO projection that selects exactly the columns you show — often the best for read-only screens and APIs.
  3. Batch fetching: spring.jpa.properties.hibernate.default_batch_fetch_size=50 loads lazy associations in groups (1 + N/50 queries) — a good global safety net.

💡 Watch your queries in development. Turn on logging.level.org.hibernate.SQL=debug (and org.hibernate.orm.jdbc.bind=trace for parameters), or count statements in tests as above. Assert the query count of important endpoints in tests so an N+1 can't sneak back in.

Recap

  • Entities: @Entity, @Id, a no-arg constructor; @ManyToOne(fetch = LAZY) owns the foreign key; keep both sides of a relationship in sync; base equals on a business key.
  • JpaRepository gives CRUD; derived query names are checked at startup; @Query for JPQL or native SQL; @Modifying for bulk updates (which bypass the persistence context).
  • Pageable → Page (with count) or Slice; projections with interfaces, records or dynamic Class<T>.
  • Persistence context: same row = same object, dirty checking writes changes at commit, SQL is flushed late. Outside a transaction, entities are detached.
  • N+1: count queries; fix with JOIN FETCH, @EntityGraph, DTO projections or batch fetching. Auditing with @EnableJpaAuditing + @CreatedDate/@CreatedBy.

Exercises

Exercise 1 🟢 easy concept

Translate into SQL-ish English: findTop3ByAuthorNameAndPublishedGreaterThanOrderByPriceDesc(String name, int year).

Show solution

"Select the 3 books whose author's name equals name and whose published year is greater than year, ordered by price, highest first." It joins book to author to compare the name.

Exercise 2 🟢 easy predict

Inside a @Transactional method you load a book, call book.setTitle("New"), and never call save. Is the change stored? What if the method isn't transactional and you load the book with findById?

Show solution

Transactional: yes — the entity is managed and dirty checking issues an UPDATE at commit. Not transactional: no — findById runs in its own short transaction and returns a detached entity; you'd have to call save(book), which merges it in a new transaction.

Exercise 3 🟢 easy code

Add a derived query List<Book> findByAuthorNameOrderByTitle(String name)… without editing the shared repository: declare a small extra repository interface BookFinder extends Repository<Book, Long> with that method, and print Jane Austen's books.

Show solution

Extending the bare Repository marker interface gives you no inherited methods at all — useful for read-only or narrowly scoped repositories.

Exercise 4 🟢 easy concept

Why is spring.jpa.hibernate.ddl-auto=update a bad idea in production? What should you use instead?

Show solution

update lets Hibernate guess schema changes at startup: it never drops or renames columns, can't migrate data, may create wrong types or indexes, and leaves no reviewed history. Use versioned migrations (Flyway or Liquibase) and set ddl-auto=validate, so the app fails fast if entities and schema disagree.

Exercise 5 🟡 medium code

Write a JPQL @Query returning a record AuthorStats(String name, long books, BigDecimal avgPrice) per author, using a constructor expression (SELECT new …(…)), ordered by name.

Show solution

The constructor expression needs the class's fully qualified name; keep such DTOs top-level (a nested record would need the binary name StatsRepository$AuthorStats). A mistake here fails at startup — repository queries are validated when the context starts, so one broken query stops the whole application. JPQL's AVG returns a Double, so the record component is Double; use Math.round or a BigDecimal computation if you need exact money values.

Exercise 7 🟡 medium debug

A controller returns List<Book> directly as JSON. With open-in-view=false it fails with LazyInitializationException; with open-in-view=true it "works", but the endpoint runs dozens of queries and sometimes recurses forever. Explain both symptoms and the proper fix.

Show solution

Jackson serialises after the service's transaction ended. It calls getAuthor() on each book: without an open session, the lazy proxy can't load → exception. With open-in-view, each author is loaded on demand (N+1), and serialising author.books → book.author → … loops (bidirectional relationship). Fix: don't expose entities; map to DTOs (records) inside a transactional service, fetching exactly what's needed (fetch join or projection).

Exercise 8 🟡 medium code

Remove a book from an author with orphanRemoval = true: inside a transaction, load Frank Herbert and remove "Dune Messiah" from his books list. Show that the book count drops from 5 to 4.

Show solution

With orphanRemoval, a child removed from its parent's collection is deleted. Use it only when children can't exist without their parent (order lines, not books shared by libraries).

Exercise 9 🔴 hard code

Prove the N+1 fix with batch fetching: run the same "title by author" report over findAll() with spring.jpa.properties.hibernate.default_batch_fetch_size=10 and print the statement count.

Show solution

One query for the books, one … WHERE id IN (?, ?, ?) for all three authors. A Java trap to avoid when you measure this: ….map(…).count() would report a single query, because since Java 9 count() may skip map entirely when the stream's size is known — the authors would never be touched. Batch fetching doesn't change your code and caps the damage of forgotten fetch joins — many teams set it globally.

Exercise 10 🔴 hard mini-project · playground

Model the Library Loans domain with JPA in its own package: Member (name, unique email), Loan (@ManyToOne member, @ManyToOne book by ISBN string for simplicity, dueDate, returnedAt). Write LoanRepository with a derived query for a member's open loans (returnedAt IsNull), a JPQL query for overdue loans with the member fetched, and a count of open loans per member. Demonstrate them with a few loans.

Show solution

The returned loan isn't overdue: returnedAt was set by dirty checking inside the seeding transaction. The JOIN FETCH lets the report print member names without extra queries. In Chapter 20 this model gets Flyway migrations, a service with business rules and a REST API.
