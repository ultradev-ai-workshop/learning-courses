Test a controller without starting the app

Full @SpringBootTests take seconds each; you want many fast tests for a controller's mapping, JSON and status codes.

@WebMvcTestMockMvcTesterChapter 16

Solution

The test needs a @SpringBootConfiguration somewhere above its package to start from — your main application class. (On this page it's the one in com.example.h6 below.)

Pitfalls

  • Every distinct set of @MockitoBeans creates a new cached context; keep them consistent across test classes.
  • Boot 4: add spring-boot-starter-webmvc-test; @MockBean is gone — use @MockitoBean.

Test against a real PostgreSQL

Your repository uses PostgreSQL features (JSONB, ON CONFLICT) that H2 doesn't have.

Testcontainers@ServiceConnectionChapter 16

Solution

Add spring-boot-testcontainers and org.testcontainers:postgresql (test scope). Declare the container once in a shared configuration, and import it where needed:

The same configuration gives you a local development database: a TestLibraryApplication in src/test/java with SpringApplication.from(LibraryApplication::main).with(ContainersConfig.class).run(args) — run it from the IDE and a PostgreSQL container starts with the app.

Pitfalls

  • Containers need Docker (or a compatible runtime) on the CI agent.
  • Declaring the container as a bean (rather than a static field per test class) lets the context cache share one container across test classes.

Add a health check for a dependency

The app depends on a search service; operations want to see its state in /actuator/health — without restarting pods when it's down.

HealthIndicatorreadinessChapter 18

Solution

Search being down takes the instance out of the load balancer (readiness) but doesn't restart it (liveness). If the app can work in a degraded mode without search, leave it out of readiness too and only alert on it.

Pitfalls

  • Health checks run on every probe — keep them cheap and give network checks a short timeout (or cache the result).
  • show-components/show-details reveal your architecture; use when-authorized on public endpoints.

Handle requests on virtual threads

The service spends most of its time waiting for other services and the database; Tomcat's 200 threads are the bottleneck.

virtual threadsJava 21+Chapter 19

Solution

One property switches Tomcat, @Async, @Scheduled and other Boot-managed executors to virtual threads.

Pitfalls

  • The connection pool is now the limit: 10 000 virtual threads still share 10 database connections. Size the pool for the database, and protect dependencies with @ConcurrencyLimit.
  • Thread-local caches (some old libraries) multiply with thousands of threads; measure memory after switching.

Shut down without dropping requests

During deployments, a few requests fail with connection errors each time a pod is replaced.

graceful shutdownKubernetesChapter 19

Solution

Graceful shutdown is on by default: on SIGTERM (or context.close()) the server stops accepting connections and waits for active requests, up to spring.lifecycle.timeout-per-shutdown-phase:

On Kubernetes, also add a preStop sleep (5–10 s) so the endpoint is removed from the Service before shutdown starts, and keep terminationGracePeriodSeconds above preStop + shutdown timeout.

Pitfalls

  • The JVM must receive SIGTERM: use the exec form of ENTRYPOINT, not sh -c.
  • Long-running jobs need their own stop logic (SmartLifecycle.stop or checking interruption).

Build a native executable

A small service must start in milliseconds and use little memory (scale to zero, CLI tool, serverless).

GraalVMAOTChapter 19

Solution

Spring's AOT engine generates the reflection, proxy and resource hints for Spring itself. For your own reflection, register hints with @RegisterReflectionForBinding or a RuntimeHintsRegistrar.

Pitfalls

  • Bean conditions and profiles are fixed at build time: --spring.profiles.active=prod at runtime can't add beans that weren't in the build.
  • Peak throughput is lower than a warmed-up JIT; for long-running services, the JVM with an AOT cache is often the better trade-off.
