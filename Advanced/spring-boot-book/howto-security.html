Store passwords and upgrade old hashes

Legacy users have SHA-256 hashes; new ones should get BCrypt — and old hashes should be upgraded as users log in.

DelegatingPasswordEncoderUserDetailsPasswordServiceChapter 17

Solution

The delegating encoder verifies any supported {id}-prefixed hash and reports when it should be re-encoded. If your UserDetailsService also implements UserDetailsPasswordService, Spring Security re-hashes the password after a successful login automatically:

For hashes stored without a prefix (e.g. bare SHA-256 hex), run a one-off migration that adds the prefix ({sha256}…), and register that id in a custom DelegatingPasswordEncoder map.

Pitfalls

  • Never "upgrade" by decrypting — hashes can't be reversed; upgrades only happen when the user types the password.
  • Rate-limit login attempts; BCrypt slows each guess, but doesn't stop a million parallel ones.

Get the current user anywhere

The service layer needs the logged-in user's name to stamp "created by" — without passing it through every method.

SecurityContextHolder@AuthenticationPrincipalChapter 17

Solution

In controllers, inject it (@AuthenticationPrincipal Jwt jwt, Principal). Elsewhere, wrap SecurityContextHolder in a small bean so it can be faked in tests:

The context is per thread: @Async methods and new threads don't see it unless you propagate it (DelegatingSecurityContextExecutor, or Boot's context propagation for task executors). For JPA auditing, implement AuditorAware with this bean (H3).

Pitfalls

  • Never trust a user name sent by the client in the body or a header — take it from the authentication.
  • Don't store the Authentication in a singleton field (Chapter 3): it belongs to one request.
