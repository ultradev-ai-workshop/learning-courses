Set up dev / test / prod configuration

Local development uses H2 and verbose logging, production uses PostgreSQL and JSON logs. One jar must serve both.

profilesprofile groupsChapters 3–4

Solution

Put shared defaults in application.yml, differences in profile documents or files, and activate the profile from outside (an environment variable in production):

Activate with SPRING_PROFILES_ACTIVE=prod in the deployment, @ActiveProfiles("test") in tests, and spring.profiles.default=dev in application.yml so a plain local run picks dev.

Pitfalls

  • spring.profiles.active inside a profile-specific document is not allowed (it would be circular) — use groups.
  • Prefer different values to different beans; keep @Profile for genuine alternatives (a fake mail sender).
  • Don't make a profile called default meaningful — it's the special "no profile active" profile.

Keep secrets out of the repository

The database password and an API key must not be in application.yml or in git, but the app needs them at startup.

environment variablesconfigtreeChapter 4

Solution

Reference secrets by placeholder and supply them from the environment, or from files mounted by Kubernetes/Docker (one file per secret) with configtree::

Folders become dots in the property name (payments/api-key → payments.api-key) and the trailing newline is trimmed. In application.yml you then write spring.datasource.password: ${db-password}.

Pitfalls

  • Don't print or log secrets (this recipe prints only a length); Actuator's /env masks values by default — keep management.endpoint.env.show-values=never.
  • For local development, use an untracked dev.properties imported with optional:file:./dev.properties and add it to .gitignore.
  • Rotate any secret that ever reached git history — deleting the line later doesn't remove it from history.

Add your own typed, validated settings

Your feature needs a URL, a timeout and a list of allowed countries — with sensible defaults, and a clear error if someone misconfigures them.

@ConfigurationPropertiesrecordsChapter 4

Solution

Inject ShippingProperties into the beans that need it. Add spring-boot-configuration-processor (optional, annotation processor) to get IDE auto-completion for shipping.*. A value like shipping.countries=de fails at startup with a report naming the property, the value and where it came from.

Pitfalls

  • @Validated needs spring-boot-starter-validation on the classpath; without it, constraints are silently ignored.
  • Don't inject ShippingProperties into static fields or read it in constructors of unrelated classes — keep configuration flowing through injection.

Switch from Tomcat to Jetty

Your organisation standardises on Jetty, or you want to compare servers.

embedded serverstartersChapter 5

Solution

Exclude Tomcat from the web starter and add the Jetty starter; auto-configuration does the rest:

Server-neutral settings (server.port, server.shutdown, compression, SSL) keep working; server-specific ones move from server.tomcat.* to server.jetty.*.

Pitfalls

  • Undertow is no longer supported in Spring Boot 4 (it doesn't support Servlet 6.1).
  • Check mvn dependency:tree afterwards: another dependency may pull Tomcat back in, and with both on the classpath the result is confusing.

Find out where a property's value comes from

A setting has a value nobody expects. Is it the YAML file, an environment variable, a profile document?

Environment/actuator/envChapters 4, 18

Solution

Ask the environment for the property's origin. With Actuator, GET /actuator/env/library.max-open-loans lists every source that defines the key, highest priority first. In code:

The first line wins. For files, the origin includes the file name and line number — e.g. class path resource [application.yml] - 12:20.

Pitfalls

  • Remember relaxed binding: LIBRARY_MODE in the environment also sets library.mode — search for both spellings.
  • IDE run configurations often inject properties or environment variables invisibly; check them when "it only happens on my machine".
